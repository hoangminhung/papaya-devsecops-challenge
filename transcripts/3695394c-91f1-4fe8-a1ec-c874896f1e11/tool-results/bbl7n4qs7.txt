    29	## 1. The decision in one page
    30	
    31	Engineering and Compliance disagree only about **writes to production**; reads of metadata and all
    32	of non-prod are outside Compliance's sentence (framing §3.1). Real customer data is layer 6.
    33	
    34	**Chosen approach "A + D2'"** (Options §9, owner decision 2026-11-09):
    35	
    36	1. **Default path:** every prod change is a pull request, approved by a named human who is not the
    37	   author, applied by CI. Incidents included ("IaC first").
    38	2. **Fallback (break-glass):** only when the PR path cannot be used, a human gets an approved grant
    39	   with a 1-hour role session (effective window up to about 2 h, ⚠️ R2.9 #3) and runs an approved command list in a terminal without an agent (layer 7) [design].
    40	3. **Nothing standing:** no human or agent holds standing prod write; no long-lived credentials.
    41	
    42	| Engineering gets | Compliance gets |
    43	|---|---|
    44	| A free loop in non-prod: read, change, deploy without approval (non-prod is synthetic or masked, GĐ-14; stores not yet scanned are excluded, layer 6). | Every prod change approved **before** apply by a named human ≠ author (GĐ-8, GĐ-11), enforced in GitHub and AWS IAM, outside the agent (limits below). |
    45	| Read-only prod metadata for the agent. | No standing prod write (S1), no long-lived CI keys (S2, with an owner-approved exception for k0s/Firebase deploy credentials, OD1, OD6; storage conditions [design], layer 5). |
    46	| Self-service PRs, one approval, same-day ship (S4). | One evidence chain per change; approval and change records ≥ 6 years (📖 R5.2.9; applied to change records ⚠️ R5.7 #2). |
    47	| Incident lane: approval wait ≤ 15 min, 24/7 (S7). Decision-to-apply target ≤ 30 min (Options §9); current estimate 11–46 min ⚠️, measured first in rollout. | Agent-side controls as a second layer, not the control of record. |
    48	
    49	**Where the design falls short, stated openly:**
    50	
    51	- **The fallback meets the approval rule only partly** (approves a command list, not an applied
    52	  change); accepted by the owner (Options §9 Q2). It is a second, process-controlled path, while the
    53	  framing asked for one technically enforced path (framing §3.3, Options §7). It stays narrow only
    54	  if most incidents are expressible in IaC (unknown, Options §8); layer 7 measures this.
    55	- **On GitHub Team nobody sees the prod diff before apply** (⚠️ R4.6 #1; Team assumed, GĐ-5).
    56	  Risky prod diffs stop the deploy until an owner of the stack approves the prod preview [design].
    57	- **Admins can edit the gate**; logged, not prevented (logging 📖 R3.2.2; ability to edit ⚠️ R3.2.2,
    58	  R3.6 #1). An admin's agent has
    59	  the same power, because the agent uses its engineer's GitHub login (⚠️ R6.5 #10).
    60	- **Some rules are process, not technology:** see "Process rules" in layer 1. The owner's rule
    61	  "the PR approver is always an engineer, never an agent" (OD5) is absolute as policy, but on
    62	  laptops it is enforced by policy and training, not by a technical control: an agent could approve
    63	  through its engineer's login, and no detection was found.
    64	- **Incident approvers vs domain review:** code-owner review means an approver must own the file,
    65	  at L2 as at L3. So that one on-call primary can approve any deployable path at 2 a.m., the on-call approver
    66	  group co-owns every deployable path (owner decision OD9, layer 3). The cost: GitHub accepts an
    67	  approval from any listed owner (📖 R3.2.7), so on normal days that group could approve another
    68	  domain's PR. Domain review on normal days becomes a process rule with a monthly check, not a
    69	  technical control. Because on-call approvers only
    70	  approve (OD7), a night incident needs two people awake: the incident responder and the on-call
    71	  approver (the backup only replaces an unavailable primary).
    72	- **One approver for high-risk changes.** L3 changes (IAM, stateful deletes, workflow files) get one
    73	  approver, like L2, but the path is owned by the L3 owner team (or by the stack's owners for L3
    74	  content in domain files, OD8), and risky prod diffs stop for a look at
    75	  the prod preview (OD2, OD8, layer 3). A single reviewer can miss things; this is the owner's trade-off
    76	  for speed.
    77	- **k0s and Firebase are weaker:** no prod preview or risk stop, no CloudTrail for k0s changes
    78	  (so S3 reconciliation does not cover them), and no break-glass when Actions is down (G1, G2).
    79	- **New dependencies on two GitHub Apps** (required check, CI agent): if the required-check app is
    80	  down, every merge to `main` is blocked, incident PRs included; that counts as "pipeline
    81	  unavailable" for JIT. Their keys and hosting are open (G19).
    82	- **HIPAA applicability is a legal question** (⚠️ R1.11.1.11); the design treats Papaya as a
    83	  business associate, as the brief implies.
    84	
    85	**Cross-cutting rules** (owner's balance principle, research 6.8):
    86	
    87	1. **The boundary is IAM and the CI gate.** Server-managed settings are "a client-side control, not
    88	   a security boundary" (📖 R1.1.7); local admins can edit endpoint files (📖 R1.1.8).
    89	2. **Assume prompt injection succeeds:** neither OWASP nor NIST knows a full prevention (📖 R6.1.1, R6.1.2).
    90	3. **Friction where damage is large, none where it is small**, measured, with a time-boxed escape.
    91	4. **Evidence by construction:** the path produces the records.

    93	### Roles
    94	
    95	| Role | Rule |
    96	|---|---|
    97	| Author (engineer + their agent) | Never approves own change; GitHub blocks PR authors from approving (📖 R3.3.1). |
    98	| Approver | Always an engineer, never an agent (owner rule, OD5). Named in CODEOWNERS; ≠ author, ≠ last pusher (📖 R3.2.3); for an app-opened PR, ≠ the person who triggered it (⚠️ R3.3.4, layer 5). |
    99	| Incident responder | Engineer who diagnoses and writes the fix or the JIT request. Never the on-call approver of the same shift (OD7). |
   100	| On-call approver | Engineer on the on-call schedule, primary + backup, 24/7; wait ≤ 15 min (S7). While on call they only approve: they write no fix and file no JIT request, so the approver is always distinct from the author (OD7). The primary approves; the backup replaces an unavailable primary (OD2). No platform-team membership is required; all engineers follow one agreed approval procedure (OD2). |
   101	| Data owner [design] | Named per tenant; co-approves real-data reads, or reviews a night-time read the next working day (layer 6). |
   102	| Control owner | DevSecOps (1–2 people, GĐ-1); owns policies and metrics; not the only approver. |
   103	| L3 owner team | Owns the process-defining L3 paths and the SCP stack (layer 3); composition open (G17). |

   107	## Layer 1 — Identity and access
   108	
   109	**Principle.** Every action traces to one named human. Nobody holds standing prod write: prod is
   110	written by the pipeline role, or in the fallback by an approved, time-boxed grant. Prod reads default
   111	to metadata. No long-lived credentials. Prod and non-prod are separate boundaries.
   112	
   113	**On Papaya's stack**
   114	
   115	- **The engineer's access is the agent's access.** The agent uses the engineer's AWS SSO cache, and
   116	  one portal session reaches every role assigned to that engineer (📖 R2.2.1, R2.2.2; token-reuse
   117	  detail ⚠️ R2.2.2). A separate
   118	  "agent" permission set does not separate them (⚠️ R2.9 #1). The control is what the **engineer**
   119	  holds.
   120	- **Process rules** that follow from this:
   121	  - the JIT terminal runs no agent, though the grant is reachable from the same laptop (owner
   122	    accepted as a process control, D2);
   123	  - the incident-analysis session is meant to use only read-only roles (D2; `--restricted` per D3,
   124	    research 6.9.4 Q2);
   125	  - the real-data terminal runs no agent when the store holds PHI [design], same weakness as D2;
   126	  - an agent never approves PRs: an owner rule (OD5), enforced on laptops by policy and training.
   127	    GitHub blocks self-approval only. The auto-mode default block list
   128	    excerpt read names "approving Claude's own pull request" (📖 R6.3.3); whether approving
   129	    someone else's PR is blocked is unverified (⚠️), and the list
   130	    applies only in auto mode. No detection was found (⚠️; `actor_is_agent` in the audit log has no
   131	    documented meaning, R3.5.6).
   132	- **IAM Identity Center permission sets** (📖 R2.1.1) [design names]:
   133	  - `ProdReadMetadata`: metrics, redacted log groups, configuration; no data-plane read on claim
   134	    stores; 1 h session, the minimum (📖 R2.1.4). Until a service's logs are redacted at source
   135	    (layer 6), it gets that service's metrics only. Lambda configuration can hold secrets resolved by
   136	    Serverless in plain text (⚠️ R4.4.7), so configuration reads are allowed per service only after
   137	    its secrets move to runtime resolution (⚠️ R4.6 #7). Cost: until then the agent reads
   138	    timeout/memory from the IaC code;
   139	  - `NonProdDeveloper`: broad, non-prod accounts only;
   140	  - `InfraOperator-<service>`: assigned only by the JIT flow (layer 7), via a partner product, the
   141	    TEAM sample (📖 R2.4.1, R2.4.1b) or a small home-built flow (⚠️ R2.4.2) on the documented APIs
   142	    `CreateAccountAssignment` / `DeleteAccountAssignment` (📖 R2.4.2);
   143	  - no standing prod-write permission set.
   144	- **SCPs on the prod OU** [design] (SCPs cap member-account principals, 📖 R2.3.1, R2.3.2):
   145	  - deny data-plane reads on claim stores except application roles and the approved data-read role,
   146	    by `aws:PrincipalArn` (📖 R2.3.8; pattern ⚠️ R2.9 #4). Actions, e.g. `s3:GetObject`,
   147	    `sqs:ReceiveMessage`, `states:GetExecutionHistory`, are incomplete and unchecked (⚠️ G13);
   148	  - deny `lambda:UpdateFunctionCode` / `lambda:UpdateFunctionConfiguration` (⚠️ R4.6 #3) except
   149	    CloudFormation `deploymentRole`s, the Pulumi prod deploy role (if Pulumi manages Lambdas) and the
   150	    JIT roles. This closes `serverless deploy function`, which changes config outside CloudFormation
   151	    (📖 R4.4.4), and needs `deploymentRole` set on every Serverless stack (key 📖 R4.4.5; need ⚠️ R4.6 #3);
   152	  - a pre-deployed revocation Deny on `identitystore:UserId` (📖 R2.4.4); protect the org trail (📖 R2.6.2).
   153	  - Limits: 10 SCPs per target, 10,240 characters; no SCP applies to the management account
   154	    (📖 R2.3.2, R2.3.4), so whatever deploys SCPs there is the most sensitive role (L3 path, held by the L3 owner team only, not co-owned by the on-call group; OD13).
   155	- **Sessions/MFA:** portal session length set on purpose; an IdP session can extend it silently
   156	  (📖 R2.1.5, R2.1.6). MFA lives in the external IdP if one is used (📖 R2.1.7).
   157	- **CI → AWS:** GitHub OIDC, no stored keys (📖 R3.4.1). The prod role trusts only the `production`
   158	  environment of the monorepo, in its `sub` format (📖 R3.4.3, R3.4.4; immutable format assumed,
   159	  ⚠️ R3.7 A2), ideally customised with the deploy workflow's `job_workflow_ref` (📖 R3.4.5; on Team ⚠️ G10).
   160	- **CI → GCP:** Workload Identity Federation restricted to Papaya's GitHub organization, which Google
   161	  requires (📖 R3.4.5b).
   162	- **k0s, GCP and Firebase for humans:** same principles; mechanisms not researched (G1–G3). Today
   163	  k0s is reached with kubeconfigs, no SSO (GĐ-4, unconfirmed). Interim: no admin kubeconfig and no GCP
   164	  owner role on laptops; prod deploys only from CI. Firebase is not on the GCP BAA list (📖 R5.5.3), so
   165	  Firebase Hosting must hold no PHI (⚠️ R5.7 #7).
   166	
   167	**Audit evidence.** Identity Center assignment export (S1); CloudTrail `CreateAccountAssignment` /
   168	`DeleteAccountAssignment` per grant (📖 R2.4.2), linked to its approval by request ID [design]; SCPs
   169	and trust policies as Pulumi code; IAM Access Analyzer `check-no-new-access` on policy PRs
   170	(📖 R2.8.1; from phase 2); quarterly access review of permission sets and GitHub admins.
   171	
   172	**Cost / value.** Engineers lose standing prod write and keep a free non-prod loop. Prod reads stay
   173	fast for metrics and metadata, but shrink during the transition: because the engineer's access is the
   174	agent's access, from phase 1 the engineer too loses raw logs and configuration of services not yet
   175	redacted or moved to runtime secrets. Configuration values come from the IaC code instead (layer 1
   176	above); raw logs that may hold customer data need an L3-data grant. The data owner is not on the
   177	on-call schedule, so at night the grant is approved by the on-call approver alone and the data owner
   178	reviews it the next working day [design]; the wait still counts against S7. This is
   179	the largest cost of the first months. Compliance gets least privilege that is enforced.

   183	## Layer 2 — Agent runtime controls
   184	
   185	**Principle.** Agent-side controls are hygiene, not the boundary. They are central, versioned in git
   186	and the same for everyone. Defaults are safe; overrides are measured. The session that reads
   187	untrusted content holds as little power as possible (📖 R6.1.2).
   188	
   189	**On Papaya's stack**
   190	
   191	- **Delivery:** server-managed settings (available on Team, 📖 R1.1.5) for all laptops. With MDM, also
   192	  an endpoint file; by default one managed source supplies most keys, so the two must carry the same
   193	  keys or use `managedSourcesBehavior: "merge"` (📖 R1.1.3, R1.1.4). MDM is unknown; both are prepared.
   194	- **Baseline** (template: Anthropic's `settings-hipaa.json`, 📖 R5.5.4). All keys 📖 at the row cited. Only the phase-1 subset in layer 8 ships first; the other keys (sandbox, `allowManagedHooksOnly`, credential denies, `allowManagedPermissionRulesOnly`, `allowedProviders`, `forceLoginOrgUUID`, the `ask` rule for WebFetch, and the other deny rules) arrive in phase 2 (OD4):
   195	
   196	  | Key | Value and reason |
   197	  |---|---|
   198	  | `permissions.defaultMode` | `default` (Manual). A default, not a lock: users can switch to auto; VS Code remembers the last pick (D1, R6.9.3). |
   199	  | `permissions.allow` | Read-only commands Papaya uses, to cut prompts (R6.9.3). It contains no command listed in `sandbox.excludedCommands` (`aws`, `pulumi`, `serverless`): an allowed excluded command would run outside the sandbox, with `~/.aws` and the network, without a prompt (⚠️ inference from R1.2.6, R1.6.4) [design]. Cost: a prompt for every `aws` read. |
   200	  | `allowManagedPermissionRulesOnly` | `true`, one rule set (D1, research 6.9.4 Q4; R1.2.5). Cost: project and user rules are ignored, so the managed set must carry every deny/ask rule projects need; prompts likely rise (⚠️ research 6.9.4 Q4). |
   201	  | `permissions.disableBypassPermissionsMode` | `"disable"`: removes bypass mode (P3a; R1.2.2). Auto mode, where a classifier approves instead of a person, stays available (D1) and is measured through `permission_mode`. |
   202	  | `permissions.deny` / `ask` | Deny credential paths (R5.5.4; `Read(...)` syntax ⚠️ R1.8 #5). Ask for `WebFetch`, which the sandbox domain list does not limit (R1.6.2); cost: a prompt per fetch. The HIPAA template denies WebFetch (R5.5.4); "ask" is a deliberate deviation so that documentation lookups still work. |
   203	  | `requiredMinimumVersion` | ≥ 2.1.285 for `allowedProviders` (R1.1.15), which also covers `--restricted` (2.1.248, R6.9.1b) and the plugin-pin fix (2.1.179, R6.2.7); ≥ 2.1.295 if any managed hook uses `onFailure: "block"` (R1.5.2); and ≥ the latest fixed advisory at rollout (R6.3.9). It does not end running sessions and fails open on a bad value (R1.1.13). |
   204	  | `allowedProviders` + `forceLoginOrgUUID` | `["anthropic"]` + Papaya's org; closes most bypasses on **endpoint-managed** machines (R1.1.15). `forceLoginOrgUUID` checks claude.ai sign-ins only, not Claude Console sign-ins (R5.5.5); with it set, sessions on `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` or `apiKeyHelper` are refused (R1.11.3.11). |
   205	  | `allowManagedHooksOnly` | `true` (R1.5.4). |
   206	  | sandbox | `sandbox.enabled`, `failIfUnavailable`, `allowUnsandboxedCommands: false`, narrow `network.allowedDomains` locked by `network.allowManagedDomainsOnly`; `credentials` / `filesystem.denyRead` on `~/.aws`, which the sandbox can otherwise read (R1.6.3, R1.6.4). |
   207	  | `sandbox.autoAllowBashIfSandboxed` | Left at its default `true` (owner decision OD12). This widens D1's "Manual + read-only allowlist": every sandboxed command, writes in the working directory and calls to allowed domains included, runs without a prompt. Detail: sandboxed Bash runs without a prompt, so in Manual mode prompts are for edits, unsandboxed commands and fetches, not every command (R5.5.5b). A deliberate choice: the sandbox (no `~/.aws`, allowlisted network) is the control for those commands. The HIPAA README says to set `false` if policy needs a person to approve each command (R5.5.5b); cost of `false`: a prompt per command. |
   208	  | MCP, plugins | Layer 4. |
   209	  | OTel | Exporter on, content flags `0` (R1.1.20, R5.5.4). |
   210	
   211	- **Trade-off on AWS credentials [design].** With `~/.aws` hidden from the sandbox, the plan is to
   212	  list `aws`, `pulumi` and `serverless` in `sandbox.excludedCommands`. Excluded commands run "with
   213	  full access" (📖 R1.6.4), which likely includes the network (⚠️ inference). How the list matches
   214	  commands (prefix or text, and chained commands) is not researched (⚠️). This is worse than an
   215	  egress channel: `pulumi preview` runs the Pulumi program and `serverless` loads its config and
   216	  plugins, all code in the repo that the agent can edit, so excluding them lets repo code run
   217	  outside the sandbox with network access and with `~/.aws` readable (⚠️ inference). For these
   218	  commands the sandbox gives no protection. And an injected `aws` command could send out the SSO
   219	  token cache itself. That token likely opens every role assigned to the engineer for the rest of the
   220	  portal session (📖 R2.1.5; token reuse ⚠️ R2.2.2), probably including JIT or data-read grants added
   221	  later in that session (⚠️ inference). Mitigations [design]: a short portal session (📖 R2.1.5); end
   222	  the existing portal session and sign in fresh **before** a JIT or data-read grant is created
   223	  (whether ending a session invalidates a token already stolen is unverified ⚠️; ending it does not
   224	  end role sessions, 📖 R2.4.3); an SCP that denies writes to resources outside Papaya's organization using
   225	  `aws:ResourceOrgID` (key 📖 R2.3.8), on every OU, since the token can be stolen from a non-prod
   226	  session; legitimate writes to outside resources need exceptions (⚠️ not inventoried). That SCP only stops Papaya's own credentials writing to a
   227	  foreign bucket; it does not stop a command that sends the token to a non-AWS endpoint or uses the
   228	  attacker's credentials (⚠️ inference). Prefer running `pulumi` and `serverless` against real
   229	  accounts only in CI; on laptops keep them to non-prod roles, and move them into the phase-3
   230	  container. Residual risk: token theft during a session. It is accepted
   231	  because the engineer holds no **standing** prod write and no **standing** PHI read; during a JIT
   232	  or data-read window the protection is the process rule in layer 1 (D2). Stronger option, phase 3:
   233	  a separate OS user or container for prod-reading sessions
   234	  (⚠️ R6.5 #2).
   235	- **Session types:**
   236	
   237	  | Session | Identity | Flags | Enforcement |
   238	  |---|---|---|---|
   239	  | Daily development (laptop) | non-prod roles + `ProdReadMetadata` | baseline | Auto mode by choice (D1); `--restricted` recommended (D3). |
   240	  | Incident analysis (laptop) | meant to be `ProdReadMetadata` only | `--restricted --tools "Bash,Read,Grep,Glob"`, started in an empty scratch directory, not the repo [design] | Process rule (D3, research 6.9.4 Q1–Q2). No WebFetch, and file tools confined to the working directory (📖 R6.9.1b); Edit/Write are excluded only if `--tools` acts as an exclusive list (⚠️ unverified), but Bash can still write in its working directory (📖 R1.6.3) and call any role in the cache. |
   241	  | CI agent (hosted runner) | own GitHub App token; never `production` | `--restricted`, explicit `--tools`; all rules in a managed-settings file on the runner | Workflow file under CODEOWNERS (D3, research 6.9.4 Q5). The file is advisory if `Bash` is in `--tools` (layer 5). |
   242	  | JIT terminal | JIT grant | no agent | Process rule (D2). |
   243	  | Auto-mode environment (phase 3) | non-prod only | auto encouraged | D1 option (c). |
   244	
   245	- **Phase-1 interim posture:** the sandbox and credential denies arrive in phase 2 (OD4), so for
   246	  the first 30–60 days `~/.aws` is readable and the network is open to every Bash command; in auto
   247	  mode the classifier is the only gate. Impact is bounded once standing prod write is removed at the
   248	  end of phase 1 (layer 1); before that, today's exposure continues, and token theft is easier in this window.
   249	- **Hard limits:** Bash rules are not a boundary (📖 R1.2.6); hooks fail open unless
   250	  `"onFailure": "block"` (📖 R1.5.2); `--restricted` cannot be forced by a setting (📖 R6.9.1), and a `PATH` wrapper on laptops can be bypassed (⚠️ R6.9.1c);
   251	  on laptops **without MDM**, a different login, an API key or a `CLAUDE_CODE_USE_*` variable skips
   252	  server-managed settings, `allowedProviders` included (📖 R1.1.7; ⚠️ R1.8 #3, G11). So S5's
   253	  "nobody can turn off all prompts unnoticed" is likely unreachable without MDM (⚠️).
   254	- **Auto memory:** engineers review it and delete it after a suspicious session; residual risk with a
   255	  named owner (D3).
   256	- **Fallback:** switch to `disableAutoMode` (📖 R1.2.2) if the planted-injection test steers auto mode, a serious
   257	  advisory appears, or an audit finds auto mode touched a protected scope (D1).
   258	
   259	**Audit evidence.** Managed settings as an expected copy in git with PR approvals. The live copy is
   260	edited in the Claude admin console by Owners / Primary Owners (📖 R1.1.5), not by PR, and Team audit
   261	events for settings changes are unconfirmed (⚠️ R1.1.12). `/status` shows which managed source
   262	applies (📖 R1.1.18), and likely not the key values (⚠️), so it cannot detect a console edit; until a way to read the
   263	live values is found (G18), an Owner exports the console settings monthly and diffs them with git
   264	[design], and the list of Claude org Owners is kept short and reviewed quarterly; `/status` and `claude doctor` from
   265	sampled machines (📖 R1.1.18); OTel `claude_code.tool_decision` (`permission_mode`) and
   266	`claude_code.tool.blocked_on_user` (`duration_ms`, rubber-stamping signal) (fields 📖 research 6.6
   267	D1 metrics; thresholds ⚠️).

   269	**Cost / value.** More prompts than auto mode, partly offset by the read-only allowlist. Compliance
   270	gets one organization policy with evidence instead of personal choices (P3c).

   274	## Layer 3 — Change workflow by risk level
   275	
   276	**Principle.** The level is set by the damage a change can do. One default path above non-prod: a
   277	reviewed PR applied by the pipeline, with the JIT fallback (layer 7) as the only other write path.
   278	The approver reviews the code change that will be applied. Every prod change needs two people, and
   279	no more by default: one who makes it and one who approves it; the on-call backup only replaces an
   280	unavailable primary (OD2). Higher risk narrows **who** may approve (the owners of that path), not how
   281	many. Separately, any prod diff that looks risky stops the deploy, whatever its level; that adds a
   282	second approval by an owner of the same stack, which keeps it to two people (OD8). Confirmed by the owner
   283	(OD13): the original author opens the approval PR and the first approver
   284	approves it. If the first approver is unavailable, another owner of the stack approves; that makes
   285	three people and is recorded as a deviation, counted monthly (OD11). A cross-team PR needs one
   286	approval, as GitHub accepts one on-call group member for files of several owner teams (OD10,
   287	OD9, 📖 R3.2.7); domain review there is a recommendation, counted in the monthly report. A real-data read is not a change and has its own rule, L3-data. Incidents use the same
   288	path with faster people, not fewer security checks.
   289	
   290	| Level | What | Examples | Approval | Path |
   291	|---|---|---|---|---|
   292	| **L0** | Read: non-prod anything; prod metadata | metrics, redacted logs | none | read-only identity |
   293	| **L1** | Change in non-prod | deploy a branch to dev; `pulumi preview` on non-prod (needs state-write permission on a DIY S3 backend, 📖 R4.3.3) | author only | non-prod roles or PR pipeline |
   294	| **L2** | Routine prod change in code | Lambda timeout/memory, ECS desired count, release | 1 code owner ≠ author, ≠ last pusher | PR → `main` → deploy workflow |
   295	| **L3** | High-risk prod change | IAM/SCP; replace/delete of stateful resources; network; `.github/**`, CODEOWNERS, `CLAUDE.md`, `CLAUDE.local.md`, `.claude/**`, `.claude.json`, `.mcp.json`, `.husky/`, `.gitmodules`, `.ripgreprc`, plugin/MCP catalogue and the rest of the canonical list in layer 5; advisory policy finding | 1 code owner ≠ author, ≠ last pusher. L3 paths (workflow and agent-config files, catalogue, the SCP stack): the L3 owner team only (OD13); IAM-only stacks are deployable, so the L3 owner team plus the on-call group (OD9). L3 content inside a domain file (an IAM statement in `serverless.yml`, a stateful delete): the stack's owner, then the risk stop (OD8). In incidents: the on-call approver for deployable paths (OD9); paths that define the process (CODEOWNERS, agent config, catalogue, workflows) wait for the L3 owner team | same path; for IaC changes the risk stop also applies; workflow and agent-config files have no prod diff |
   296	| **L3-JIT** | Break-glass | ECS force-redeploy while Actions is down | on-call approver ≠ requester (Options §4b); incidents only, as the owner accepted it (Options §9 Q2); the on-call approver counts as owner of the service in the request (OD13) | layer 7 |
   297	| **L3-data** | Real customer data read | one tenant's failed claim record | an approver ≠ requester and an agreement (GĐ-9); data-owner co-approval [design], beyond GĐ-9; at night, see layer 6 | layer 6 |
   298	
   299	`CLAUDE.md` and the other agent configuration files are L3, because they define the workflow for
   300	the whole team (OD3). With code-owner review on, every PR, L2 included, needs an approval from an
   301	owner of the files it touches (📖 R3.2.3, R3.2.7; per-file behaviour ⚠️ not a separate research row).
   302	What differs at L3 is **which team** owns the path: L3 paths are owned in CODEOWNERS by a designated
   303	L3 owner team (deployable L3 paths also by the on-call group, OD9), L2 paths by their domain team; and IaC changes at L3 meet the
   304	risk stop. Most IAM, network and stateful changes sit inside domain files, so they are approved by
   305	the stack's owners, not the L3 team (OD8); automated checks make up for this: IAM Access Analyzer
   306	`check-no-new-access` (📖 R2.8.1) and the Pulumi policy pack (📖 R4.2.2), both from phase 2 (layer 5). Cost: changes to `CLAUDE.md` (where D3 puts shared knowledge) need the L3 owner team, not
   307	the domain team that edits it most.
   308	
   309	**On Papaya's stack**
   310	
   311	- **Gate = merge to `main`.** On Team, environment reviewers do not exist for private repos
   312	  (📖 R3.1.2). Ruleset on `main`: PR required, 1 approval, code-owner review, dismiss stale approvals,
   313	  approval by someone other than the last pusher, required checks from a pinned source app, no force
   314	  push, empty bypass list (📖 R3.2.2, R3.2.3, R3.2.5). Branch up to date before merge, since there is
   315	  no merge queue (⚠️ R4.6 #1; whether updating drops approvals is open, Options §8).
   316	- **L3 approvals [design]:** CODEOWNERS plus code-owner review only, no path-based required
   317	  reviewers rule. That rule (📖 R3.2.4) asks for approvals from specific teams, which the on-call
   318	  group would not satisfy at night, and how it combines several teams is not researched (⚠️), so it
   319	  would break OD9 or add a third person. GitHub stops the author from approving (📖 R3.3.1). A required check with a pinned source app (📖 R3.2.5), set by a dedicated GitHub App that reacts to review events and is the pinned source [design; hosting, key storage and whether its key counts against S2 are not researched, ⚠️ G19], adds what
   320	  the rules cannot: for app-opened PRs it excludes the person who triggered the agent, and it counts
   321	  only human approvals, since an app's approval might count (⚠️ R3.3.4, R3.7 A3). A workflow
   322	  instead of an app is weaker: pinning the source to GitHub Actions likely lets any workflow set a
   323	  check of the same name, and the trigger that runs on review events from trusted code is not
   324	  researched (⚠️ G19).
   325	- **Who approves at night (OD9):** a fixed GitHub team with write permission (owners without it
   326	  are silently not assigned, 📖 R3.2.7; the CODEOWNERS validation check covers this), the on-call approvers, is listed as
   327	  co-owner on every deployable path in CODEOWNERS (infrastructure and service code), next to the
   328	  domain team. Confirmed by the owner (OD13): the group does **not** co-own the paths that
   329	  define the process (`.github/**`, CODEOWNERS, `CLAUDE.md` and agent config, catalogue); those stay
   330	  with the L3 owner team only. If a broken workflow blocks a night fix, the pipeline counts as
   331	  unavailable and the JIT fallback applies (layer 7). One primary and one backup from that team are on call. Technically any member can approve any
   332	  path; by rule the primary approves and the backup only if the primary is unavailable (OD2).
   333	  Membership is fixed, not changed per shift [design]. GitHub team membership is set in organization
   334	  settings, not by a PR; managing it as code (e.g. with Pulumi's GitHub provider) and the audit
   335	  event for a membership change are not researched (⚠️ G16). Meanwhile the layer-7 settings
   336	  comparison includes the group's member list. Cost: an approval from any
   337	  listed owner satisfies code-owner review (📖 R3.2.7), so on normal days a member could approve
   338	  another domain's PR, on or off shift. Mitigation [design]: process rule "approve another
   339	  domain's PR only if it carries the `incident` label and you are on shift", and a monthly report of
   340	  every cross-domain approval by group members on PRs without that label (layer 7). Whether Papaya's team size allows full coverage is unknown
   341	  (§1, S7).
   342	- **Risk stop [design]:** applies to every deploy, whatever the level. The deploy job previews prod;
   343	  on stateful replace/delete, an IAM change, a network or security-group change, or an advisory
   344	  policy finding (from phase 2) it stops and posts the filtered preview. The original author opens a second PR that adds
   345	  `deploy-approvals/<stack>/<sha>.yaml` (`<sha>` = the stopped commit) holding that SHA and the
   346	  preview hash; the workflow does not open it, because the setting that lets Actions create and approve PRs stays
   347	  off (📖 R3.3.3; ⚠️ R3.6 #3). CODEOWNERS on `deploy-approvals/<stack>/` names the owners of that stack and the
   348	  on-call group (OD8, OD9). The approver is ≠ author and may be the first PR's approver, who now sees
   349	  the prod diff. Merging it triggers the deploy on the new HEAD, which previews again and continues
   350	  only if the hash matches the approved one; if another PR merged in between, the hash differs and
   351	  the deploy stops again (Options §1; hash stability ⚠️ Options §8). Cost: while a stack is
   352	  stopped, later merges to that stack stop too until a matching approval lands; in an incident, a
   353	  risky change already waiting on `main` blocks the fix for the same stack until it is approved or
   354	  reverted. A
   355	  `mandatory` policy violation always blocks `pulumi up` (📖 R4.2.2): the fix is a code change, or a
   356	  change to the policy pack through its own L3 PR. Preview output is filtered for
   357	  outputs and secrets before it is posted (Options §1; ⚠️ R4.6 #2).
   358	- **Merge approval = deploy approval** only if (⚠️ R3.6 #1, from 📖 R3.1.3, R3.4.5c): `production`
   359	  allows only `main`; only the reusable deploy workflow (under CODEOWNERS) references it; no ref/SHA
   360	  inputs; no `issue_comment`, `pull_request_target` or `workflow_run` triggers; one concurrency group
   361	  per stack without `cancel-in-progress` (📖 R4.1.4).
   362	- **Pulumi:** PRs preview non-prod only, because a prod preview runs PR code with state-write and
   363	  secret access (📖 R4.3.3, R4.3.4; ⚠️ R4.6 #2). On `main`: prod preview, then `pulumi up` with the
   364	  policy pack, which stops on a mandatory violation (📖 R4.2.2). Prod runs allow no `--skip-preview`
   365	  (📖 R4.1.2) and no targeting, replace, `state`, `import`, `destroy` (⚠️ R4.6 #3, G12). Pulumi Cloud,
   366	  if used: OIDC via `pulumi/auth-actions`, no stored token (📖 R4.1.4).
   367	- **Serverless v4:** `serverless package`; `serverless diff --json` (sf-core ≥ 4.37.0), parsed by CI
   368	  because differences do not change the exit code (📖 R4.4.2); `serverless deploy --package`
   369	  (📖 R4.4.3); a least-privilege `deploymentRole`, which cannot be removed later and is usable by
   370	  anyone who may operate the stack (📖 R4.4.5), so JIT roles get no stack-operation rights.
   371	- **State:** writable by deploy roles (and possibly the drift role, layer 7); Pulumi
   372	  secrets via `awskms` on a DIY backend (📖 R4.3.3, R4.3.4; ⚠️ R4.6 #7).
   373	- **k0s [design]:** manifests in the monorepo, applied by CI; no write RBAC for humans or agents in
   374	  prod; read roles exclude logs and exec in namespaces with claim data (mechanism: G1). The risk
   375	  stop is described for Pulumi and Serverless only; for k0s manifests (RBAC changes are the IAM
   376	  equivalent) a `kubectl diff`-based stop is a candidate, not researched (⚠️ G1). Firebase deploys
   377	  have no preview step in this design (⚠️ G2).
   378	- **Incident lane:** label `incident`, on-call approver paged, security checks always run (S10), only
   379	  slow unrelated tests skipped [design]. A required check skipped by a path filter may stay
   380	  pending and block the merge (open, Options §8); this directly affects S7.
   381	
   382	**Example: Lambda timeouts at 2 a.m.** (Options §6)
   383	
   384	The incident responder is engineer E; the on-call approver is R (a backup replaces R only if R is
   385	unavailable).
   386	
   387	1. E's incident-analysis session reads metrics and redacted logs and proposes `timeout` 30 → 90 s,
   388	   memory 1024 → 2048 MB, and a larger visibility timeout on the source queue (ratio ⚠️ Options §8).
   389	2. A second session (edit tools; not meant to use prod roles) edits `serverless.yml`, runs
   390	   `serverless diff` on non-prod, and opens a PR labelled `incident` as E.
   391	3. R, a co-owner of `serverless.yml` through the on-call group (OD9), reviews the diff. If R
   392	   catches a missing queue change, R does not fix it (OD7): E pushes the fix, the stale approval is
   393	   dismissed, and R approves again, one more review round (Options §6). E merges.
   394	4. The deploy workflow packages, previews prod, finds no risky change, deploys with the OIDC role.
   395	5. Estimate 11–46 min (⚠️ Options §6) against ≤ 30 min: measured first in rollout.
   396	
   397	**Audit evidence.** The PR (diff, approvers, checks); run log and preview artifact, exported because
   398	retention is unverified (⚠️ G7); deploy-role CloudTrail events; all linked by commit SHA and run ID.
   399	
   400	**Cost / value.** One approver for every prod change, from the owners of the path; two approvals,
   401	usually by the same approver, when the risk stop fires (OD13; OD11). Cross-team PRs: one approval (OD10). None in non-prod.
   402	Compliance gets four-eyes enforced by GitHub. Gap: on Team the prod diff is not seen before apply.

   443	## Layer 5 — CI/CD hardening
   444	
   445	**Principle.** CI is the default production writer, so it is the main target. Short-lived,
   446	least-privilege credentials per job. Every CI dependency is pinned. Agent-written code passes the same
   447	checks as human code (S10).
   448	
   449	**On Papaya's stack**
   450	
   451	- **Credentials:** OIDC instead of keys and tokens in repository secrets, which any writer can read
   452	  (📖 R3.4.1, R3.5.3b). Org default for `GITHUB_TOKEN` set to "restricted", `permissions:` per job (📖 R3.5.3).
   453	  "Allow GitHub Actions to create and approve pull requests" off (📖 R3.3.3). Serverless License Key in
   454	  SSM, read by the deploy role (sf ≥ 4.4.19, 📖 R4.4.8). Until G1/G2 are solved, k0s and Firebase
   455	  deploys may need a stored credential in GitHub: a kubeconfig or token for k0s, a Firebase token or
   456	  service-account key for Firebase Hosting. The owner accepts this as an exception to S2 = 0 until it
   457	  is checked whether k0s and Firebase deploys can use OIDC (OD1, OD6). Conditions [design]:
   458	  - stored only as an **environment secret of `production`**, never as a repository secret. Anyone
   459	    with write access can read repository secrets (📖 R3.5.3b), which would turn the exception into
   460	    standing prod write for every engineer and their agent. Environment secrets and a deployment
   461	    branch rule limited to `main` are available on Team for private repos (📖 R3.1.2, R3.1.3), and
   462	    only the reviewed deploy workflow references the environment (layer 3);
   463	  - the deploy job runs on GitHub-hosted runners. On self-hosted runners, jobs "are not run in an
   464	    isolated container, even if they use environments", so environment secrets there must be
   465	    treated like repository secrets (📖 R3.1.5). Self-hosted runners "can be persistently
   466	    compromised by untrusted code" from anyone who can open a PR, and runner groups limit only which
   467	    repositories use them (📖 R3.5.2); in a monorepo any workflow can likely target the runner's label (⚠️ G15).
   468	    How to restrict a runner to one workflow is not researched (⚠️ G15); just-in-time runners exist
   469	    (📖 R3.5.2, not read in detail). If reaching k0s needs a self-hosted runner, that
   470	    runner is dedicated to the `production` deploy, and the residual risk is recorded;
   471	  - that environment secret is the single source of truth: no copy elsewhere (OD1);
   472	  - an owner, an expiry and rotation in the exception register;
   473	  - optionally a separate environment (e.g. `production-k0s`), limited to `main` and referenced
   474	    only by the k0s/Firebase deploy workflow, so AWS deploy jobs cannot read these secrets
   475	    [design].
   476	
   477	  Residual risk: admins can change the environment, and a deleted environment comes back without
   478	  protection (⚠️ R3.1.4); the alerts and settings comparison in layer 7 cover this. The exception
   479	  covers **CI deploy credentials only**. Runtime credentials, such as a k0s autoscaler's AWS access to
   480	  add or remove nodes, live in the cluster, not in GitHub; they follow layer 1 (no static keys, a
   481	  role attached to the machine; ⚠️ not researched for k0s, G1).
   482	- **Side paths:** Pulumi ESC, Pulumi Deployments and Serverless Dashboard providers reach AWS
   483	  (📖 R4.4.9) outside the GitHub gate (⚠️ R4.4.9); not used for prod (⚠️ R4.6 #6).
   484	- **Pinning:** workflow lockfile (`gh actions-lock`) or full SHA, enforced by the org policy "Require
   485	  actions to be pinned to a full-length commit SHA" (availability on Team ⚠️); the lockfile does not pin reusable workflows, so
   486	  the deploy workflow lives in the same repo (📖 R3.5.5; conclusion [design]).
   487	- **CODEOWNERS** on `.github/`, `CLAUDE.md`, `CLAUDE.local.md`, `.claude/`, `.claude.json`, `.mcp.json`,
   488	  `.husky/`, `.gitmodules`, `.ripgreprc`, `.devcontainer/` (📖 R3.2.8; list ⚠️ R6.5 #5, R6.3.11), plus
   489	  `.npmrc` (registry redirection) [design], the policy packs, the SCP code and the
   490	  catalogue file. This is the canonical L3 path list that layer 3 refers to. Not on it:
   491	  `deploy-approvals/<stack>/`, owned by the stack's owners and the on-call group (OD8, OD9). The private plugin
   492	  marketplace is a separate repo and needs its own ruleset and CODEOWNERS [design]. CI validates the file, because
   493	  invalid lines are skipped silently (📖 R3.2.7).
   494	- **No privileged triggers with untrusted code** (`pull_request_target`, `workflow_run` + checkout,
   495	  📖 R3.5.4).
   496	- **Agent review:** an independent agent (not the one that made the change) may post an automated
   497	  review as an extra check; it never counts as an approval (GĐ-11).
   498	- **Agents in CI:** `claude-code-action` with a custom GitHub App limited to Contents, Issues, Pull
   499	  requests (📖 R1.7.8), whose own credentials are listed in the S2 inventory (⚠️ G19); Anthropic workload identity federation, not a personal OAuth token (📖 R1.7.6);
   500	  `--restricted` and explicit `--tools` (D3; passing it through `claude_args` unverified, ⚠️ research
   501	  6.9.4 Q5); a managed-settings file on the runner, which also guards against mods (📖 R1.5.6; for
   502	  federation auth ⚠️); MCP set fixed by CI because `.mcp.json` loads without a prompt in `-p` runs
   503	  (📖 R1.3.5); never `environment: production` (⚠️ R3.6 #4). Hosted runners give `sudo` (📖 R3.5.1),
   504	  so with `Bash` in `--tools` the runner file is advisory (⚠️ R3.5.1, R3.6 #4).
   505	- **App-opened PRs:** a required check set by a dedicated GitHub App, pinned as its source (layer 3), confirms at least one approval by a
   506	  human who did not trigger the run; counting approvals is not enough, since the app's own approval
   507	  might count (⚠️ R3.3.4, R3.7 A3; 📖 R3.2.5).
   508	- **Required checks (S10):** from phase 1, secret scanning, dependency check, SAST (products: G4);
   509	  from phase 2, IAM Access Analyzer `check-no-new-access` (📖 R2.8.1) and Pulumi policy packs
   510	  (📖 R4.2.2). For Serverless stacks, Access Analyzer would check the IAM policies in the
   511	  CloudFormation template that `serverless package` produces, against the deployed ones (⚠️ not
   512	  researched); policy packs do not apply to them. Until phase 2, the only compensation for OD8 is
   513	  the risk stop, which fires on every IAM change in the prod preview.

   515	**Audit evidence.** Workflows and lockfile in git; audit-log events such as
   516	`org.update_actions_secret`, `repo.set_workflow_permission_can_approve_pr`, `repository_ruleset.update`
   517	(📖 R3.3.3, R3.5.6). An audit event for environment-secret changes was not researched (⚠️); the
   518	settings comparison in layer 7 covers the S2 exception meanwhile. Check results per PR; secrets inventory (S2).
   519	
   520	**Cost / value.** One-time migration to OIDC and pinned actions; slower action updates. Compliance
   521	gets S2 and the same guardrails for agent and human code.

   525	## Layer 6 — Data protection and prompt-injection defence
   526	
   527	**Principle.** The design keeps PHI from reaching the coding agent (owner decision, research 1.9).
   528	Some paths rely on process (below), so this is a target, not a guarantee. Other customer
   529	personal data is outside that hard boundary ("not extended", research 5.8): the agent reads metadata
   530	by default and may read such data case by case under GĐ-9. Real-data reads are approved, name one
   531	tenant, are time-boxed, and need an agreement (BAA/DPA, partner contract) (GĐ-9). Everything read

   591	## Layer 7 — Observability, audit, incident response and break-glass
   592	
   593	**Principle.** One tamper-evident evidence chain per prod change. One routed alert channel with a
   594	named on-call, approvers included. Unapproved change is detected (drift, reconciliation). Break-glass
   595	is approved before use, time-boxed and reconciled after.
   596	
   597	**On Papaya's stack**
   598	
   599	- **Audit stores:**
   600	  - organization CloudTrail to a log-archive account with integrity validation (📖 R2.6.2, R2.6.4,
   601	    R2.6.5); change records ≥ 6 years; raw-log retention for Papaya's compliance owner (⚠️ R5.7 #2).
   602	    Data events only on PHI buckets, prod Lambda invoke and prod SQS (cost 📖 R2.6.3; selection
   603	    ⚠️ R2.9 #5), which makes the archive
   604	    PHI-bearing (⚠️ research 1.11.4 L15). CloudTrail Lake is closed to new customers (📖 R2.6.6);
   605	  - GitHub org audit log kept 180 days, so exported (📖 R3.5.6);
   606	  - alerts on `repository_ruleset.update`, `environment.update_protection_rule`,

   609	    deleted `production` environment comes back unprotected (⚠️ R3.1.4): a job compares live settings

   611	  - Aurora SQL is likely invisible to CloudTrail (⚠️ R2.7.1): Database Activity Streams, alerts on

   615	  preview and CloudTrail events. Monthly reconciliation: every prod write event matches a record

   619	  prod secrets in state, which is noted (⚠️ R4.6 #2). Scheduled `pulumi preview --refresh
   620	  --expect-no-changes` or `pulumi refresh --preview-only` (📖 R4.1.1, R4.3.1, R4.3.2). On a DIY S3
   621	  backend, preview needs state-write permission (📖 R4.3.3); whether a refresh preview writes more
   622	  than locks is open (⚠️ R4.6 #2, G14). So either the drift role gets state write (and the same
   623	  trust care as the deploy role), or Pulumi Cloud drift detection is used (📖 R4.3.2, Pro+). The
   624	  latter runs on Pulumi Deployments, which holds credentials to prod, so it re-opens a side path that
   625	  layer 5 excludes and needs the same trust narrowing and audit (📖 R4.4.9; ⚠️ R4.6 #6). CloudFormation
   626	  drift detection, explicitly set properties only (📖 R4.4.6). No auto-remediation: it is an unreviewed
   627	  `pulumi up --refresh` (📖 R4.3.2). Each finding gets an actor and a ticket.
   628	- **On-call:** phase 1 delivers the named approver schedule (primary + backup engineers, 24/7), as
   629	  decided in framing round 1, and, because of OD7, a minimal incident-responder schedule; the
   630	  latter extends that decision. The primary approves; the backup steps in only if the primary is
   631	  unavailable (OD2). On-call approvers only approve during their shift; the fix is written by an
   632	  incident responder (OD7). Alert routing and the
   633	  rest of on-call follow in phase 2 (tools: G5); in phase 1 the responder calls the approver by phone from the published schedule.

   637	  |---|---|
