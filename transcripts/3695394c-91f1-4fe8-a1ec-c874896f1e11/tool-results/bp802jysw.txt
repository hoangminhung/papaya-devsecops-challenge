    29	## 1. The decision in one page
    30	
    31	Engineering and Compliance disagree only about **writes to production**; reads of metadata and all
    32	of non-prod are outside Compliance's sentence (framing §3.1). Real customer data is layer 6.
    33	
    34	**Chosen approach "A + D2'"** (Options §9, owner decision 2026-11-09):
    35	
    36	1. **Default path:** every prod change is a pull request, approved by a named human who is not the
    37	   author, applied by CI. Incidents included ("IaC first").
    38	2. **Fallback (break-glass):** only when the PR path cannot be used, a human gets an approved grant
    39	   with a 1-hour role session (effective window up to about 2 h) and runs an approved command list in a terminal without an agent (layer 7) [design].
    40	3. **Nothing standing:** no human or agent holds standing prod write; no long-lived credentials.
    41	
    42	| Engineering gets | Compliance gets |
    43	|---|---|
    44	| A free loop in non-prod: read, change, deploy without approval (non-prod is synthetic or masked, GĐ-14; stores not yet scanned are excluded, layer 6). | Every prod change approved **before** apply by a named human ≠ author (GĐ-8, GĐ-11), enforced in GitHub and AWS IAM, outside the agent (limits below). |
    45	| Read-only prod metadata for the agent. | No standing prod write (S1), no long-lived CI keys (S2, with an owner-approved exception for k0s/Firebase deploy credentials, OD1, OD6; storage conditions [design], layer 5). |
    46	| Self-service PRs, one approval, same-day ship (S4). | One evidence chain per change; approval and change records ≥ 6 years (📖 R5.2.9; applied to change records ⚠️ R5.7 #2). |
    47	| Incident lane: approval wait ≤ 15 min, 24/7 (S7). Decision-to-apply target ≤ 30 min (Options §9); current estimate 11–46 min ⚠️, measured first in rollout. | Agent-side controls as a second layer, not the control of record. |
    48	
    49	**Where the design falls short, stated openly:**
    50	
    51	- **The fallback meets the approval rule only partly** (approves a command list, not an applied
    52	  change); accepted by the owner (Options §9 Q2). It is a second, process-controlled path, while the
    53	  framing asked for one technically enforced path (framing §3.3, Options §7). It stays narrow only
    54	  if most incidents are expressible in IaC (unknown, Options §8); layer 7 measures this.
    55	- **On GitHub Team nobody sees the prod diff before apply** (⚠️ R4.6 #1; Team assumed, GĐ-5).
    56	  Risky prod diffs stop the deploy until an engineer approves the prod preview [design].
    57	- **Admins can edit the gate**; logged, not prevented (logging 📖 R3.2.2; ability to edit ⚠️ R3.2.2,
    58	  R3.6 #1). An admin's agent has
    59	  the same power, because the agent uses its engineer's GitHub login (⚠️ R6.5 #10).
    60	- **Some rules are process, not technology:** see "Process rules" in layer 1. The owner's rule
    61	  "the PR approver is always an engineer, never an agent" (OD5) is absolute as policy, but on
    62	  laptops it is enforced by policy and training, not by a technical control: an agent could approve
    63	  through its engineer's login, and no detection was found.
    64	- **Incident approvers vs domain review:** code-owner review means the on-call approver can only
    65	  approve paths they own, at L2 as at L3 (e.g. `serverless.yml` in the Lambda example, layer 3).
    66	  For every path to be approvable at 2 a.m., either the schedule always holds an owner of every
    67	  deployable path, or on-call approvers are made owners of everything, which weakens domain review
    68	  on normal days. Neither is verified (Options §1, §7, §8); S7 depends on it. The design's current
    69	  choice is in layer 3 ("Who approves at night"). Because on-call approvers only
    70	  approve (OD7), a night incident needs two people awake: the incident responder and the on-call
    71	  approver (the backup only replaces an unavailable primary).
    72	- **One approver for high-risk changes.** L3 changes (IAM, stateful deletes, workflow files) get one
    73	  approver, like L2, but that approver must own the path, and risky prod diffs stop for a look at
    74	  the prod preview (OD2, layer 3). A single reviewer can miss things; this is the owner's trade-off
    75	  for speed.
    76	- **HIPAA applicability is a legal question** (⚠️ R1.11.1.11); the design treats Papaya as a
    77	  business associate, as the brief implies.
    78	
    79	**Cross-cutting rules** (owner's balance principle, research 6.8):
    80	
    81	1. **The boundary is IAM and the CI gate.** Server-managed settings are "a client-side control, not
    82	   a security boundary" (📖 R1.1.7); local admins can edit endpoint files (📖 R1.1.8).
    83	2. **Assume prompt injection succeeds:** neither OWASP nor NIST knows a full prevention (📖 R6.1.1, R6.1.2).
    84	3. **Friction where damage is large, none where it is small**, measured, with a time-boxed escape.
    85	4. **Evidence by construction:** the path produces the records.
    86	
    87	### Roles
    88	
    89	| Role | Rule |
    90	|---|---|
    91	| Author (engineer + their agent) | Never approves own change; GitHub blocks PR authors from approving (📖 R3.3.1). |
    92	| Approver | Always an engineer, never an agent (owner rule, OD5). Named in CODEOWNERS; ≠ author, ≠ last pusher (📖 R3.2.3); for an app-opened PR, ≠ the person who triggered it (⚠️ R3.3.4, layer 5). |
    93	| Incident responder | Engineer who diagnoses and writes the fix or the JIT request. Never the on-call approver of the same shift (OD7). |
    94	| On-call approver | Engineer on the on-call schedule, primary + backup, 24/7; wait ≤ 15 min (S7). While on call they only approve: they write no fix and file no JIT request, so the approver is always distinct from the author (OD7). The primary approves; the backup replaces an unavailable primary (OD2). No platform-team membership is required; all engineers follow one agreed approval procedure (OD2). |
    95	| Data owner [design] | Named per tenant; co-approves real-data reads (layer 6). |
    96	| Control owner | DevSecOps (1–2 people, GĐ-1); owns policies and metrics; not the only approver. |

   100	## Layer 1 — Identity and access
   101	
   102	**Principle.** Every action traces to one named human. Nobody holds standing prod write: prod is
   103	written by the pipeline role, or in the fallback by an approved, time-boxed grant. Prod reads default
   104	to metadata. No long-lived credentials. Prod and non-prod are separate boundaries.
   105	
   106	**On Papaya's stack**
   107	
   108	- **The engineer's access is the agent's access.** The agent uses the engineer's AWS SSO cache, and
   109	  one portal session reaches every role assigned to that engineer (📖 R2.2.1, R2.2.2; token-reuse
   110	  detail ⚠️ R2.2.2). A separate
   111	  "agent" permission set does not separate them (⚠️ R2.9 #1). The control is what the **engineer**
   112	  holds.
   113	- **Process rules** that follow from this:
   114	  - the JIT terminal runs no agent, though the grant is reachable from the same laptop (owner
   115	    accepted as a process control, D2);
   116	  - the incident-analysis session is meant to use only read-only roles (D2; `--restricted` per D3,
   117	    research 6.9.4 Q2);
   118	  - the real-data terminal runs no agent when the store holds PHI [design], same weakness as D2;
   119	  - an agent never approves PRs: an owner rule (OD5), enforced on laptops by policy and training.
   120	    GitHub blocks self-approval only. The auto-mode default block list
   121	    excerpt read names "approving Claude's own pull request" (📖 R6.3.3); whether approving
   122	    someone else's PR is blocked is unverified (⚠️), and the list
   123	    applies only in auto mode. No detection was found (⚠️; `actor_is_agent` in the audit log has no
   124	    documented meaning, R3.5.6).
   125	- **IAM Identity Center permission sets** (📖 R2.1.1) [design names]:
   126	  - `ProdReadMetadata`: metrics, redacted log groups, configuration; no data-plane read on claim
   127	    stores; 1 h session, the minimum (📖 R2.1.4). Until a service's logs are redacted at source
   128	    (layer 6), it gets that service's metrics only. Lambda configuration can hold secrets resolved by
   129	    Serverless in plain text (⚠️ R4.4.7), so configuration reads are allowed per service only after
   130	    its secrets move to runtime resolution (⚠️ R4.6 #7). Cost: until then the agent reads
   131	    timeout/memory from the IaC code;
   132	  - `NonProdDeveloper`: broad, non-prod accounts only;
   133	  - `InfraOperator-<service>`: assigned only by the JIT flow (layer 7), via a partner product, the
   134	    TEAM sample (📖 R2.4.1, R2.4.1b) or a small home-built flow (⚠️ R2.4.2) on the documented APIs
   135	    `CreateAccountAssignment` / `DeleteAccountAssignment` (📖 R2.4.2);
   136	  - no standing prod-write permission set.
   137	- **SCPs on the prod OU** [design] (SCPs cap member-account principals, 📖 R2.3.1, R2.3.2):
   138	  - deny data-plane reads on claim stores except application roles and the approved data-read role,
   139	    by `aws:PrincipalArn` (📖 R2.3.8; pattern ⚠️ R2.9 #4). Actions, e.g. `s3:GetObject`,
   140	    `sqs:ReceiveMessage`, `states:GetExecutionHistory`, are incomplete and unchecked (⚠️ G13);
   141	  - deny `lambda:UpdateFunctionCode` / `lambda:UpdateFunctionConfiguration` (⚠️ R4.6 #3) except
   142	    CloudFormation `deploymentRole`s, the Pulumi prod deploy role (if Pulumi manages Lambdas) and the
   143	    JIT roles. This closes `serverless deploy function`, which changes config outside CloudFormation
   144	    (📖 R4.4.4), and needs `deploymentRole` set on every Serverless stack (key 📖 R4.4.5; need ⚠️ R4.6 #3);
   145	  - a pre-deployed revocation Deny on `identitystore:UserId` (📖 R2.4.4); protect the org trail (📖 R2.6.2).
   146	  - Limits: 10 SCPs per target, 10,240 characters; no SCP applies to the management account
   147	    (📖 R2.3.2, R2.3.4), so whatever deploys SCPs there is the most sensitive role (L3 path).
   148	- **Sessions/MFA:** portal session length set on purpose; an IdP session can extend it silently
   149	  (📖 R2.1.5, R2.1.6). MFA lives in the external IdP if one is used (📖 R2.1.7).
   150	- **CI → AWS:** GitHub OIDC, no stored keys (📖 R3.4.1). The prod role trusts only the `production`
   151	  environment of the monorepo, in its `sub` format (📖 R3.4.3, R3.4.4; immutable format assumed,
   152	  ⚠️ R3.7 A2), ideally customised with the deploy workflow's `job_workflow_ref` (📖 R3.4.5; on Team ⚠️ G10).
   153	- **CI → GCP:** Workload Identity Federation restricted to Papaya's GitHub organization, which Google
   154	  requires (📖 R3.4.5b).
   155	- **k0s, GCP and Firebase for humans:** same principles; mechanisms not researched (G1–G3). Today
   156	  k0s is reached with kubeconfigs, no SSO (GĐ-4, unconfirmed). Interim: no admin kubeconfig and no GCP
   157	  owner role on laptops; prod deploys only from CI. Firebase is not on the GCP BAA list (📖 R5.5.3), so
   158	  Firebase Hosting must hold no PHI (⚠️ R5.7 #7).
   159	
   160	**Audit evidence.** Identity Center assignment export (S1); CloudTrail `CreateAccountAssignment` /
   161	`DeleteAccountAssignment` per grant (📖 R2.4.2), linked to its approval by request ID [design]; SCPs
   162	and trust policies as Pulumi code; IAM Access Analyzer `check-no-new-access` on policy PRs
   163	(📖 R2.8.1); quarterly access review of permission sets and GitHub admins.
   164	
   165	**Cost / value.** Engineers lose standing prod write and keep a free non-prod loop. Prod reads stay
   166	fast for metrics and metadata, but shrink during the transition: because the engineer's access is the
   167	agent's access, from phase 1 the engineer too loses raw logs and configuration of services not yet
   168	redacted or moved to runtime secrets, and needs an L3-data grant to read them in an incident. This is
   169	the largest cost of the first months. Compliance gets least privilege that is enforced.

   173	## Layer 2 — Agent runtime controls
   174	
   175	**Principle.** Agent-side controls are hygiene, not the boundary. They are central, versioned in git
   176	and the same for everyone. Defaults are safe; overrides are measured. The session that reads
   177	untrusted content holds as little power as possible (📖 R6.1.2).
   178	
   179	**On Papaya's stack**
   180	
   181	- **Delivery:** server-managed settings (available on Team, 📖 R1.1.5) for all laptops. With MDM, also
   182	  an endpoint file; by default one managed source supplies most keys, so the two must carry the same
   183	  keys or use `managedSourcesBehavior: "merge"` (📖 R1.1.3, R1.1.4). MDM is unknown; both are prepared.
   184	- **Baseline** (template: Anthropic's `settings-hipaa.json`, 📖 R5.5.4). All keys 📖 at the row cited:
   185	
   186	  | Key | Value and reason |
   187	  |---|---|
   188	  | `permissions.defaultMode` | `default` (Manual). A default, not a lock: users can switch to auto; VS Code remembers the last pick (D1, R6.9.3). |
   189	  | `permissions.allow` | Read-only commands Papaya uses, to cut prompts (R6.9.3). |
   190	  | `allowManagedPermissionRulesOnly` | `true`, one rule set (D1, research 6.9.4 Q4; R1.2.5). Cost: project and user rules are ignored, so the managed set must carry every deny/ask rule projects need; prompts likely rise (⚠️ research 6.9.4 Q4). |
   191	  | `permissions.disableBypassPermissionsMode` | `"disable"`: removes bypass mode (P3a; R1.2.2). Auto mode, where a classifier approves instead of a person, stays available (D1) and is measured through `permission_mode`. |
   192	  | `permissions.deny` / `ask` | Deny credential paths (R5.5.4; `Read(...)` syntax ⚠️ R1.8 #5). Ask for `WebFetch`, which the sandbox domain list does not limit (R1.6.2); cost: a prompt per fetch. The HIPAA template denies WebFetch (R5.5.4); "ask" is a deliberate deviation so that documentation lookups still work. |
   193	  | `requiredMinimumVersion` | ≥ 2.1.285 for `allowedProviders` (R1.1.15), which also covers `--restricted` (2.1.248, R6.9.1b) and the plugin-pin fix (2.1.179, R6.2.7); ≥ 2.1.295 if any managed hook uses `onFailure: "block"` (R1.5.2); and ≥ the latest fixed advisory at rollout (R6.3.9). It does not end running sessions and fails open on a bad value (R1.1.13). |
   194	  | `allowedProviders` + `forceLoginOrgUUID` | `["anthropic"]` + Papaya's org; closes most bypasses on **endpoint-managed** machines (R1.1.15). `forceLoginOrgUUID` checks claude.ai sign-ins only, not Claude Console sign-ins (R5.5.5); with it set, sessions on `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` or `apiKeyHelper` are refused (R1.11.3.11). |
   195	  | `allowManagedHooksOnly` | `true` (R1.5.4). |
   196	  | sandbox | `sandbox.enabled`, `failIfUnavailable`, `allowUnsandboxedCommands: false`, narrow `network.allowedDomains` locked by `network.allowManagedDomainsOnly`; `credentials` / `filesystem.denyRead` on `~/.aws`, which the sandbox can otherwise read (R1.6.3, R1.6.4). |
   197	  | MCP, plugins | Layer 4. |
   198	  | OTel | Exporter on, content flags `0` (R1.1.20, R5.5.4). |
   199	
   200	- **Trade-off on AWS credentials [design].** With `~/.aws` hidden from the sandbox, the plan is to
   201	  list `aws`, `pulumi` and `serverless` in `sandbox.excludedCommands`. Excluded commands run "with
   202	  full access" (📖 R1.6.4), which likely includes the network (⚠️ inference). How the list matches
   203	  commands (prefix or text, and chained commands) is not researched (⚠️). This is worse than an
   204	  egress channel: `pulumi preview` runs the Pulumi program and `serverless` loads its config and
   205	  plugins, all code in the repo that the agent can edit, so excluding them lets repo code run
   206	  outside the sandbox with network access and with `~/.aws` readable (⚠️ inference). For these
   207	  commands the sandbox gives no protection. And an injected `aws` command could send out the SSO
   208	  token cache itself. That token likely opens every role assigned to the engineer for the rest of the
   209	  portal session (📖 R2.1.5; token reuse ⚠️ R2.2.2), probably including JIT or data-read grants added
   210	  later in that session (⚠️ inference). Mitigations [design]: a short portal session (📖 R2.1.5); end
   211	  the existing portal session and sign in fresh **before** a JIT or data-read grant is created
   212	  (whether ending a session invalidates a token already stolen is unverified ⚠️; ending it does not
   213	  end role sessions, 📖 R2.4.3); an SCP that denies writes to resources outside Papaya's organization using
   214	  `aws:ResourceOrgID` (key 📖 R2.3.8). That SCP only stops Papaya's own credentials writing to a
   215	  foreign bucket; it does not stop a command that sends the token to a non-AWS endpoint or uses the
   216	  attacker's credentials (⚠️ inference). Prefer running `pulumi` and `serverless` against real
   217	  accounts only in CI; on laptops keep them to non-prod roles, and move them into the phase-3
   218	  container. Residual risk: token theft during a session. It is accepted
   219	  because the engineer holds no **standing** prod write and no **standing** PHI read; during a JIT
   220	  or data-read window the protection is the process rule in layer 1 (D2). Stronger option, phase 3:
   221	  a separate OS user or container for prod-reading sessions
   222	  (⚠️ R6.5 #2).
   223	- **Session types:**
   224	
   225	  | Session | Identity | Flags | Enforcement |
   226	  |---|---|---|---|
   227	  | Daily development (laptop) | non-prod roles + `ProdReadMetadata` | baseline | Auto mode by choice (D1); `--restricted` recommended (D3). |
   228	  | Incident analysis (laptop) | meant to be `ProdReadMetadata` only | `--restricted --tools "Bash,Read,Grep,Glob"`, started in an empty scratch directory, not the repo [design] | Process rule (D3, research 6.9.4 Q1–Q2). No WebFetch, and file tools confined to the working directory (📖 R6.9.1b); Edit/Write are excluded only if `--tools` acts as an exclusive list (⚠️ unverified), but Bash can still write in its working directory (📖 R1.6.3) and call any role in the cache. |
   229	  | CI agent (hosted runner) | own GitHub App token; never `production` | `--restricted`, explicit `--tools`; all rules in a managed-settings file on the runner | Workflow file under CODEOWNERS (D3, research 6.9.4 Q5). The file is advisory if `Bash` is in `--tools` (layer 5). |
   230	  | JIT terminal | JIT grant | no agent | Process rule (D2). |
   231	  | Auto-mode environment (phase 3) | non-prod only | auto encouraged | D1 option (c). |
   232	
   233	- **Hard limits:** Bash rules are not a boundary (📖 R1.2.6); hooks fail open unless
   234	  `"onFailure": "block"` (📖 R1.5.2); `--restricted` cannot be forced by a setting (📖 R6.9.1), and a `PATH` wrapper on laptops can be bypassed (⚠️ R6.9.1c);
   235	  on laptops **without MDM**, a different login, an API key or a `CLAUDE_CODE_USE_*` variable skips
   236	  server-managed settings, `allowedProviders` included (📖 R1.1.7; ⚠️ R1.8 #3, G11). So S5's
   237	  "nobody can turn off all prompts unnoticed" is likely unreachable without MDM (⚠️).
   238	- **Auto memory:** engineers review it and delete it after a suspicious session; residual risk with a
   239	  named owner (D3).
   240	- **Fallback:** switch to `disableAutoMode` (📖 R1.2.2) if the planted-injection test steers auto mode, a serious
   241	  advisory appears, or an audit finds auto mode touched a protected scope (D1).
   242	
   243	**Audit evidence.** Managed settings in git with PR approvals; `/status` and `claude doctor` from
   244	sampled machines (📖 R1.1.18); OTel `claude_code.tool_decision` (`permission_mode`) and
   245	`claude_code.tool.blocked_on_user` (`duration_ms`, rubber-stamping signal) (fields 📖 research 6.6
   246	D1 metrics; thresholds ⚠️). Settings-change audit events on Team: unknown (⚠️ R1.1.12).
   247	
   248	**Cost / value.** More prompts than auto mode, partly offset by the read-only allowlist. Compliance
   249	gets one organization policy with evidence instead of personal choices (P3c).

   253	## Layer 3 — Change workflow by risk level
   254	
   255	**Principle.** The level is set by the damage a change can do. One default path above non-prod: a
   256	reviewed PR applied by the pipeline, with the JIT fallback (layer 7) as the only other write path.
   257	The approver reviews the code change that will be applied. Every prod change needs two people, and
   258	no more by default: one who makes it and one who approves it; the on-call backup only replaces an
   259	unavailable primary (OD2). Higher risk narrows **who** may approve (the owners of that path), not how
   260	many. Separately, any prod diff that looks risky stops the deploy, whatever its level; that adds a
   261	second approval, by the same or another owner, not a third person. Two edge cases: a PR that touches
   262	paths of several owner teams needs an approval from each, which stays two people only if one
   263	approver belongs to all those teams (otherwise it is a deviation from "two people" that the owner
   264	should confirm, or the PR is split); a real-data read is not a change and has its own rule,
   265	L3-data. Incidents use the same
   266	path with faster people, not fewer security checks.
   267	
   268	| Level | What | Examples | Approval | Path |
   269	|---|---|---|---|---|
   270	| **L0** | Read: non-prod anything; prod metadata | metrics, redacted logs | none | read-only identity |
   271	| **L1** | Change in non-prod | deploy a branch to dev; `pulumi preview` on non-prod (needs state-write permission on a DIY S3 backend, 📖 R4.3.3) | author only | non-prod roles or PR pipeline |
   272	| **L2** | Routine prod change in code | Lambda timeout/memory, ECS desired count, release | 1 code owner ≠ author, ≠ last pusher | PR → `main` → deploy workflow |
   273	| **L3** | High-risk prod change | IAM/SCP; replace/delete of stateful resources; network; `.github/**`, CODEOWNERS, `CLAUDE.md`, `CLAUDE.local.md`, `.claude/**`, `.claude.json`, `.mcp.json`, `.husky/`, `.gitmodules`, `.ripgreprc`, plugin/MCP catalogue; advisory policy finding | 1 code owner of the L3 path ≠ author, ≠ last pusher (in incidents: the on-call approver if they own the path, see "Who approves at night") | same path; for IaC changes the risk stop also applies; workflow and agent-config files have no prod diff |
   274	| **L3-JIT** | Break-glass | ECS force-redeploy while Actions is down | on-call approver ≠ requester (Options §4b) | layer 7 |
   275	| **L3-data** | Real customer data read | one tenant's failed claim record | an approver ≠ requester and an agreement (GĐ-9); data-owner co-approval [design], beyond GĐ-9 | layer 6 |
   276	
   277	`CLAUDE.md` and the other agent configuration files are L3, because they define the workflow for
   278	the whole team (OD3). With code-owner review on, every PR, L2 included, needs an approval from an
   279	owner of the files it touches (📖 R3.2.3, R3.2.7; per-file behaviour ⚠️ not a separate research row).
   280	What differs at L3 is **which team** owns the path: L3 paths are owned by a designated L3 owner team
   281	through a path-based rule (📖 R3.2.4), L2 paths by their domain team; and IaC changes at L3 meet the
   282	risk stop. Cost: changes to `CLAUDE.md` (where D3 puts shared knowledge) need the L3 owner team, not
   283	the domain team that edits it most.
   284	
   285	**On Papaya's stack**
   286	
   287	- **Gate = merge to `main`.** On Team, environment reviewers do not exist for private repos
   288	  (📖 R3.1.2). Ruleset on `main`: PR required, 1 approval, code-owner review, dismiss stale approvals,
   289	  approval by someone other than the last pusher, required checks from a pinned source app, no force
   290	  push, empty bypass list (📖 R3.2.2, R3.2.3, R3.2.5). Branch up to date before merge, since there is
   291	  no merge queue (⚠️ R4.6 #1; whether updating drops approvals is open, Options §8).
   292	- **L3 approvals [design]:** a path-based rule requires 1 approval from the team that owns each L3
   293	  path (📖 R3.2.4); GitHub stops the author from approving (📖 R3.3.1). A required check with a pinned source app (📖 R3.2.5) adds what
   294	  the rules cannot: for app-opened PRs it excludes the person who triggered the agent, and it counts
   295	  only human approvals, since an app's approval might count (⚠️ R3.3.4, R3.7 A3).
   296	- **Who approves at night [design; agent's reading of OD2, to confirm with the owner]:** the
   297	  on-call approver schedule is drawn only from engineers who already own paths, and each shift
   298	  holds an owner of every L3 path and of every deployable L2 path. Nobody is added to an owner team
   299	  for a shift. If a shift cannot cover a path, an owner of that path is paged off-schedule and the
   300	  wait is counted against S7; this does not open the JIT fallback, which is for an unavailable
   301	  pipeline, not a missing approver. Whether Papaya's team size allows full coverage is unknown
   302	  (§1, S7).
   303	- **Risk stop [design]:** applies to every deploy, whatever the level. The deploy job previews prod;
   304	  on stateful replace/delete, an IAM change, a network or security-group change, or an advisory
   305	  policy finding it stops. A second PR adds `deploy-approvals/<stack>/<sha>.yaml`, where `<sha>`
   306	  is the commit of the original merge (not the commit the second PR creates) and the file holds the
   307	  preview hash. CODEOWNERS on `deploy-approvals/<stack>/` names the owners of that stack, and the L3
   308	  owner team when the stop came from an L3 trigger (IAM, network, stateful), so the prod diff is
   309	  seen by an owner of the risky path. The approver is ≠ author and may be the same approver as the
   310	  first PR, who now sees the prod diff. A re-run of the deploy for the original commit continues only
   311	  if the hash matches (Options §1; hash stability ⚠️ Options §8). A
   312	  `mandatory` policy violation always blocks `pulumi up` (📖 R4.2.2): the fix is a code change, or a
   313	  change to the policy pack through its own L3 PR. Preview output is filtered for
   314	  outputs and secrets before it is posted (Options §1; ⚠️ R4.6 #2).
   315	- **Merge approval = deploy approval** only if (⚠️ R3.6 #1, from 📖 R3.1.3, R3.4.5c): `production`
   316	  allows only `main`; only the reusable deploy workflow (under CODEOWNERS) references it; no ref/SHA
   317	  inputs; no `issue_comment`, `pull_request_target` or `workflow_run` triggers; one concurrency group
   318	  per stack without `cancel-in-progress` (📖 R4.1.4).
   319	- **Pulumi:** PRs preview non-prod only, because a prod preview runs PR code with state-write and
   320	  secret access (📖 R4.3.3, R4.3.4; ⚠️ R4.6 #2). On `main`: prod preview, then `pulumi up` with the
   321	  policy pack, which stops on a mandatory violation (📖 R4.2.2). Prod runs allow no `--skip-preview`
   322	  (📖 R4.1.2) and no targeting, replace, `state`, `import`, `destroy` (⚠️ R4.6 #3, G12). Pulumi Cloud,
   323	  if used: OIDC via `pulumi/auth-actions`, no stored token (📖 R4.1.4).
   324	- **Serverless v4:** `serverless package`; `serverless diff --json` (sf-core ≥ 4.37.0), parsed by CI
   325	  because differences do not change the exit code (📖 R4.4.2); `serverless deploy --package`
   326	  (📖 R4.4.3); a least-privilege `deploymentRole`, which cannot be removed later and is usable by
   327	  anyone who may operate the stack (📖 R4.4.5), so JIT roles get no stack-operation rights.
   328	- **State:** writable by deploy roles (and possibly the drift role, layer 7); Pulumi
   329	  secrets via `awskms` on a DIY backend (📖 R4.3.3, R4.3.4; ⚠️ R4.6 #7).
   330	- **k0s [design]:** manifests in the monorepo, applied by CI; no write RBAC for humans or agents in
   331	  prod; read roles exclude logs and exec in namespaces with claim data (mechanism: G1).
   332	- **Incident lane:** label `incident`, on-call approver paged, security checks always run (S10), only
   333	  slow unrelated tests skipped [design].
   334	
   335	**Example: Lambda timeouts at 2 a.m.** (Options §6)
   336	
   337	The incident responder is engineer E; the on-call approver is R (a backup replaces R only if R is
   338	unavailable).
   339	
   340	1. E's incident-analysis session reads metrics and redacted logs and proposes `timeout` 30 → 90 s,
   341	   memory 1024 → 2048 MB, and a larger visibility timeout on the source queue (ratio ⚠️ Options §8).
   342	2. A second session (edit tools; not meant to use prod roles) edits `serverless.yml`, runs
   343	   `serverless diff` on non-prod, and opens a PR labelled `incident` as E.
   344	3. R, who owns `serverless.yml` for this service (layer 3, "Who approves at night"), reviews the
   345	   diff, and can catch a missing queue change, then approves. E merges.
   346	4. The deploy workflow packages, previews prod, finds no risky change, deploys with the OIDC role.
   347	5. Estimate 11–46 min (⚠️ Options §6) against ≤ 30 min: measured first in rollout.
   348	
   349	**Audit evidence.** The PR (diff, approvers, checks); run log and preview artifact, exported because
   350	retention is unverified (⚠️ G7); deploy-role CloudTrail events; all linked by commit SHA and run ID.
   351	
   352	**Cost / value.** One approver for every prod change, from the owners of the path; two approvals
   353	(same or another owner) when the risk stop fires; more than one approver only for a PR across
   354	several owner teams. None in non-prod.
   355	Compliance gets four-eyes enforced by GitHub. Gap: on Team the prod diff is not seen before apply.

   396	## Layer 5 — CI/CD hardening
   397	
   398	**Principle.** CI is the default production writer, so it is the main target. Short-lived,
   399	least-privilege credentials per job. Every CI dependency is pinned. Agent-written code passes the same
   400	checks as human code (S10).
   401	
   402	**On Papaya's stack**
   403	
   404	- **Credentials:** OIDC instead of keys and tokens in repository secrets, which any writer can read
   405	  (📖 R3.4.1, R3.5.3b). Org default for `GITHUB_TOKEN` set to "restricted", `permissions:` per job (📖 R3.5.3).
   406	  "Allow GitHub Actions to create and approve pull requests" off (📖 R3.3.3). Serverless License Key in
   407	  SSM, read by the deploy role (sf ≥ 4.4.19, 📖 R4.4.8). Until G1/G2 are solved, k0s and Firebase
   408	  deploys may need a stored credential in GitHub: a kubeconfig or token for k0s, a Firebase token or
   409	  service-account key for Firebase Hosting. The owner accepts this as an exception to S2 = 0 until it
   410	  is checked whether k0s and Firebase deploys can use OIDC (OD1, OD6). Conditions [design]:
   411	  - stored only as an **environment secret of `production`**, never as a repository secret. Anyone
   412	    with write access can read repository secrets (📖 R3.5.3b), which would turn the exception into
   413	    standing prod write for every engineer and their agent. Environment secrets and a deployment
   414	    branch rule limited to `main` are available on Team for private repos (📖 R3.1.2, R3.1.3), and
   415	    only the reviewed deploy workflow references the environment (layer 3);
   416	  - the deploy job runs on GitHub-hosted runners. On self-hosted runners, jobs "are not run in an
   417	    isolated container, even if they use environments", so environment secrets there must be
   418	    treated like repository secrets (📖 R3.1.5). If reaching k0s needs a self-hosted runner, that
   419	    runner is dedicated to the `production` deploy, and the residual risk is recorded;
   420	  - that environment secret is the single source of truth: no copy elsewhere (OD1);
   421	  - an owner, an expiry and rotation in the exception register;
   422	  - optionally a separate environment (e.g. `production-k0s`), limited to `main` and referenced
   423	    only by the k0s/Firebase deploy workflow, so AWS deploy jobs cannot read these secrets
   424	    [design].
   425	
   426	  Residual risk: admins can change the environment, and a deleted environment comes back without
   427	  protection (⚠️ R3.1.4); the alerts and settings comparison in layer 7 cover this. The exception
   428	  covers **CI deploy credentials only**. Runtime credentials, such as a k0s autoscaler's AWS access to
   429	  add or remove nodes, live in the cluster, not in GitHub; they follow layer 1 (no static keys, a
   430	  role attached to the machine; ⚠️ not researched for k0s, G1).
   431	- **Side paths:** Pulumi ESC, Pulumi Deployments and Serverless Dashboard providers reach AWS
   432	  (📖 R4.4.9) outside the GitHub gate (⚠️ R4.4.9); not used for prod (⚠️ R4.6 #6).
   433	- **Pinning:** workflow lockfile (`gh actions-lock`) or full SHA, enforced by the org policy "Require
   434	  actions to be pinned to a full-length commit SHA"; the lockfile does not pin reusable workflows, so
   435	  the deploy workflow lives in the same repo (📖 R3.5.5; conclusion [design]).
   436	- **CODEOWNERS** on `.github/`, `CLAUDE.md`, `CLAUDE.local.md`, `.claude/`, `.claude.json`, `.mcp.json`,
   437	  `.husky/`, `.gitmodules`, `.ripgreprc` (📖 R3.2.8; list ⚠️ R6.5 #5); CI validates the file, because
   438	  invalid lines are skipped silently (📖 R3.2.7).
   439	- **No privileged triggers with untrusted code** (`pull_request_target`, `workflow_run` + checkout,
   440	  📖 R3.5.4).
   441	- **Agents in CI:** `claude-code-action` with a custom GitHub App limited to Contents, Issues, Pull
   442	  requests (📖 R1.7.8); Anthropic workload identity federation, not a personal OAuth token (📖 R1.7.6);
   443	  `--restricted` and explicit `--tools` (D3; passing it through `claude_args` unverified, ⚠️ research
   444	  6.9.4 Q5); a managed-settings file on the runner, which also guards against mods (📖 R1.5.6; for
   445	  federation auth ⚠️); MCP set fixed by CI because `.mcp.json` loads without a prompt in `-p` runs
   446	  (📖 R1.3.5); never `environment: production` (⚠️ R3.6 #4). Hosted runners give `sudo` (📖 R3.5.1),
   447	  so with `Bash` in `--tools` the runner file is advisory (⚠️ R3.5.1, R3.6 #4).
   448	- **App-opened PRs:** a required check with a pinned source app confirms at least one approval by a
   449	  human who did not trigger the run; counting approvals is not enough, since the app's own approval
   450	  might count (⚠️ R3.3.4, R3.7 A3; 📖 R3.2.5).
   451	- **Required checks (S10):** secret scanning, dependency check, SAST (products: G4); IAM Access
   452	  Analyzer `check-no-new-access` (📖 R2.8.1); Pulumi policy packs (📖 R4.2.2).
   453	
   454	**Audit evidence.** Workflows and lockfile in git; audit-log events such as
   455	`org.update_actions_secret`, `repo.set_workflow_permission_can_approve_pr`, `repository_ruleset.update`
   456	(📖 R3.3.3, R3.5.6). An audit event for environment-secret changes was not researched (⚠️); the
   457	settings comparison in layer 7 covers the S2 exception meanwhile. Check results per PR; secrets inventory (S2).
   458	
   459	**Cost / value.** One-time migration to OIDC and pinned actions; slower action updates. Compliance
   460	gets S2 and the same guardrails for agent and human code.

   464	## Layer 6 — Data protection and prompt-injection defence
   465	
   466	**Principle.** The design keeps PHI from reaching the coding agent (owner decision, research 1.9).
   467	Some paths rely on process (below), so this is a target, not a guarantee. Other customer
   468	personal data is outside that hard boundary ("not extended", research 5.8): the agent reads metadata
   469	by default and may read such data case by case under GĐ-9. Real-data reads are approved, name one
   470	tenant, are time-boxed, and need an agreement (BAA/DPA, partner contract) (GĐ-9). Everything read
   471	from outside is untrusted. Non-prod is synthetic or masked (GĐ-14).
   472	
   473	**On Papaya's stack**
   474	
   475	- **Paths to PHI** (research 1.11.4 lists 17):
   476	  - AWS stores: closed by identity, through `ProdReadMetadata` as the only standing prod role from
   477	    phase 1 (existing broad read roles are removed) and the SCP from phase 2
   478	    (layer 1); no Aurora credentials, no prod exec, no `lambda:InvokeFunction` for agent-usable roles
   479	    [design; actions ⚠️ G13];
   480	  - k0s logs/exec and GCP stores (L1, L11, L13): same principle, mechanism open (G1, G3);
   481	  - tickets/chat via MCP, pasted text, internal admin pages, prod AI traces, fixtures, CI logs (L5,
   482	    L8–L10, L12, L14): process and hygiene only;
   483	  - logs redacted at source with raw payloads in a separate log group; alerts carry IDs, not payloads [design].
   484	- **Real-data request** [design]: tenant, purpose, store, window, agreement; approved by the data owner
   485	  and an approver ≠ requester; JIT data-read role, 1 h. Per-tenant scoping through session tags
   486	  (📖 R2.1.8) is unresolved, because tags come from user attributes (⚠️).
   487	  - **PHI:** a human reads in a terminal without an agent (process rule, layer 1); the agent gets a
   488	    redacted summary. This
   489	    narrows GĐ-9 because the agent stays outside PHI scope (research 1.9) and Team is not shown as
   490	    BAA-covered (⚠️ R1.11.3.4). Enterprise + BAA only for a separate environment if needed (research 1.9).
   491	  - **Non-PHI personal data:** the agent may read it within the approved request (GĐ-9). Claim
   492	    tables mix health, ID and bank data (research 1.11.4 L2), so a store that holds PHI is treated as
   493	    PHI unless the agent reads a view or extract without PHI [design].
   494	- **Partner-uploaded claim documents (A7b):** never in an agent session raw; reproduce with synthetic
   495	  documents, or de-identify first [design]. The document is PHI and an injection vector (research
   496	  1.11.4 L6).
   497	- **Injection** (these lower frequency; layers 1 and 3 limit impact): Manual by default; the auto-mode
   498	  classifier missed 17 % of 52 real overeager actions and 5.7 % of 1,000 synthetic exfiltration
   499	  attempts (📖 R6.3.5). Broad allowed domains such as `github.com` are a documented exfiltration path
   500	  (📖 R6.3.7). The incident session has no WebFetch, likely no edit tools (layer 2), and runs outside
   501	  the repo, but its Bash can still write locally and send data out through excluded
   502	  commands (layer 2), including the SSO token cache; "no standing write, no PHI read" limits what
   503	  the token opens, except during a JIT or data-read window (layer 2 mitigations). Shared knowledge
   504	  goes in `CLAUDE.md` under review; auto memory is exempt from the protected-path rules unless `--restricted` (📖 R6.3.11, D3).
   505	- **Tenants:** one tenant per data-read grant; a session that read one tenant's data does not post to
   506	  shared places without review (⚠️ R6.5 #8, process). Logical separation in shared accounts is assumed
   507	  (GĐ-3, unconfirmed).
   508	- **Non-prod:** no prod copies (S11). A scan of non-prod stores runs at the start of phase 1 (tool:
   509	  G4); a store not yet scanned follows the L3-data rule [design; GĐ-14 says only that non-prod is synthetic]. Cost: until scanned, that store is
   510	  not part of the free loop.
   511	- **Local stores:** transcripts and memory hold what the agent read (research 1.11.4); set
   512	  `cleanupPeriodDays` (30 in the HIPAA sample, 📖 R5.5.4; what it deletes ⚠️).
   513	- **Cross-border (Vietnam example):** processing data collected in Vietnam on a platform abroad is a
   514	  transfer (📖 R5.4.5); agent flows, including employee names in logs and transcripts, update the
   515	  transfer impact assessment (⚠️ R5.7 #4, needs Papaya legal).
   516	
   517	**Audit evidence.** SCP/IAM text as the written access rule for sensitive data (📖 R5.4.3; ⚠️ R5.7 #5);
   518	data-read requests and the data-read role's CloudTrail; planted-injection reports (layer 8); non-prod
   519	scan results (S11).
   520	
   521	**Cost / value.** Debugging with redacted and synthetic data; a request for the rare real-data read.
   522	Compliance gets "minimum necessary" (📖 R1.11.1.8) enforced by IAM for AWS stores (fully from phase 2;
   523	actions ⚠️ G13) and by process
   524	elsewhere, and a record per exception (S9).

   532	is approved before use, time-boxed and reconciled after.

   534	**On Papaya's stack**
   535	
   536	- **Audit stores:**
   537	  - organization CloudTrail to a log-archive account with integrity validation (📖 R2.6.2, R2.6.4,
   538	    R2.6.5); change records ≥ 6 years; raw-log retention for Papaya's compliance owner (⚠️ R5.7 #2).
   539	    Data events only on PHI buckets, prod Lambda invoke and prod SQS (cost 📖 R2.6.3; selection
   540	    ⚠️ R2.9 #5), which makes the archive
   541	    PHI-bearing (⚠️ research 1.11.4 L15). CloudTrail Lake is closed to new customers (📖 R2.6.6);

   543	  - alerts on `repository_ruleset.update`, `environment.update_protection_rule`,
   544	    `environment.remove_protection_rule`, `environment.delete`, `protected_branch.policy_override`
   545	    (📖 R3.5.6, R3.1.4; selection ⚠️ R3.6 #1). UI changes to the branch policy may leave no event, and a
   546	    deleted `production` environment comes back unprotected (⚠️ R3.1.4): a job compares live settings
   547	    with an expected copy (G8);
   548	  - Aurora SQL is likely invisible to CloudTrail (⚠️ R2.7.1): Database Activity Streams, alerts on

   551	- **Change record [design]:** keyed by commit SHA or JIT request ID; links PR, approvals, run ID,
   552	  preview and CloudTrail events. Monthly reconciliation: every prod write event matches a record
   553	  approved before apply (S3). Actor: `onBehalfOf.userId` where present, else session name plus
   554	  directory lookup (📖 R2.5.1; ⚠️ R2.5.3).
   555	- **Drift [design]:** its own role, trusted only from a `drift` environment on `main`; it can read
   556	  prod secrets in state, which is noted (⚠️ R4.6 #2). Scheduled `pulumi preview --refresh
   557	  --expect-no-changes` or `pulumi refresh --preview-only` (📖 R4.1.1, R4.3.1, R4.3.2). On a DIY S3
   558	  backend, preview needs state-write permission (📖 R4.3.3); whether a refresh preview writes more
   559	  than locks is open (⚠️ R4.6 #2, G14). So either the drift role gets state write (and the same

   563	  drift detection, explicitly set properties only (📖 R4.4.6). No auto-remediation: it is an unreviewed
