     1	# Framework: coding agents for DevSecOps at Papaya
     2	
     3	> Status: draft v2, for owner review · Updated: 2026-11-09
     4	> Audience: a panel of Engineering and Compliance. Every layer states what it costs engineers and
     5	> what it gives Compliance.
     6	
     7	## How to read this
     8	
     9	The framework has eight layers. Each layer has three parts:
    10	
    11	- **Principle**: the rule, independent of any tool. It still holds if a tool changes.
    12	- **On Papaya's stack**: how the rule is applied with Pulumi, Serverless Framework, GitHub
    13	  Actions, AWS, GCP, k0s and Claude Code.
    14	- **Audit evidence**: the records the layer produces, so an auditor can test it without asking
    15	  anyone.

    36	## 1. The decision in one page
    37	
    38	**The conflict is narrow.** Engineering and Compliance disagree only about *writes to
    39	production*. Reading metadata and everything in non-prod are outside Compliance's sentence
    40	(framing §3.1). Reading real customer data is a separate question (layer 6).
    41	
    42	**Chosen approach: "A + D2'"** (Options §9, owner decision 2026-11-09):
    43	
    44	1. **Every production change is a pull request**, approved by a named human who is not the author,
    45	   and applied by the CI pipeline. This holds during incidents too ("IaC first").
    46	2. **A narrow fallback (break-glass)**: only when the PR path cannot be used, a human gets a
    47	   short, approved just-in-time (JIT) permission and runs an approved command list in a terminal
    48	   without an agent [design]. Details in layer 7.
    49	3. **Nobody holds standing production write access**, and the agent is never given a production
    50	   write identity. During a JIT window the grant is reachable from the same laptop, so "no agent in
    51	   that terminal" is a process rule (D2).
    52	
    53	| Engineering gets | Compliance gets |
    54	|---|---|
    55	| A free loop in non-prod: the agent reads, changes and deploys without approval (safe because non-prod holds synthetic data only, GĐ-14). | Every prod change approved **before** apply by a named human ≠ author (GĐ-8, GĐ-11), enforced by GitHub rulesets and AWS IAM rather than by the agent. |
    56	| Read-only prod metadata for the agent (config, metrics, redacted logs). | No standing prod write for any human (S1); no long-lived keys in CI (S2). |
    57	| Self-service: open a PR, get one approval, ship the same day (S4: wait ≤ 1 h in working hours). | One evidence chain per change. Approval and change records kept ≥ 6 years (📖 R5.2.9; applied to change records ⚠️ R5.7 #2). |
    58	| An incident lane: approval wait ≤ 15 min 24/7 (S7). Decision-to-apply target ≤ 30 min (Options §9 Q3); current estimate 11–46 min ⚠️, measured in phase 1. | Agent-side controls (managed settings, tool catalogue) as a second layer, not as the control of record. |
    59	
    60	**Where the design does not fully meet Compliance's sentence (stated openly):**
    61	
    62	- **The JIT fallback meets it only partly.** The approver approves a command list, not an applied
    63	  change, and "the human, not the agent, ran it" is a process rule (Options §5.1). The owner
    64	  accepted this (Options §9 Q2). It is measured (layer 7).
    65	- **On the GitHub Team plan nobody sees the prod diff before apply** (⚠️ R4.6 #1; Team is the
    66	  owner's assumption GĐ-5). The reviewer sees the code diff and a non-prod preview. The deploy job
    67	  stops on risky prod diffs and asks for a second approval [design].
    68	- **Admins can edit the gate.** Repository admins and holders of "edit repository rules" can
    69	  change or disable rulesets; this is logged, not prevented (📖 R3.2.2, ⚠️ R3.6 #1). The agent on
    70	  a laptop acts with its engineer's GitHub login, so an admin's agent has the same power. Few
    71	  admins, access reviews and alerts mitigate this (layers 7, 8).
    72	- **Incident approvers are scarce.** If the on-call approver is a code owner of every path, domain
    73	  review gets weaker; L3 incidents need a platform approver on call 24/7 with a backup, which a
    74	  1–2 person DevSecOps team cannot staff alone (Options §1, §7; GĐ-1).
    75	- **The fallback is narrow only by assumption.** If most Papaya incidents need operations outside
    76	  IaC, A + D2' drifts toward "JIT for incidents" until runbooks exist (Options §7; share unknown,
    77	  Options §8). Layer 7 measures it.
    78	- **Two paths, not one.** The framing asked for "one path, technically enforced" (framing §3.3).
    79	  The fallback is a deliberate, process-controlled second path (Options §7).
    80	- **HIPAA applicability is a legal question** (⚠️ R1.11.1.11). The design follows the brief and
    81	  treats Papaya as a business associate.
    82	
    83	**Cross-cutting rules** (from the owner's balance principle, `work/02-research.md` 6.8):
    84	
    85	1. **The boundary is IAM and the CI gate.** Agent-side controls lower how often things go wrong;
    86	   the docs call server-managed settings "a client-side control, not a security boundary"
    87	   (📖 R1.1.7), and a local admin can edit endpoint-managed files (📖 R1.1.8).
    88	2. **Assume prompt injection succeeds.** OWASP and NIST state there is no full prevention
    89	   (📖 R6.1.1, R6.1.2).
    90	3. **Friction where damage is large, none where it is small.** If the safe path is slower than the
    91	   shortcut, people take the shortcut (P3b). So friction is measured and has a time-boxed escape.
    92	4. **Nothing standing.** No standing prod write, no long-lived credentials.
    93	5. **Evidence by construction.** The path itself produces the records.
    94	
    95	### Roles
    96	
    97	| Role | Who | Rule |
    98	|---|---|---|
    99	| Author | The engineer, and the agent working for them | Never approves their own change. GitHub blocks PR authors from approving (📖 R3.3.1). |
   100	| Approver | A named human with write access, listed in CODEOWNERS | ≠ author, ≠ last pusher (📖 R3.2.3). For a PR opened by a GitHub App, ≠ the person who triggered it (⚠️ R3.3.4, enforced by a check, layer 5). |
   101	| On-call approver | Primary + backup, 24/7, named in the on-call schedule | Same rule as Approver. Target: approval wait ≤ 15 min (S7). |
   102	| Platform approver | Platform team member, also on the on-call schedule | Second approval for L3 changes. |
   103	| Data owner | Named per tenant (for example the account owner for that insurer) | Approves real-data reads for that tenant (layer 6), together with an approver ≠ requester. |
   104	| Control owner | DevSecOps (1–2 people, GĐ-1) | Owns policy files and metrics. Is **not** the only approver. |
   105	
   106	Roles other than Author and Approver are [design].
   107	
   108	"An agent never approves" (GĐ-11) is enforced only partly: GitHub blocks self-approval, but an
   109	agent using its engineer's `gh` login could approve **someone else's** PR as that engineer. The
   110	auto-mode classifier blocks only "approving Claude's own pull request" (📖 R6.3.3). In CI, a GitHub
   111	App with pull-request write might approve PRs; whether such an approval counts is unknown
   112	(⚠️ R3.7 A3), so the gate relies on a check that requires a human approver (layer 5). This is a
   113	process rule with residual risk. No detection mechanism was found in the researched sources; the
   114	org audit log's `actor_is_agent` field is a candidate whose meaning is undocumented (⚠️ R3.5.6).

   118	## Layer 1 — Identity and access
   119	
   120	**Principle**
   121	
   122	- Every action traces to one named human.
   123	- Nobody holds standing write access to production. Production is written by the pipeline role,
   124	  or, in the fallback, by an approved, time-boxed human grant.
   125	- Production reads default to metadata. Reads of stores that hold customer data are blocked by a
   126	  guardrail that member-account identities cannot edit.
   127	- No long-lived credentials. Prod and non-prod are separate boundaries.
   128	
   129	**On Papaya's stack**
   130	
   131	- **The human's access is the agent's access.** On a laptop the agent uses the engineer's AWS SSO
   132	  cache, and one portal session reaches every role assigned to the engineer (📖 R2.2.1, R2.2.2). A
   133	  separate "agent" permission set therefore does not separate them (⚠️ R2.9 #1). The control is
   134	  what the **engineer** holds.
   135	- **AWS IAM Identity Center permission sets** (📖 R2.1.1):
   136	  - `ProdReadMetadata`: config, metrics and redacted log groups in prod; no data-plane read on
   137	    stores holding claim data (from phase 1, before the SCP in phase 2); session duration 1 h, the
   138	    minimum (📖 R2.1.4). Caveat: function configuration can contain secrets, because values that
   139	    Serverless resolves may sit in Lambda environment variables in plain text (⚠️ R4.4.7). Phase 1
   140	    moves secrets to runtime resolution (⚠️ R4.6 #7); until a service is moved, its configuration
   141	    read is excluded and the agent reads timeout/memory from the IaC code. Cost: a less exact view
   142	    of live state for those services.
   143	  - `NonProdDeveloper`: broad rights in non-prod accounts only.
   144	  - **No standing prod-write permission set.**
   145	  - `InfraOperator-<service>`: assigned only by the JIT flow (layer 7). Tooling: a partner product,
   146	    the TEAM sample, or a small flow on `CreateAccountAssignment` / `DeleteAccountAssignment`
   147	    (📖 R2.4.1, R2.4.1b, R2.4.2).
   148	- **Guardrails in the prod OU (SCPs)**, which cap member-account principals (📖 R2.3.1, R2.3.2) [design]:
   149	  - deny data-plane reads on stores holding claim data except application roles and the approved
   150	    data-read role, selected by `aws:PrincipalArn` (key 📖 R2.3.8; pattern ⚠️ R2.9 #4). Example
   151	    actions, incomplete and not checked against the IAM reference (⚠️ research 1.11.4, G13):
   152	    `s3:GetObject` on the claim-documents bucket, `sqs:ReceiveMessage`, `states:GetExecutionHistory`;
   153	  - deny `lambda:UpdateFunctionCode` and `lambda:UpdateFunctionConfiguration` (action names
   154	    ⚠️ R4.6 #3) except the CloudFormation `deploymentRole` and the named JIT roles, to close
   155	    `serverless deploy function`, which changes config outside CloudFormation (📖 R4.4.4; SCP or IAM
   156	    not chosen);
   157	  - the role that deploys SCPs works in the management account, where no SCP applies (📖 R2.3.2):
   158	    it is the most sensitive deploy role and gets its own L3 path rule;
   159	  - a pre-deployed revocation Deny on `identitystore:userId` (📖 R2.4.4);
   160	  - protect the organization trail and log archive (📖 R2.6.2).
   161	  Limits: 10 SCPs per target, 10,240 characters each; nothing applies to the management account
   162	  (📖 R2.3.2, R2.3.4).
   163	- **Sessions and MFA:** set the access-portal session length on purpose; the IdP session can
   164	  silently extend it (📖 R2.1.5, R2.1.6). MFA is managed in the external IdP if one is used (📖 R2.1.7).
   165	- **CI → AWS:** GitHub OIDC, no stored keys (📖 R3.4.1). The prod deploy role trusts only tokens
   166	  from the `production` environment of Papaya's monorepo, in the repo's `sub` format (📖 R3.4.3,
   167	  R3.4.4; the immutable format is assumed, ⚠️ R3.7 A2). Preferably the `sub` is customised to also
   168	  include the reusable deploy workflow's `job_workflow_ref` (📖 R3.4.5; availability on Team ⚠️, G10).
   169	  Non-prod roles trust non-prod environments or `pull_request` (⚠️ R4.6 #2).
   170	- **CI → GCP:** Workload Identity Federation with an attribute condition on Papaya's GitHub
   171	  organization, which Google requires (📖 R3.4.5b).
   172	- **GCP, k0s and Firebase for humans:** same principles; mechanisms not researched (G1–G3). Today
   173	  engineers reach k0s with kubeconfigs and no SSO (GĐ-4, unconfirmed). Interim rule: no admin
   174	  kubeconfig and no GCP owner role on laptops; prod deploys to k0s and Firebase run only from CI.
   175	  Until G1/G2 are solved, those CI jobs may still need a stored kubeconfig or token: a time-boxed
   176	  exception to S2, with an owner, in the exception register (layer 8). Firebase is not on the GCP
   177	  BAA list, so Firebase Hosting must hold no PHI (📖 R5.5.3).
   178	
   179	**Audit evidence**
   180	
   181	- Export of Identity Center assignments: no standing prod-write assignment (S1).
   182	- CloudTrail `CreateAccountAssignment` / `DeleteAccountAssignment` per JIT grant (📖 R2.4.2), linked
   183	  to the approval record by request ID [design].
   184	- SCPs and trust policies as Pulumi code: version history = change history.
   185	- IAM Access Analyzer `check-no-new-access` on every PR that changes a policy (📖 R2.8.1).
   186	- Quarterly access review (permission sets, GitHub admins).
   187	
   188	**Cost / value.** Engineers lose standing prod write; they keep fast prod reads and a free non-prod
   189	loop. Compliance gets least privilege that is enforced, not promised.

   193	## Layer 2 — Agent runtime controls
   194	
   195	**Principle**
   196	
   197	- Agent-side controls are hygiene: they cut mistakes; they are not the boundary (📖 R1.1.7, R1.1.8).
   198	- They are set centrally, the same for everyone, and versioned in git.
   199	- Safe defaults with a measured escape hatch. A default that people keep overriding is replaced,
   200	  not defended.
   201	- The session that reads untrusted content should hold as little power as possible (📖 R6.1.2).
   202	
   203	**On Papaya's stack**
   204	
   205	- **Delivery:** server-managed settings from the claude.ai admin console (available on Team,
   206	  📖 R1.1.5) for all laptops. Where MDM exists, also an endpoint `managed-settings.json`, protected
   207	  at OS level, though a local admin can still edit it (📖 R1.1.3, R1.1.8). MDM is unknown, so both
   208	  paths are prepared (R1.9).
   209	- **Baseline keys** (template: Anthropic's `settings-hipaa.json`, 📖 R5.5.4):
   210	
   211	  | Key | Value | Why | Source |
   212	  |---|---|---|---|
   213	  | `permissions.defaultMode` | `default` (Manual) | D1. A default, not a lock: users can switch to auto; VS Code remembers the last pick. | 📖 R6.9.3 |
   214	  | `permissions.allow` (managed) | read-only commands Papaya uses, e.g. `Bash(aws cloudwatch get-metric-data *)` | Fewer prompts for safe reads (P3b) | 📖 R6.9.3 |
   215	  | `allowManagedPermissionRulesOnly` | `true` | One rule set for everyone (D1, owner Q4). Cost: project and user allow/deny/ask rules are ignored and always-allow choices are hidden, so the managed set must carry every deny/ask rule projects rely on, and prompts likely rise (⚠️ research 6.9.4 Q4). | 📖 R1.2.5 |
   216	  | `permissions.deny` | credential paths, e.g. `Read(~/.aws/**)` | The sandbox does not cover the Read tool (📖 R1.6.2) | deny on credential paths 📖 R5.5.4; exact `Read(...)` syntax ⚠️ R1.8 #5 |
   217	  | `permissions.ask` | `WebFetch` in daily sessions | WebFetch is not limited by the sandbox domain list (📖 R1.6.2). Cost: one prompt per fetch. | rule order deny → ask → allow 📖 R6.9.3 |
   218	  | `permissions.disableBypassPermissionsMode` | `"disable"` | Removes "prompts off" (P3a) | 📖 R1.2.2 |
   219	  | `requiredMinimumVersion` | ≥ 2.1.295, and ≥ the latest fixed advisory at rollout (this also covers the plugin-pin fix in 2.1.179) | `onFailure: "block"` needs 2.1.295 (📖 R1.5.2), `allowedProviders` 2.1.285 (📖 R1.1.15), fail-closed locks 2.1.282 (📖 R1.1.11); advisory history (📖 R6.3.9) | 📖 R1.1.13 |
   220	  | `allowedProviders` + `forceLoginOrgUUID` | `["anthropic"]` + Papaya's org | On endpoint-managed machines, closes most bypasses | 📖 R1.1.15 |
   221	  | `allowManagedHooksOnly` | `true` | Repo and user hooks cannot run | 📖 R1.5.4 |
   222	  | `sandbox.enabled`, `sandbox.failIfUnavailable`, `sandbox.allowUnsandboxedCommands: false`, narrow `sandbox.network.allowedDomains` locked with `sandbox.network.allowManagedDomainsOnly: true` | on | Shell commands only (R1.6.2); without the lock, list keys merge across scopes and users could widen it (R1.1.2) | 📖 R1.6.4 |
   223	  | `sandbox.credentials` / `sandbox.filesystem.denyRead` on `~/.aws` | on, with `aws` in `sandbox.excludedCommands` | Trade-off below | 📖 R1.6.3, R1.6.4 |
   224	  | MCP and plugin keys | see layer 4 | | |
   225	  | OTel exporter with content flags `0` | on | Usage evidence without prompt content | 📖 R1.1.20, R5.5.4 |
   226	
   227	- **Trade-off on AWS credentials in the sandbox.** By default the sandbox can read `~/.aws`
   228	  (📖 R1.6.3). Denying it stops other shell commands from reading the credential cache, but then
   229	  the agent can call AWS only through `aws` as an excluded command, which "run[s] with full access"
   230	  (📖 R1.6.4), including unrestricted network: `aws` itself becomes an egress channel outside the
   231	  allowlist (for example a copy to a bucket outside Papaya). This is accepted because the engineer
   232	  holds no prod write and no PHI read; the deny only narrows which programs can take the
   233	  credentials. Residual risk: exfiltration of what the session has read, through `aws`. The same
   234	  applies to `pulumi` and `serverless`, which also need the credentials for the free non-prod loop:
   235	  they are excluded commands too, with the same risk; the alternative (non-prod deploys only through
   236	  CI) costs the loop its speed. A stronger
   237	  option is a separate OS user or container for prod-reading sessions with only
   238	  `ProdReadMetadata` (⚠️ R6.5 #2, phase 3).
   239	- **Session types:**
   240	
   241	  | Session | Where | Identity | Flags | Enforcement |
   242	  |---|---|---|---|---|
   243	  | Daily development | laptop | non-prod roles + `ProdReadMetadata` | managed baseline | Auto mode allowed by choice (D1). `--restricted` recommended (D3). |
   244	  | Incident analysis | laptop | intended: `ProdReadMetadata` only | `--restricted --tools "Bash,Read,Grep,Glob"` (📖 R6.9.1b) | **Process rule** (D3, owner Q1–Q2). No Edit/Write tools, but Bash remains: writes and network calls are limited only by the sandbox and Manual prompts, and Bash can reach any role in the SSO cache (📖 R2.2.2). |
   245	  | CI agent | GitHub-hosted runner | its own GitHub App token; **no** prod environment | `--restricted`, explicit `--tools`; rules in a managed-settings file on the runner, with `allowManagedPermissionRulesOnly: true` as on laptops (owner Q4, Q5) | In the workflow file under CODEOWNERS (D3). |
   246	  | JIT terminal (fallback only) | laptop | JIT grant | **no agent running** | **Process rule** (D2). |
   247	  | Auto-mode environment (phase 3) | separate environment, non-prod credentials only | non-prod | auto mode encouraged | D1 option (c). |
   248	
   249	- **Hard limits, stated openly:**
   250	  - Bash permission rules are not a security boundary (📖 R1.2.6).
   251	  - Hooks fail open unless `"onFailure": "block"` is set (📖 R1.5.2).
   252	  - `--restricted` cannot be forced by a setting on laptops (📖 R6.9.1, R6.9.1c).
   253	  - **On laptops without MDM there is no way to close the bypasses** of server-managed settings: a
   254	    different login, an API key or a `CLAUDE_CODE_USE_*` variable skips them, including
   255	    `allowedProviders` sent from the server (📖 R1.1.7; ⚠️ R1.8 #3; G11). So S5's second target
   256	    ("nobody can turn off all prompts unnoticed") is likely not achievable without MDM (⚠️). The compensating
   257	    controls are IAM and the CI gate.
   258	  - In a JIT window the grant sits in the same SSO cache the agent can reach (📖 R2.2.2). "No agent
   259	    in the JIT terminal" is a process control (D2).
   260	- **Personal auto memory:** engineers review it periodically and delete it after a session that
   261	  handled suspicious content; the rest is a residual risk with a named owner (D3).
   262	- **Fallback:** switch to `disableAutoMode` if the planted-injection test (layer 8) steers auto
   263	  mode, a serious advisory appears, or an audit finds auto mode touched a protected scope (D1).
   264	
   265	**Audit evidence**
   266	
   267	- The managed settings file in git, with PR approvals.
   268	- `/status` and `claude doctor` output from sampled machines (📖 R1.1.18).
   269	- OTel: `claude_code.tool_decision` with `permission_mode`; `claude_code.tool.blocked_on_user`
   270	  with `duration_ms` as a rubber-stamping signal (fields 📖 research 6.6 D1 metrics; threshold ⚠️).
   271	- Settings-change audit events exist; availability on Team is unknown (⚠️ R1.1.12).
   272	
   273	**Cost / value.** Manual mode prompts more than auto mode; the managed read-only allowlist offsets
   274	part of it. Compliance gets an organization policy with evidence instead of personal choices (P3c).

   278	## Layer 3 — Change workflow by risk level
   279	
   280	**Principle**
   281	
   282	- The level is set by the damage a change can do, not by who asks.
   283	- Above non-prod, one path: a reviewed PR, applied by the pipeline. The approver reviews the code
   284	  change that will be applied and is a named human who is not the author. (On GitHub Team the prod
   285	  diff itself is not seen before apply, ⚠️ R4.6 #1.)
   286	- Higher risk adds a specialised second approver, not a different path.
   287	- An incident uses the same path with faster people, not fewer security checks.
   288	
   289	**Levels**
   290	
   291	| Level | What | Examples | Approver | Path |
   292	|---|---|---|---|---|
   293	| **L0** | Read: anything in non-prod; metadata in prod | `aws cloudwatch get-metric-data`, redacted logs | none | Direct, read-only identity |
   294	| **L1** | Change in non-prod (synthetic data, GĐ-14) | Deploy a branch to dev, try a queue setting, `pulumi preview` on non-prod (it writes state, 📖 R4.3.3) | none beyond the author | Direct with non-prod roles, or PR pipeline. Precondition: a clean non-prod data scan (S11); until then non-prod follows the L3-data rule (GĐ-14). |
   295	| **L2** | Routine prod change expressible as code | Lambda timeout/memory, ECS desired count, app release | 1 code owner ≠ author, ≠ last pusher | PR → merge to `main` → deploy workflow |
   296	| **L3** | High-risk prod change | IAM or SCP; replace/delete of a stateful resource; network; `.github/**`, CODEOWNERS, agent config files (layer 5), plugin/MCP catalogue; policy-pack violation | L2 + platform approver | Same PR path; second approval by path rule or by the deploy job's risk stop |
   297	| **L3-JIT** | Break-glass when the PR path cannot be used | ECS force-redeploy while Actions is down | on-call approver ≠ requester (Options §4b) | JIT fallback, layer 7 |
   298	| **L3-data** | Read of real customer data | Inspect one tenant's failed claim record | data owner + approver ≠ requester; a suitable agreement must exist (GĐ-9) | Data-read request, layer 6 |
   299	
   300	**On Papaya's stack**
   301	
   302	- **The gate is the merge to `main`.** On GitHub Team, environment required reviewers are not
   303	  available for private repos (📖 R3.1.2; Team is assumed, GĐ-5). A ruleset on `main` sets
   304	  (📖 R3.2.3, R3.2.5):
   305	  - require a pull request, 1 approval, code-owner review;
   306	  - dismiss stale approvals when the diff changes;
   307	  - require approval from someone other than the last person to push;
   308	  - required status checks with a pinned source app;
   309	  - block force pushes; empty bypass list (📖 R3.2.2);
   310	  - branches up to date before merge, since there is no merge queue (⚠️ R4.6 #1). Whether updating
   311	    the branch drops approvals is open (Options §8).
   312	- **L3 by path:** path-based required reviewers with **2 approvals** from `platform` on
   313	  `infra/iam/**`, `.github/**` and the other L3 paths (📖 R3.2.4, which allows 0–10 approvals per
   314	  team). One approval would not be enough: a platform member who is also a code owner would satisfy
   315	  both rules at once, because any one code owner is enough (📖 R3.2.7).
   316	- **L3 by preview [design]:** the deploy job on `main` runs the prod preview. On replace/delete of a
   317	  stateful resource, an IAM change or a policy violation, it stops. The engineer opens a second PR
   318	  adding `deploy-approvals/<sha>.yaml` with the preview hash; platform approves; the job re-runs and
   319	  continues only if the hash matches (Options §1; hash stability ⚠️ Options §8). A required check
   320	  with a pinned source app (📖 R3.2.5) confirms that this approver differs from the first PR's
   321	  approver.
   322	- **Prod preview output** is filtered for stack outputs and secrets before it is posted or exported
   323	  (Options §1; ⚠️ R4.6 #2).
   324	- **Making "merge approval = deploy approval" true** (⚠️ R3.6 #1, built on 📖 R3.1.3, R3.4.5c):
   325	  - the `production` environment allows only `main`;
   326	  - only the CODEOWNERS-protected reusable deploy workflow references `production`;
   327	  - deploy workflows take no ref or SHA input and use no `issue_comment`, `pull_request_target`
   328	    or `workflow_run` trigger;
   329	  - one concurrency group per stack, without `cancel-in-progress` (📖 R4.1.4).
   330	- **Pulumi:**
   331	  - PRs preview **non-prod stacks only**: a prod preview would run PR code with state-write and
   332	    secret access (📖 R4.3.3, R4.3.4; ⚠️ R4.6 #2);
   333	  - on `main`: `pulumi preview` on prod, then `pulumi up` with the policy pack; a mandatory
   334	    violation stops the deployment (📖 R4.2.2);
   335	  - prod runs use an allowlist of commands and flags (⚠️ R4.6 #3): no `--skip-preview` (📖 R4.1.2),
   336	    no `--target` (📖 R4.1.1); also no `--target-replace`, `--replace` or `--exclude`, and no
   337	    `state`, `import`, `destroy` or `stack rm` (names from R4.6 #3; the `pulumi up` reference was not
   338	    read for them, ⚠️ G12);
   339	  - Pulumi Cloud, if used: CI authenticates with OIDC through `pulumi/auth-actions`, not a stored
   340	    `PULUMI_ACCESS_TOKEN` (📖 R4.1.4).
   341	- **Serverless Framework (v4):**
   342	  - `serverless package`, then `serverless diff --json` (sf-core ≥ 4.37.0). "Differences against the
   343	    deployed stack do not cause a non-zero exit code", so CI parses the JSON (📖 R4.4.2);
   344	  - `serverless deploy --package` deploys that artifact (📖 R4.4.3);
   345	  - a least-privilege `provider.iam.deploymentRole`; it cannot be removed later, and anyone allowed
   346	    to operate the stack can use it without `iam:PassRole` (📖 R4.4.5). So JIT roles get no
   347	    CloudFormation stack-operation rights.
   348	- **State:** Pulumi and Serverless state buckets are readable and writable by deploy roles only;
   349	  Pulumi secrets use `awskms` on a DIY backend (📖 R4.3.3, R4.3.4; ⚠️ R4.6 #7). `ProdReadMetadata`
   350	  has no access to them.
   351	- **k0s [design]:** the same path: manifests in the monorepo, applied by a CI job; humans and
   352	  agents hold no write RBAC in prod; read-only roles exclude logs and exec in namespaces that hold
   353	  claim data. Mechanism not researched (G1).
   354	- **Incident lane:** PR label `incident`; the on-call approver is paged; security checks always run
   355	  (S10); only slow, unrelated tests are skipped [design]. Path filters on required checks may leave
   356	  them pending (⚠️ Options §8).
   357	
   358	**Example: Lambda timeouts at 2 a.m.** (Options §6)
   359	
   360	1. The incident-analysis session reads metrics and redacted logs and proposes: `timeout` 30 → 90 s,
   361	   `memorySize` 1024 → 2048, and a larger visibility timeout on the source queue (the ratio AWS
   362	   recommends is not checked, ⚠️ Options §8).
   363	2. A second session, with edit tools and not meant to use the prod identity (process rule), edits
   364	   `serverless.yml`, runs `serverless diff` on non-prod, and opens a PR labelled `incident` under
   365	   the engineer's GitHub identity.
   366	3. The on-call approver reviews the diff (and catches it if the queue change is missing) and
   367	   approves. The engineer merges.
   368	4. The deploy workflow packages, previews prod, finds no risky change, and deploys with the OIDC role.
   369	5. Estimated 11–46 min (⚠️ unmeasured, Options §6) against a ≤ 30 min target, so measuring this lane
   370	   is a phase-1 task.
   371	
   372	**Audit evidence**
   373	
   374	- The PR: diff, approvers, check results, labels.
   375	- The run: prod-preview artifact and deploy log, exported because run retention is limited (G7).
   376	- CloudTrail events of the deploy role.
   377	- All linked by commit SHA and run ID (change record, layer 7).
   378	
   379	**Cost / value.** One approval for routine prod changes, two for risky ones, none in non-prod.
   380	Compliance gets four-eyes enforced by GitHub and a record per change. Open gap: on Team the
   381	reviewer sees the non-prod preview, not the prod diff.

   387	**Principle**
   388

   390	  R5.5.5). It is installed only from a reviewed catalogue, pinned to a version.
   391	- The catalogue is the inventory (P4c).

   394	**On Papaya's stack**
   395	
   396	- **Plugins:**

   403	  - With `allowManagedHooksOnly`, plugin hooks run only if the plugin is force-enabled in managed

   406	    `cc-plugin-sec-default@builtin` → `options` (📖 R1.5.6).

   414	  - `disableClaudeAiConnectors: true` (📖 R1.3.7).

   416	    (📖 R1.3.2).

   422	  - pinned version, reviewer's name, review date.
   423	- **Known gaps:** server-managed settings cannot target groups (📖 R1.1.6, R1.4.4); changes to a

   439	## Layer 5 — CI/CD hardening
   440	
   441	**Principle**
   442	
   443	- CI is the default production writer (the JIT fallback is the exception), so it is the most
   444	  valuable target.
   445	- No long-lived credentials; least-privilege, short-lived tokens per job.
   446	- Every third-party dependency of CI is pinned.
   447	- Code written by an agent goes through the same checks as code written by a person (S10).
   448	
   449	**On Papaya's stack**
   450	
   451	- **Credentials:**
   452	  - replace AWS keys and long-lived tokens in repository secrets with OIDC (📖 R3.4.1); anyone with
   453	    write access can read repository secrets (📖 R3.5.3b);
   454	  - `GITHUB_TOKEN` default "restricted"; each job declares `permissions:` (📖 R3.5.3);
   455	  - "Allow GitHub Actions to create and approve pull requests" stays **off** (📖 R3.3.3);
   456	  - Serverless License Key in SSM per account, read by the deploy role (sf ≥ 4.4.19, 📖 R4.4.8).
   457	- **Side paths to prod:** Pulumi ESC, Pulumi Deployments and Serverless Dashboard providers each
   458	  hold a path to AWS (features 📖 R4.4.9) outside the GitHub gate (⚠️ R4.4.9). Default: not used
   459	  for prod (⚠️ R4.6 #6).
   460	- **Pin CI dependencies:** workflow lockfile (`gh actions-lock`) or full SHA, enforced by the org
   461	  policy "Require actions to be pinned to a full-length commit SHA" (📖 R3.5.5). The lockfile does
   462	  not pin reusable workflows (📖 R3.5.5), so the deploy workflow is called from the same repo.
   463	- **Protect the files that steer CI and agents** with CODEOWNERS: `.github/`, `CLAUDE.md`,
   464	  `CLAUDE.local.md`, `.claude/`, `.claude.json`, `.mcp.json`, `.husky/`, `.gitmodules`, `.ripgreprc`
   465	  (📖 R3.2.8; list ⚠️ R6.5 #5). CI validates the CODEOWNERS file, because invalid lines are skipped
   466	  silently (📖 R3.2.7).
   467	- **No privileged triggers with untrusted code:** no `pull_request_target` or `workflow_run` job
   468	  that checks out PR code (📖 R3.5.4).
   469	- **Agents in CI:**
   470	  - `claude-code-action` with a custom GitHub App limited to Contents, Issues and Pull requests
   471	    (📖 R1.7.8);
   472	  - authentication through Anthropic workload identity federation, not a personal OAuth token
   473	    (📖 R1.7.6);
   474	  - `--restricted`, explicit `--tools`, rules from a `--settings` file on the runner (D3; 📖 R6.9.1b).
   475	    Whether the action passes `--restricted` through `claude_args` is unverified (⚠️ research 6.9.4 Q5);
   476	  - the MCP set is fixed by the CI configuration, because project `.mcp.json` servers load without a
   477	    prompt in `-p` runs (📖 R1.3.5);
   478	  - never `environment: production` (⚠️ R3.6 #4);
   479	  - managed settings on the runner, because a CI run on an API key without managed settings is
   480	    exposed to mods (📖 R1.5.6);
   481	  - hosted runners give the job passwordless `sudo` (📖 R3.5.1), so if `Bash` is in `--tools`, the
   482	    agent could rewrite the runner's managed-settings file: it is then advisory (⚠️ R3.5.1, R3.6 #4);
   483	  - an app-authored PR needs a required check with a pinned source app (📖 R3.2.5) that confirms at
   484	    least one approval from a human who did not trigger the run. Counting approvals is not enough,
   485	    because an approval by the app itself might count (⚠️ R3.3.4, R3.7 A3).
   486	- **Required security checks on every PR to `main` (S10):** secret scanning, dependency check, SAST.
   487	  The products are **not researched** (G4). Researched checks: IAM Access Analyzer
   488	  `check-no-new-access` (📖 R2.8.1) and Pulumi policy packs (📖 R4.2.2).
   489	
   490	**Audit evidence**
   491	
   492	- Workflow files and the lockfile in git.
   493	- Org audit log events such as `org.update_actions_secret`, `repo.set_workflow_permission_can_approve_pr`,
   494	  `repository_ruleset.update` (📖 R3.3.3, R3.5.6).
   495	- Check results attached to each PR.
   496	- Inventory of repository secrets: zero cloud credentials (S2).
   497	
   498	**Cost / value.** A one-time migration of workflows to OIDC and pinned actions; slower updates of
   499	actions. Compliance gets S2 and the same guardrails for agent and human code.

   503	## Layer 6 — Data protection and prompt-injection defence
   504	
   505	**Principle**
   506	
   507	- **PHI never reaches the coding agent** (owner decision, research 1.9). For AWS data stores this
   508	  is intended to be enforced by what agent-usable identities can read (from phase 2 by SCP; in
   509	  phase 1 by the permission set). k0s logs and exec and GCP stores (research 1.11.4 L1, L11, L13)
   510	  follow the same principle, with mechanisms still to research (G1, G3). Other paths (tickets and
   511	  chat through MCP, text people paste, internal admin pages, prod AI traces, fixtures and CI logs;
   512	  L5, L8–L10, L12, L14) are covered by process and hygiene controls only.
   513	- **Other customer personal data** (e.g. a national ID number or bank account on its own) is not
   514	  under that hard boundary (owner: "not extended", research 5.8). By default the agent reads
   515	  metadata only; it may read such data case by case under GĐ-9.
   516	- Reading real data is an approved, tenant-scoped, time-boxed exception that needs a suitable
   517	  agreement (BAA/DPA, partner contract) (GĐ-9).
   518	- Everything the agent reads from outside is untrusted: logs, tickets, PR text, web pages, MCP
   519	  results, uploaded documents.
   520	- Non-prod holds synthetic data only (GĐ-14).
   521	
   522	**On Papaya's stack**
   523	
   524	- **Close the paths by identity.** Research 1.11.4 lists 17 ways PHI can reach the agent (logs,
   525	  SQL, S3, queues, tickets, uploaded documents, exec, replay…). The main control is that
   526	  agent-usable identities have **no data-plane read** on PHI stores (⚠️ R2.9 #4, research 1.11.4):
   527	  - SCP deny on claim buckets and queues (layer 1);
   528	  - no Aurora credentials for engineers' agents; no prod exec (ECS Exec, `kubectl exec`) and no
   529	    `lambda:InvokeFunction` for agent-usable roles [design; exact IAM action for ECS Exec not
   530	    researched];
   531	  - logs redacted at source, raw payloads in a separate log group that `ProdReadMetadata` cannot
   532	    read [design];
   533	  - alerts carry IDs and links, not payloads [design].
   534	- **The real-data exception (GĐ-9)** [design]:
   535	  - a request names tenant, purpose, store, time window and the agreement that allows it (BAA/DPA,
   536	    partner contract); the data owner and an approver ≠ requester approve it;
   537	  - a JIT data-read role, 1 h; scoping it to one tenant is intended through session tags (📖 R2.1.8),
   538	    but tags come from user attributes, so per-request tenant scope is unresolved (⚠️);
   539	  - **PHI:** the human reads in a terminal without an agent, and the agent gets only a redacted
   540	    summary. This narrows GĐ-9 for PHI because the owner keeps the agent outside PHI scope (research
   541	    1.9) and the Team plan is not shown as covered by Anthropic's BAA (⚠️ R1.11.3.4). Enterprise +
   542	    BAA is considered only for a separate environment if a real need appears (research 1.9). The
   543	    "no agent in that terminal" part is a process rule: the grant sits in the same SSO cache (📖 R2.2.2);
   544	  - **non-PHI personal data:** the agent may read it within the approved request (GĐ-9), subject to
   545	    the cross-border point below.
   546	- **Partner-uploaded claim documents (A7b).** Never open a raw partner document in an agent session.
   547	  Reproduce bugs with synthetic documents; if a real one is needed, de-identify it first [design].
   548	  The document is both PHI and an injection vector (research 1.11.4 L6).
   549	- **Injection controls** (each lowers frequency; layers 1 and 3 limit impact):
   550	  - Manual mode by default (layer 2); the auto-mode classifier missed 17 % of 52 real overeager
   551	    actions (📖 R6.3.5);
   552	  - narrow sandbox egress; allowing a broad domain such as `github.com` is a documented
   553	    exfiltration path (📖 R6.3.7);
   554	  - the incident-analysis session has no edit tools and no WebFetch (📖 R6.9.1b), so a poisoned log
   555	    line cannot edit code. It can still run Bash: it could send data the session has read out, or
   556	    use any role in the SSO cache. The sandbox allowlist bounds only sandboxed shell commands;
   557	    `aws` and other excluded commands are outside it (layer 2). The "no standing write, no PHI
   558	    read" rule bounds what is at stake;
   559	  - shared knowledge in `CLAUDE.md` under CODEOWNERS; auto memory is outside protected paths unless
   560	    `--restricted` (📖 R6.3.11, D3).
   561	- **Tenant isolation:** one tenant per data-read grant; a session that read one tenant's data does
   562	  not write to shared places (PRs, tickets, chat) without review (⚠️ R6.5 #8, process rule). Tenants
   563	  are assumed logically separated in shared accounts (GĐ-3, unconfirmed).
   564	- **Non-prod:** no copies from prod to non-prod (S11); periodic scan of non-prod stores (tool: G4).
   565	- **Local stores:** transcripts and memory hold what the agent read (research 1.11.4). Set
   566	  `cleanupPeriodDays` (the HIPAA sample uses 30, 📖 R5.5.4).
   567	- **Cross-border (Vietnam example):** processing personal data collected in Vietnam on a platform
   568	  abroad counts as a transfer (📖 R5.4.5). If agent flows carry such data, they update Papaya's
   569	  transfer impact assessment (⚠️ R5.7 #4, needs Papaya legal). Employee names and emails in
   570	  CloudTrail, git and transcripts raise the same question (⚠️ R5.7 #4).
   571	
   572	**Audit evidence**
   573	
   574	- SCP and IAM text: the written access rule for sensitive data (📖 R5.4.3, Decree 356 Art. 4(2);
   575	  ⚠️ R5.7 #5).
   576	- Data-read requests (requester, approver, tenant, window) and CloudTrail of the data-read role.
   577	- Planted-injection test reports (layer 8).
   578	- Non-prod scan results (S11).
   579	
   580	**Cost / value.** Engineers debug with redacted data and synthetic documents; the rare real-data
   581	read needs a request. Compliance gets "minimum necessary" (📖 R1.11.1.8) enforced by IAM, and a
   582	record for every exception (S9).

   586	## Layer 7 — Observability, audit, incident response and break-glass
   587	
   588	**Principle**
   589	
   590	- One evidence chain per production change: who proposed, who approved, what was approved, what was
   591	  applied, when. Tamper-evident.
   592	- Every prod alert goes to one routed channel with a named on-call, including on-call approvers.
   593	- Unapproved change is detected: drift and reconciliation are compliance signals.
   594	- Break-glass is time-boxed, approved before use, and reconciled after.
   595	
   596	**On Papaya's stack**
   597	
   598	- **Audit stores:**
   599	  - an organization CloudTrail to a log-archive account with integrity validation (📖 R2.6.2,
   600	    R2.6.4, R2.6.5). Retention: approval and change records ≥ 6 years (📖 R5.2.9; applied to change
   601	    records ⚠️ R5.7 #2); whether raw logs
   602	    need 6 years is for Papaya's compliance owner (⚠️ R5.7 #2). Data events only on PHI buckets, prod
   603	    Lambda invoke and prod SQS, because of cost (📖 R2.6.3); these make the archive a PHI-bearing
   604	    store (⚠️ research 1.11.4 L15). CloudTrail Lake is closed to new customers (📖 R2.6.6);
   605	  - the GitHub org audit log keeps 180 days, so it is exported (📖 R3.5.6);
   606	  - alerts on `repository_ruleset.update`, `environment.update_protection_rule`,
   607	    `environment.remove_protection_rule`, `environment.delete`, `protected_branch.policy_override`
   608	    (📖 R3.5.6, R3.1.4; selection ⚠️ R3.6 #1). Limits: `environment.update_protection_rule` covers API changes; UI changes
   609	    to the branch policy may leave no event, and a deleted `production` environment is recreated
   610	    without protection by the next workflow (⚠️ R3.1.4). Hence the configuration comparison job (layer 8);
   611	  - Aurora: SQL over a normal connection is likely invisible to CloudTrail (⚠️ R2.7.1); Database
   612	    Activity Streams, an alert on lost-record events, and the stream treated as PHI (📖 R2.7.2;
   613	    Serverless v2 support ⚠️);
   614	  - Claude Code OTel without prompt content (layer 2).
   615	- **Change record [design]:** one record per prod change, keyed by commit SHA or JIT request ID,
   616	  linking PR, approvals, run ID, preview artifact and CloudTrail events. Monthly reconciliation:
   617	  every prod write event must match an approved record, approved before apply (S3). The actor is
   618	  `onBehalfOf.userId` where present, otherwise session name plus directory lookup (📖 R2.5.1;
   619	  ⚠️ R2.5.3 for member-account events). Detecting a PR approval that an agent gave through its
   620	  engineer's login is not possible with the researched data sources (⚠️ open).
   621	- **Drift detection** runs with its own read role, trusted only from a `drift` environment limited
   622	  to `main`; it can read prod secrets in state, which is noted and restricted (⚠️ R4.6 #2). Commands:
   623	  scheduled `pulumi preview --refresh --expect-no-changes` or
   624	  `pulumi refresh --preview-only` (📖 R4.1.1, R4.3.1, R4.3.2); CloudFormation drift detection for
   625	  Serverless stacks, which checks only explicitly set properties (📖 R4.4.6). Auto-remediation stays
   626	  off, since it runs an unreviewed `pulumi up --refresh` (📖 R4.3.2). Each finding gets an actor and a ticket.
   627	- **On-call:** phase 1 delivers only the named approver schedule (primary and backup, 24/7), as
   628	  decided in framing round 1; it includes a platform approver because L3 needs one (Options §1). The rest of on-call and one alert
   629	  route for prod come in phase 2. Paging and alert tools are not researched (G5).
   630	- **Break-glass = the JIT fallback (D2', all steps [design] unless marked):**
   631	
   632	  | Step | Rule |
   633	  |---|---|
   634	  | When | Only if the PR path cannot be used: the operation is not in IaC and has no runbook, GitHub/Actions is down, or the pipeline is broken. The approver refuses JIT for anything expressible in IaC while the pipeline works, and records why. |
   635	  | Request | Exact command list, service scope, reason, incident link. The request and approval channel must not depend on GitHub, since a GitHub outage is one of the triggers. |
   636	  | Approval | On-call approver ≠ requester, before the grant. |
   637	  | Grant | `InfraOperator-<service>`, session 1 h (📖 R2.1.4). Deleting the assignment likely stops only new role sessions (⚠️ R2.4.2, R2.9 #3); ending the portal session does not end role sessions (📖 R2.4.3). An immediate stop needs the revocation SCP (📖 R2.4.4). |
   638	  | Execution | The human types the commands in a terminal with no agent; the agent may propose them from its analysis session (D2, process rule). |
   639	  | After | A job compares CloudTrail writes in the window with the list. A codify PR within a fixed deadline (opened as soon as GitHub is back, if it was down); drift detection until it merges. |
   640	  | Identity Center outage | Emergency direct SAML federation to roles, built and tested in advance (📖 R2.1.11; ⚠️ R2.9 #2). No user is mapped to the emergency roles until an approved activation, so they are not standing access (S1); every activation is alerted. |
   641	
   642	  **Example request:** "INC-123, service `claims-doc-extract`, Actions outage. Commands:
   643	  `aws ecs update-service --cluster <prod-cluster> --service <svc> --force-new-deployment`. Scope:
   644	  `InfraOperator-claims`, 1 h." The approver checks that the change is not expressible in IaC while
   645	  the pipeline works, then approves this list only.
   646	
   647	  Metrics (Options §7), with starting thresholds to calibrate (⚠️): JIT used for a change that should
   648	  have gone through a PR (review at 1); windows with writes outside the list (review at 1); codify
   649	  PRs past deadline (review at 1); JIT grants per month and the share of incidents that needed
   650	  non-IaC operations (review if more than about a quarter of incidents). When a threshold is passed,
   651	  make the PR lane faster or move the operation to a runbook; do not widen JIT.
   652	- **Roadmap:** pre-approved runbooks for repeated non-IaC operations, if SSM Automation's approval
   653	  step meets three conditions (Options §2; source outside `02-research.md`, G6); break-glass from an
   654	  environment without the agent installed (D2, ⚠️).
   655	
   656	**Audit evidence**
   657	
   658	- CloudTrail with digest validation; exported GitHub audit log.
   659	- Change records and the monthly reconciliation report (S3; S8: evidence for a random change in
   660	  ≤ 30 min).
   661	- JIT request records, reconciliation results, codify PRs.
   662	- Drift reports and their tickets.
   663	- On-call schedule and approval-wait times (S7).
   664	
   665	**Cost / value.** The incident lane is slower than direct access (estimated 11–46 min against
   666	2–20 min, Options §6, unmeasured), and JIT needs a written command list. Compliance gets approval
   667	before apply even in incidents, and detection when something slips through.

   671	## Layer 8 — Governance and rollout
   672	
   673	**Principle**
   674	
   675	- Every control has an owner, a metric and a review date.
   676	- Policies live in git and change through PRs, like code.
   677	- Access is never removed before its replacement works; otherwise the rule breaks in the first
   678	  incident.
   679	- Controls are tested against realistic attacks, not only reviewed on paper.
   680	
   681	**On Papaya's stack**
   682	
   683	- **Ownership:**
   684	
   685	  | Area | Owner |
   686	  |---|---|
   687	  | Framework, managed settings, MCP/plugin catalogue, metrics | DevSecOps |
   688	  | Deploy workflows, rulesets, Pulumi/Serverless pipelines | Platform team |
   689	  | Evidence review, supplier register, ISO Statement of Applicability | Compliance |
   690	  | CODEOWNERS per domain | Engineering leads |
   691	  | On-call schedule (incl. approvers) | Engineering management |
   692	
   693	- **Policy as code:** managed settings, the MCP/plugin catalogue, SCPs, trust policies, CODEOWNERS
   694	  and deploy workflows are files under CODEOWNERS. GitHub settings that are not files (rulesets,
   695	  environments) are compared with an expected copy by a scheduled job (⚠️ R3.6 #1; API not
   696	  researched, G8).
   697	- **Admins:** few GitHub admins and holders of "edit repository rules"; quarterly review; alerts as
   698	  in layer 7.
   699	- **Metrics** (framing §5, in full):
   700	  - S1 standing prod-write credentials or assignments = 0.
   701	  - S2 long-lived cloud credentials in GitHub secrets = 0 (time-boxed exceptions listed).
   702	  - S3 prod changes without a matching approval = 0; approvals after apply = 0.
   703	  - S4 infra PR to prod within the working day (median); approval wait ≤ 1 h; no new approval step in non-prod.
   704	  - S5 machines with the policy = 100 %; people who can turn off all prompts unnoticed = 0. The
   705	    second target is not reachable without MDM (layer 2, G11).
   706	  - S6 tools outside the catalogue = 0; requests handled ≤ 5 working days.
   707	  - S7 named on-call schedule; 100 % of prod alerts through one route; incident approval wait ≤ 15 min.
   708	  - S8 evidence for a random change in ≤ 30 min.
   709	  - S9 real-data reads without an approved request = 0.
   710	  - S10 PRs to `main` with secret scan, dependency check and SAST passing = 100 %; direct pushes to
   711	    `main` = 0; secrets found after merge = 0.
   712	  - S11 prod copies in non-prod = 0.
   713	- **Rollout** (≈ 90 days, GĐ-12 unconfirmed). Priorities from framing round 1 Q8: (1) remove
   714	  long-lived CI credentials, (2) narrow standing prod access, (3) MCP/plugin catalogue; the on-call
   715	  approver list comes first or together with (2):
   716	
   717	  | Phase | Days | Items |
   718	  |---|---|---|
   719	  | 1 | 0–30 | In order: (1) measure the incident PR lane on one real service (target ≤ 30 min; first task per Options §9). (2) OIDC for all deploy workflows; remove AWS keys and long-lived tokens; move laptop-only deploys (GĐ-10) to CI. (3) Rulesets and CODEOWNERS on `main`. (4) On-call approver schedule (primary + backup + platform) and a minimal JIT fallback (request, approval, 1 h assignment). (5) **Then** remove standing prod-write assignments. (6) Managed settings baseline; MCP/plugin catalogue v1. (7) Start verifying the SSM runbook option (Options §7); non-prod data scan (S11). Items 6–7 can slip to phase 2 if the 1–2 person team (GĐ-1) runs short. |
   720	  | 2 | 30–60 | SCP data-plane deny; drift detection; audit-log export, change records and reconciliation; Aurora activity streams; JIT reconciliation job; rest of on-call and one alert route for prod. |
   721	  | 3 | 60–90 | Planted-injection test on the real configuration (📖 R6.1.1, R6.1.5; ⚠️ R6.5 #12); auto-mode non-prod environment (D1 c); separate OS user or container for prod-reading sessions; first ISO 27001 evidence pack; 90-day review of D1–D3. |

   723	- **Exceptions:** a deviation from this framework is a ticket with an owner, a reason and an
