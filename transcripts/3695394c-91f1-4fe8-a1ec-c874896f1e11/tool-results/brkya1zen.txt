=================== 0001-prod-changes-only-through-ci.md
# ADR-0001: Every production change goes through a reviewed PR applied by CI

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (Options §9, "A + D2'")
- **Scope:** all writes to production AWS, GCP, k0s and Firebase; incidents included (k0s and Firebase
  have no risk stop and no break-glass yet, G1, G2; human GCP access is open, G3)

## 1. Context

Engineering wants Claude Code to talk to AWS directly; Compliance wants no production change without
a named human who reviewed and approved it. "Most engineers' profiles can reach production" (brief), and deploys from laptops are assumed
(GĐ-10, unconfirmed), so an agent on that laptop can deploy too. Incidents are where the pressure to bypass
review is highest.

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. PR → approval → CI deploy for everything ("IaC first") | One path, approval before apply, evidence by construction | Slower incidents (est. 11–46 min ⚠️ vs 2–20 min, Options §6) |
| B. SSM Automation runbooks with an approval step | Approval inside AWS | Not verified that it meets the approval rule (G6); only for operations someone scripted. Kept on the roadmap, verified in phase 2 (OD4) |
| C. JIT direct access for the engineer + agent | Fastest | Approves access, not the change; agent holds prod write |
| D. Hosted agent with its own identity | Clean separation | New platform; does not remove the need for approval |

## 3. Decision

Option A is the default path for every production change, incidents included. A narrow JIT
fallback exists only when the PR path cannot be used during an incident (ADR-0005). The owner accepts
that this fallback meets the approval rule only partly (Options §9 Q2). Incident target: ≤ 30 min from
decision to apply.

## 4. Consequences

- **Positive:** the PR, its approvals, the run log and CloudTrail form one evidence chain keyed by
  commit SHA. Agent-written and human-written changes pass the same checks (S10).
- **Negative / trade-offs:** slower incident fixes; operations that are not in IaC must first be
  written as code or a runbook. Two write paths remain (PR and JIT), while the framing asked for one.
- **Risks & how we watch them:** the fallback stays narrow only if most incidents are expressible in
  IaC (unknown, Options §8). Metrics: JIT grants per month, share of incidents needing non-IaC
  operations; above about 25 % (⚠️ starting threshold), make the PR lane faster or add a runbook, never widen JIT.
- **Example:** Lambda timeouts at 2 a.m. The responder's agent proposes `timeout` 30 → 90 s in
  `serverless.yml`; the PR is labelled `incident`; the on-call approver reviews and approves; CI
  packages, previews prod and deploys with the OIDC role. Estimate 11–46 min (⚠️ Options §6).
- **Next steps:** measure the incident PR lane on one service first (phase 1).

## 5. References

- Framework §1 and layer 3; `work/03-options.md` §1, §6, §9.
- Related: ADR-0002, ADR-0003, ADR-0005.
=================== 0002-no-standing-prod-write-read-only-agent-identity.md
# ADR-0002: Nobody holds standing prod write; in prod, the engineer's (and so the agent's) only standing role reads metadata

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (Options §9; D2)
- **Scope:** AWS IAM Identity Center permission sets and SCPs on the prod OU; k0s and GCP by the same principle

## 1. Context

On a laptop the agent uses the engineer's AWS SSO cache, and one portal session reaches every role
assigned to that engineer (📖 R2.2.1, R2.2.2; token-reuse detail ⚠️ R2.2.2). A separate "agent"
permission set therefore does not separate the agent from the engineer (⚠️ R2.9 #1). Whatever the
engineer holds, the agent holds.

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. Separate agent permission set, engineer keeps write | Looks like least privilege | Same SSO cache: the agent can still assume the write role |
| B. No standing prod write for anyone; `ProdReadMetadata` as the only standing prod role | Agent cannot write prod with the engineer's identity | Engineers also lose direct writes and raw-log reads |
| C. Separate OS user or container for agent sessions | Real separation of credentials | More setup; planned for phase 3 only |

## 3. Decision

Option B. Prod is written only by the CI pipeline role, or by an approved, time-boxed JIT grant
(ADR-0005). The standing prod role is `ProdReadMetadata` [design name]: metrics, redacted log groups,
configuration of services whose secrets are resolved at runtime; no data-plane reads of claim stores;
1-hour role session, the minimum (📖 R2.1.4). From phase 2, SCPs on the prod OU deny data-plane reads and
direct Lambda updates except for named roles (pattern ⚠️ R2.9 #4, R4.6 #3). Option C follows in phase 3.

## 4. Consequences

- **Positive:** an agent, even a manipulated one, cannot write prod or read customer data with the
  engineer's standing identity. Compliance gets least privilege enforced by IAM (S1).
- **Negative / trade-offs:** during the transition, engineers lose raw logs and configuration of
  services not yet redacted. Configuration values then come from the IaC code; raw logs need a
  data-read grant in an incident. Process rules remain where
  IAM cannot separate engineer and agent: no agent in the JIT terminal (D2).
- **Risks & how we watch them:** SSO-token theft during a session could open later grants (⚠️);
  mitigations are a short portal session and a fresh sign-in before a grant. The data-plane action
  list is incomplete (⚠️ G13). Identity Center assignment export is reviewed quarterly.
- **Next steps:** phase 1 removes broad read roles only after the minimal real-data read flow works,
  then removes standing prod write once its prerequisites are in place.

## 5. References

- Framework layer 1, layer 2 ("Trade-off on AWS credentials"), layer 8 rollout.
- Related: ADR-0001, ADR-0005, ADR-0009.
=================== 0003-merge-to-main-is-the-approval-gate.md
# ADR-0003: The merge to `main` is the approval gate: two people, code owners, on-call co-ownership

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (GĐ-5, GĐ-8, GĐ-11; OD2, OD5, OD7, OD9, OD10, OD13)
- **Scope:** GitHub monorepo rulesets, CODEOWNERS, `production` environment, on-call schedule

## 1. Context

Papaya is assumed to be on GitHub Team (GĐ-5). There, environment required reviewers do not exist for private repositories (📖 R3.1.2), so
the deploy job cannot wait for an approval. The approval must happen earlier. Incidents need an
approver within 15 minutes, 24/7 (S7), and code-owner review means the approver must own the files.

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. Upgrade to Enterprise for environment reviewers | Approval sits next to the deploy | Cost; not assumed (GĐ-5) |
| B. Merge to `main` as the gate; `production` limited to `main` | Works on Team; the approver sees the code that will be applied | Nobody sees the prod diff before apply (partly handled by ADR-0004) |
| C. More approvers for high-risk changes | More eyes | Slower; the owner wants two people per change |

## 3. Decision

Option B. Ruleset on `main`: PR required, 1 approval, code-owner review, dismiss stale approvals,
approval by someone other than the last pusher, required checks from a pinned source app, empty
bypass list (📖 R3.2.2, R3.2.3, R3.2.5). `production` accepts only `main` (📖 R3.1.3).

- **Two people per change:** one makes it, one approves it; the approver is always an engineer,
  never an agent (OD2, OD5). L3 changes need one approver too, who must own the path.
- **Incidents:** on-call engineers only approve; an incident responder writes the fix (OD7).
- **Night coverage:** an on-call approver group co-owns every deployable path in CODEOWNERS; one
  primary, one backup (OD9). It does not co-own process-defining paths (`.github/**`, CODEOWNERS,
  agent config, catalogue) or the SCP stack, which only the L3 owner team approves (OD13); IAM-only
  stacks are deployable, so it co-owns them with the L3 owner team.
- **Agent review:** an independent agent may post an automated review; it never counts as an
  approval (GĐ-11).
- **Cross-team PRs:** one approval is enough (OD10).

## 4. Consequences

- **Positive:** four-eyes enforced by GitHub, not by the agent. One rule for normal days and incidents.
- **Negative / trade-offs:** GitHub accepts an approval from any listed owner (📖 R3.2.7), so the
  on-call group can approve another domain's PR; domain review on normal days is a process rule.
  One reviewer for high-risk changes can miss things (owner's trade-off for speed).
- **Risks & how we watch them:** admins can edit the gate (ability ⚠️ R3.2.2, R3.6 #1; logging 📖 R3.2.2), logged, not prevented;
  alerts on ruleset changes and a monthly report of cross-domain approvals on PRs without the
  `incident` label. An agent could approve through its engineer's login; no detection found (⚠️). The
  required-check app's hosting, key and triggers are open (⚠️ G19).
- **Next steps:** rulesets, CODEOWNERS and its validation check in phase 1; the composition of the L3
  owner team is open (G17).

## 5. References

- Framework layer 3 ("Gate = merge to `main`", "Who approves at night"), layer 7 (audit alerts).
- Related: ADR-0001, ADR-0004.
=================== 0004-risk-stop-on-risky-prod-diffs.md
# ADR-0004: Risky prod diffs stop the deploy until a stack owner approves the prod preview

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (OD8, OD11, OD13)
- **Scope:** deploy workflows for Pulumi and Serverless stacks; k0s and Firebase not covered yet

## 1. Context

With the gate at merge time (ADR-0003), the approver reviews the code change, not the prod diff. A
PR may not preview prod, because that would run PR code with state-write and secret access
(📖 R4.3.3, R4.3.4; ⚠️ R4.6 #2). So a stateful delete or an IAM change can reach prod without anyone
seeing its real effect. Most IAM, network and stateful changes sit inside domain files such as
`serverless.yml`, not in separate L3 paths.

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. Accept the gap | No extra step | Destructive diffs applied unseen |
| B. Risk stop, approved by the L3 owner team | Specialist review | Often a third person; L3 team must be on call 24/7 |
| C. Risk stop, approved by an owner of the stack | Stays at two people; works at night | Less specialist review; compensated by automated checks |

## 3. Decision

Option C [design]. The deploy job on `main` previews prod. On stateful replace/delete, an IAM
change, a network or security-group change, or (from phase 2) an advisory policy finding, it stops
and posts the filtered preview. The original author opens a PR (the workflow cannot, because "Allow GitHub Actions to create and
approve pull requests" stays off, 📖 R3.3.3) adding
`deploy-approvals/<stack>/<sha>.yaml` with the SHA and preview hash; the first approver approves it
(OD13). If that approver is unavailable, another stack owner approves; this makes three people and
is recorded as a deviation (OD11). After the merge the workflow previews again on the new HEAD and
continues only if the hash matches. Serverless uses `serverless diff --json` (sf-core ≥ 4.37.0), parsed by CI because
differences do not change the exit code (📖 R4.4.2). A `mandatory` Pulumi policy violation always
blocks `pulumi up` (📖 R4.2.2).

## 4. Consequences

- **Positive:** the person who approves now sees the prod diff for the changes that can do lasting
  damage. Still two people in the normal case.
- **Negative / trade-offs:** while a stack is stopped, later deploys to it stop too (the hash
  differs), including an incident fix, until the approval lands or the change is reverted. One more review round when the stop fires.
- **Risks & how we watch them:** preview output may not be stable enough to hash (⚠️ Options §8); if
  not, compare a structured summary. Until phase 2, the risk stop is the only compensation for OD8;
  Access Analyzer `check-no-new-access` (📖 R2.8.1) and policy packs follow. k0s and Firebase have no
  preview step in this design (⚠️ G1, G2).
- **Next steps:** risk stop in the deploy job in phase 1.

## 5. References

- Framework layer 3 ("Risk stop"), layer 5 (required checks); `work/03-options.md` §1.
- Related: ADR-0001, ADR-0003.
=================== 0005-break-glass-is-time-limited-jit.md
# ADR-0005: Break-glass is a time-limited, approved JIT grant, for incidents only

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (GĐ-8; Options §9 Q2; D2; OD7, OD13)
- **Scope:** AWS production accounts through IAM Identity Center; k0s and Firebase not covered (G1, G2)

## 1. Context

Some incidents cannot use the PR path: GitHub or Actions is down, the pipeline is broken, or the
operation is not in IaC and has no runbook. Without a defined fallback, people keep standing access
"just in case", which ADR-0002 removes.

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. No fallback | Single path | Outage of GitHub blocks every fix; pressure to keep standing access |
| B. Standing break-glass account, used first and approved later | Always available | Standing prod write; unapproved use, rejected by the owner (GĐ-8, Options §0.4) |
| C. Approved JIT grant, 1-hour role session, command list, reconciled after | Approval before use; time-boxed; traceable | Approves a command list, not an applied change (partial) |

## 3. Decision

Option C, used only during an incident when the PR path cannot be used.

- **Request:** command list, scope, reason, incident link, in a channel that does not depend on GitHub.
- **Approval:** the on-call approver ≠ requester, before the grant; the on-call approver counts as
  owner of the service (OD13).
- **Grant:** `InfraOperator-<service>` [design name], assigned via `CreateAccountAssignment` and removed
  via `DeleteAccountAssignment` (📖 R2.4.2); role session 1 h (📖 R2.1.4).
- **Execution:** the incident responder types the commands in a terminal without an agent (D2, OD7).
- **Example request** (illustrative command ⚠️): "INC-123, ECS service `claims-api`, Actions outage.
  Run `aws ecs update-service --cluster <prod-cluster> --service <svc> --force-new-deployment`. Scope
  `InfraOperator-claims`, 1 h."
- **After:** CloudTrail writes in the window are compared with the list; a codify PR follows by a
  fixed deadline; drift detection runs until it merges.

## 4. Consequences

- **Positive:** no standing prod write even for emergencies; every use has an approval, a window and
  a reconciliation.
- **Negative / trade-offs:** meets the approval rule only partly (owner accepted). "No agent in the
  JIT terminal" is a process rule: the grant is reachable from the same laptop.
- **Risks & how we watch them:** deleting the assignment likely stops only new sessions, so a grant
  can run up to about 2 h (⚠️ R2.4.2, R2.9 #3). An immediate stop needs the revocation SCP, which keeps
  the user blocked ≥ 12 h (📖 R2.4.4); no night-time path to apply it is designed yet (⚠️ G20).
  Metrics: JIT used where a PR was possible, writes outside the list, late codify PRs (review at 1).
- **Next steps:** minimal JIT with per-grant CloudTrail comparison in phase 1; revocation SCP and
  automated reconciliation in phase 2.

## 5. References

- Framework layer 7 ("Break-glass = JIT fallback"); `work/03-options.md` §4b, §9.
- Related: ADR-0001, ADR-0002.
=================== 0006-mcp-and-plugins-only-from-allowlist.md
# ADR-0006: MCP servers and plugins are allowed only from a reviewed, pinned catalogue

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (framework approval 2026-11-09; rollout priority framing Q8)
- **Scope:** Claude Code on all engineer laptops and in CI; Papaya's internal plugin marketplace

## 1. Context

Local MCP servers, plugins and hooks run with the engineer's access (📖 R1.6.2, R5.5.5); remote MCP
servers receive tokens and data. Papaya runs an internal plugin marketplace (brief, Appendix A), and
engineers install MCP servers without review (brief); use of Linear and Slack through MCP is assumed
(⚠️ G9). An unreviewed server or a plugin update can read the repo, the SSO cache or claim
data and send it out.

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. Free choice, guidance only | No friction | No inventory; any server can exfiltrate |
| B. Denylist known-bad servers | Low friction | Misses new and changed servers |
| C. Allowlist (catalogue) enforced by managed settings | Inventory and supplier records; blocks unknown servers | Up to 5 working days' wait for a new tool (S6) |

## 3. Decision

Option C. The catalogue is a file in git, changed by PR under the L3 owner team.

- **Plugins:** only Papaya's marketplace via managed `strictKnownMarketplaces`, plus
  `blockedMarketplaces` (📖 R1.4.2); sources pinned to `ref`/`sha` (📖 R1.4.1b, link only);
  `disableSideloadFlags` (📖 R1.4.2); version floor covering the plugin-pin fix of 2.1.179 (📖 R6.2.7).
- **MCP:** `allowedMcpServers` with `allowManagedMcpServersOnly: true` (📖 R1.3.1, R1.3.4); match by
  `serverUrl` or `serverCommand` (exact argv), never `serverName`, which "is not a security control"
  (📖 R1.3.3); `disableClaudeAiConnectors: true` (📖 R1.3.7).
- **Review checklist** [design]: publisher, local or remote, what it reads and where it sends data,
  supplier-register entry and BAA/DPA status, no token passthrough (📖 R6.4.2), pinned version.
  Example entry: `serverCommand` = `["npx", "<package>@<exact-version>"]` [design; placeholder].
- **CI:** server-managed settings do not reach a CI job (📖 R1.7.10); CI uses a managed-settings
  file on the runner and a fixed MCP set, because `.mcp.json` loads without a prompt in `-p` runs
  (📖 R1.3.5).

## 4. Consequences

- **Positive:** Compliance gets an asset inventory and supplier records (P4c); unknown servers are
  refused before they load.
- **Negative / trade-offs:** waiting time for new tools; review effort for 1–2 DevSecOps people.
- **Risks & how we watch them:** `disableSideloadFlags` does not cover `.mcp.json` or `claude mcp add`
  (📖 R1.4.2), so the MCP allowlist must be locked. No per-group targeting in server-managed settings
  (📖 R1.1.6). Tool description changes after approval are not covered (⚠️). Without MDM, laptops can
  bypass server-managed settings (📖 R1.1.7; ⚠️ G11). Evidence: OTel `plugin_installed` /
  `plugin_loaded` (📖 R1.4.6).
- **Next steps:** catalogue v1 in phase 1 (may slip to phase 2 only with owner agreement).

## 5. References

- Framework layer 4; layer 8 rollout.
- Related: ADR-0007.
=================== 0007-agent-settings-are-hygiene-not-the-boundary.md
# ADR-0007: Claude Code managed settings are hygiene, not the security boundary

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (GĐ-6, Options §0.4; D1, D3; OD4, OD7b, OD12)
- **Scope:** Claude Code on laptops (server-managed settings, Team plan) and in CI

## 1. Context

The brief names "permission prompts turned off" as a problem. It is tempting to make Claude Code
settings the main control. But server-managed settings are "a client-side control, not a security
boundary" (📖 R1.1.7), local admins can edit endpoint files (📖 R1.1.8), Bash rules are not a boundary
(📖 R1.2.6), and on laptops without MDM another login or provider skips server-managed settings
(📖 R1.1.7; ⚠️ G11).

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| 0. Today (brief): some engineers turn prompts off; no organization policy is described (P3c) | No friction | Prompts turned off unnoticed; no evidence |
| A. Settings as the boundary (lock everything, block auto mode) | Simple story | Bypassable on laptops; high friction; people work around it |
| B. Settings as hygiene; IAM and the CI gate as the boundary | Boundary holds even if settings are bypassed | Settings give weaker guarantees than they appear to |

## 3. Decision

Option B. The boundary is IAM (ADR-0002) and the merge gate (ADR-0003). Managed settings set safe,
uniform defaults:

- `permissions.defaultMode` = `"default"` (Manual), with a read-only allowlist that excludes `aws`, `pulumi`,
  `serverless` (D1, OD7b; 📖 R6.9.3); auto mode stays available and is measured.
- `disableBypassPermissionsMode: "disable"` (📖 R1.2.2); `requiredMinimumVersion` floor (📖 R1.1.13).
- Sandbox with `~/.aws` hidden (📖 R1.6.3, R1.6.4) [design]; `sandbox.autoAllowBashIfSandboxed` kept `true` (OD12, 📖 R5.5.5b).
- OTel exporter without prompt content (📖 R1.1.20, R5.5.4).

Outside managed settings: the `--restricted` flag (📖 R6.9.1b) in CI, set in the workflow file under
CODEOWNERS, and, as a process rule, in the incident-analysis session; a setting cannot force it
(📖 R6.9.1) (D3).

Phase 1 ships `defaultMode`, the allowlist, bypass removal, the catalogue keys, the version floor and
OTel; the rest of the baseline follows in phase 2 (OD4).

## 4. Consequences

- **Positive:** a bypassed or misconfigured agent still cannot write prod or read PHI. Compliance gets
  one organization policy with evidence instead of personal choices.
- **Negative / trade-offs:** more prompts than auto mode; a prompt for every `aws` read. S5
  ("nobody can turn off all prompts unnoticed") is likely unreachable without MDM (⚠️).
- **Risks & how we watch them:** the auto-mode classifier missed 17 % of 52 real overeager actions
  (📖 R6.3.5); fallback to `disableAutoMode` (📖 R1.2.2) if the planted-injection test steers it (D1). The live
  settings are edited in the admin console, not by PR (📖 R1.1.5); an Owner exports them monthly and
  diffs them with git until a better method exists (G18).
  Until phase 2 there is no sandbox: `~/.aws` is readable and the network open; in auto mode the
  classifier is the only gate. `aws`, `pulumi`, `serverless` run outside the sandbox even later
  (📖 R1.6.4; ⚠️ inference), so SSO-token theft remains possible; bounded by ADR-0002.
- **Next steps:** phase-1 subset; planted-injection test in phase 3.

## 5. References

- Framework layer 2; layer 8 rollout; research 6.6 (D1–D3).
- Related: ADR-0002, ADR-0006.
=================== 0008-oidc-no-long-lived-ci-keys.md
# ADR-0008: CI uses OIDC; no long-lived CI keys, with one time-boxed exception

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (framing Q8; OD1, OD6; target S2)
- **Scope:** GitHub Actions deploy workflows to AWS, GCP, k0s and Firebase

## 1. Context

CI becomes the only routine production writer (ADR-0001), so it is the main target. Repository
secrets can be read by anyone with write access (📖 R3.5.3b), which includes every engineer and their
agent. A long-lived key there is standing prod write in disguise.

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. Keep stored keys, rotate them | No migration | Standing prod write for all writers |
| B. OIDC everywhere, no exception | S2 = 0 | k0s and Firebase may not support it yet (G1, G2) |
| C. OIDC for AWS and GCP; a controlled exception for k0s/Firebase deploy credentials | Removes most keys now | One exception to manage |

## 3. Decision

Option C.

- **AWS:** GitHub OIDC (📖 R3.4.1); the prod role trusts only the `production` environment of the
  monorepo (📖 R3.4.3, R3.4.4), ideally narrowed by `job_workflow_ref` (📖 R3.4.5; on Team ⚠️ G10).
- **GCP:** Workload Identity Federation restricted to Papaya's GitHub organization (📖 R3.4.5b).
- **k0s/Firebase exception** (OD1, OD6): CI deploy credentials only, until it is checked whether they
  can use OIDC. Conditions [design]: a `production` environment secret, never a repository secret
  (📖 R3.1.2, R3.1.3); GitHub-hosted runners, because on self-hosted runners environment secrets act
  like repository secrets (📖 R3.1.5); if k0s needs a self-hosted runner, it is dedicated to the
  `production` deploy and the residual risk is recorded (⚠️ G15); a single source of truth; owner, expiry, rotation.
- `GITHUB_TOKEN` default "restricted" (📖 R3.5.3); actions pinned by lockfile or full SHA (📖 R3.5.5).

## 4. Consequences

- **Positive:** no stored AWS or GCP keys to leak (S2); every deploy credential is tied to a reviewed
  workflow on `main`.
- **Negative / trade-offs:** one-time migration; slower action updates. The exception remains until
  G1/G2 are solved.
- **Risks & how we watch them:** admins can change or delete the environment, and a deleted
  environment comes back without protection (⚠️ R3.1.4); alerts and a settings comparison cover it.
  The GitHub Apps used for CI agents and the required check have their own keys (⚠️ G19).
  Runtime credentials inside the cluster are out of the exception (OD6).
- **Next steps:** OIDC and removal of stored keys in phase 1; k0s/Firebase credentials moved to
  environment secrets before standing prod write is removed.

## 5. References

- Framework layer 1 ("CI → AWS", "CI → GCP"), layer 5 ("Credentials").
- Related: ADR-0001.
=================== 0009-agent-stays-outside-phi.md
# ADR-0009: The coding agent stays outside PHI; real-data reads are approved per tenant

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (research 1.9, 5.8 "not extended"; GĐ-9, GĐ-14)
- **Scope:** coding-agent sessions on laptops and in CI; production stores of all insurer tenants

## 1. Context

Papaya holds medical records, national IDs and bank accounts for several insurer tenants in
different countries. Claude Team is not shown as BAA-covered (⚠️ R1.11.3.4). Partner-uploaded claim
documents are both PHI and a prompt-injection vector (research 1.11.4 L6). Neither OWASP nor NIST
knows a full prevention for prompt injection (📖 R6.1.1, R6.1.2).

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. Agent reads prod data freely | Fastest debugging | PHI in transcripts; injection can exfiltrate; no BAA |
| B. Agent never reads any customer data | Simplest rule | Blocks legitimate debugging of non-PHI data |
| C. Agent outside PHI; other personal data case by case under an approved, per-tenant grant | Matches the owner's boundary; debugging still possible | Process controls on some paths |

## 3. Decision

Option C.

- **PHI:** never in an agent session. A human reads in a terminal without an agent and gives the
  agent a redacted summary. A store that holds PHI counts as PHI unless the agent reads a view without
  it [design].
- **Other personal data:** readable within an approved request naming one tenant, purpose, store,
  window and agreement (BAA/DPA, partner contract) (GĐ-9); approved by an approver ≠ requester and
  co-approved by the tenant's data owner [design]; data-read role, 1 h [design]. The same request
  applies when a human reads PHI. At night the
  on-call approver approves alone and the data owner reviews the grant the next working day [design].
- **Partner documents:** reproduced with synthetic documents or de-identified first [design].
- **Non-prod:** synthetic or masked only (GĐ-14); no prod copies (S11).

This is a target, not a guarantee: "no agent in the PHI terminal" is a process rule [design] with
the same weakness as D2, since the grant is reachable from the same laptop.

## 4. Consequences

- **Positive:** "minimum necessary" (📖 R1.11.1.8) enforced by IAM for AWS stores; one record per
  exception (S9). Assumes injection succeeds and limits what it can reach.
- **Negative / trade-offs:** debugging with redacted or synthetic data; a request for each real read.
- **Risks & how we watch them:** of the 17 paths to PHI (research 1.11.4), tickets, chat, pasted text,
  admin pages and CI logs are covered by process only; k0s and GCP stores follow the same principle
  with mechanisms still open (G1, G3). Per-tenant scoping through session tags (📖 R2.1.8) is
  unresolved, because tags come from user attributes (⚠️). During a data-read window a stolen SSO
  token could open the grant (⚠️, ADR-0007). Data-plane deny actions are incomplete (⚠️ G13). Planted-injection test in
  phase 3.
- **Next steps:** non-prod data scan and the minimal real-data read flow in phase 1; data-plane SCP in
  phase 2.

=================== 0010-risk-level-decides-who-approves.md
# ADR-0010: Risk level decides who approves, not how many; non-prod needs no approval

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (GĐ-14; OD2, OD3, OD8, OD9)
- **Scope:** every change made by engineers and their agents, from non-prod to production

## 1. Context

Engineering says "Let Claude Code talk to AWS directly" (brief); the need behind it is speed. Compliance's sentence is
about production writes only (framing §3.1). A single rule for all changes either slows non-prod for
no gain or leaves high-risk prod changes with too light a review. The owner also wants every prod
change to need two people, no more by default: one who makes it and one who approves it (OD2).

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. Same approval for everything | Simple | Non-prod loop slowed for no gain; high-risk changes get no extra scrutiny |
| B. More approvers as risk grows (e.g. two for L3) | More eyes on dangerous changes | Breaks the two-person rule; slower incidents |
| C. Risk level narrows who may approve, plus a risk stop; non-prod free | Fast where damage is small; specialist owners where it is large | One reviewer for high-risk changes can miss things |

## 3. Decision

Option C [design levels]:

| Level | What | Approval |
|---|---|---|
| L0 | Reads: non-prod anything, prod metadata | none |
| L1 | Changes in non-prod (synthetic or masked data only, GĐ-14) | none, author only |
| L2 | Routine prod change, e.g. Lambda memory 1024 → 2048 MB | 1 code owner ≠ author, ≠ last pusher |
| L3 | IAM/SCP, stateful replace/delete, network, workflow and agent-config files, catalogue, advisory policy finding (full list: framework layer 5) | 1 owner of that path |
| L3-JIT | Break-glass in an incident | on-call approver ≠ requester (ADR-0005) |
| L3-data | Real customer data read | approver ≠ requester + agreement; data-owner co-approval [design] (ADR-0009) |

`CLAUDE.md` and the other agent-configuration files are L3, because they define the workflow for the
whole team (OD3). Process-defining paths and the SCP stack are owned by the L3 owner team; IAM or
stateful changes inside a domain file are approved by that stack's owners (OD8, OD13). At every level,
the risk stop applies to any deploy whose prod diff is risky (ADR-0004).

## 4. Consequences

- **Positive:** a free non-prod loop for engineers and agents (S4); the same two-person rule for every
  prod change, incidents included. Compliance gets a written rule for who may approve what.
- **Negative / trade-offs:** one approver for high-risk changes (owner's trade-off for speed);
  `CLAUDE.md` edits wait for the L3 owner team, not the domain team that edits them most.
- **Risks & how we watch them:** the free loop holds only if non-prod has no real data; a non-prod
  store not yet scanned follows the L3-data rule until scanned (S11). A risky diff hidden in an L2 PR is
  caught by the risk stop, not by the level.
- **Next steps:** non-prod data scan and CODEOWNERS with the L3 path list in phase 1; composition of
  the L3 owner team is open (G17).

## 5. References

- Framework layer 3 (levels table), layer 5 (canonical L3 path list), layer 6 (non-prod).
- Related: ADR-0003, ADR-0004, ADR-0005, ADR-0009.
