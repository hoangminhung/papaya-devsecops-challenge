# Threat model: coding agents in Papaya's DevSecOps workflow

> Status: draft for owner review · Updated: 2026-11-09 · Builds on [`framework.md`](framework.md) and
> [`adr/`](adr/README.md)

## How to read this

Each threat maps to the controls that **prevent** it, **detect** it or **test** it, the **evidence**
an auditor can ask for, and the **residual risk** that stays. Controls point to the framework layer
(L1–L8) and ADR, and say when they arrive if not in phase 1. Markers follow the framework legend:
📖 R*x.y* = documented research row in `work/02-research.md`; ⚠️ = inference or unverified;
[design] = proposal of this submission. Codes: S-n success criteria, G-n gaps, OD-n owner decisions,
GĐ-n framing assumptions, D1–D3 owner decisions in research 6.6, "Options §n" sections of
`work/03-options.md`.

★ = threat named in the task. The table assumes prompt injection succeeds sometimes: neither OWASP
nor NIST knows a full prevention (📖 R6.1.1, R6.1.2). Controls therefore limit what a hijacked agent
can reach, rather than trying to keep every input clean.

## Assets, actors, trust boundaries

- **Assets:** claim data (medical records, national IDs, bank accounts) of several insurer tenants;
  production infrastructure (AWS, GCP, k0s, Firebase); credentials (SSO cache, CI secrets, app keys);
  the evidence chain (PRs, CloudTrail, change records).
- **Actors:** an external attacker who controls content the agent reads (partner uploads, tickets,
  logs, PR comments, web pages); a malicious or compromised MCP server or plugin publisher; an insider
  who weakens controls for speed; a thief of a CI credential.
- **Boundaries:** the laptop is not trusted (GĐ-6); the boundaries that hold are AWS IAM/SCPs and the
  merge to `main` (ADR-0002, ADR-0003). Agent settings are hygiene (ADR-0007). Hooks, plugins and local
  MCP servers run outside the sandbox with the engineer's access (📖 R1.6.2, R5.5.5).

## What the controls do not cover

- **Process-only controls:** raw partner documents kept out of agent sessions (T1); no agent in the JIT
  or PHI terminal (T6, T14); agents never approve PRs on laptops (T7); tenant posting rule (T6); incident-session flags (T19). They
  rely on training and are checked by sampling, not enforced.
- **Code outside the sandbox:** hooks, plugins and local MCP servers are limited only by review before
  approval (T2, T3); excluded commands (`aws`, `pulumi`, `serverless`) only by prompts in Manual mode or
  the classifier in auto mode (T1, T10).
- **Laptops without MDM:** server-managed settings can be skipped (T2–T4; G11). The IAM and merge-gate
  boundaries still hold.
- **k0s, GCP and Firebase:** same principles, mechanisms open (G1–G3); no risk stop, no break-glass,
  no detection of a leaked deploy token.
- **Phase 1 window:** until phase 2 there is no sandbox, no credential deny rules, no
  `allowManagedHooksOnly`, no `allowedProviders`, no SCPs, no audit-log alerts and no policy checks
  (T1, T3–T5, T10, T12–T14, T17). Standing prod write stays until its prerequisites are in place (layer 8).

# ADR-0001: Every production change goes through a reviewed PR applied by CI

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (Options §9, "A + D2'")
- **Scope:** all writes to production AWS, GCP, k0s and Firebase; incidents included (k0s and Firebase
  have no risk stop and no break-glass yet, G1, G2; human GCP access is open, G3)

## 1. Context

Engineering wants Claude Code to talk to AWS directly; Compliance wants no production change without
a named human who reviewed and approved it. "Most engineers' profiles can reach production" (brief), and deploys from laptops are assumed
(GĐ-10, unconfirmed), so an agent on that laptop can deploy too. Incidents are where the pressure to bypass
review is highest.

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. PR → approval → CI deploy for everything ("IaC first") | One path, approval before apply, evidence by construction | Slower incidents (est. 11–46 min ⚠️ vs 2–20 min, Options §6) |
| B. SSM Automation runbooks with an approval step | Approval inside AWS | Not verified that it meets the approval rule (G6); only for operations someone scripted. Kept on the roadmap, verified in phase 2 (OD4) |
| C. JIT direct access for the engineer + agent | Fastest | Approves access, not the change; agent holds prod write |
| D. Hosted agent with its own identity | Clean separation | New platform; does not remove the need for approval |

## 3. Decision

"A + D2'": option A is the default path for every production change, incidents included. A narrow JIT
fallback exists only when the PR path cannot be used during an incident (ADR-0005). The owner accepts
that this fallback meets the approval rule only partly (Options §9 Q2). Incident target: ≤ 30 min from
decision to apply.
=== docs/adr/0002-no-standing-prod-write-read-only-agent-identity.md
# ADR-0002: Nobody holds standing prod write; in prod, the engineer's (and so the agent's) only standing role reads metadata

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (Options §9; D2)
- **Scope:** AWS IAM Identity Center permission sets and SCPs on the prod OU; k0s, GCP and Firebase by the same principle

## 1. Context

On a laptop the agent uses the engineer's AWS SSO cache, and one portal session reaches every role
assigned to that engineer (📖 R2.2.1, R2.2.2; token-reuse detail ⚠️ R2.2.2). A separate "agent"
permission set therefore does not separate the agent from the engineer (⚠️ R2.9 #1). Whatever the
engineer holds, the agent holds.

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. Separate agent permission set, engineer keeps write | Looks like least privilege | Same SSO cache: the agent can still assume the write role |
| B. No standing prod write for anyone; `ProdReadMetadata` as the only standing prod role | Agent cannot write prod with the engineer's identity | Engineers also lose direct writes and raw-log reads |
| C. Separate OS user or container for agent sessions | Real separation of credentials | More setup; planned for phase 3 only |

## 3. Decision

Option B. Prod is written only by the CI pipeline role, or by an approved, time-boxed JIT grant
(ADR-0005). The standing prod role is `ProdReadMetadata` [design name]: metrics, redacted log groups,
configuration of services whose secrets are resolved at runtime; no data-plane reads of claim stores;
1-hour role session, the minimum (📖 R2.1.4). From phase 2, SCPs on the prod OU deny data-plane reads and
direct Lambda updates except for named roles (pattern ⚠️ R2.9 #4, R4.6 #3). Option C follows in phase 3.

# ADR-0004: Risky prod diffs stop the deploy until a stack owner approves the prod preview

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (OD8, OD11, OD13)
- **Scope:** deploy workflows for Pulumi and Serverless stacks; k0s and Firebase not covered yet

## 1. Context

With the gate at merge time (ADR-0003), the approver reviews the code change, not the prod diff. A
PR may not preview prod, because that would run PR code with state-write and secret access
(📖 R4.3.3, R4.3.4; ⚠️ R4.6 #2). So a stateful delete or an IAM change can reach prod without anyone
seeing its real effect. Most IAM, network and stateful changes sit inside domain files such as
`serverless.yml`, not in separate L3 paths (assumed ⚠️; we have no access to the repo).

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. Accept the gap | No extra step | Destructive diffs applied unseen |
| B. Risk stop, approved by the L3 owner team | Specialist review | Often a third person; L3 team must be on call 24/7 |
| C. Risk stop, approved by an owner of the stack | Stays at two people; works at night | Less specialist review; compensated by automated checks |
