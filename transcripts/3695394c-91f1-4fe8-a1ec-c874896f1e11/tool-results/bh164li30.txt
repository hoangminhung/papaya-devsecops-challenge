    29	## 1. The decision in one page
    30	
    31	Engineering and Compliance disagree only about **writes to production**; reads of metadata and all
    32	of non-prod are outside Compliance's sentence (framing §3.1). Real customer data is layer 6.
    33	
    34	**Chosen approach "A + D2'"** (Options §9, owner decision 2026-11-09):
    35	
    36	1. **Default path:** every prod change is a pull request, approved by a named human who is not the
    37	   author, applied by CI. Incidents included ("IaC first").
    38	2. **Fallback (break-glass):** only when the PR path cannot be used, a human gets an approved grant
    39	   with a 1-hour role session (effective window up to about 2 h) and runs an approved command list in a terminal without an agent (layer 7) [design].
    40	3. **Nothing standing:** no human or agent holds standing prod write; no long-lived credentials.
    41	
    42	| Engineering gets | Compliance gets |
    43	|---|---|
    44	| A free loop in non-prod: read, change, deploy without approval (non-prod is synthetic or masked, GĐ-14; stores not yet scanned are excluded, layer 6). | Every prod change approved **before** apply by a named human ≠ author (GĐ-8, GĐ-11), enforced in GitHub and AWS IAM, outside the agent (limits below). |
    45	| Read-only prod metadata for the agent. | No standing prod write (S1), no long-lived CI keys (S2, with an owner-approved exception for k0s/Firebase deploy credentials, OD1, OD6; storage conditions [design], layer 5). |
    46	| Self-service PRs, one approval, same-day ship (S4). | One evidence chain per change; approval and change records ≥ 6 years (📖 R5.2.9; applied to change records ⚠️ R5.7 #2). |
    47	| Incident lane: approval wait ≤ 15 min, 24/7 (S7). Decision-to-apply target ≤ 30 min (Options §9); current estimate 11–46 min ⚠️, measured first in rollout. | Agent-side controls as a second layer, not the control of record. |
    48	
    49	**Where the design falls short, stated openly:**
    50	
    51	- **The fallback meets the approval rule only partly** (approves a command list, not an applied
    52	  change); accepted by the owner (Options §9 Q2). It is a second, process-controlled path, while the
    53	  framing asked for one technically enforced path (framing §3.3, Options §7). It stays narrow only
    54	  if most incidents are expressible in IaC (unknown, Options §8); layer 7 measures this.
    55	- **On GitHub Team nobody sees the prod diff before apply** (⚠️ R4.6 #1; Team assumed, GĐ-5).
    56	  Risky prod diffs stop the deploy until an owner of the stack approves the prod preview [design].
    57	- **Admins can edit the gate**; logged, not prevented (logging 📖 R3.2.2; ability to edit ⚠️ R3.2.2,
    58	  R3.6 #1). An admin's agent has
    59	  the same power, because the agent uses its engineer's GitHub login (⚠️ R6.5 #10).
    60	- **Some rules are process, not technology:** see "Process rules" in layer 1. The owner's rule
    61	  "the PR approver is always an engineer, never an agent" (OD5) is absolute as policy, but on
    62	  laptops it is enforced by policy and training, not by a technical control: an agent could approve
    63	  through its engineer's login, and no detection was found.
    64	- **Incident approvers vs domain review:** code-owner review means an approver must own the file,
    65	  at L2 as at L3. So that one on-call primary can approve any path at 2 a.m., the on-call approver
    66	  group co-owns every deployable path (owner decision OD9, layer 3). The cost: GitHub accepts an
    67	  approval from any listed owner (📖 R3.2.7), so on normal days that group could approve another
    68	  domain's PR. Domain review on normal days becomes a process rule with a monthly check, not a
    69	  technical control. Because on-call approvers only
    70	  approve (OD7), a night incident needs two people awake: the incident responder and the on-call
    71	  approver (the backup only replaces an unavailable primary).
    72	- **One approver for high-risk changes.** L3 changes (IAM, stateful deletes, workflow files) get one
    73	  approver, like L2, but the path is owned by the L3 owner team (or by the stack's owners for L3
    74	  content in domain files, OD8), and risky prod diffs stop for a look at
    75	  the prod preview (OD2, OD8, layer 3). A single reviewer can miss things; this is the owner's trade-off
    76	  for speed.
    77	- **HIPAA applicability is a legal question** (⚠️ R1.11.1.11); the design treats Papaya as a
    78	  business associate, as the brief implies.
    79	
    80	**Cross-cutting rules** (owner's balance principle, research 6.8):
    81	
    82	1. **The boundary is IAM and the CI gate.** Server-managed settings are "a client-side control, not
    83	   a security boundary" (📖 R1.1.7); local admins can edit endpoint files (📖 R1.1.8).
    84	2. **Assume prompt injection succeeds:** neither OWASP nor NIST knows a full prevention (📖 R6.1.1, R6.1.2).
    85	3. **Friction where damage is large, none where it is small**, measured, with a time-boxed escape.
    86	4. **Evidence by construction:** the path produces the records.
    87	
    88	### Roles
    89	
    90	| Role | Rule |
    91	|---|---|
    92	| Author (engineer + their agent) | Never approves own change; GitHub blocks PR authors from approving (📖 R3.3.1). |
    93	| Approver | Always an engineer, never an agent (owner rule, OD5). Named in CODEOWNERS; ≠ author, ≠ last pusher (📖 R3.2.3); for an app-opened PR, ≠ the person who triggered it (⚠️ R3.3.4, layer 5). |
    94	| Incident responder | Engineer who diagnoses and writes the fix or the JIT request. Never the on-call approver of the same shift (OD7). |
    95	| On-call approver | Engineer on the on-call schedule, primary + backup, 24/7; wait ≤ 15 min (S7). While on call they only approve: they write no fix and file no JIT request, so the approver is always distinct from the author (OD7). The primary approves; the backup replaces an unavailable primary (OD2). No platform-team membership is required; all engineers follow one agreed approval procedure (OD2). |
    96	| Data owner [design] | Named per tenant; co-approves real-data reads, or reviews a night-time read the next working day (layer 6). |
    97	| Control owner | DevSecOps (1–2 people, GĐ-1); owns policies and metrics; not the only approver. |

   101	## Layer 1 — Identity and access
   102	
   103	**Principle.** Every action traces to one named human. Nobody holds standing prod write: prod is
   104	written by the pipeline role, or in the fallback by an approved, time-boxed grant. Prod reads default
   105	to metadata. No long-lived credentials. Prod and non-prod are separate boundaries.
   106	
   107	**On Papaya's stack**
   108	
   109	- **The engineer's access is the agent's access.** The agent uses the engineer's AWS SSO cache, and
   110	  one portal session reaches every role assigned to that engineer (📖 R2.2.1, R2.2.2; token-reuse
   111	  detail ⚠️ R2.2.2). A separate
   112	  "agent" permission set does not separate them (⚠️ R2.9 #1). The control is what the **engineer**
   113	  holds.
   114	- **Process rules** that follow from this:
   115	  - the JIT terminal runs no agent, though the grant is reachable from the same laptop (owner
   116	    accepted as a process control, D2);
   117	  - the incident-analysis session is meant to use only read-only roles (D2; `--restricted` per D3,
   118	    research 6.9.4 Q2);
   119	  - the real-data terminal runs no agent when the store holds PHI [design], same weakness as D2;
   120	  - an agent never approves PRs: an owner rule (OD5), enforced on laptops by policy and training.
   121	    GitHub blocks self-approval only. The auto-mode default block list
   122	    excerpt read names "approving Claude's own pull request" (📖 R6.3.3); whether approving
   123	    someone else's PR is blocked is unverified (⚠️), and the list
   124	    applies only in auto mode. No detection was found (⚠️; `actor_is_agent` in the audit log has no
   125	    documented meaning, R3.5.6).
   126	- **IAM Identity Center permission sets** (📖 R2.1.1) [design names]:
   127	  - `ProdReadMetadata`: metrics, redacted log groups, configuration; no data-plane read on claim
   128	    stores; 1 h session, the minimum (📖 R2.1.4). Until a service's logs are redacted at source
   129	    (layer 6), it gets that service's metrics only. Lambda configuration can hold secrets resolved by
   130	    Serverless in plain text (⚠️ R4.4.7), so configuration reads are allowed per service only after
   131	    its secrets move to runtime resolution (⚠️ R4.6 #7). Cost: until then the agent reads
   132	    timeout/memory from the IaC code;
   133	  - `NonProdDeveloper`: broad, non-prod accounts only;
   134	  - `InfraOperator-<service>`: assigned only by the JIT flow (layer 7), via a partner product, the
   135	    TEAM sample (📖 R2.4.1, R2.4.1b) or a small home-built flow (⚠️ R2.4.2) on the documented APIs
   136	    `CreateAccountAssignment` / `DeleteAccountAssignment` (📖 R2.4.2);
   137	  - no standing prod-write permission set.
   138	- **SCPs on the prod OU** [design] (SCPs cap member-account principals, 📖 R2.3.1, R2.3.2):
   139	  - deny data-plane reads on claim stores except application roles and the approved data-read role,
   140	    by `aws:PrincipalArn` (📖 R2.3.8; pattern ⚠️ R2.9 #4). Actions, e.g. `s3:GetObject`,
   141	    `sqs:ReceiveMessage`, `states:GetExecutionHistory`, are incomplete and unchecked (⚠️ G13);
   142	  - deny `lambda:UpdateFunctionCode` / `lambda:UpdateFunctionConfiguration` (⚠️ R4.6 #3) except
   143	    CloudFormation `deploymentRole`s, the Pulumi prod deploy role (if Pulumi manages Lambdas) and the
   144	    JIT roles. This closes `serverless deploy function`, which changes config outside CloudFormation
   145	    (📖 R4.4.4), and needs `deploymentRole` set on every Serverless stack (key 📖 R4.4.5; need ⚠️ R4.6 #3);
   146	  - a pre-deployed revocation Deny on `identitystore:UserId` (📖 R2.4.4); protect the org trail (📖 R2.6.2).
   147	  - Limits: 10 SCPs per target, 10,240 characters; no SCP applies to the management account
   148	    (📖 R2.3.2, R2.3.4), so whatever deploys SCPs there is the most sensitive role (L3 path).
   149	- **Sessions/MFA:** portal session length set on purpose; an IdP session can extend it silently
   150	  (📖 R2.1.5, R2.1.6). MFA lives in the external IdP if one is used (📖 R2.1.7).
   151	- **CI → AWS:** GitHub OIDC, no stored keys (📖 R3.4.1). The prod role trusts only the `production`
   152	  environment of the monorepo, in its `sub` format (📖 R3.4.3, R3.4.4; immutable format assumed,
   153	  ⚠️ R3.7 A2), ideally customised with the deploy workflow's `job_workflow_ref` (📖 R3.4.5; on Team ⚠️ G10).
   154	- **CI → GCP:** Workload Identity Federation restricted to Papaya's GitHub organization, which Google
   155	  requires (📖 R3.4.5b).
   156	- **k0s, GCP and Firebase for humans:** same principles; mechanisms not researched (G1–G3). Today
   157	  k0s is reached with kubeconfigs, no SSO (GĐ-4, unconfirmed). Interim: no admin kubeconfig and no GCP
   158	  owner role on laptops; prod deploys only from CI. Firebase is not on the GCP BAA list (📖 R5.5.3), so
   159	  Firebase Hosting must hold no PHI (⚠️ R5.7 #7).
   160	
   161	**Audit evidence.** Identity Center assignment export (S1); CloudTrail `CreateAccountAssignment` /
   162	`DeleteAccountAssignment` per grant (📖 R2.4.2), linked to its approval by request ID [design]; SCPs
   163	and trust policies as Pulumi code; IAM Access Analyzer `check-no-new-access` on policy PRs
   164	(📖 R2.8.1); quarterly access review of permission sets and GitHub admins.
   165	
   166	**Cost / value.** Engineers lose standing prod write and keep a free non-prod loop. Prod reads stay
   167	fast for metrics and metadata, but shrink during the transition: because the engineer's access is the
   168	agent's access, from phase 1 the engineer too loses raw logs and configuration of services not yet
   169	redacted or moved to runtime secrets. Configuration values come from the IaC code instead (layer 1
   170	above); raw logs that may hold customer data need an L3-data grant. The data owner is not on the
   171	on-call schedule, so at night the grant is approved by the on-call approver alone and the data owner
   172	reviews it the next working day [design]; the wait still counts against S7. This is
   173	the largest cost of the first months. Compliance gets least privilege that is enforced.

   177	## Layer 2 — Agent runtime controls
   178	
   179	**Principle.** Agent-side controls are hygiene, not the boundary. They are central, versioned in git
   180	and the same for everyone. Defaults are safe; overrides are measured. The session that reads
   181	untrusted content holds as little power as possible (📖 R6.1.2).
   182	
   183	**On Papaya's stack**
   184	
   185	- **Delivery:** server-managed settings (available on Team, 📖 R1.1.5) for all laptops. With MDM, also
   186	  an endpoint file; by default one managed source supplies most keys, so the two must carry the same
   187	  keys or use `managedSourcesBehavior: "merge"` (📖 R1.1.3, R1.1.4). MDM is unknown; both are prepared.
   188	- **Baseline** (template: Anthropic's `settings-hipaa.json`, 📖 R5.5.4). All keys 📖 at the row cited. Only the phase-1 subset in layer 8 ships first; the other keys (sandbox, `allowManagedHooksOnly`, credential denies, `allowManagedPermissionRulesOnly`, `allowedProviders`) arrive in phase 2 (OD4):
   189	
   190	  | Key | Value and reason |
   191	  |---|---|
   192	  | `permissions.defaultMode` | `default` (Manual). A default, not a lock: users can switch to auto; VS Code remembers the last pick (D1, R6.9.3). |
   193	  | `permissions.allow` | Read-only commands Papaya uses, to cut prompts (R6.9.3). It contains no command listed in `sandbox.excludedCommands` (`aws`, `pulumi`, `serverless`): an allowed excluded command would run outside the sandbox, with `~/.aws` and the network, without a prompt (⚠️ inference from R1.2.6, R1.6.4) [design]. Cost: a prompt for every `aws` read. |
   194	  | `allowManagedPermissionRulesOnly` | `true`, one rule set (D1, research 6.9.4 Q4; R1.2.5). Cost: project and user rules are ignored, so the managed set must carry every deny/ask rule projects need; prompts likely rise (⚠️ research 6.9.4 Q4). |
   195	  | `permissions.disableBypassPermissionsMode` | `"disable"`: removes bypass mode (P3a; R1.2.2). Auto mode, where a classifier approves instead of a person, stays available (D1) and is measured through `permission_mode`. |
   196	  | `permissions.deny` / `ask` | Deny credential paths (R5.5.4; `Read(...)` syntax ⚠️ R1.8 #5). Ask for `WebFetch`, which the sandbox domain list does not limit (R1.6.2); cost: a prompt per fetch. The HIPAA template denies WebFetch (R5.5.4); "ask" is a deliberate deviation so that documentation lookups still work. |
   197	  | `requiredMinimumVersion` | ≥ 2.1.285 for `allowedProviders` (R1.1.15), which also covers `--restricted` (2.1.248, R6.9.1b) and the plugin-pin fix (2.1.179, R6.2.7); ≥ 2.1.295 if any managed hook uses `onFailure: "block"` (R1.5.2); and ≥ the latest fixed advisory at rollout (R6.3.9). It does not end running sessions and fails open on a bad value (R1.1.13). |
   198	  | `allowedProviders` + `forceLoginOrgUUID` | `["anthropic"]` + Papaya's org; closes most bypasses on **endpoint-managed** machines (R1.1.15). `forceLoginOrgUUID` checks claude.ai sign-ins only, not Claude Console sign-ins (R5.5.5); with it set, sessions on `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` or `apiKeyHelper` are refused (R1.11.3.11). |
   199	  | `allowManagedHooksOnly` | `true` (R1.5.4). |
   200	  | sandbox | `sandbox.enabled`, `failIfUnavailable`, `allowUnsandboxedCommands: false`, narrow `network.allowedDomains` locked by `network.allowManagedDomainsOnly`; `credentials` / `filesystem.denyRead` on `~/.aws`, which the sandbox can otherwise read (R1.6.3, R1.6.4). |
   201	  | `sandbox.autoAllowBashIfSandboxed` | Left at its default `true`: sandboxed Bash runs without a prompt, so in Manual mode prompts are for edits, unsandboxed commands and fetches, not every command (R5.5.5b). A deliberate choice: the sandbox (no `~/.aws`, allowlisted network) is the control for those commands. The HIPAA README says to set `false` if policy needs a person to approve each command (R5.5.5b); cost of `false`: a prompt per command. |
   202	  | MCP, plugins | Layer 4. |
   203	  | OTel | Exporter on, content flags `0` (R1.1.20, R5.5.4). |
   204	
   205	- **Trade-off on AWS credentials [design].** With `~/.aws` hidden from the sandbox, the plan is to
   206	  list `aws`, `pulumi` and `serverless` in `sandbox.excludedCommands`. Excluded commands run "with
   207	  full access" (📖 R1.6.4), which likely includes the network (⚠️ inference). How the list matches
   208	  commands (prefix or text, and chained commands) is not researched (⚠️). This is worse than an
   209	  egress channel: `pulumi preview` runs the Pulumi program and `serverless` loads its config and
   210	  plugins, all code in the repo that the agent can edit, so excluding them lets repo code run
   211	  outside the sandbox with network access and with `~/.aws` readable (⚠️ inference). For these
   212	  commands the sandbox gives no protection. And an injected `aws` command could send out the SSO
   213	  token cache itself. That token likely opens every role assigned to the engineer for the rest of the
   214	  portal session (📖 R2.1.5; token reuse ⚠️ R2.2.2), probably including JIT or data-read grants added
   215	  later in that session (⚠️ inference). Mitigations [design]: a short portal session (📖 R2.1.5); end
   216	  the existing portal session and sign in fresh **before** a JIT or data-read grant is created
   217	  (whether ending a session invalidates a token already stolen is unverified ⚠️; ending it does not
   218	  end role sessions, 📖 R2.4.3); an SCP that denies writes to resources outside Papaya's organization using
   219	  `aws:ResourceOrgID` (key 📖 R2.3.8), on every OU, since the token can be stolen from a non-prod
   220	  session; legitimate writes to outside resources need exceptions (⚠️ not inventoried). That SCP only stops Papaya's own credentials writing to a
   221	  foreign bucket; it does not stop a command that sends the token to a non-AWS endpoint or uses the
   222	  attacker's credentials (⚠️ inference). Prefer running `pulumi` and `serverless` against real
   223	  accounts only in CI; on laptops keep them to non-prod roles, and move them into the phase-3
   224	  container. Residual risk: token theft during a session. It is accepted
   225	  because the engineer holds no **standing** prod write and no **standing** PHI read; during a JIT
   226	  or data-read window the protection is the process rule in layer 1 (D2). Stronger option, phase 3:
   227	  a separate OS user or container for prod-reading sessions
   228	  (⚠️ R6.5 #2).
   229	- **Session types:**
   230	
   231	  | Session | Identity | Flags | Enforcement |
   232	  |---|---|---|---|
   233	  | Daily development (laptop) | non-prod roles + `ProdReadMetadata` | baseline | Auto mode by choice (D1); `--restricted` recommended (D3). |
   234	  | Incident analysis (laptop) | meant to be `ProdReadMetadata` only | `--restricted --tools "Bash,Read,Grep,Glob"`, started in an empty scratch directory, not the repo [design] | Process rule (D3, research 6.9.4 Q1–Q2). No WebFetch, and file tools confined to the working directory (📖 R6.9.1b); Edit/Write are excluded only if `--tools` acts as an exclusive list (⚠️ unverified), but Bash can still write in its working directory (📖 R1.6.3) and call any role in the cache. |
   235	  | CI agent (hosted runner) | own GitHub App token; never `production` | `--restricted`, explicit `--tools`; all rules in a managed-settings file on the runner | Workflow file under CODEOWNERS (D3, research 6.9.4 Q5). The file is advisory if `Bash` is in `--tools` (layer 5). |
   236	  | JIT terminal | JIT grant | no agent | Process rule (D2). |
   237	  | Auto-mode environment (phase 3) | non-prod only | auto encouraged | D1 option (c). |
   238	
   239	- **Hard limits:** Bash rules are not a boundary (📖 R1.2.6); hooks fail open unless
   240	  `"onFailure": "block"` (📖 R1.5.2); `--restricted` cannot be forced by a setting (📖 R6.9.1), and a `PATH` wrapper on laptops can be bypassed (⚠️ R6.9.1c);
   241	  on laptops **without MDM**, a different login, an API key or a `CLAUDE_CODE_USE_*` variable skips
   242	  server-managed settings, `allowedProviders` included (📖 R1.1.7; ⚠️ R1.8 #3, G11). So S5's
   243	  "nobody can turn off all prompts unnoticed" is likely unreachable without MDM (⚠️).
   244	- **Auto memory:** engineers review it and delete it after a suspicious session; residual risk with a
   245	  named owner (D3).
   246	- **Fallback:** switch to `disableAutoMode` (📖 R1.2.2) if the planted-injection test steers auto mode, a serious
   247	  advisory appears, or an audit finds auto mode touched a protected scope (D1).
   248	
   249	**Audit evidence.** Managed settings in git with PR approvals; `/status` and `claude doctor` from
   250	sampled machines (📖 R1.1.18); OTel `claude_code.tool_decision` (`permission_mode`) and
   251	`claude_code.tool.blocked_on_user` (`duration_ms`, rubber-stamping signal) (fields 📖 research 6.6
   252	D1 metrics; thresholds ⚠️). Settings-change audit events on Team: unknown (⚠️ R1.1.12).
   253	
   254	**Cost / value.** More prompts than auto mode, partly offset by the read-only allowlist. Compliance
   255	gets one organization policy with evidence instead of personal choices (P3c).

   259	## Layer 3 — Change workflow by risk level
   260	
   261	**Principle.** The level is set by the damage a change can do. One default path above non-prod: a
   262	reviewed PR applied by the pipeline, with the JIT fallback (layer 7) as the only other write path.
   263	The approver reviews the code change that will be applied. Every prod change needs two people, and
   264	no more by default: one who makes it and one who approves it (until OQ-A is answered, the
   265	cross-team process rule below can need more); the on-call backup only replaces an
   266	unavailable primary (OD2). Higher risk narrows **who** may approve (the owners of that path), not how
   267	many. Separately, any prod diff that looks risky stops the deploy, whatever its level; that adds a
   268	second approval by an owner of the same stack, which keeps it to two people (OD8). Agent's reading
   269	of OD8 [design], to confirm: the original author opens the approval PR and the first approver
   270	approves it; if the first approver is unavailable, another owner of the stack approves, which makes
   271	three people (open question OQ-B). Two edge cases: GitHub accepts one on-call group member for

   273	cross-team PR is a process rule only; whether such PRs should be split is an open question for the
   274	owner (OQ-A, below). A real-data read is not a change and has its own rule, L3-data. Incidents use the same
   275	path with faster people, not fewer security checks.

   297	
   298	- **Gate = merge to `main`.** On Team, environment reviewers do not exist for private repos
   299	  (📖 R3.1.2). Ruleset on `main`: PR required, 1 approval, code-owner review, dismiss stale approvals,

   301	  push, empty bypass list (📖 R3.2.2, R3.2.3, R3.2.5). Branch up to date before merge, since there is

   303	- **L3 approvals [design]:** CODEOWNERS plus code-owner review only, no path-based required
   304	  reviewers rule. That rule (📖 R3.2.4) asks for approvals from specific teams, which the on-call
   305	  group would not satisfy at night, and how it combines several teams is not researched (⚠️), so it
   306	  would break OD9 or add a third person. GitHub stops the author from approving (📖 R3.3.1). A required check with a pinned source app (📖 R3.2.5) adds what
   307	  the rules cannot: for app-opened PRs it excludes the person who triggered the agent, and it counts
   308	  only human approvals, since an app's approval might count (⚠️ R3.3.4, R3.7 A3).

   310	  co-owner on every deployable path in CODEOWNERS (infrastructure and service code), next to the
   311	  domain team. Agent's reading of OD9, to confirm: the group does **not** co-own the paths that

   314	  unavailable and the JIT fallback applies (layer 7). One primary and one backup from that team are on call. Technically any member can approve any

   317	  settings, not by a PR; managing it as code (e.g. with Pulumi's GitHub provider) and the audit

   319	  comparison includes the group's member list. Cost: an approval from any
   320	  listed owner satisfies code-owner review (📖 R3.2.7), so on normal days a member could approve
   321	  another domain's PR. Mitigation [design]: process rule "outside your shift, approve only your own
   322	  domain", and a monthly report of approvals by group members outside their shifts and outside their
   323	  domain (layer 7). Whether Papaya's team size allows full coverage is unknown
   324	  (§1, S7).
   325	- **Risk stop [design]:** applies to every deploy, whatever the level. The deploy job previews prod;
   326	  on stateful replace/delete, an IAM change, a network or security-group change, or an advisory
   327	  policy finding it stops and posts the filtered preview. An engineer opens a second PR that adds
   328	  `deploy-approvals/<stack>/<sha>.yaml` (`<sha>` = the stopped commit) holding that SHA and the
   329	  preview hash; the workflow does not open it, because the setting that lets Actions create and approve PRs stays
   330	  off (📖 R3.3.3; ⚠️ R3.6 #3). CODEOWNERS on `deploy-approvals/<stack>/` names the owners of that stack and the
   331	  on-call group (OD8, OD9). The approver is ≠ author and may be the first PR's approver, who now sees
   332	  the prod diff. Merging it triggers the deploy on the new HEAD, which previews again and continues
   333	  only if the hash matches the approved one; if another PR merged in between, the hash differs and
   334	  the deploy stops again (Options §1; hash stability ⚠️ Options §8). Cost: while a stack is
   335	  stopped, later merges to that stack stop too until a matching approval lands; in an incident, a
   336	  risky change already waiting on `main` blocks the fix for the same stack until it is approved or
   337	  reverted. A
   338	  `mandatory` policy violation always blocks `pulumi up` (📖 R4.2.2): the fix is a code change, or a
   339	  change to the policy pack through its own L3 PR. Preview output is filtered for
   340	  outputs and secrets before it is posted (Options §1; ⚠️ R4.6 #2).
   341	- **Merge approval = deploy approval** only if (⚠️ R3.6 #1, from 📖 R3.1.3, R3.4.5c): `production`
   342	  allows only `main`; only the reusable deploy workflow (under CODEOWNERS) references it; no ref/SHA
   343	  inputs; no `issue_comment`, `pull_request_target` or `workflow_run` triggers; one concurrency group
   344	  per stack without `cancel-in-progress` (📖 R4.1.4).
   345	- **Pulumi:** PRs preview non-prod only, because a prod preview runs PR code with state-write and
   346	  secret access (📖 R4.3.3, R4.3.4; ⚠️ R4.6 #2). On `main`: prod preview, then `pulumi up` with the
   347	  policy pack, which stops on a mandatory violation (📖 R4.2.2). Prod runs allow no `--skip-preview`
   348	  (📖 R4.1.2) and no targeting, replace, `state`, `import`, `destroy` (⚠️ R4.6 #3, G12). Pulumi Cloud,
   349	  if used: OIDC via `pulumi/auth-actions`, no stored token (📖 R4.1.4).
   350	- **Serverless v4:** `serverless package`; `serverless diff --json` (sf-core ≥ 4.37.0), parsed by CI
   351	  because differences do not change the exit code (📖 R4.4.2); `serverless deploy --package`
   352	  (📖 R4.4.3); a least-privilege `deploymentRole`, which cannot be removed later and is usable by
   353	  anyone who may operate the stack (📖 R4.4.5), so JIT roles get no stack-operation rights.
   354	- **State:** writable by deploy roles (and possibly the drift role, layer 7); Pulumi
   355	  secrets via `awskms` on a DIY backend (📖 R4.3.3, R4.3.4; ⚠️ R4.6 #7).
   356	- **k0s [design]:** manifests in the monorepo, applied by CI; no write RBAC for humans or agents in
   357	  prod; read roles exclude logs and exec in namespaces with claim data (mechanism: G1).
   358	- **Incident lane:** label `incident`, on-call approver paged, security checks always run (S10), only
   359	  slow unrelated tests skipped [design].

   361	**Example: Lambda timeouts at 2 a.m.** (Options §6)
   362	
   363	The incident responder is engineer E; the on-call approver is R (a backup replaces R only if R is
   364	unavailable).
   365	
   366	1. E's incident-analysis session reads metrics and redacted logs and proposes `timeout` 30 → 90 s,
   367	   memory 1024 → 2048 MB, and a larger visibility timeout on the source queue (ratio ⚠️ Options §8).
   368	2. A second session (edit tools; not meant to use prod roles) edits `serverless.yml`, runs
   369	   `serverless diff` on non-prod, and opens a PR labelled `incident` as E.
   370	3. R, a co-owner of `serverless.yml` through the on-call group (OD9), reviews the diff. If R
   371	   catches a missing queue change, R does not fix it (OD7): E pushes the fix, the stale approval is
   372	   dismissed, and R approves again, one more review round (Options §6). E merges.
   373	4. The deploy workflow packages, previews prod, finds no risky change, deploys with the OIDC role.
   374	5. Estimate 11–46 min (⚠️ Options §6) against ≤ 30 min: measured first in rollout.
   375

   377	retention is unverified (⚠️ G7); deploy-role CloudTrail events; all linked by commit SHA and run ID.

   379	**Cost / value.** One approver for every prod change, from the owners of the path; two approvals by
   380	the same approver when the risk stop fires. Cross-team PRs: open (OQ-A). None in non-prod.
   381	Compliance gets four-eyes enforced by GitHub. Gap: on Team the prod diff is not seen before apply.

   422	## Layer 5 — CI/CD hardening
   423	
   424	**Principle.** CI is the default production writer, so it is the main target. Short-lived,
   425	least-privilege credentials per job. Every CI dependency is pinned. Agent-written code passes the same
   426	checks as human code (S10).
   427	
   428	**On Papaya's stack**
   429	
   430	- **Credentials:** OIDC instead of keys and tokens in repository secrets, which any writer can read
   431	  (📖 R3.4.1, R3.5.3b). Org default for `GITHUB_TOKEN` set to "restricted", `permissions:` per job (📖 R3.5.3).
   432	  "Allow GitHub Actions to create and approve pull requests" off (📖 R3.3.3). Serverless License Key in
   433	  SSM, read by the deploy role (sf ≥ 4.4.19, 📖 R4.4.8). Until G1/G2 are solved, k0s and Firebase
   434	  deploys may need a stored credential in GitHub: a kubeconfig or token for k0s, a Firebase token or
   435	  service-account key for Firebase Hosting. The owner accepts this as an exception to S2 = 0 until it
   436	  is checked whether k0s and Firebase deploys can use OIDC (OD1, OD6). Conditions [design]:
   437	  - stored only as an **environment secret of `production`**, never as a repository secret. Anyone
   438	    with write access can read repository secrets (📖 R3.5.3b), which would turn the exception into
   439	    standing prod write for every engineer and their agent. Environment secrets and a deployment
   440	    branch rule limited to `main` are available on Team for private repos (📖 R3.1.2, R3.1.3), and
   441	    only the reviewed deploy workflow references the environment (layer 3);
   442	  - the deploy job runs on GitHub-hosted runners. On self-hosted runners, jobs "are not run in an
   443	    isolated container, even if they use environments", so environment secrets there must be
   444	    treated like repository secrets (📖 R3.1.5). Self-hosted runners "can be persistently
   445	    compromised by untrusted code" from anyone who can open a PR, and runner groups limit only which
   446	    repositories use them (📖 R3.5.2); in a monorepo any workflow can likely target the runner's label (⚠️ G15).
   447	    How to restrict a runner to one workflow is not researched (⚠️ G15); just-in-time runners exist
   448	    (📖 R3.5.2, not read in detail). If reaching k0s needs a self-hosted runner, that
   449	    runner is dedicated to the `production` deploy, and the residual risk is recorded;
   450	  - that environment secret is the single source of truth: no copy elsewhere (OD1);
   451	  - an owner, an expiry and rotation in the exception register;
   452	  - optionally a separate environment (e.g. `production-k0s`), limited to `main` and referenced
   453	    only by the k0s/Firebase deploy workflow, so AWS deploy jobs cannot read these secrets
   454	    [design].
   455	
   456	  Residual risk: admins can change the environment, and a deleted environment comes back without
   457	  protection (⚠️ R3.1.4); the alerts and settings comparison in layer 7 cover this. The exception
   458	  covers **CI deploy credentials only**. Runtime credentials, such as a k0s autoscaler's AWS access to
   459	  add or remove nodes, live in the cluster, not in GitHub; they follow layer 1 (no static keys, a
   460	  role attached to the machine; ⚠️ not researched for k0s, G1).
   461	- **Side paths:** Pulumi ESC, Pulumi Deployments and Serverless Dashboard providers reach AWS
   462	  (📖 R4.4.9) outside the GitHub gate (⚠️ R4.4.9); not used for prod (⚠️ R4.6 #6).
   463	- **Pinning:** workflow lockfile (`gh actions-lock`) or full SHA, enforced by the org policy "Require
   464	  actions to be pinned to a full-length commit SHA"; the lockfile does not pin reusable workflows, so
   465	  the deploy workflow lives in the same repo (📖 R3.5.5; conclusion [design]).
   466	- **CODEOWNERS** on `.github/`, `CLAUDE.md`, `CLAUDE.local.md`, `.claude/`, `.claude.json`, `.mcp.json`,
   467	  `.husky/`, `.gitmodules`, `.ripgreprc` (📖 R3.2.8; list ⚠️ R6.5 #5); CI validates the file, because
   468	  invalid lines are skipped silently (📖 R3.2.7).
   469	- **No privileged triggers with untrusted code** (`pull_request_target`, `workflow_run` + checkout,
   470	  📖 R3.5.4).
   471	- **Agents in CI:** `claude-code-action` with a custom GitHub App limited to Contents, Issues, Pull

   475	  federation auth ⚠️); MCP set fixed by CI because `.mcp.json` loads without a prompt in `-p` runs
   476	  (📖 R1.3.5); never `environment: production` (⚠️ R3.6 #4). Hosted runners give `sudo` (📖 R3.5.1),

   498	## Layer 6 — Data protection and prompt-injection defence
   499	
   500	**Principle.** The design keeps PHI from reaching the coding agent (owner decision, research 1.9).
   501	Some paths rely on process (below), so this is a target, not a guarantee. Other customer
   502	personal data is outside that hard boundary ("not extended", research 5.8): the agent reads metadata
   503	by default and may read such data case by case under GĐ-9. Real-data reads are approved, name one
   504	tenant, are time-boxed, and need an agreement (BAA/DPA, partner contract) (GĐ-9). Everything read
   505	from outside is untrusted. Non-prod is synthetic or masked (GĐ-14).
   506	
   507	**On Papaya's stack**
   508	
   509	- **Paths to PHI** (research 1.11.4 lists 17):
   510	  - AWS stores: closed by identity, through `ProdReadMetadata` as the only standing prod role from
   511	    phase 1 (existing broad read roles are removed) and the SCP from phase 2
   512	    (layer 1); no Aurora credentials, no prod exec, no `lambda:InvokeFunction` for agent-usable roles
   513	    [design; actions ⚠️ G13];
   514	  - k0s logs/exec and GCP stores (L1, L11, L13): same principle, mechanism open (G1, G3);
   515	  - tickets/chat via MCP, pasted text, internal admin pages, prod AI traces, fixtures, CI logs (L5,
   516	    L8–L10, L12, L14): process and hygiene only;
   517	  - logs redacted at source with raw payloads in a separate log group; alerts carry IDs, not payloads [design].
   518	- **Real-data request** [design]: tenant, purpose, store, window, agreement; approved by the data owner
   519	  and an approver ≠ requester; JIT data-read role, 1 h. At night the data owner is not on call: the
   520	  on-call approver approves alone and the data owner reviews the grant the next working day. This
   521	  applies to non-PHI and PHI alike; for PHI the reader is still a human without an agent. Per-tenant scoping through session tags
   522	  (📖 R2.1.8) is unresolved, because tags come from user attributes (⚠️).
   523	  - **PHI:** a human reads in a terminal without an agent (process rule, layer 1); the agent gets a
   524	    redacted summary. This
   525	    narrows GĐ-9 because the agent stays outside PHI scope (research 1.9) and Team is not shown as
   526	    BAA-covered (⚠️ R1.11.3.4). Enterprise + BAA only for a separate environment if needed (research 1.9).
   527	  - **Non-PHI personal data:** the agent may read it within the approved request (GĐ-9). Claim
   528	    tables mix health, ID and bank data (research 1.11.4 L2), so a store that holds PHI is treated as
   529	    PHI unless the agent reads a view or extract without PHI [design].
   530	- **Partner-uploaded claim documents (A7b):** never in an agent session raw; reproduce with synthetic
   531	  documents, or de-identify first [design]. The document is PHI and an injection vector (research
   532	  1.11.4 L6).
   533	- **Injection** (these lower frequency; layers 1 and 3 limit impact): Manual by default (sandboxed Bash runs without a prompt, layer 2); the auto-mode
   534	  classifier missed 17 % of 52 real overeager actions and 5.7 % of 1,000 synthetic exfiltration
   535	  attempts (📖 R6.3.5). Broad allowed domains such as `github.com` are a documented exfiltration path
   536	  (📖 R6.3.7). The incident session has no WebFetch, likely no edit tools (layer 2), and runs outside
   537	  the repo, but its Bash can still write locally and send data out through excluded
   538	  commands (layer 2), including the SSO token cache; "no standing write, no PHI read" limits what
   539	  the token opens, except during a JIT or data-read window (layer 2 mitigations). Shared knowledge
   540	  goes in `CLAUDE.md` under review; auto memory is exempt from the protected-path rules unless `--restricted` (📖 R6.3.11, D3).
   541	- **Tenants:** one tenant per data-read grant; a session that read one tenant's data does not post to
   542	  shared places without review (⚠️ R6.5 #8, process). Logical separation in shared accounts is assumed
   543	  (GĐ-3, unconfirmed).

   564	## Layer 7 — Observability, audit, incident response and break-glass
   565	
   566	**Principle.** One tamper-evident evidence chain per prod change. One routed alert channel with a
   567	named on-call, approvers included. Unapproved change is detected (drift, reconciliation). Break-glass
   568	is approved before use, time-boxed and reconciled after.
   569	
   570	**On Papaya's stack**
   571	
   572	- **Audit stores:**
   573	  - organization CloudTrail to a log-archive account with integrity validation (📖 R2.6.2, R2.6.4,
   574	    R2.6.5); change records ≥ 6 years; raw-log retention for Papaya's compliance owner (⚠️ R5.7 #2).
   575	    Data events only on PHI buckets, prod Lambda invoke and prod SQS (cost 📖 R2.6.3; selection
   576	    ⚠️ R2.9 #5), which makes the archive
   577	    PHI-bearing (⚠️ research 1.11.4 L15). CloudTrail Lake is closed to new customers (📖 R2.6.6);
   578	  - GitHub org audit log kept 180 days, so exported (📖 R3.5.6);
   579	  - alerts on `repository_ruleset.update`, `environment.update_protection_rule`,
   580	    `environment.remove_protection_rule`, `environment.delete`, `protected_branch.policy_override`
   581	    (📖 R3.5.6, R3.1.4; selection ⚠️ R3.6 #1). UI changes to the branch policy may leave no event, and a
   582	    deleted `production` environment comes back unprotected (⚠️ R3.1.4): a job compares live settings
   583	    with an expected copy (G8);
   584	  - Aurora SQL is likely invisible to CloudTrail (⚠️ R2.7.1): Database Activity Streams, alerts on
   585	    lost-record events (📖 R2.7.2; Serverless v2 ⚠️), stream treated as PHI (⚠️ R2.7.3);
   586	  - Claude Code OTel without prompt content (layer 2).
   587	- **Change record [design]:** keyed by commit SHA or JIT request ID; links PR, approvals, run ID,
   588	  preview and CloudTrail events. Monthly reconciliation: every prod write event matches a record
   589	  approved before apply (S3). Actor: `onBehalfOf.userId` where present, else session name plus
   590	  directory lookup (📖 R2.5.1; ⚠️ R2.5.3).
   591	- **Drift [design]:** its own role, trusted only from a `drift` environment on `main`; it can read
   592	  prod secrets in state, which is noted (⚠️ R4.6 #2). Scheduled `pulumi preview --refresh
   593	  --expect-no-changes` or `pulumi refresh --preview-only` (📖 R4.1.1, R4.3.1, R4.3.2). On a DIY S3
   594	  backend, preview needs state-write permission (📖 R4.3.3); whether a refresh preview writes more
   595	  than locks is open (⚠️ R4.6 #2, G14). So either the drift role gets state write (and the same
   596	  trust care as the deploy role), or Pulumi Cloud drift detection is used (📖 R4.3.2, Pro+). The
   597	  latter runs on Pulumi Deployments, which holds credentials to prod, so it re-opens a side path that
   598	  layer 5 excludes and needs the same trust narrowing and audit (📖 R4.4.9; ⚠️ R4.6 #6). CloudFormation
   599	  drift detection, explicitly set properties only (📖 R4.4.6). No auto-remediation: it is an unreviewed
   600	  `pulumi up --refresh` (📖 R4.3.2). Each finding gets an actor and a ticket.
   601	- **On-call:** phase 1 delivers the named approver schedule (primary + backup engineers, 24/7), as
   602	  decided in framing round 1, and, because of OD7, a minimal incident-responder schedule; the
   603	  latter extends that decision. The primary approves; the backup steps in only if the primary is
   604	  unavailable (OD2). On-call approvers only approve during their shift; the fix is written by an
   605	  incident responder (OD7). Alert routing and the
   606	  rest of on-call follow in phase 2 (tools: G5); in phase 1 the responder calls the approver by phone from the published schedule.
   607	- **Break-glass = JIT fallback** [design unless marked]:
   608	
   609	  | Step | Rule |
   610	  |---|---|
   611	  | When | The PR path cannot be used: operation not in IaC and no runbook; GitHub/Actions down; pipeline broken. The approver refuses JIT for anything expressible in IaC while the pipeline works, and records why. |
   612	  | Request | Command list, scope, reason, incident link, in a channel that does not depend on GitHub. |
   613	  | Approval | On-call approver ≠ requester, before the grant (Options §4b; OD7; backup rule OD2). |
   614	  | Grant | `InfraOperator-<service>`; role session 1 h (📖 R2.1.4). Deleting the assignment likely stops only new sessions (⚠️ R2.4.2, R2.9 #3), so the real window can approach 2 h; ending the portal session does not end role sessions (📖 R2.4.3). An immediate stop needs the revocation SCP, which must keep the user blocked for at least 12 h (📖 R2.4.4). |
   615	  | Execution | The grant goes to the requester (the incident responder), who types the commands; no agent in that terminal (D2). D2 said the on-call person runs them; OD7 moves that to the responder, since on-call engineers only approve. |
   616	  | After | A job compares CloudTrail writes in the window with the list; a codify PR within a fixed deadline (as soon as GitHub is back); drift detection until it merges. |
   617	  | Identity Center outage | Emergency SAML federation to roles, built and tested in advance (📖 R2.1.11; ⚠️ R2.9 #2); no user mapped until an approved activation, which is alerted. |
   618	
   619	  **Example request (illustrative command ⚠️):** "INC-123, ECS service `claims-api`, Actions outage. Run
   620	  `aws ecs update-service --cluster <prod-cluster> --service <svc> --force-new-deployment`. Scope
   621	  `InfraOperator-claims`, 1 h."
   622	
   623	  **Metrics** (Options §7; starting thresholds ⚠️ to calibrate): JIT used where a PR was possible
   624	  (review at 1); writes outside the list (review at 1); codify PRs late (review at 1); grants per
   625	  month and share of incidents needing non-IaC operations (review above about 25 %, a value new in
   626	  this draft). On a breach,
   627	  make the PR lane faster or add a runbook; do not widen JIT.
   628	- **Roadmap:** runbooks for repeated non-IaC operations, if SSM Automation's approval step meets three
   629	  conditions (Options §2; outside 02-research, G6); break-glass from an environment without the agent
   630	  (D2, ⚠️).
   631	
   632	**Audit evidence.** Validated CloudTrail; exported GitHub audit log; change records and monthly
   633	reconciliation (S3, S8 ≤ 30 min); JIT requests, reconciliations, codify PRs; drift tickets; on-call
   634	schedule and approval waits (S7); monthly report of approvals by on-call group members outside
   635	their shift and domain (OD9).
   636	
   637	**Cost / value.** The incident lane is slower than direct access (estimated 11–46 vs 2–20 min,
   638	Options §6), and JIT needs a written command list. Compliance gets approval before apply even in
