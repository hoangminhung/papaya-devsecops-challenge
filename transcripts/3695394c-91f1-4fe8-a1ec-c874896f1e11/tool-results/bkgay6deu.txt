    29	## 1. The decision in one page
    30	
    31	Engineering and Compliance disagree only about **writes to production**; reads of metadata and all
    32	of non-prod are outside Compliance's sentence (framing §3.1). Real customer data is layer 6.
    33	
    34	**Chosen approach "A + D2'"** (Options §9, owner decision 2026-11-09):
    35	
    36	1. **Default path:** every prod change is a pull request, approved by a named human who is not the
    37	   author, applied by CI. Incidents included ("IaC first").
    38	2. **Fallback (break-glass):** only when the PR path cannot be used, a human gets an approved grant
    39	   with a 1-hour role session (effective window up to about 2 h) and runs an approved command list in a terminal without an agent (layer 7) [design].
    40	3. **Nothing standing:** no human or agent holds standing prod write; no long-lived credentials.
    41	
    42	| Engineering gets | Compliance gets |
    43	|---|---|
    44	| A free loop in non-prod: read, change, deploy without approval (non-prod is synthetic or masked, GĐ-14; stores not yet scanned are excluded, layer 6). | Every prod change approved **before** apply by a named human ≠ author (GĐ-8, GĐ-11), enforced in GitHub and AWS IAM, outside the agent (limits below). |
    45	| Read-only prod metadata for the agent. | No standing prod write (S1), no long-lived CI keys (S2, with an owner-approved exception for k0s/Firebase deploy credentials, OD1, OD6; storage conditions [design], layer 5). |
    46	| Self-service PRs, one approval, same-day ship (S4). | One evidence chain per change; approval and change records ≥ 6 years (📖 R5.2.9; applied to change records ⚠️ R5.7 #2). |
    47	| Incident lane: approval wait ≤ 15 min, 24/7 (S7). Decision-to-apply target ≤ 30 min (Options §9); current estimate 11–46 min ⚠️, measured first in rollout. | Agent-side controls as a second layer, not the control of record. |
    48	
    49	**Where the design falls short, stated openly:**
    50	
    51	- **The fallback meets the approval rule only partly** (approves a command list, not an applied
    52	  change); accepted by the owner (Options §9 Q2). It is a second, process-controlled path, while the
    53	  framing asked for one technically enforced path (framing §3.3, Options §7). It stays narrow only
    54	  if most incidents are expressible in IaC (unknown, Options §8); layer 7 measures this.
    55	- **On GitHub Team nobody sees the prod diff before apply** (⚠️ R4.6 #1; Team assumed, GĐ-5).
    56	  Risky prod diffs stop the deploy until an owner of the stack approves the prod preview [design].
    57	- **Admins can edit the gate**; logged, not prevented (logging 📖 R3.2.2; ability to edit ⚠️ R3.2.2,
    58	  R3.6 #1). An admin's agent has
    59	  the same power, because the agent uses its engineer's GitHub login (⚠️ R6.5 #10).
    60	- **Some rules are process, not technology:** see "Process rules" in layer 1. The owner's rule
    61	  "the PR approver is always an engineer, never an agent" (OD5) is absolute as policy, but on
    62	  laptops it is enforced by policy and training, not by a technical control: an agent could approve
    63	  through its engineer's login, and no detection was found.
    64	- **Incident approvers vs domain review:** code-owner review means an approver must own the file,
    65	  at L2 as at L3. So that one on-call primary can approve any path at 2 a.m., the on-call approver
    66	  group co-owns every deployable path (owner decision OD9, layer 3). The cost: GitHub accepts an
    67	  approval from any listed owner (📖 R3.2.7), so on normal days that group could approve another
    68	  domain's PR. Domain review on normal days becomes a process rule with a monthly check, not a
    69	  technical control. Because on-call approvers only
    70	  approve (OD7), a night incident needs two people awake: the incident responder and the on-call
    71	  approver (the backup only replaces an unavailable primary).
    72	- **One approver for high-risk changes.** L3 changes (IAM, stateful deletes, workflow files) get one
    73	  approver, like L2, but that approver must own the path, and risky prod diffs stop for a look at
    74	  the prod preview (OD2, OD8, layer 3). A single reviewer can miss things; this is the owner's trade-off
    75	  for speed.
    76	- **HIPAA applicability is a legal question** (⚠️ R1.11.1.11); the design treats Papaya as a
    77	  business associate, as the brief implies.
    78	
    79	**Cross-cutting rules** (owner's balance principle, research 6.8):
    80	
    81	1. **The boundary is IAM and the CI gate.** Server-managed settings are "a client-side control, not
    82	   a security boundary" (📖 R1.1.7); local admins can edit endpoint files (📖 R1.1.8).
    83	2. **Assume prompt injection succeeds:** neither OWASP nor NIST knows a full prevention (📖 R6.1.1, R6.1.2).
    84	3. **Friction where damage is large, none where it is small**, measured, with a time-boxed escape.
    85	4. **Evidence by construction:** the path produces the records.
    86	
    87	### Roles
    88	
    89	| Role | Rule |
    90	|---|---|
    91	| Author (engineer + their agent) | Never approves own change; GitHub blocks PR authors from approving (📖 R3.3.1). |
    92	| Approver | Always an engineer, never an agent (owner rule, OD5). Named in CODEOWNERS; ≠ author, ≠ last pusher (📖 R3.2.3); for an app-opened PR, ≠ the person who triggered it (⚠️ R3.3.4, layer 5). |
    93	| Incident responder | Engineer who diagnoses and writes the fix or the JIT request. Never the on-call approver of the same shift (OD7). |
    94	| On-call approver | Engineer on the on-call schedule, primary + backup, 24/7; wait ≤ 15 min (S7). While on call they only approve: they write no fix and file no JIT request, so the approver is always distinct from the author (OD7). The primary approves; the backup replaces an unavailable primary (OD2). No platform-team membership is required; all engineers follow one agreed approval procedure (OD2). |
    95	| Data owner [design] | Named per tenant; co-approves real-data reads, or reviews a night-time read the next working day (layer 6). |
    96	| Control owner | DevSecOps (1–2 people, GĐ-1); owns policies and metrics; not the only approver. |

   100	## Layer 1 — Identity and access
   101	
   102	**Principle.** Every action traces to one named human. Nobody holds standing prod write: prod is
   103	written by the pipeline role, or in the fallback by an approved, time-boxed grant. Prod reads default
   104	to metadata. No long-lived credentials. Prod and non-prod are separate boundaries.
   105	
   106	**On Papaya's stack**
   107	
   108	- **The engineer's access is the agent's access.** The agent uses the engineer's AWS SSO cache, and
   109	  one portal session reaches every role assigned to that engineer (📖 R2.2.1, R2.2.2; token-reuse
   110	  detail ⚠️ R2.2.2). A separate
   111	  "agent" permission set does not separate them (⚠️ R2.9 #1). The control is what the **engineer**
   112	  holds.
   113	- **Process rules** that follow from this:
   114	  - the JIT terminal runs no agent, though the grant is reachable from the same laptop (owner
   115	    accepted as a process control, D2);
   116	  - the incident-analysis session is meant to use only read-only roles (D2; `--restricted` per D3,
   117	    research 6.9.4 Q2);
   118	  - the real-data terminal runs no agent when the store holds PHI [design], same weakness as D2;
   119	  - an agent never approves PRs: an owner rule (OD5), enforced on laptops by policy and training.
   120	    GitHub blocks self-approval only. The auto-mode default block list
   121	    excerpt read names "approving Claude's own pull request" (📖 R6.3.3); whether approving
   122	    someone else's PR is blocked is unverified (⚠️), and the list
   123	    applies only in auto mode. No detection was found (⚠️; `actor_is_agent` in the audit log has no
   124	    documented meaning, R3.5.6).
   125	- **IAM Identity Center permission sets** (📖 R2.1.1) [design names]:
   126	  - `ProdReadMetadata`: metrics, redacted log groups, configuration; no data-plane read on claim
   127	    stores; 1 h session, the minimum (📖 R2.1.4). Until a service's logs are redacted at source
   128	    (layer 6), it gets that service's metrics only. Lambda configuration can hold secrets resolved by
   129	    Serverless in plain text (⚠️ R4.4.7), so configuration reads are allowed per service only after
   130	    its secrets move to runtime resolution (⚠️ R4.6 #7). Cost: until then the agent reads
   131	    timeout/memory from the IaC code;
   132	  - `NonProdDeveloper`: broad, non-prod accounts only;
   133	  - `InfraOperator-<service>`: assigned only by the JIT flow (layer 7), via a partner product, the
   134	    TEAM sample (📖 R2.4.1, R2.4.1b) or a small home-built flow (⚠️ R2.4.2) on the documented APIs
   135	    `CreateAccountAssignment` / `DeleteAccountAssignment` (📖 R2.4.2);
   136	  - no standing prod-write permission set.
   137	- **SCPs on the prod OU** [design] (SCPs cap member-account principals, 📖 R2.3.1, R2.3.2):
   138	  - deny data-plane reads on claim stores except application roles and the approved data-read role,
   139	    by `aws:PrincipalArn` (📖 R2.3.8; pattern ⚠️ R2.9 #4). Actions, e.g. `s3:GetObject`,
   140	    `sqs:ReceiveMessage`, `states:GetExecutionHistory`, are incomplete and unchecked (⚠️ G13);
   141	  - deny `lambda:UpdateFunctionCode` / `lambda:UpdateFunctionConfiguration` (⚠️ R4.6 #3) except
   142	    CloudFormation `deploymentRole`s, the Pulumi prod deploy role (if Pulumi manages Lambdas) and the
   143	    JIT roles. This closes `serverless deploy function`, which changes config outside CloudFormation
   144	    (📖 R4.4.4), and needs `deploymentRole` set on every Serverless stack (key 📖 R4.4.5; need ⚠️ R4.6 #3);
   145	  - a pre-deployed revocation Deny on `identitystore:UserId` (📖 R2.4.4); protect the org trail (📖 R2.6.2).
   146	  - Limits: 10 SCPs per target, 10,240 characters; no SCP applies to the management account
   147	    (📖 R2.3.2, R2.3.4), so whatever deploys SCPs there is the most sensitive role (L3 path).
   148	- **Sessions/MFA:** portal session length set on purpose; an IdP session can extend it silently
   149	  (📖 R2.1.5, R2.1.6). MFA lives in the external IdP if one is used (📖 R2.1.7).
   150	- **CI → AWS:** GitHub OIDC, no stored keys (📖 R3.4.1). The prod role trusts only the `production`
   151	  environment of the monorepo, in its `sub` format (📖 R3.4.3, R3.4.4; immutable format assumed,
   152	  ⚠️ R3.7 A2), ideally customised with the deploy workflow's `job_workflow_ref` (📖 R3.4.5; on Team ⚠️ G10).
   153	- **CI → GCP:** Workload Identity Federation restricted to Papaya's GitHub organization, which Google
   154	  requires (📖 R3.4.5b).
   155	- **k0s, GCP and Firebase for humans:** same principles; mechanisms not researched (G1–G3). Today
   156	  k0s is reached with kubeconfigs, no SSO (GĐ-4, unconfirmed). Interim: no admin kubeconfig and no GCP
   157	  owner role on laptops; prod deploys only from CI. Firebase is not on the GCP BAA list (📖 R5.5.3), so
   158	  Firebase Hosting must hold no PHI (⚠️ R5.7 #7).
   159	
   160	**Audit evidence.** Identity Center assignment export (S1); CloudTrail `CreateAccountAssignment` /
   161	`DeleteAccountAssignment` per grant (📖 R2.4.2), linked to its approval by request ID [design]; SCPs
   162	and trust policies as Pulumi code; IAM Access Analyzer `check-no-new-access` on policy PRs
   163	(📖 R2.8.1); quarterly access review of permission sets and GitHub admins.
   164	
   165	**Cost / value.** Engineers lose standing prod write and keep a free non-prod loop. Prod reads stay
   166	fast for metrics and metadata, but shrink during the transition: because the engineer's access is the
   167	agent's access, from phase 1 the engineer too loses raw logs and configuration of services not yet
   168	redacted or moved to runtime secrets. Configuration values come from the IaC code instead (layer 1
   169	above); raw logs that may hold customer data need an L3-data grant. The data owner is not on the
   170	on-call schedule, so at night the grant is approved by the on-call approver alone and the data owner
   171	reviews it the next working day [design]; the wait still counts against S7. This is
   172	the largest cost of the first months. Compliance gets least privilege that is enforced.

   176	## Layer 2 — Agent runtime controls
   177	
   178	**Principle.** Agent-side controls are hygiene, not the boundary. They are central, versioned in git
   179	and the same for everyone. Defaults are safe; overrides are measured. The session that reads
   180	untrusted content holds as little power as possible (📖 R6.1.2).
   181	
   182	**On Papaya's stack**
   183	
   184	- **Delivery:** server-managed settings (available on Team, 📖 R1.1.5) for all laptops. With MDM, also
   185	  an endpoint file; by default one managed source supplies most keys, so the two must carry the same
   186	  keys or use `managedSourcesBehavior: "merge"` (📖 R1.1.3, R1.1.4). MDM is unknown; both are prepared.
   187	- **Baseline** (template: Anthropic's `settings-hipaa.json`, 📖 R5.5.4). All keys 📖 at the row cited:
   188	
   189	  | Key | Value and reason |
   190	  |---|---|
   191	  | `permissions.defaultMode` | `default` (Manual). A default, not a lock: users can switch to auto; VS Code remembers the last pick (D1, R6.9.3). |
   192	  | `permissions.allow` | Read-only commands Papaya uses, to cut prompts (R6.9.3). It contains no command listed in `sandbox.excludedCommands` (`aws`, `pulumi`, `serverless`): an allowed excluded command would run outside the sandbox, with `~/.aws` and the network, without a prompt (⚠️ inference from R1.2.6, R1.6.4) [design]. Cost: a prompt for every `aws` read. |
   193	  | `allowManagedPermissionRulesOnly` | `true`, one rule set (D1, research 6.9.4 Q4; R1.2.5). Cost: project and user rules are ignored, so the managed set must carry every deny/ask rule projects need; prompts likely rise (⚠️ research 6.9.4 Q4). |
   194	  | `permissions.disableBypassPermissionsMode` | `"disable"`: removes bypass mode (P3a; R1.2.2). Auto mode, where a classifier approves instead of a person, stays available (D1) and is measured through `permission_mode`. |
   195	  | `permissions.deny` / `ask` | Deny credential paths (R5.5.4; `Read(...)` syntax ⚠️ R1.8 #5). Ask for `WebFetch`, which the sandbox domain list does not limit (R1.6.2); cost: a prompt per fetch. The HIPAA template denies WebFetch (R5.5.4); "ask" is a deliberate deviation so that documentation lookups still work. |
   196	  | `requiredMinimumVersion` | ≥ 2.1.285 for `allowedProviders` (R1.1.15), which also covers `--restricted` (2.1.248, R6.9.1b) and the plugin-pin fix (2.1.179, R6.2.7); ≥ 2.1.295 if any managed hook uses `onFailure: "block"` (R1.5.2); and ≥ the latest fixed advisory at rollout (R6.3.9). It does not end running sessions and fails open on a bad value (R1.1.13). |
   197	  | `allowedProviders` + `forceLoginOrgUUID` | `["anthropic"]` + Papaya's org; closes most bypasses on **endpoint-managed** machines (R1.1.15). `forceLoginOrgUUID` checks claude.ai sign-ins only, not Claude Console sign-ins (R5.5.5); with it set, sessions on `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` or `apiKeyHelper` are refused (R1.11.3.11). |
   198	  | `allowManagedHooksOnly` | `true` (R1.5.4). |
   199	  | sandbox | `sandbox.enabled`, `failIfUnavailable`, `allowUnsandboxedCommands: false`, narrow `network.allowedDomains` locked by `network.allowManagedDomainsOnly`; `credentials` / `filesystem.denyRead` on `~/.aws`, which the sandbox can otherwise read (R1.6.3, R1.6.4). |
   200	  | `sandbox.autoAllowBashIfSandboxed` | Left at its default `true`: sandboxed Bash runs without a prompt, so in Manual mode prompts are for edits, unsandboxed commands and fetches, not every command (R5.5.5b). A deliberate choice: the sandbox (no `~/.aws`, allowlisted network) is the control for those commands. The HIPAA README says to set `false` if policy needs a person to approve each command (R5.5.5b); cost of `false`: a prompt per command. |
   201	  | MCP, plugins | Layer 4. |
   202	  | OTel | Exporter on, content flags `0` (R1.1.20, R5.5.4). |
   203	
   204	- **Trade-off on AWS credentials [design].** With `~/.aws` hidden from the sandbox, the plan is to
   205	  list `aws`, `pulumi` and `serverless` in `sandbox.excludedCommands`. Excluded commands run "with
   206	  full access" (📖 R1.6.4), which likely includes the network (⚠️ inference). How the list matches
   207	  commands (prefix or text, and chained commands) is not researched (⚠️). This is worse than an
   208	  egress channel: `pulumi preview` runs the Pulumi program and `serverless` loads its config and
   209	  plugins, all code in the repo that the agent can edit, so excluding them lets repo code run
   210	  outside the sandbox with network access and with `~/.aws` readable (⚠️ inference). For these
   211	  commands the sandbox gives no protection. And an injected `aws` command could send out the SSO
   212	  token cache itself. That token likely opens every role assigned to the engineer for the rest of the
   213	  portal session (📖 R2.1.5; token reuse ⚠️ R2.2.2), probably including JIT or data-read grants added
   214	  later in that session (⚠️ inference). Mitigations [design]: a short portal session (📖 R2.1.5); end
   215	  the existing portal session and sign in fresh **before** a JIT or data-read grant is created
   216	  (whether ending a session invalidates a token already stolen is unverified ⚠️; ending it does not
   217	  end role sessions, 📖 R2.4.3); an SCP that denies writes to resources outside Papaya's organization using
   218	  `aws:ResourceOrgID` (key 📖 R2.3.8), on every OU, since the token can be stolen from a non-prod
   219	  session; legitimate writes to outside resources need exceptions (⚠️ not inventoried). That SCP only stops Papaya's own credentials writing to a
   220	  foreign bucket; it does not stop a command that sends the token to a non-AWS endpoint or uses the
   221	  attacker's credentials (⚠️ inference). Prefer running `pulumi` and `serverless` against real
   222	  accounts only in CI; on laptops keep them to non-prod roles, and move them into the phase-3
   223	  container. Residual risk: token theft during a session. It is accepted
   224	  because the engineer holds no **standing** prod write and no **standing** PHI read; during a JIT
   225	  or data-read window the protection is the process rule in layer 1 (D2). Stronger option, phase 3:
   226	  a separate OS user or container for prod-reading sessions
   227	  (⚠️ R6.5 #2).
   228	- **Session types:**
   229	
   230	  | Session | Identity | Flags | Enforcement |
   231	  |---|---|---|---|
   232	  | Daily development (laptop) | non-prod roles + `ProdReadMetadata` | baseline | Auto mode by choice (D1); `--restricted` recommended (D3). |
   233	  | Incident analysis (laptop) | meant to be `ProdReadMetadata` only | `--restricted --tools "Bash,Read,Grep,Glob"`, started in an empty scratch directory, not the repo [design] | Process rule (D3, research 6.9.4 Q1–Q2). No WebFetch, and file tools confined to the working directory (📖 R6.9.1b); Edit/Write are excluded only if `--tools` acts as an exclusive list (⚠️ unverified), but Bash can still write in its working directory (📖 R1.6.3) and call any role in the cache. |
   234	  | CI agent (hosted runner) | own GitHub App token; never `production` | `--restricted`, explicit `--tools`; all rules in a managed-settings file on the runner | Workflow file under CODEOWNERS (D3, research 6.9.4 Q5). The file is advisory if `Bash` is in `--tools` (layer 5). |
   235	  | JIT terminal | JIT grant | no agent | Process rule (D2). |
   236	  | Auto-mode environment (phase 3) | non-prod only | auto encouraged | D1 option (c). |
   237	
   238	- **Hard limits:** Bash rules are not a boundary (📖 R1.2.6); hooks fail open unless
   239	  `"onFailure": "block"` (📖 R1.5.2); `--restricted` cannot be forced by a setting (📖 R6.9.1), and a `PATH` wrapper on laptops can be bypassed (⚠️ R6.9.1c);
   240	  on laptops **without MDM**, a different login, an API key or a `CLAUDE_CODE_USE_*` variable skips
   241	  server-managed settings, `allowedProviders` included (📖 R1.1.7; ⚠️ R1.8 #3, G11). So S5's
   242	  "nobody can turn off all prompts unnoticed" is likely unreachable without MDM (⚠️).
   243	- **Auto memory:** engineers review it and delete it after a suspicious session; residual risk with a
   244	  named owner (D3).
   245	- **Fallback:** switch to `disableAutoMode` (📖 R1.2.2) if the planted-injection test steers auto mode, a serious
   246	  advisory appears, or an audit finds auto mode touched a protected scope (D1).
   247	
   248	**Audit evidence.** Managed settings in git with PR approvals; `/status` and `claude doctor` from
   249	sampled machines (📖 R1.1.18); OTel `claude_code.tool_decision` (`permission_mode`) and
   250	`claude_code.tool.blocked_on_user` (`duration_ms`, rubber-stamping signal) (fields 📖 research 6.6
   251	D1 metrics; thresholds ⚠️). Settings-change audit events on Team: unknown (⚠️ R1.1.12).
   252	
   253	**Cost / value.** More prompts than auto mode, partly offset by the read-only allowlist. Compliance
   254	gets one organization policy with evidence instead of personal choices (P3c).

   258	## Layer 3 — Change workflow by risk level
   259	
   260	**Principle.** The level is set by the damage a change can do. One default path above non-prod: a
   261	reviewed PR applied by the pipeline, with the JIT fallback (layer 7) as the only other write path.
   262	The approver reviews the code change that will be applied. Every prod change needs two people, and
   263	no more by default: one who makes it and one who approves it; the on-call backup only replaces an
   264	unavailable primary (OD2). Higher risk narrows **who** may approve (the owners of that path), not how
   265	many. Separately, any prod diff that looks risky stops the deploy, whatever its level; that adds a
   266	second approval by an owner of the same stack; by rule the first approver gives it, so it stays two
   267	people (OD8). A different owner steps in only if the first approver is unavailable, which makes three
   268	people and is recorded as a deviation. Two edge cases: GitHub accepts one on-call group member for
   269	files of several owner teams (OD9, 📖 R3.2.7), so "an approval from each domain team" on a
   270	cross-team PR is a process rule only; whether such PRs should be split is an open question for the

   283	`CLAUDE.md` and the other agent configuration files are L3, because they define the workflow for
   284	the whole team (OD3). With code-owner review on, every PR, L2 included, needs an approval from an
   285	owner of the files it touches (📖 R3.2.3, R3.2.7; per-file behaviour ⚠️ not a separate research row).

   293	**On Papaya's stack**
   294	
   295	- **Gate = merge to `main`.** On Team, environment reviewers do not exist for private repos
   296	  (📖 R3.1.2). Ruleset on `main`: PR required, 1 approval, code-owner review, dismiss stale approvals,
   297	  approval by someone other than the last pusher, required checks from a pinned source app, no force
   298	  push, empty bypass list (📖 R3.2.2, R3.2.3, R3.2.5). Branch up to date before merge, since there is
   299	  no merge queue (⚠️ R4.6 #1; whether updating drops approvals is open, Options §8).
   300	- **L3 approvals [design]:** CODEOWNERS plus code-owner review only, no path-based required
   301	  reviewers rule. That rule (📖 R3.2.4) asks for approvals from specific teams, which the on-call
   302	  group would not satisfy at night, and how it combines several teams is not researched (⚠️), so it
   303	  would break OD9 or add a third person. GitHub stops the author from approving (📖 R3.3.1). A required check with a pinned source app (📖 R3.2.5) adds what
   304	  the rules cannot: for app-opened PRs it excludes the person who triggered the agent, and it counts
   305	  only human approvals, since an app's approval might count (⚠️ R3.3.4, R3.7 A3).
   306	- **Who approves at night (OD9):** a fixed GitHub team, the on-call approvers, is listed as
   307	  co-owner on every deployable path in CODEOWNERS, L3 paths included, next to the domain or L3
   308	  team. One primary and one backup from that team are on call. Technically any member can approve any
   309	  path; by rule the primary approves and the backup only if the primary is unavailable (OD2).
   310	  Membership changes only through a CODEOWNERS/team PR, not per shift. Cost: an approval from any
   311	  listed owner satisfies code-owner review (📖 R3.2.7), so on normal days a member could approve
   312	  another domain's PR. Mitigation [design]: process rule "outside your shift, approve only your own
   313	  domain", and a monthly report of approvals by group members outside their shifts and outside their
   314	  domain (layer 7). Whether Papaya's team size allows full coverage is unknown
   315	  (§1, S7).
   316	- **Risk stop [design]:** applies to every deploy, whatever the level. The deploy job previews prod;
   317	  on stateful replace/delete, an IAM change, a network or security-group change, or an advisory
   318	  policy finding it stops and posts the filtered preview. An engineer opens a second PR that adds
   319	  `deploy-approvals/<stack>/<sha>.yaml` (`<sha>` = the stopped commit) holding that SHA and the
   320	  preview hash; the workflow does not open it, because the setting that lets Actions create and approve PRs stays
   321	  off (📖 R3.3.3; ⚠️ R3.6 #3). CODEOWNERS on `deploy-approvals/<stack>/` names the owners of that stack and the
   322	  on-call group (OD8, OD9). The approver is ≠ author and may be the first PR's approver, who now sees
   323	  the prod diff. Merging it triggers the deploy on the new HEAD, which previews again and continues
   324	  only if the hash matches the approved one; if another PR merged in between, the hash differs and
   325	  the deploy stops again (Options §1; hash stability ⚠️ Options §8). Cost: while a stack is
   326	  stopped, later merges to that stack stop too until a matching approval lands. A
   327	  `mandatory` policy violation always blocks `pulumi up` (📖 R4.2.2): the fix is a code change, or a
   328	  change to the policy pack through its own L3 PR. Preview output is filtered for
   329	  outputs and secrets before it is posted (Options §1; ⚠️ R4.6 #2).
   330	- **Merge approval = deploy approval** only if (⚠️ R3.6 #1, from 📖 R3.1.3, R3.4.5c): `production`
   331	  allows only `main`; only the reusable deploy workflow (under CODEOWNERS) references it; no ref/SHA
   332	  inputs; no `issue_comment`, `pull_request_target` or `workflow_run` triggers; one concurrency group
   333	  per stack without `cancel-in-progress` (📖 R4.1.4).
   334	- **Pulumi:** PRs preview non-prod only, because a prod preview runs PR code with state-write and
   335	  secret access (📖 R4.3.3, R4.3.4; ⚠️ R4.6 #2). On `main`: prod preview, then `pulumi up` with the
   336	  policy pack, which stops on a mandatory violation (📖 R4.2.2). Prod runs allow no `--skip-preview`
   337	  (📖 R4.1.2) and no targeting, replace, `state`, `import`, `destroy` (⚠️ R4.6 #3, G12). Pulumi Cloud,
   338	  if used: OIDC via `pulumi/auth-actions`, no stored token (📖 R4.1.4).
   339	- **Serverless v4:** `serverless package`; `serverless diff --json` (sf-core ≥ 4.37.0), parsed by CI
   340	  because differences do not change the exit code (📖 R4.4.2); `serverless deploy --package`
   341	  (📖 R4.4.3); a least-privilege `deploymentRole`, which cannot be removed later and is usable by
   342	  anyone who may operate the stack (📖 R4.4.5), so JIT roles get no stack-operation rights.
   343	- **State:** writable by deploy roles (and possibly the drift role, layer 7); Pulumi
   344	  secrets via `awskms` on a DIY backend (📖 R4.3.3, R4.3.4; ⚠️ R4.6 #7).
   345	- **k0s [design]:** manifests in the monorepo, applied by CI; no write RBAC for humans or agents in
   346	  prod; read roles exclude logs and exec in namespaces with claim data (mechanism: G1).
   347	- **Incident lane:** label `incident`, on-call approver paged, security checks always run (S10), only
   348	  slow unrelated tests skipped [design].

   350	**Example: Lambda timeouts at 2 a.m.** (Options §6)
   351	
   352	The incident responder is engineer E; the on-call approver is R (a backup replaces R only if R is
   353	unavailable).
   354	
   355	1. E's incident-analysis session reads metrics and redacted logs and proposes `timeout` 30 → 90 s,
   356	   memory 1024 → 2048 MB, and a larger visibility timeout on the source queue (ratio ⚠️ Options §8).
   357	2. A second session (edit tools; not meant to use prod roles) edits `serverless.yml`, runs
   358	   `serverless diff` on non-prod, and opens a PR labelled `incident` as E.
   359	3. R, a co-owner of `serverless.yml` through the on-call group (OD9), reviews the diff. If R
   360	   catches a missing queue change, R does not fix it (OD7): E pushes the fix, the stale approval is
   361	   dismissed, and R approves again, one more review round (Options §6). E merges.
   362	4. The deploy workflow packages, previews prod, finds no risky change, deploys with the OIDC role.
   363	5. Estimate 11–46 min (⚠️ Options §6) against ≤ 30 min: measured first in rollout.
   364	
   365	**Audit evidence.** The PR (diff, approvers, checks); run log and preview artifact, exported because
   366	retention is unverified (⚠️ G7); deploy-role CloudTrail events; all linked by commit SHA and run ID.
   367	
   368	**Cost / value.** One approver for every prod change, from the owners of the path; two approvals by
   369	the same approver when the risk stop fires. Cross-team PRs: open (OQ-A). None in non-prod.
   370	Compliance gets four-eyes enforced by GitHub. Gap: on Team the prod diff is not seen before apply.

   411	## Layer 5 — CI/CD hardening
   412	
   413	**Principle.** CI is the default production writer, so it is the main target. Short-lived,
   414	least-privilege credentials per job. Every CI dependency is pinned. Agent-written code passes the same
   415	checks as human code (S10).
   416	
   417	**On Papaya's stack**
   418	
   419	- **Credentials:** OIDC instead of keys and tokens in repository secrets, which any writer can read
   420	  (📖 R3.4.1, R3.5.3b). Org default for `GITHUB_TOKEN` set to "restricted", `permissions:` per job (📖 R3.5.3).
   421	  "Allow GitHub Actions to create and approve pull requests" off (📖 R3.3.3). Serverless License Key in
   422	  SSM, read by the deploy role (sf ≥ 4.4.19, 📖 R4.4.8). Until G1/G2 are solved, k0s and Firebase
   423	  deploys may need a stored credential in GitHub: a kubeconfig or token for k0s, a Firebase token or
   424	  service-account key for Firebase Hosting. The owner accepts this as an exception to S2 = 0 until it
   425	  is checked whether k0s and Firebase deploys can use OIDC (OD1, OD6). Conditions [design]:
   426	  - stored only as an **environment secret of `production`**, never as a repository secret. Anyone
   427	    with write access can read repository secrets (📖 R3.5.3b), which would turn the exception into
   428	    standing prod write for every engineer and their agent. Environment secrets and a deployment
   429	    branch rule limited to `main` are available on Team for private repos (📖 R3.1.2, R3.1.3), and
   430	    only the reviewed deploy workflow references the environment (layer 3);
   431	  - the deploy job runs on GitHub-hosted runners. On self-hosted runners, jobs "are not run in an
   432	    isolated container, even if they use environments", so environment secrets there must be
   433	    treated like repository secrets (📖 R3.1.5). Self-hosted runners "can be persistently
   434	    compromised by untrusted code" from anyone who can open a PR, and runner groups limit only which
   435	    repositories use them (📖 R3.5.2); in a monorepo any workflow can likely target the runner's label (⚠️ G15).
   436	    How to restrict a runner to one workflow is not researched (⚠️ G15); just-in-time runners exist
   437	    (📖 R3.5.2, not read in detail). If reaching k0s needs a self-hosted runner, that
   438	    runner is dedicated to the `production` deploy, and the residual risk is recorded;
   439	  - that environment secret is the single source of truth: no copy elsewhere (OD1);
   440	  - an owner, an expiry and rotation in the exception register;
   441	  - optionally a separate environment (e.g. `production-k0s`), limited to `main` and referenced
   442	    only by the k0s/Firebase deploy workflow, so AWS deploy jobs cannot read these secrets
   443	    [design].
   444	
   445	  Residual risk: admins can change the environment, and a deleted environment comes back without
   446	  protection (⚠️ R3.1.4); the alerts and settings comparison in layer 7 cover this. The exception
   447	  covers **CI deploy credentials only**. Runtime credentials, such as a k0s autoscaler's AWS access to
   448	  add or remove nodes, live in the cluster, not in GitHub; they follow layer 1 (no static keys, a
   449	  role attached to the machine; ⚠️ not researched for k0s, G1).
   450	- **Side paths:** Pulumi ESC, Pulumi Deployments and Serverless Dashboard providers reach AWS
   451	  (📖 R4.4.9) outside the GitHub gate (⚠️ R4.4.9); not used for prod (⚠️ R4.6 #6).
   452	- **Pinning:** workflow lockfile (`gh actions-lock`) or full SHA, enforced by the org policy "Require
   453	  actions to be pinned to a full-length commit SHA"; the lockfile does not pin reusable workflows, so
   454	  the deploy workflow lives in the same repo (📖 R3.5.5; conclusion [design]).
   455	- **CODEOWNERS** on `.github/`, `CLAUDE.md`, `CLAUDE.local.md`, `.claude/`, `.claude.json`, `.mcp.json`,
   456	  `.husky/`, `.gitmodules`, `.ripgreprc` (📖 R3.2.8; list ⚠️ R6.5 #5); CI validates the file, because
   457	  invalid lines are skipped silently (📖 R3.2.7).
   458	- **No privileged triggers with untrusted code** (`pull_request_target`, `workflow_run` + checkout,
   459	  📖 R3.5.4).
   460	- **Agents in CI:** `claude-code-action` with a custom GitHub App limited to Contents, Issues, Pull
   461	  requests (📖 R1.7.8); Anthropic workload identity federation, not a personal OAuth token (📖 R1.7.6);
   462	  `--restricted` and explicit `--tools` (D3; passing it through `claude_args` unverified, ⚠️ research
   463	  6.9.4 Q5); a managed-settings file on the runner, which also guards against mods (📖 R1.5.6; for
   464	  federation auth ⚠️); MCP set fixed by CI because `.mcp.json` loads without a prompt in `-p` runs
   465	  (📖 R1.3.5); never `environment: production` (⚠️ R3.6 #4). Hosted runners give `sudo` (📖 R3.5.1),
   466	  so with `Bash` in `--tools` the runner file is advisory (⚠️ R3.5.1, R3.6 #4).
   467	- **App-opened PRs:** a required check with a pinned source app confirms at least one approval by a
   468	  human who did not trigger the run; counting approvals is not enough, since the app's own approval
   469	  might count (⚠️ R3.3.4, R3.7 A3; 📖 R3.2.5).
   470	- **Required checks (S10):** secret scanning, dependency check, SAST (products: G4); IAM Access
   471	  Analyzer `check-no-new-access` (📖 R2.8.1); Pulumi policy packs (📖 R4.2.2).

   473	**Audit evidence.** Workflows and lockfile in git; audit-log events such as
   474	`org.update_actions_secret`, `repo.set_workflow_permission_can_approve_pr`, `repository_ruleset.update`

   483	## Layer 6 — Data protection and prompt-injection defence
   484	
   485	**Principle.** The design keeps PHI from reaching the coding agent (owner decision, research 1.9).
   486	Some paths rely on process (below), so this is a target, not a guarantee. Other customer
   487	personal data is outside that hard boundary ("not extended", research 5.8): the agent reads metadata
   488	by default and may read such data case by case under GĐ-9. Real-data reads are approved, name one
   489	tenant, are time-boxed, and need an agreement (BAA/DPA, partner contract) (GĐ-9). Everything read
   490	from outside is untrusted. Non-prod is synthetic or masked (GĐ-14).
   491	
   492	**On Papaya's stack**
   493	
   494	- **Paths to PHI** (research 1.11.4 lists 17):
   495	  - AWS stores: closed by identity, through `ProdReadMetadata` as the only standing prod role from
   496	    phase 1 (existing broad read roles are removed) and the SCP from phase 2
   497	    (layer 1); no Aurora credentials, no prod exec, no `lambda:InvokeFunction` for agent-usable roles
   498	    [design; actions ⚠️ G13];
   499	  - k0s logs/exec and GCP stores (L1, L11, L13): same principle, mechanism open (G1, G3);
   500	  - tickets/chat via MCP, pasted text, internal admin pages, prod AI traces, fixtures, CI logs (L5,
   501	    L8–L10, L12, L14): process and hygiene only;
   502	  - logs redacted at source with raw payloads in a separate log group; alerts carry IDs, not payloads [design].
   503	- **Real-data request** [design]: tenant, purpose, store, window, agreement; approved by the data owner
   504	  and an approver ≠ requester; JIT data-read role, 1 h. At night the data owner is not on call: the
   505	  on-call approver approves alone and the data owner reviews the grant the next working day. This
   506	  applies to non-PHI and PHI alike; for PHI the reader is still a human without an agent. Per-tenant scoping through session tags
   507	  (📖 R2.1.8) is unresolved, because tags come from user attributes (⚠️).
   508	  - **PHI:** a human reads in a terminal without an agent (process rule, layer 1); the agent gets a
   509	    redacted summary. This
   510	    narrows GĐ-9 because the agent stays outside PHI scope (research 1.9) and Team is not shown as
   511	    BAA-covered (⚠️ R1.11.3.4). Enterprise + BAA only for a separate environment if needed (research 1.9).
   512	  - **Non-PHI personal data:** the agent may read it within the approved request (GĐ-9). Claim
   513	    tables mix health, ID and bank data (research 1.11.4 L2), so a store that holds PHI is treated as
   514	    PHI unless the agent reads a view or extract without PHI [design].
   515	- **Partner-uploaded claim documents (A7b):** never in an agent session raw; reproduce with synthetic
   516	  documents, or de-identify first [design]. The document is PHI and an injection vector (research
   517	  1.11.4 L6).
   518	- **Injection** (these lower frequency; layers 1 and 3 limit impact): Manual by default (sandboxed Bash runs without a prompt, layer 2); the auto-mode
   519	  classifier missed 17 % of 52 real overeager actions and 5.7 % of 1,000 synthetic exfiltration
   520	  attempts (📖 R6.3.5). Broad allowed domains such as `github.com` are a documented exfiltration path
   521	  (📖 R6.3.7). The incident session has no WebFetch, likely no edit tools (layer 2), and runs outside
   522	  the repo, but its Bash can still write locally and send data out through excluded
   523	  commands (layer 2), including the SSO token cache; "no standing write, no PHI read" limits what
   524	  the token opens, except during a JIT or data-read window (layer 2 mitigations). Shared knowledge
   525	  goes in `CLAUDE.md` under review; auto memory is exempt from the protected-path rules unless `--restricted` (📖 R6.3.11, D3).
   526	- **Tenants:** one tenant per data-read grant; a session that read one tenant's data does not post to
   527	  shared places without review (⚠️ R6.5 #8, process). Logical separation in shared accounts is assumed
   528	  (GĐ-3, unconfirmed).
   529	- **Non-prod:** no prod copies (S11). A scan of non-prod stores runs at the start of phase 1 (tool:
   530	  G4); a store not yet scanned follows the L3-data rule (GĐ-14: until cleaned, non-prod follows the GĐ-9 data-read rule). Cost: until scanned, that store is
   531	  not part of the free loop.
   532	- **Local stores:** transcripts and memory hold what the agent read (research 1.11.4); set
   533	  `cleanupPeriodDays` (30 in the HIPAA sample, 📖 R5.5.4; what it deletes ⚠️).
   534	- **Cross-border (Vietnam example):** processing data collected in Vietnam on a platform abroad is a
   535	  transfer (📖 R5.4.5); agent flows, including employee names in logs and transcripts, update the
   536	  transfer impact assessment (⚠️ R5.7 #4, needs Papaya legal).
   537	
   538	**Audit evidence.** SCP/IAM text as the written access rule for sensitive data (📖 R5.4.3; ⚠️ R5.7 #5);
   539	data-read requests and the data-read role's CloudTrail; planted-injection reports (layer 8); non-prod
   540	scan results (S11).
   541	
   542	**Cost / value.** Debugging with redacted and synthetic data; a request for the rare real-data read.
   543	Compliance gets "minimum necessary" (📖 R1.11.1.8) enforced by IAM for AWS stores (fully from phase 2;
   544	actions ⚠️ G13) and by process
   545	elsewhere, and a record per exception (S9).

   549	## Layer 7 — Observability, audit, incident response and break-glass
   550	
   551	**Principle.** One tamper-evident evidence chain per prod change. One routed alert channel with a
   552	named on-call, approvers included. Unapproved change is detected (drift, reconciliation). Break-glass
   553	is approved before use, time-boxed and reconciled after.
   554	
   555	**On Papaya's stack**
   556	
   557	- **Audit stores:**
   558	  - organization CloudTrail to a log-archive account with integrity validation (📖 R2.6.2, R2.6.4,
   559	    R2.6.5); change records ≥ 6 years; raw-log retention for Papaya's compliance owner (⚠️ R5.7 #2).
   560	    Data events only on PHI buckets, prod Lambda invoke and prod SQS (cost 📖 R2.6.3; selection
   561	    ⚠️ R2.9 #5), which makes the archive
   562	    PHI-bearing (⚠️ research 1.11.4 L15). CloudTrail Lake is closed to new customers (📖 R2.6.6);
   563	  - GitHub org audit log kept 180 days, so exported (📖 R3.5.6);
   564	  - alerts on `repository_ruleset.update`, `environment.update_protection_rule`,
   565	    `environment.remove_protection_rule`, `environment.delete`, `protected_branch.policy_override`
   566	    (📖 R3.5.6, R3.1.4; selection ⚠️ R3.6 #1). UI changes to the branch policy may leave no event, and a
   567	    deleted `production` environment comes back unprotected (⚠️ R3.1.4): a job compares live settings
   568	    with an expected copy (G8);
   569	  - Aurora SQL is likely invisible to CloudTrail (⚠️ R2.7.1): Database Activity Streams, alerts on
   570	    lost-record events (📖 R2.7.2; Serverless v2 ⚠️), stream treated as PHI (⚠️ R2.7.3);
   571	  - Claude Code OTel without prompt content (layer 2).
   572	- **Change record [design]:** keyed by commit SHA or JIT request ID; links PR, approvals, run ID,
   573	  preview and CloudTrail events. Monthly reconciliation: every prod write event matches a record
   574	  approved before apply (S3). Actor: `onBehalfOf.userId` where present, else session name plus
   575	  directory lookup (📖 R2.5.1; ⚠️ R2.5.3).
   576	- **Drift [design]:** its own role, trusted only from a `drift` environment on `main`; it can read
   577	  prod secrets in state, which is noted (⚠️ R4.6 #2). Scheduled `pulumi preview --refresh
   578	  --expect-no-changes` or `pulumi refresh --preview-only` (📖 R4.1.1, R4.3.1, R4.3.2). On a DIY S3
   579	  backend, preview needs state-write permission (📖 R4.3.3); whether a refresh preview writes more
   580	  than locks is open (⚠️ R4.6 #2, G14). So either the drift role gets state write (and the same
   581	  trust care as the deploy role), or Pulumi Cloud drift detection is used (📖 R4.3.2, Pro+). The
   582	  latter runs on Pulumi Deployments, which holds credentials to prod, so it re-opens a side path that
   583	  layer 5 excludes and needs the same trust narrowing and audit (📖 R4.4.9; ⚠️ R4.6 #6). CloudFormation
   584	  drift detection, explicitly set properties only (📖 R4.4.6). No auto-remediation: it is an unreviewed
   585	  `pulumi up --refresh` (📖 R4.3.2). Each finding gets an actor and a ticket.
   586	- **On-call:** phase 1 delivers the named approver schedule (primary + backup engineers, 24/7), as
   587	  decided in framing round 1, and, because of OD7, a minimal incident-responder schedule; the
   588	  latter extends that decision. The primary approves; the backup steps in only if the primary is
   589	  unavailable (OD2). On-call approvers only approve during their shift; the fix is written by an
   590	  incident responder (OD7). Alert routing and the
   591	  rest of on-call follow in phase 2 (tools: G5); in phase 1 the responder calls the approver by phone from the published schedule.
   592	- **Break-glass = JIT fallback** [design unless marked]:
   593	
   594	  | Step | Rule |
   595	  |---|---|
   596	  | When | The PR path cannot be used: operation not in IaC and no runbook; GitHub/Actions down; pipeline broken. The approver refuses JIT for anything expressible in IaC while the pipeline works, and records why. |
   597	  | Request | Command list, scope, reason, incident link, in a channel that does not depend on GitHub. |
   598	  | Approval | On-call approver ≠ requester, before the grant (Options §4b; OD7; backup rule OD2). |
   599	  | Grant | `InfraOperator-<service>`; role session 1 h (📖 R2.1.4). Deleting the assignment likely stops only new sessions (⚠️ R2.4.2, R2.9 #3), so the real window can approach 2 h; ending the portal session does not end role sessions (📖 R2.4.3). An immediate stop needs the revocation SCP, which must keep the user blocked for at least 12 h (📖 R2.4.4). |
   600	  | Execution | The grant goes to the requester (the incident responder), who types the commands; no agent in that terminal (D2). D2 said the on-call person runs them; OD7 moves that to the responder, since on-call engineers only approve. |
   601	  | After | A job compares CloudTrail writes in the window with the list; a codify PR within a fixed deadline (as soon as GitHub is back); drift detection until it merges. |
   602	  | Identity Center outage | Emergency SAML federation to roles, built and tested in advance (📖 R2.1.11; ⚠️ R2.9 #2); no user mapped until an approved activation, which is alerted. |
   603	
   604	  **Example request (illustrative command ⚠️):** "INC-123, ECS service `claims-api`, Actions outage. Run
   605	  `aws ecs update-service --cluster <prod-cluster> --service <svc> --force-new-deployment`. Scope
   606	  `InfraOperator-claims`, 1 h."
   607	
   608	  **Metrics** (Options §7; starting thresholds ⚠️ to calibrate): JIT used where a PR was possible
   609	  (review at 1); writes outside the list (review at 1); codify PRs late (review at 1); grants per
   610	  month and share of incidents needing non-IaC operations (review above about 25 %, a value new in
   611	  this draft). On a breach,
   612	  make the PR lane faster or add a runbook; do not widen JIT.
   613	- **Roadmap:** runbooks for repeated non-IaC operations, if SSM Automation's approval step meets three
   614	  conditions (Options §2; outside 02-research, G6); break-glass from an environment without the agent
   615	  (D2, ⚠️).
   616	
   617	**Audit evidence.** Validated CloudTrail; exported GitHub audit log; change records and monthly
   618	reconciliation (S3, S8 ≤ 30 min); JIT requests, reconciliations, codify PRs; drift tickets; on-call
   619	schedule and approval waits (S7); monthly report of approvals by on-call group members outside
   620	their shift and domain (OD9).
   621	
   622	**Cost / value.** The incident lane is slower than direct access (estimated 11–46 vs 2–20 min,
   623	Options §6), and JIT needs a written command list. Compliance gets approval before apply even in
   624	incidents, plus detection.

   628	## Layer 8 — Governance and rollout
   629	
   630	**Principle.** Every control has an owner, a metric and a review date. Policies are files changed by
   631	PR. Access is never removed before its replacement works. Controls are tested against realistic
   632	attacks.
   633	
   634	**On Papaya's stack**
   635	
   636	- **Owners:** DevSecOps (framework, managed settings, catalogue, metrics); a platform team or named
   637	  engineers (deploy workflows, rulesets, pipelines; whether Papaya has a platform team is unknown ⚠️); Compliance (evidence review, supplier register, Statement of
   638	  Applicability); engineering leads (decide CODEOWNERS content; changes to it are approved by the L3 owner team); engineering management (on-call schedule).
   639	- **Policy as code:** managed settings, catalogue, SCPs, trust policies, CODEOWNERS and workflows are
   640	  files under CODEOWNERS; GitHub settings that are not files are compared with an expected copy
   641	  (⚠️ R3.6 #1; G8). Few GitHub admins, reviewed quarterly.
   642	- **Metrics:** S1–S11 exactly as in framing §5; this framework adds the JIT metrics (layer 7) and the
   643	  prompt metrics (layer 2). S2 and S5 have caveats (OD1; layer 2).
   644	- **Rollout** (≈ 90 days, GĐ-12 unconfirmed). Framing Q8 (round 1): (1) remove long-lived CI credentials,
   645	  (2) narrow standing prod access, (3) MCP/plugin catalogue; the on-call approver list before or with (2).
