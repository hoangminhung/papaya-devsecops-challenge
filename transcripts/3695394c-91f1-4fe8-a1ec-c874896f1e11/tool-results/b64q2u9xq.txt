### 5.7 What this means for Papaya (inferences — to be used in the design)

1. **The "named human" rule is policy, not a quoted requirement (⚠️).** Neither the HIPAA text
   (5.2.10) nor, as far as I recall, ISO Annex A (5.1.8) literally requires "a named human approves
   every prod change". Both require unique identity, audit controls, integrity and records. So the
   design should present the Compliance rule as Papaya's chosen way to meet 8.32 / 5.3 and
   164.312(a)(2)(i) / (b) / (c). The record chain in 5.6 is what proves it to an auditor.
2. **Retention value: at least 6 years for approval and change records.** 164.316(b)(2)(i)
   requires 6-year retention of required documentation (5.2.9). Whether raw audit logs themselves
   must be kept 6 years is interpretation (⚠️). Topic 2 already plans an organization trail to a
   log-archive account with an explicit retention decision (2.9); this sets the value for approval
   and change records. **New item:** the GitHub org audit log keeps 180 days (3.5.6), so the GitHub
   side needs its own export.
3. **Emergency access (⚠️ mapping).** HIPAA requires a documented procedure for obtaining ePHI
   during an emergency (5.2.6). It does not speak about production changes. A break-glass path to
   prod is one common way to support it, and the agreed "incident approvals within 15 min, 24/7"
   is Papaya's policy for emergency changes. Either way, the emergency path must leave the same
   evidence as the normal one.
4. **Cross-border transfer in the Vietnam example (⚠️ inference).** A Claude session is a
   platform outside Vietnam (5.4.5). If it processed personal data collected in Vietnam, that would
   be a cross-border transfer. If Papaya already moves Vietnamese personal data to foreign cloud,
   it already holds (or owes) a transfer impact assessment, and agent data flows would be an
   **update** to it (Art. 20(3), Art. 22), not a new duty. Two cautions:
   - "Infrastructure metadata" is not automatically free of personal data: CloudTrail events, git
     history and session transcripts contain **employee** names and emails. Two exemptions concern
     employee data: Law Art. 20(6)(b) (storing own employees' data on cloud) and Decree Art.
     17(3)(d) (cross-border HR management). Whether sending employee identities in logs to a model
     provider falls under either is ⚠️.
   - Extending the owner's PHI decision (1.9) from PHI to **all customer personal data** (including
     basic data such as ID numbers, 5.4.3) is a scope change. It is a question for the owner, not a
     settled decision (5.8). **Owner decided 2026-11-08: not extended (5.8).**
5. **Sensitive data needs written access rules** (Decree Art. 4(2), 5.4.3). The Topic 2 design of no
   data-plane access for agent identities (2.9; PHI paths in 1.11.4) is the matching control, and its SCP/IAM text
   is the written rule.
6. **The NPRM shows where the requirements are heading** (5.3.2): MFA on all relevant ePHI systems
   and for privilege changes, real-time monitoring and recording of activity, yearly vendor
   verification and an asset inventory. MFA through Identity Center and a supplier register are
   cheap. Real-time monitoring of **all** activity is not: CloudTrail data events cover only the RDS Data
   API, not SQL sent over database connections (⚠️ inference, 2.7.1). The design should label these as forward-looking, not as current requirements.
7. **Supplier register entries are concrete** (5.5.1–5.5.3): Anthropic and GitHub certificates are
   self-service for org owners or via the Trust Portal. The GCP BAA covers Agent Platform
   generative AI but **not Firebase**, so Firebase Hosting must stay PHI-free (consistent with a
   static front end, ⚠️ not verified for Papaya).
8. **Team-plan limits remain visible.** Tenant Restrictions (5.5.6) is available to Enterprise plans
   and Console organizations, so a Team org cannot use it to block claude.ai sign-ins to other
   organizations (⚠️ inference). Stopping use of personal accounts on corporate code then depends
   on network and device controls (MDM is unknown, 1.9). `settings-hipaa.json` (5.5.4) is still
   a good **template** for Team managed settings, key by key, subject to Topic 1's plan notes. The
   README says it applies "whether or not the HIPAA configuration is in effect", and that the same
   keys must also go into server-managed settings if the org uses them (5.5.4).
9. **Risk-register input from the README** (5.5.5, 5.5.5b): the laptops' managed file does not
   reach the Claude Code GitHub Action, so CI needs its own runner-side file (1.7.10 b), which can
   be tampered with on hosted runners (3.5.1). Injected instructions are limited only by the
   sandbox network allowlist, and in auto mode a classifier, not a person, approves actions.
