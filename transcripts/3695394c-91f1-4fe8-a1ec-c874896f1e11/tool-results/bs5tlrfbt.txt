    29	## 1. The decision in one page
    30	
    31	Engineering and Compliance disagree only about **writes to production**; reads of metadata and all
    32	of non-prod are outside Compliance's sentence (framing §3.1). Real customer data is layer 6.
    33	
    34	**Chosen approach "A + D2'"** (Options §9, owner decision 2026-11-09):
    35	
    36	1. **Default path:** every prod change is a pull request, approved by a named human who is not the
    37	   author, applied by CI. Incidents included ("IaC first").
    38	2. **Fallback (break-glass):** only when the PR path cannot be used, a human gets an approved grant
    39	   with a 1-hour role session (effective window up to about 2 h, ⚠️ R2.9 #3) and runs an approved command list in a terminal without an agent (layer 7) [design].
    40	3. **Nothing standing:** no human or agent holds standing prod write; no long-lived credentials.
    41	
    42	| Engineering gets | Compliance gets |
    43	|---|---|
    44	| A free loop in non-prod: read, change, deploy without approval (non-prod is synthetic or masked, GĐ-14; stores not yet scanned are excluded, layer 6). | Every prod change approved **before** apply by a named human ≠ author (GĐ-8, GĐ-11), enforced in GitHub and AWS IAM, outside the agent (limits below). |
    45	| Read-only prod metadata for the agent. | No standing prod write (S1), no long-lived CI keys (S2, with an owner-approved exception for k0s/Firebase deploy credentials, OD1, OD6; storage conditions [design], layer 5). |
    46	| Self-service PRs, one approval, same-day ship (S4). | One evidence chain per change; approval and change records ≥ 6 years (📖 R5.2.9; applied to change records ⚠️ R5.7 #2). |
    47	| Incident lane: approval wait ≤ 15 min, 24/7 (S7). Decision-to-apply target ≤ 30 min (Options §9); current estimate 11–46 min ⚠️, measured first in rollout. | Agent-side controls as a second layer, not the control of record. |
    48	
    49	**Where the design falls short, stated openly:**
    50	
    51	- **The fallback meets the approval rule only partly** (approves a command list, not an applied
    52	  change); accepted by the owner (Options §9 Q2). It is a second, process-controlled path, while the
    53	  framing asked for one technically enforced path (framing §3.3, Options §7). It stays narrow only
    54	  if most incidents are expressible in IaC (unknown, Options §8); layer 7 measures this.
    55	- **On GitHub Team nobody sees the prod diff before apply** (⚠️ R4.6 #1; Team assumed, GĐ-5).
    56	  Risky prod diffs stop the deploy until an owner of the stack approves the prod preview [design].
    57	- **Admins can edit the gate**; logged, not prevented (logging 📖 R3.2.2; ability to edit ⚠️ R3.2.2,
    58	  R3.6 #1). An admin's agent has
    59	  the same power, because the agent uses its engineer's GitHub login (⚠️ R6.5 #10).
    60	- **Some rules are process, not technology:** see "Process rules" in layer 1. The owner's rule
    61	  "the PR approver is always an engineer, never an agent" (OD5) is absolute as policy, but on
    62	  laptops it is enforced by policy and training, not by a technical control: an agent could approve
    63	  through its engineer's login, and no detection was found.
    64	- **Incident approvers vs domain review:** code-owner review means an approver must own the file,
    65	  at L2 as at L3. So that one on-call primary can approve any deployable path at 2 a.m., the on-call approver
    66	  group co-owns every deployable path (owner decision OD9, layer 3). The cost: GitHub accepts an
    67	  approval from any listed owner (📖 R3.2.7), so on normal days that group could approve another
    68	  domain's PR. Domain review on normal days becomes a process rule with a monthly check, not a
    69	  technical control. Because on-call approvers only
    70	  approve (OD7), a night incident needs two people awake: the incident responder and the on-call
    71	  approver (the backup only replaces an unavailable primary).
    72	- **One approver for high-risk changes.** L3 changes (IAM, stateful deletes, workflow files) get one
    73	  approver, like L2, but the path is owned by the L3 owner team (or by the stack's owners for L3
    74	  content in domain files, OD8), and risky prod diffs stop for a look at
    75	  the prod preview (OD2, OD8, layer 3). A single reviewer can miss things; this is the owner's trade-off
    76	  for speed.
    77	- **HIPAA applicability is a legal question** (⚠️ R1.11.1.11); the design treats Papaya as a
    78	  business associate, as the brief implies.
    79	
    80	**Cross-cutting rules** (owner's balance principle, research 6.8):
    81	
    82	1. **The boundary is IAM and the CI gate.** Server-managed settings are "a client-side control, not
    83	   a security boundary" (📖 R1.1.7); local admins can edit endpoint files (📖 R1.1.8).
    84	2. **Assume prompt injection succeeds:** neither OWASP nor NIST knows a full prevention (📖 R6.1.1, R6.1.2).
    85	3. **Friction where damage is large, none where it is small**, measured, with a time-boxed escape.
    86	4. **Evidence by construction:** the path produces the records.
    87	
    88	### Roles
    89	
    90	| Role | Rule |
    91	|---|---|
    92	| Author (engineer + their agent) | Never approves own change; GitHub blocks PR authors from approving (📖 R3.3.1). |
    93	| Approver | Always an engineer, never an agent (owner rule, OD5). Named in CODEOWNERS; ≠ author, ≠ last pusher (📖 R3.2.3); for an app-opened PR, ≠ the person who triggered it (⚠️ R3.3.4, layer 5). |
    94	| Incident responder | Engineer who diagnoses and writes the fix or the JIT request. Never the on-call approver of the same shift (OD7). |
    95	| On-call approver | Engineer on the on-call schedule, primary + backup, 24/7; wait ≤ 15 min (S7). While on call they only approve: they write no fix and file no JIT request, so the approver is always distinct from the author (OD7). The primary approves; the backup replaces an unavailable primary (OD2). No platform-team membership is required; all engineers follow one agreed approval procedure (OD2). |
    96	| Data owner [design] | Named per tenant; co-approves real-data reads, or reviews a night-time read the next working day (layer 6). |
    97	| Control owner | DevSecOps (1–2 people, GĐ-1); owns policies and metrics; not the only approver. |
    98	| L3 owner team | Owns the process-defining L3 paths and the SCP stack (layer 3); composition open (G17). |

   102	## Layer 1 — Identity and access
   103	
   104	**Principle.** Every action traces to one named human. Nobody holds standing prod write: prod is
   105	written by the pipeline role, or in the fallback by an approved, time-boxed grant. Prod reads default
   106	to metadata. No long-lived credentials. Prod and non-prod are separate boundaries.
   107	
   108	**On Papaya's stack**
   109	
   110	- **The engineer's access is the agent's access.** The agent uses the engineer's AWS SSO cache, and
   111	  one portal session reaches every role assigned to that engineer (📖 R2.2.1, R2.2.2; token-reuse
   112	  detail ⚠️ R2.2.2). A separate
   113	  "agent" permission set does not separate them (⚠️ R2.9 #1). The control is what the **engineer**
   114	  holds.
   115	- **Process rules** that follow from this:
   116	  - the JIT terminal runs no agent, though the grant is reachable from the same laptop (owner
   117	    accepted as a process control, D2);
   118	  - the incident-analysis session is meant to use only read-only roles (D2; `--restricted` per D3,
   119	    research 6.9.4 Q2);
   120	  - the real-data terminal runs no agent when the store holds PHI [design], same weakness as D2;
   121	  - an agent never approves PRs: an owner rule (OD5), enforced on laptops by policy and training.
   122	    GitHub blocks self-approval only. The auto-mode default block list
   123	    excerpt read names "approving Claude's own pull request" (📖 R6.3.3); whether approving
   124	    someone else's PR is blocked is unverified (⚠️), and the list
   125	    applies only in auto mode. No detection was found (⚠️; `actor_is_agent` in the audit log has no
   126	    documented meaning, R3.5.6).
   127	- **IAM Identity Center permission sets** (📖 R2.1.1) [design names]:
   128	  - `ProdReadMetadata`: metrics, redacted log groups, configuration; no data-plane read on claim
   129	    stores; 1 h session, the minimum (📖 R2.1.4). Until a service's logs are redacted at source
   130	    (layer 6), it gets that service's metrics only. Lambda configuration can hold secrets resolved by
   131	    Serverless in plain text (⚠️ R4.4.7), so configuration reads are allowed per service only after
   132	    its secrets move to runtime resolution (⚠️ R4.6 #7). Cost: until then the agent reads
   133	    timeout/memory from the IaC code;
   134	  - `NonProdDeveloper`: broad, non-prod accounts only;
   135	  - `InfraOperator-<service>`: assigned only by the JIT flow (layer 7), via a partner product, the
   136	    TEAM sample (📖 R2.4.1, R2.4.1b) or a small home-built flow (⚠️ R2.4.2) on the documented APIs
   137	    `CreateAccountAssignment` / `DeleteAccountAssignment` (📖 R2.4.2);
   138	  - no standing prod-write permission set.
   139	- **SCPs on the prod OU** [design] (SCPs cap member-account principals, 📖 R2.3.1, R2.3.2):
   140	  - deny data-plane reads on claim stores except application roles and the approved data-read role,
   141	    by `aws:PrincipalArn` (📖 R2.3.8; pattern ⚠️ R2.9 #4). Actions, e.g. `s3:GetObject`,
   142	    `sqs:ReceiveMessage`, `states:GetExecutionHistory`, are incomplete and unchecked (⚠️ G13);
   143	  - deny `lambda:UpdateFunctionCode` / `lambda:UpdateFunctionConfiguration` (⚠️ R4.6 #3) except
   144	    CloudFormation `deploymentRole`s, the Pulumi prod deploy role (if Pulumi manages Lambdas) and the
   145	    JIT roles. This closes `serverless deploy function`, which changes config outside CloudFormation
   146	    (📖 R4.4.4), and needs `deploymentRole` set on every Serverless stack (key 📖 R4.4.5; need ⚠️ R4.6 #3);
   147	  - a pre-deployed revocation Deny on `identitystore:UserId` (📖 R2.4.4); protect the org trail (📖 R2.6.2).
   148	  - Limits: 10 SCPs per target, 10,240 characters; no SCP applies to the management account
   149	    (📖 R2.3.2, R2.3.4), so whatever deploys SCPs there is the most sensitive role (L3 path, held by the L3 owner team only, not co-owned by the on-call group; part of AR 2).
   150	- **Sessions/MFA:** portal session length set on purpose; an IdP session can extend it silently
   151	  (📖 R2.1.5, R2.1.6). MFA lives in the external IdP if one is used (📖 R2.1.7).
   152	- **CI → AWS:** GitHub OIDC, no stored keys (📖 R3.4.1). The prod role trusts only the `production`
   153	  environment of the monorepo, in its `sub` format (📖 R3.4.3, R3.4.4; immutable format assumed,
   154	  ⚠️ R3.7 A2), ideally customised with the deploy workflow's `job_workflow_ref` (📖 R3.4.5; on Team ⚠️ G10).
   155	- **CI → GCP:** Workload Identity Federation restricted to Papaya's GitHub organization, which Google
   156	  requires (📖 R3.4.5b).
   157	- **k0s, GCP and Firebase for humans:** same principles; mechanisms not researched (G1–G3). Today
   158	  k0s is reached with kubeconfigs, no SSO (GĐ-4, unconfirmed). Interim: no admin kubeconfig and no GCP
   159	  owner role on laptops; prod deploys only from CI. Firebase is not on the GCP BAA list (📖 R5.5.3), so
   160	  Firebase Hosting must hold no PHI (⚠️ R5.7 #7).
   161	
   162	**Audit evidence.** Identity Center assignment export (S1); CloudTrail `CreateAccountAssignment` /
   163	`DeleteAccountAssignment` per grant (📖 R2.4.2), linked to its approval by request ID [design]; SCPs
   164	and trust policies as Pulumi code; IAM Access Analyzer `check-no-new-access` on policy PRs
   165	(📖 R2.8.1; from phase 2); quarterly access review of permission sets and GitHub admins.
   166	
   167	**Cost / value.** Engineers lose standing prod write and keep a free non-prod loop. Prod reads stay
   168	fast for metrics and metadata, but shrink during the transition: because the engineer's access is the
   169	agent's access, from phase 1 the engineer too loses raw logs and configuration of services not yet
   170	redacted or moved to runtime secrets. Configuration values come from the IaC code instead (layer 1
   171	above); raw logs that may hold customer data need an L3-data grant. The data owner is not on the
   172	on-call schedule, so at night the grant is approved by the on-call approver alone and the data owner
   173	reviews it the next working day [design]; the wait still counts against S7. This is
   174	the largest cost of the first months. Compliance gets least privilege that is enforced.

   178	## Layer 2 — Agent runtime controls
   179	
   180	**Principle.** Agent-side controls are hygiene, not the boundary. They are central, versioned in git
   181	and the same for everyone. Defaults are safe; overrides are measured. The session that reads
   182	untrusted content holds as little power as possible (📖 R6.1.2).
   183	
   184	**On Papaya's stack**
   185	
   186	- **Delivery:** server-managed settings (available on Team, 📖 R1.1.5) for all laptops. With MDM, also
   187	  an endpoint file; by default one managed source supplies most keys, so the two must carry the same
   188	  keys or use `managedSourcesBehavior: "merge"` (📖 R1.1.3, R1.1.4). MDM is unknown; both are prepared.
   189	- **Baseline** (template: Anthropic's `settings-hipaa.json`, 📖 R5.5.4). All keys 📖 at the row cited. Only the phase-1 subset in layer 8 ships first; the other keys (sandbox, `allowManagedHooksOnly`, credential denies, `allowManagedPermissionRulesOnly`, `allowedProviders`, `forceLoginOrgUUID`, the `ask` rule for WebFetch, and the other deny rules) arrive in phase 2 (OD4):
   190	
   191	  | Key | Value and reason |
   192	  |---|---|
   193	  | `permissions.defaultMode` | `default` (Manual). A default, not a lock: users can switch to auto; VS Code remembers the last pick (D1, R6.9.3). |
   194	  | `permissions.allow` | Read-only commands Papaya uses, to cut prompts (R6.9.3). It contains no command listed in `sandbox.excludedCommands` (`aws`, `pulumi`, `serverless`): an allowed excluded command would run outside the sandbox, with `~/.aws` and the network, without a prompt (⚠️ inference from R1.2.6, R1.6.4) [design]. Cost: a prompt for every `aws` read. |
   195	  | `allowManagedPermissionRulesOnly` | `true`, one rule set (D1, research 6.9.4 Q4; R1.2.5). Cost: project and user rules are ignored, so the managed set must carry every deny/ask rule projects need; prompts likely rise (⚠️ research 6.9.4 Q4). |
   196	  | `permissions.disableBypassPermissionsMode` | `"disable"`: removes bypass mode (P3a; R1.2.2). Auto mode, where a classifier approves instead of a person, stays available (D1) and is measured through `permission_mode`. |
   197	  | `permissions.deny` / `ask` | Deny credential paths (R5.5.4; `Read(...)` syntax ⚠️ R1.8 #5). Ask for `WebFetch`, which the sandbox domain list does not limit (R1.6.2); cost: a prompt per fetch. The HIPAA template denies WebFetch (R5.5.4); "ask" is a deliberate deviation so that documentation lookups still work. |
   198	  | `requiredMinimumVersion` | ≥ 2.1.285 for `allowedProviders` (R1.1.15), which also covers `--restricted` (2.1.248, R6.9.1b) and the plugin-pin fix (2.1.179, R6.2.7); ≥ 2.1.295 if any managed hook uses `onFailure: "block"` (R1.5.2); and ≥ the latest fixed advisory at rollout (R6.3.9). It does not end running sessions and fails open on a bad value (R1.1.13). |
   199	  | `allowedProviders` + `forceLoginOrgUUID` | `["anthropic"]` + Papaya's org; closes most bypasses on **endpoint-managed** machines (R1.1.15). `forceLoginOrgUUID` checks claude.ai sign-ins only, not Claude Console sign-ins (R5.5.5); with it set, sessions on `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` or `apiKeyHelper` are refused (R1.11.3.11). |
   200	  | `allowManagedHooksOnly` | `true` (R1.5.4). |
   201	  | sandbox | `sandbox.enabled`, `failIfUnavailable`, `allowUnsandboxedCommands: false`, narrow `network.allowedDomains` locked by `network.allowManagedDomainsOnly`; `credentials` / `filesystem.denyRead` on `~/.aws`, which the sandbox can otherwise read (R1.6.3, R1.6.4). |
   202	  | `sandbox.autoAllowBashIfSandboxed` | Agent's choice, to confirm (OQ-C) [design]: left at its default `true`. This widens D1's "Manual + read-only allowlist": every sandboxed command, writes in the working directory and calls to allowed domains included, runs without a prompt. Detail: sandboxed Bash runs without a prompt, so in Manual mode prompts are for edits, unsandboxed commands and fetches, not every command (R5.5.5b). A deliberate choice: the sandbox (no `~/.aws`, allowlisted network) is the control for those commands. The HIPAA README says to set `false` if policy needs a person to approve each command (R5.5.5b); cost of `false`: a prompt per command. |
   203	  | MCP, plugins | Layer 4. |
   204	  | OTel | Exporter on, content flags `0` (R1.1.20, R5.5.4). |
   205	
   206	- **Trade-off on AWS credentials [design].** With `~/.aws` hidden from the sandbox, the plan is to
   207	  list `aws`, `pulumi` and `serverless` in `sandbox.excludedCommands`. Excluded commands run "with
   208	  full access" (📖 R1.6.4), which likely includes the network (⚠️ inference). How the list matches
   209	  commands (prefix or text, and chained commands) is not researched (⚠️). This is worse than an
   210	  egress channel: `pulumi preview` runs the Pulumi program and `serverless` loads its config and
   211	  plugins, all code in the repo that the agent can edit, so excluding them lets repo code run
   212	  outside the sandbox with network access and with `~/.aws` readable (⚠️ inference). For these
   213	  commands the sandbox gives no protection. And an injected `aws` command could send out the SSO
   214	  token cache itself. That token likely opens every role assigned to the engineer for the rest of the
   215	  portal session (📖 R2.1.5; token reuse ⚠️ R2.2.2), probably including JIT or data-read grants added
   216	  later in that session (⚠️ inference). Mitigations [design]: a short portal session (📖 R2.1.5); end
   217	  the existing portal session and sign in fresh **before** a JIT or data-read grant is created
   218	  (whether ending a session invalidates a token already stolen is unverified ⚠️; ending it does not
   219	  end role sessions, 📖 R2.4.3); an SCP that denies writes to resources outside Papaya's organization using
   220	  `aws:ResourceOrgID` (key 📖 R2.3.8), on every OU, since the token can be stolen from a non-prod
   221	  session; legitimate writes to outside resources need exceptions (⚠️ not inventoried). That SCP only stops Papaya's own credentials writing to a
   222	  foreign bucket; it does not stop a command that sends the token to a non-AWS endpoint or uses the
   223	  attacker's credentials (⚠️ inference). Prefer running `pulumi` and `serverless` against real
   224	  accounts only in CI; on laptops keep them to non-prod roles, and move them into the phase-3
   225	  container. Residual risk: token theft during a session. It is accepted
   226	  because the engineer holds no **standing** prod write and no **standing** PHI read; during a JIT
   227	  or data-read window the protection is the process rule in layer 1 (D2). Stronger option, phase 3:
   228	  a separate OS user or container for prod-reading sessions
   229	  (⚠️ R6.5 #2).
   230	- **Session types:**
   231	
   232	  | Session | Identity | Flags | Enforcement |
   233	  |---|---|---|---|
   234	  | Daily development (laptop) | non-prod roles + `ProdReadMetadata` | baseline | Auto mode by choice (D1); `--restricted` recommended (D3). |
   235	  | Incident analysis (laptop) | meant to be `ProdReadMetadata` only | `--restricted --tools "Bash,Read,Grep,Glob"`, started in an empty scratch directory, not the repo [design] | Process rule (D3, research 6.9.4 Q1–Q2). No WebFetch, and file tools confined to the working directory (📖 R6.9.1b); Edit/Write are excluded only if `--tools` acts as an exclusive list (⚠️ unverified), but Bash can still write in its working directory (📖 R1.6.3) and call any role in the cache. |
   236	  | CI agent (hosted runner) | own GitHub App token; never `production` | `--restricted`, explicit `--tools`; all rules in a managed-settings file on the runner | Workflow file under CODEOWNERS (D3, research 6.9.4 Q5). The file is advisory if `Bash` is in `--tools` (layer 5). |
   237	  | JIT terminal | JIT grant | no agent | Process rule (D2). |
   238	  | Auto-mode environment (phase 3) | non-prod only | auto encouraged | D1 option (c). |
   239	
   240	- **Phase-1 interim posture:** the sandbox and credential denies arrive in phase 2 (OD4), so for
   241	  the first 30–60 days `~/.aws` is readable and the network is open to every Bash command; in auto
   242	  mode the classifier is the only gate. Impact is bounded once standing prod write is removed at the
   243	  end of phase 1 (layer 1); before that, today's exposure continues, and token theft is easier in this window.
   244	- **Hard limits:** Bash rules are not a boundary (📖 R1.2.6); hooks fail open unless
   245	  `"onFailure": "block"` (📖 R1.5.2); `--restricted` cannot be forced by a setting (📖 R6.9.1), and a `PATH` wrapper on laptops can be bypassed (⚠️ R6.9.1c);
   246	  on laptops **without MDM**, a different login, an API key or a `CLAUDE_CODE_USE_*` variable skips
   247	  server-managed settings, `allowedProviders` included (📖 R1.1.7; ⚠️ R1.8 #3, G11). So S5's
   248	  "nobody can turn off all prompts unnoticed" is likely unreachable without MDM (⚠️).
   249	- **Auto memory:** engineers review it and delete it after a suspicious session; residual risk with a
   250	  named owner (D3).
   251	- **Fallback:** switch to `disableAutoMode` (📖 R1.2.2) if the planted-injection test steers auto mode, a serious
   252	  advisory appears, or an audit finds auto mode touched a protected scope (D1).
   253	
   254	**Audit evidence.** Managed settings as an expected copy in git with PR approvals. The live copy is
   255	edited in the Claude admin console by Owners / Primary Owners (📖 R1.1.5), not by PR, and Team audit
   256	events for settings changes are unconfirmed (⚠️ R1.1.12). `/status` shows which managed source
   257	applies (📖 R1.1.18), and likely not the key values (⚠️), so it cannot detect a console edit; until a way to read the
   258	live values is found (G18), an Owner exports the console settings monthly and diffs them with git

   269	## Layer 3 — Change workflow by risk level
   270	
   271	**Principle.** The level is set by the damage a change can do. One default path above non-prod: a
   272	reviewed PR applied by the pipeline, with the JIT fallback (layer 7) as the only other write path.
   273	The approver reviews the code change that will be applied. Every prod change needs two people, and
   274	no more by default: one who makes it and one who approves it (until OQ-A is answered, the
   275	cross-team process rule below can need more); the on-call backup only replaces an
   276	unavailable primary (OD2). Higher risk narrows **who** may approve (the owners of that path), not how
   277	many. Separately, any prod diff that looks risky stops the deploy, whatever its level; that adds a
   278	second approval by an owner of the same stack, which keeps it to two people (OD8). Agent's reading
   279	of OD8 [design], to confirm: the original author opens the approval PR and the first approver
   280	approves it; if the first approver is unavailable, another owner of the stack approves, which makes
   281	three people (open question OQ-B). Two edge cases: GitHub accepts one on-call group member for
   282	files of several owner teams (OD9, 📖 R3.2.7), so "an approval from each domain team" on a
   283	cross-team PR is a process rule only, and an interim default of the agent [design] until OQ-A; whether such PRs should be split is an open question for the
   284	owner (OQ-A, below). A real-data read is not a change and has its own rule, L3-data. Incidents use the same
   285	path with faster people, not fewer security checks.
   286	
   287	| Level | What | Examples | Approval | Path |
   288	|---|---|---|---|---|
   289	| **L0** | Read: non-prod anything; prod metadata | metrics, redacted logs | none | read-only identity |
   290	| **L1** | Change in non-prod | deploy a branch to dev; `pulumi preview` on non-prod (needs state-write permission on a DIY S3 backend, 📖 R4.3.3) | author only | non-prod roles or PR pipeline |
   291	| **L2** | Routine prod change in code | Lambda timeout/memory, ECS desired count, release | 1 code owner ≠ author, ≠ last pusher | PR → `main` → deploy workflow |
   292	| **L3** | High-risk prod change | IAM/SCP; replace/delete of stateful resources; network; `.github/**`, CODEOWNERS, `CLAUDE.md`, `CLAUDE.local.md`, `.claude/**`, `.claude.json`, `.mcp.json`, `.husky/`, `.gitmodules`, `.ripgreprc`, plugin/MCP catalogue and the rest of the canonical list in layer 5; advisory policy finding | 1 code owner ≠ author, ≠ last pusher. L3 paths (workflow and agent-config files, catalogue, stacks that hold only IAM/SCP): the L3 owner team. L3 content inside a domain file (an IAM statement in `serverless.yml`, a stateful delete): the stack's owner, then the risk stop (OD8). In incidents: the on-call approver for deployable paths (OD9); paths that define the process (CODEOWNERS, agent config, catalogue, workflows) wait for the L3 owner team | same path; for IaC changes the risk stop also applies; workflow and agent-config files have no prod diff |
   293	| **L3-JIT** | Break-glass | ECS force-redeploy while Actions is down | on-call approver ≠ requester (Options §4b); incidents only, as the owner accepted it (Options §9 Q2); agent's reading of OD9: the on-call approver counts as owner of the service in the request [design] | layer 7 |
   294	| **L3-data** | Real customer data read | one tenant's failed claim record | an approver ≠ requester and an agreement (GĐ-9); data-owner co-approval [design], beyond GĐ-9; at night, see layer 6 | layer 6 |
   295	
   296	`CLAUDE.md` and the other agent configuration files are L3, because they define the workflow for
   297	the whole team (OD3). With code-owner review on, every PR, L2 included, needs an approval from an
   298	owner of the files it touches (📖 R3.2.3, R3.2.7; per-file behaviour ⚠️ not a separate research row).
   299	What differs at L3 is **which team** owns the path: L3 paths are owned in CODEOWNERS by a designated
   300	L3 owner team (deployable L3 paths also by the on-call group, OD9), L2 paths by their domain team; and IaC changes at L3 meet the
   301	risk stop. Most IAM, network and stateful changes sit inside domain files, so they are approved by
   302	the stack's owners, not the L3 team (OD8); automated checks make up for this: IAM Access Analyzer
   303	`check-no-new-access` (📖 R2.8.1) and the Pulumi policy pack (📖 R4.2.2), both from phase 2 (layer 5). Cost: changes to `CLAUDE.md` (where D3 puts shared knowledge) need the L3 owner team, not
   304	the domain team that edits it most.
   305	
   306	**On Papaya's stack**
   307	
   308	- **Gate = merge to `main`.** On Team, environment reviewers do not exist for private repos
   309	  (📖 R3.1.2). Ruleset on `main`: PR required, 1 approval, code-owner review, dismiss stale approvals,
   310	  approval by someone other than the last pusher, required checks from a pinned source app, no force
   311	  push, empty bypass list (📖 R3.2.2, R3.2.3, R3.2.5). Branch up to date before merge, since there is
   312	  no merge queue (⚠️ R4.6 #1; whether updating drops approvals is open, Options §8).
   313	- **L3 approvals [design]:** CODEOWNERS plus code-owner review only, no path-based required
   314	  reviewers rule. That rule (📖 R3.2.4) asks for approvals from specific teams, which the on-call
   315	  group would not satisfy at night, and how it combines several teams is not researched (⚠️), so it
   316	  would break OD9 or add a third person. GitHub stops the author from approving (📖 R3.3.1). A required check with a pinned source app (📖 R3.2.5), set by a dedicated GitHub App that reacts to review events and is the pinned source [design], adds what
   317	  the rules cannot: for app-opened PRs it excludes the person who triggered the agent, and it counts
   318	  only human approvals, since an app's approval might count (⚠️ R3.3.4, R3.7 A3). A workflow
   319	  instead of an app is weaker: pinning the source to GitHub Actions likely lets any workflow set a
   320	  check of the same name, and the trigger that runs on review events from trusted code is not
   321	  researched (⚠️ G19).
   322	- **Who approves at night (OD9):** a fixed GitHub team, the on-call approvers, is listed as
   323	  co-owner on every deployable path in CODEOWNERS (infrastructure and service code), next to the
   324	  domain team. Agent's reading of OD9, to confirm: the group does **not** co-own the paths that
   325	  define the process (`.github/**`, CODEOWNERS, `CLAUDE.md` and agent config, catalogue); those stay
   326	  with the L3 owner team only. If a broken workflow blocks a night fix, the pipeline counts as
   327	  unavailable and the JIT fallback applies (layer 7). One primary and one backup from that team are on call. Technically any member can approve any
   328	  path; by rule the primary approves and the backup only if the primary is unavailable (OD2).
   329	  Membership is fixed, not changed per shift [design]. GitHub team membership is set in organization
   330	  settings, not by a PR; managing it as code (e.g. with Pulumi's GitHub provider) and the audit
   331	  event for a membership change are not researched (⚠️ G16). Meanwhile the layer-7 settings
   332	  comparison includes the group's member list. Cost: an approval from any
   333	  listed owner satisfies code-owner review (📖 R3.2.7), so on normal days a member could approve
   334	  another domain's PR, on or off shift. Mitigation [design]: process rule "approve another
   335	  domain's PR only if it carries the `incident` label and you are on shift", and a monthly report of
   336	  every cross-domain approval by group members on PRs without that label (layer 7). Whether Papaya's team size allows full coverage is unknown
   337	  (§1, S7).
   338	- **Risk stop [design]:** applies to every deploy, whatever the level. The deploy job previews prod;
   339	  on stateful replace/delete, an IAM change, a network or security-group change, or an advisory
   340	  policy finding (from phase 2) it stops and posts the filtered preview. The original author opens a second PR that adds
   341	  `deploy-approvals/<stack>/<sha>.yaml` (`<sha>` = the stopped commit) holding that SHA and the
   342	  preview hash; the workflow does not open it, because the setting that lets Actions create and approve PRs stays
   343	  off (📖 R3.3.3; ⚠️ R3.6 #3). CODEOWNERS on `deploy-approvals/<stack>/` names the owners of that stack and the
   344	  on-call group (OD8, OD9). The approver is ≠ author and may be the first PR's approver, who now sees
   345	  the prod diff. Merging it triggers the deploy on the new HEAD, which previews again and continues
   346	  only if the hash matches the approved one; if another PR merged in between, the hash differs and
   347	  the deploy stops again (Options §1; hash stability ⚠️ Options §8). Cost: while a stack is
   348	  stopped, later merges to that stack stop too until a matching approval lands; in an incident, a
   349	  risky change already waiting on `main` blocks the fix for the same stack until it is approved or
   350	  reverted. A
   351	  `mandatory` policy violation always blocks `pulumi up` (📖 R4.2.2): the fix is a code change, or a
   352	  change to the policy pack through its own L3 PR. Preview output is filtered for
   353	  outputs and secrets before it is posted (Options §1; ⚠️ R4.6 #2).
   354	- **Merge approval = deploy approval** only if (⚠️ R3.6 #1, from 📖 R3.1.3, R3.4.5c): `production`
   355	  allows only `main`; only the reusable deploy workflow (under CODEOWNERS) references it; no ref/SHA
   356	  inputs; no `issue_comment`, `pull_request_target` or `workflow_run` triggers; one concurrency group
   357	  per stack without `cancel-in-progress` (📖 R4.1.4).
   358	- **Pulumi:** PRs preview non-prod only, because a prod preview runs PR code with state-write and
   359	  secret access (📖 R4.3.3, R4.3.4; ⚠️ R4.6 #2). On `main`: prod preview, then `pulumi up` with the
   360	  policy pack, which stops on a mandatory violation (📖 R4.2.2). Prod runs allow no `--skip-preview`
   361	  (📖 R4.1.2) and no targeting, replace, `state`, `import`, `destroy` (⚠️ R4.6 #3, G12). Pulumi Cloud,
   362	  if used: OIDC via `pulumi/auth-actions`, no stored token (📖 R4.1.4).
   363	- **Serverless v4:** `serverless package`; `serverless diff --json` (sf-core ≥ 4.37.0), parsed by CI
   364	  because differences do not change the exit code (📖 R4.4.2); `serverless deploy --package`
   365	  (📖 R4.4.3); a least-privilege `deploymentRole`, which cannot be removed later and is usable by
   366	  anyone who may operate the stack (📖 R4.4.5), so JIT roles get no stack-operation rights.
   367	- **State:** writable by deploy roles (and possibly the drift role, layer 7); Pulumi
   368	  secrets via `awskms` on a DIY backend (📖 R4.3.3, R4.3.4; ⚠️ R4.6 #7).
   369	- **k0s [design]:** manifests in the monorepo, applied by CI; no write RBAC for humans or agents in
   370	  prod; read roles exclude logs and exec in namespaces with claim data (mechanism: G1). The risk
   371	  stop is described for Pulumi and Serverless only; for k0s manifests (RBAC changes are the IAM
   372	  equivalent) a `kubectl diff`-based stop is a candidate, not researched (⚠️ G1). Firebase deploys
   373	  have no preview step in this design (⚠️ G2).
   374	- **Incident lane:** label `incident`, on-call approver paged, security checks always run (S10), only
   375	  slow unrelated tests skipped [design]. A required check skipped by a path filter may stay
   376	  pending and block the merge (open, Options §8); this directly affects S7.
   377	
   378	**Example: Lambda timeouts at 2 a.m.** (Options §6)
   379	
   380	The incident responder is engineer E; the on-call approver is R (a backup replaces R only if R is
   381	unavailable).
   382	
   383	1. E's incident-analysis session reads metrics and redacted logs and proposes `timeout` 30 → 90 s,
   384	   memory 1024 → 2048 MB, and a larger visibility timeout on the source queue (ratio ⚠️ Options §8).
   385	2. A second session (edit tools; not meant to use prod roles) edits `serverless.yml`, runs
   386	   `serverless diff` on non-prod, and opens a PR labelled `incident` as E.
   387	3. R, a co-owner of `serverless.yml` through the on-call group (OD9), reviews the diff. If R
   388	   catches a missing queue change, R does not fix it (OD7): E pushes the fix, the stale approval is
   389	   dismissed, and R approves again, one more review round (Options §6). E merges.
   390	4. The deploy workflow packages, previews prod, finds no risky change, deploys with the OIDC role.
   391	5. Estimate 11–46 min (⚠️ Options §6) against ≤ 30 min: measured first in rollout.
   392	
   393	**Audit evidence.** The PR (diff, approvers, checks); run log and preview artifact, exported because
   394	retention is unverified (⚠️ G7); deploy-role CloudTrail events; all linked by commit SHA and run ID.
   395	
   396	**Cost / value.** One approver for every prod change, from the owners of the path; two approvals,
   397	usually by the same approver, when the risk stop fires (agent's reading AR 1; OQ-B). Cross-team PRs: open (OQ-A). None in non-prod.
   398	Compliance gets four-eyes enforced by GitHub. Gap: on Team the prod diff is not seen before apply.

   439	## Layer 5 — CI/CD hardening
   440	
   441	**Principle.** CI is the default production writer, so it is the main target. Short-lived,
   442	least-privilege credentials per job. Every CI dependency is pinned. Agent-written code passes the same
   443	checks as human code (S10).
   444	
   445	**On Papaya's stack**
   446	
   447	- **Credentials:** OIDC instead of keys and tokens in repository secrets, which any writer can read
   448	  (📖 R3.4.1, R3.5.3b). Org default for `GITHUB_TOKEN` set to "restricted", `permissions:` per job (📖 R3.5.3).
   449	  "Allow GitHub Actions to create and approve pull requests" off (📖 R3.3.3). Serverless License Key in
   450	  SSM, read by the deploy role (sf ≥ 4.4.19, 📖 R4.4.8). Until G1/G2 are solved, k0s and Firebase
   451	  deploys may need a stored credential in GitHub: a kubeconfig or token for k0s, a Firebase token or
   452	  service-account key for Firebase Hosting. The owner accepts this as an exception to S2 = 0 until it
   453	  is checked whether k0s and Firebase deploys can use OIDC (OD1, OD6). Conditions [design]:
   454	  - stored only as an **environment secret of `production`**, never as a repository secret. Anyone
   455	    with write access can read repository secrets (📖 R3.5.3b), which would turn the exception into
   456	    standing prod write for every engineer and their agent. Environment secrets and a deployment
   457	    branch rule limited to `main` are available on Team for private repos (📖 R3.1.2, R3.1.3), and
   458	    only the reviewed deploy workflow references the environment (layer 3);
   459	  - the deploy job runs on GitHub-hosted runners. On self-hosted runners, jobs "are not run in an
   460	    isolated container, even if they use environments", so environment secrets there must be
   461	    treated like repository secrets (📖 R3.1.5). Self-hosted runners "can be persistently
   462	    compromised by untrusted code" from anyone who can open a PR, and runner groups limit only which
   463	    repositories use them (📖 R3.5.2); in a monorepo any workflow can likely target the runner's label (⚠️ G15).
   464	    How to restrict a runner to one workflow is not researched (⚠️ G15); just-in-time runners exist
   465	    (📖 R3.5.2, not read in detail). If reaching k0s needs a self-hosted runner, that
   466	    runner is dedicated to the `production` deploy, and the residual risk is recorded;
   467	  - that environment secret is the single source of truth: no copy elsewhere (OD1);
   468	  - an owner, an expiry and rotation in the exception register;
   469	  - optionally a separate environment (e.g. `production-k0s`), limited to `main` and referenced
   470	    only by the k0s/Firebase deploy workflow, so AWS deploy jobs cannot read these secrets
   471	    [design].
   472	
   473	  Residual risk: admins can change the environment, and a deleted environment comes back without
   474	  protection (⚠️ R3.1.4); the alerts and settings comparison in layer 7 cover this. The exception
   475	  covers **CI deploy credentials only**. Runtime credentials, such as a k0s autoscaler's AWS access to
   476	  add or remove nodes, live in the cluster, not in GitHub; they follow layer 1 (no static keys, a
   477	  role attached to the machine; ⚠️ not researched for k0s, G1).
   478	- **Side paths:** Pulumi ESC, Pulumi Deployments and Serverless Dashboard providers reach AWS
   479	  (📖 R4.4.9) outside the GitHub gate (⚠️ R4.4.9); not used for prod (⚠️ R4.6 #6).
   480	- **Pinning:** workflow lockfile (`gh actions-lock`) or full SHA, enforced by the org policy "Require
   481	  actions to be pinned to a full-length commit SHA" (availability on Team ⚠️); the lockfile does not pin reusable workflows, so
   482	  the deploy workflow lives in the same repo (📖 R3.5.5; conclusion [design]).
   483	- **CODEOWNERS** on `.github/`, `CLAUDE.md`, `CLAUDE.local.md`, `.claude/`, `.claude.json`, `.mcp.json`,
   484	  `.husky/`, `.gitmodules`, `.ripgreprc`, `.devcontainer/` (📖 R3.2.8; list ⚠️ R6.5 #5, R6.3.11), plus
   485	  `.npmrc` (registry redirection) [design], `deploy-approvals/`, the policy packs, the SCP code and the
   486	  catalogue file. This is the canonical L3 path list that layer 3 refers to. The private plugin
   487	  marketplace is a separate repo and needs its own ruleset and CODEOWNERS [design]. CI validates the file, because
   488	  invalid lines are skipped silently (📖 R3.2.7).
   489	- **No privileged triggers with untrusted code** (`pull_request_target`, `workflow_run` + checkout,
   490	  📖 R3.5.4).
   491	- **Agents in CI:** `claude-code-action` with a custom GitHub App limited to Contents, Issues, Pull
   492	  requests (📖 R1.7.8); Anthropic workload identity federation, not a personal OAuth token (📖 R1.7.6);
   493	  `--restricted` and explicit `--tools` (D3; passing it through `claude_args` unverified, ⚠️ research
   494	  6.9.4 Q5); a managed-settings file on the runner, which also guards against mods (📖 R1.5.6; for
   495	  federation auth ⚠️); MCP set fixed by CI because `.mcp.json` loads without a prompt in `-p` runs
   496	  (📖 R1.3.5); never `environment: production` (⚠️ R3.6 #4). Hosted runners give `sudo` (📖 R3.5.1),
   497	  so with `Bash` in `--tools` the runner file is advisory (⚠️ R3.5.1, R3.6 #4).
   498	- **App-opened PRs:** a required check set by a dedicated GitHub App, pinned as its source (layer 3), confirms at least one approval by a
   499	  human who did not trigger the run; counting approvals is not enough, since the app's own approval
   500	  might count (⚠️ R3.3.4, R3.7 A3; 📖 R3.2.5).
   501	- **Required checks (S10):** from phase 1, secret scanning, dependency check, SAST (products: G4);

   518	## Layer 6 — Data protection and prompt-injection defence
   519	
   520	**Principle.** The design keeps PHI from reaching the coding agent (owner decision, research 1.9).
   521	Some paths rely on process (below), so this is a target, not a guarantee. Other customer
   522	personal data is outside that hard boundary ("not extended", research 5.8): the agent reads metadata
   523	by default and may read such data case by case under GĐ-9. Real-data reads are approved, name one
   524	tenant, are time-boxed, and need an agreement (BAA/DPA, partner contract) (GĐ-9). Everything read
   525	from outside is untrusted. Non-prod is synthetic or masked (GĐ-14).
   526	
   527	**On Papaya's stack**
   528	
   529	- **Paths to PHI** (research 1.11.4 lists 17):
   530	  - AWS stores: closed by identity, through `ProdReadMetadata` as the only standing prod role from
   531	    phase 1 (existing broad read roles are removed) and the SCP from phase 2
   532	    (layer 1); no Aurora credentials, no prod exec, no `lambda:InvokeFunction` for agent-usable roles
   533	    [design; actions ⚠️ G13];

   584	## Layer 7 — Observability, audit, incident response and break-glass
   585	
   586	**Principle.** One tamper-evident evidence chain per prod change. One routed alert channel with a
   587	named on-call, approvers included. Unapproved change is detected (drift, reconciliation). Break-glass
   588	is approved before use, time-boxed and reconciled after.
   589	
   590	**On Papaya's stack**
   591	
   592	- **Audit stores:**
   593	  - organization CloudTrail to a log-archive account with integrity validation (📖 R2.6.2, R2.6.4,
   594	    R2.6.5); change records ≥ 6 years; raw-log retention for Papaya's compliance owner (⚠️ R5.7 #2).
   595	    Data events only on PHI buckets, prod Lambda invoke and prod SQS (cost 📖 R2.6.3; selection
   596	    ⚠️ R2.9 #5), which makes the archive

   599	  - alerts on `repository_ruleset.update`, `environment.update_protection_rule`,
   600	    `environment.remove_protection_rule`, `environment.delete`, `protected_branch.policy_override`
   601	    (📖 R3.5.6, R3.1.4; selection ⚠️ R3.6 #1). UI changes to the branch policy may leave no event, and a
   602	    deleted `production` environment comes back unprotected (⚠️ R3.1.4): a job compares live settings
   603	    with an expected copy (G8);
   604	  - Aurora SQL is likely invisible to CloudTrail (⚠️ R2.7.1): Database Activity Streams, alerts on

   608	  preview and CloudTrail events. Monthly reconciliation: every prod write event matches a record
   609	  approved before apply (S3). Actor: `onBehalfOf.userId` where present, else session name plus
   610	  directory lookup (📖 R2.5.1; ⚠️ R2.5.3).
   611	- **Drift [design]:** its own role, trusted only from a `drift` environment on `main`; it can read
   612	  prod secrets in state, which is noted (⚠️ R4.6 #2). Scheduled `pulumi preview --refresh
   613	  --expect-no-changes` or `pulumi refresh --preview-only` (📖 R4.1.1, R4.3.1, R4.3.2). On a DIY S3
   614	  backend, preview needs state-write permission (📖 R4.3.3); whether a refresh preview writes more
   615	  than locks is open (⚠️ R4.6 #2, G14). So either the drift role gets state write (and the same
   616	  trust care as the deploy role), or Pulumi Cloud drift detection is used (📖 R4.3.2, Pro+). The
   617	  latter runs on Pulumi Deployments, which holds credentials to prod, so it re-opens a side path that
   618	  layer 5 excludes and needs the same trust narrowing and audit (📖 R4.4.9; ⚠️ R4.6 #6). CloudFormation
   619	  drift detection, explicitly set properties only (📖 R4.4.6). No auto-remediation: it is an unreviewed
   620	  `pulumi up --refresh` (📖 R4.3.2). Each finding gets an actor and a ticket.
   621	- **On-call:** phase 1 delivers the named approver schedule (primary + backup engineers, 24/7), as
   622	  decided in framing round 1, and, because of OD7, a minimal incident-responder schedule; the
   623	  latter extends that decision. The primary approves; the backup steps in only if the primary is
   624	  unavailable (OD2). On-call approvers only approve during their shift; the fix is written by an
   625	  incident responder (OD7). Alert routing and the
   626	  rest of on-call follow in phase 2 (tools: G5); in phase 1 the responder calls the approver by phone from the published schedule.

   629	  | Step | Rule |
   630	  |---|---|
   631	  | When | Only during an incident (Options §9 Q2), when the PR path cannot be used: operation not in IaC and no runbook; GitHub/Actions down; pipeline broken.
