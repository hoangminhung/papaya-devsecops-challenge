    53	## How to run
    54	
    55	```bash
    56	examples/validate.sh            # tools that are not installed are SKIPPED, and reported as such
    57	ACTIONLINT=/path/actionlint ZIZMOR=/path/zizmor examples/validate.sh
    58	```
    59	
    60	Needs Python 3 with `jsonschema`, `PyYAML` and `git`; optional `jq`, `yamllint`, `shellcheck`,
    61	`actionlint`, `zizmor`, `claude` (for `claude plugin validate`), and Node.js with
    62	`npm ci` run once in `pulumi-policy/` (downloads packages; `node_modules/` is not committed).
    63	Tests use the standard `unittest`.

   162	## Limits of the risk stop
   163	
   164	The risk stop answers one framework problem: on GitHub Team nobody sees the prod diff before
   165	apply (framework §1). It catches **risky prod diffs that nobody looked at**. It is not a boundary
   166	against **malicious or prompt-injected code that was approved**:
   167	
   168	- The stack's own code runs with the stack's prod deploy role: `npm` packages are installed before the
   169	  credentials, with install scripts off (OD22), but the Pulumi program runs during `preview` and
   170	  `up`, and Serverless plugins during `package`/`diff`/`deploy`. That code could call AWS
   171	  directly, or tamper with files the classifier reads, in the same job. The defence against it
   172	  is the PR review itself, and from phase 2 IAM Access Analyzer and policy packs (layer 5).
   173	- A stronger variant [design, not in the framework]: preview with a separate prod **preview**
   174	  role (read and state access, no write), run the classifier in its own job on a fresh
   175	  checkout without credentials, and assume the deploy role only in a later job after the stop.
   176	  It adds a role and a job split; it is an open question for the owner.
   177	- `pulumi up` previews again before applying. A change made outside the pipeline between the
   178	  two previews (JIT, drift) is not re-checked. `pulumi preview --save-plan` + `pulumi up --plan`
   179	  would bind the two, but update plans are experimental (📖 R4.1.3).
   180	- Concurrency: a running deploy is never cancelled, but GitHub cancels a run that is still
   181	  pending when a newer one arrives for the same group (📖 GitHub docs source,
   182	  `data/reusables/actions/actions-group-concurrency.md`). Some merged commits therefore have no
   183	  deploy run of their own; the newer run deploys them too, and the change record must link both
   184	  commits to that run. `queue: max` would give every commit its own run, but the same page says
   185	  the order "is not guaranteed": an older commit could then deploy after a newer one and undo it
   186	  in prod. So the default is kept on purpose [design].
   187	- The type lists are examples. For types that are missing, the rule on property names
   188	  (`policy`, `role`, `securityGroup`, `vpcConfig`, `public`, `authorization`, `logging`, …;
   189	  a narrower set on creates) catches some changes, not all.
   190	- **Code in the deploy job can act as either deploy role of its environment.** `id-token: write`
   191	  is job-wide, so the Pulumi program, Serverless plugins and any allowlisted install script can
   192	  request the job's OIDC token (⚠️ from memory of GitHub's OIDC docs) and assume either role that
   193	  trusts that environment. Since OD22 (phase 1) that is a domain stack's bounded roles, never the
   194	  IAM stack's role (`production-iam`, E4), and no other install script runs
   195	  (`npm_config_ignore_scripts`). Still on the phase-2 roadmap with OD15: a separate preview role
   196	  and a build job without `id-token`.
   197	- **Open gap:** nothing proves that a deploy really stopped at `stopped_commit` with the
   198	  approved hash. An approval merged early (naming a commit whose deploy did not stop, with a
   199	  hash computed in advance, which needs knowledge of prod inputs) is accepted if a later change
   200	  **outside** the stack's directory, such as a shared library, produces exactly that diff. Changes
