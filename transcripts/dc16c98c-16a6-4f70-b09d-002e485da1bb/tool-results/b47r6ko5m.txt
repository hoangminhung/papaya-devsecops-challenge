367	## Layer 3 — Change workflow by risk level
368	
369	**Principle.** The level is set by the damage a change can do. One default path above non-prod: a
370	reviewed PR applied by the pipeline, with the JIT fallback (layer 7) as the only other write path.
371	The approver reviews the code change that will be applied. By default a prod change needs two
372	people: one who makes it and one who approves it; the on-call backup only replaces an unavailable
373	primary (OD2). Higher risk narrows **who** may approve (the owners of that path), not how many, with
374	two exceptions: a process path needs two L3 owner team members (OD26), and a PR that touches files of
375	several teams needs an owner of each, except in an incident (OD27). Separately, any prod diff that looks risky stops the deploy, whatever its level; that adds a
376	second approval by an owner of the same stack, which keeps it to two people (OD8). Confirmed by the owner
377	(OD13): the original author opens the approval PR and the first approver
378	approves it. If the first approver is unavailable, another owner of the stack approves; that makes
379	three people and is recorded as a deviation, counted monthly (OD11). A cross-team PR needs an
380	approval from an owner of each team's files: OD10 allowed one on-call group member to cover them
381	all, but since OD27 that counts only for an incident (layer 3, "Who approves at night"). A real-data read is not a change and has its own rule, L3-data. Incidents use the same
382	path with faster people, not fewer security checks.
383	
384	| Level | What | Examples | Approval | Path |
385	|---|---|---|---|---|
386	| **L0** | Read: non-prod anything; prod metadata | metrics, redacted logs | none | read-only identity |
387	| **L1** | Change in non-prod | deploy a branch to dev; `pulumi preview` on non-prod (needs state-write permission on a DIY S3 backend, 📖 R4.3.3) | author only | non-prod roles or PR pipeline |
388	| **L2** | Routine prod change in code | Lambda timeout/memory, ECS desired count, release | 1 code owner ≠ author, ≠ last pusher | PR → `main` → deploy workflow |
389	| **L3** | High-risk prod change | IAM/SCP; replace/delete of stateful resources; network; `.github/**`, CODEOWNERS, `CLAUDE.md`, `CLAUDE.local.md`, `.claude/**`, `.claude.json`, `.mcp.json`, `.husky/`, `.gitmodules`, `.ripgreprc`, plugin/MCP catalogue and the rest of the canonical list in layer 5; advisory policy finding | 1 code owner ≠ author, ≠ last pusher. L3 process paths (workflow and agent-config files, catalogue, the SCP stack and the rest of the layer-5 list): **2** members of the L3 owner team (OD13, OD26). The IAM stack and its risk-stop approvals are process paths too (OD32): they create and re-trust the SCP-exempt roles and the permissions boundary, so on-call does not co-own them and a night change there uses JIT. That is rare by design: the IAM stack holds only those roles and the boundary (OD22); a service's everyday permissions live in its domain stack as `svc-*` roles under the boundary, which on-call can approve in an incident. L3 content inside a domain file (an IAM statement in `serverless.yml`, a stateful delete): the stack's owner, then the risk stop (OD8). In incidents: the on-call approver for deployable paths (OD9); paths that define the process (CODEOWNERS, agent config, catalogue, workflows) wait for the L3 owner team | same path; for IaC changes the risk stop also applies; workflow and agent-config files have no prod diff |
390	| **L3-JIT** | Break-glass | ECS force-redeploy while Actions is down | on-call approver ≠ requester (Options §4b); incidents only, as the author accepted it, for Papaya's sign-off (Options §9 Q2); the on-call approver counts as owner of the service in the request (OD13) | layer 7 |

396	owner of the files it touches (📖 R3.2.3, R3.2.7; per-file behaviour ⚠️ not a separate research row).

560	## Layer 4 — Supply chain for MCP servers and plugins
561	
562	**Principle.** Local MCP servers, plugins and hooks run with the engineer's access (📖 R1.6.2, R5.5.5); remote MCP servers receive tokens and data.
563	Only reviewed, pinned entries from a catalogue are allowed. The catalogue is the inventory (P4c).
564	Review takes ≤ 5 working days (S6), or people work around it.
565	
566	**On Papaya's stack**
567	
568	- **Plugins:** a private marketplace repo with `.claude-plugin/marketplace.json` (📖 R1.4.1), sources
569	  pinned to `ref`/`sha` (📖 R1.4.1b, link only). Managed `strictKnownMarketplaces` = Papaya only,
570	  `blockedMarketplaces`, `enabledPlugins: false` to pull one (📖 R1.4.2), checked before download and
571	  at session start (📖 R1.4.3). `disableSideloadFlags` rejects `--plugin-dir`, `--plugin-url`,
572	  `--agents`, `--mcp-config` but not `.mcp.json` or `claude mcp add` (📖 R1.4.2). With
573	  `allowManagedHooksOnly`, plugin hooks run only for force-enabled plugins (📖 R1.5.4). User mods are
574	  blocked by the `allowManagedModsOnly` option under `pluginConfigs` → `cc-plugin-sec-default@builtin`
575	  → `options` (📖 R1.5.6). The version floor covers the plugin-pin fix of 2.1.179 (📖 R6.2.7).
576	- **Pinning what every laptop runs (OD26) [design unless marked].** One compromised plugin, hook or
577	  local MCP server would hand an attacker many engineers' logins at once, enough to be both author
578	  and approver (threat T23). So the marketplace is pinned to a protected release tag (📖 R9.4.4),
579	  every plugin entry, internal ones included, carries a commit `sha` and a review record
580	  (📖 R9.4.5), auto-update stays off (📖 R9.4.6), and an update is a reviewed change of the pin
581	  (examples E9b). Cost: a plugin release takes three reviewed steps. Detail: [appendix K](07-framework-appendix.md#k-pinning-what-every-laptop-runs).
582	- **MCP:** "approved catalogue" = `allowedMcpServers` + `allowManagedMcpServersOnly: true`; without
583	  the lock users can widen it (📖 R1.3.1, R1.3.4). Match by `serverUrl` or `serverCommand`, never
584	  `serverName` ("not a security control", 📖 R1.3.3); `serverCommand` matches the exact argv (📖 R1.3.3).
585	  The allowlist covers servers that plugins bring too (📖 R9.4.2). A local server is admitted only
586	  as an artifact that cannot change under the same command (OD26) [design]: a container image by
587	  digest (`docker run --rm -i <image>@sha256:…`), or code shipped inside a pinned plugin
588	  (📖 R9.4.3; its path changes per version, so it is re-allowlisted on each update, ⚠️). Not
589	  `npx -y <pkg>@<version>`: that pins the package, not its dependencies [limit, examples E8].
590	  `disableClaudeAiConnectors: true` (📖 R1.3.7). With MDM, `managed-mcp.json` gives exclusive control;
591	  it cannot come from server-managed settings (📖 R1.3.2).
592	- **Review checklist** [design]: publisher; local `stdio` or remote (📖 R6.4.3); what it reads and where
593	  it sends data, with a supplier-register entry and BAA/DPA status (⚠️ R5.6); no token passthrough
594	  (📖 R6.4.2); write tools for Slack, Linear, GitHub only where needed (⚠️ R6.5 #6); how the server authenticates (Linear and Slack: G9); pinned version,
595	  reviewer, date.
596	- **Known gaps:** no per-group targeting in server-managed settings (📖 R1.1.6, R1.4.4); tool
597	  description changes after approval are not covered (⚠️ research 6.6); a remote server's
598	  behaviour can change behind the same `serverUrl`; a reviewed but malicious update still runs
599	  everywhere once its pin is approved.

601	**Audit evidence.** Catalogue file in git with an approved PR and a review record per entry, the supplier register, and OTel plugin events; full register: [04-compliance-mapping.md](04-compliance-mapping.md#register).

608	## Layer 5 — CI/CD hardening
609	
610	**Principle.** CI is the default production writer, so it is the main target. Short-lived,
611	least-privilege credentials per job. Every CI dependency is pinned. Agent-written code passes the same
612	checks as human code (S10).
613	
614	**On Papaya's stack**
615	
616	- **Credentials:** OIDC instead of keys and tokens in repository secrets, which any writer can read
617	  (📖 R3.4.1, R3.5.3b). Org default for `GITHUB_TOKEN` set to "restricted", `permissions:` per job (📖 R3.5.3).
618	  "Allow GitHub Actions to create and approve pull requests" off (📖 R3.3.3). Serverless License Key in
619	  SSM, read by the deploy role (sf ≥ 4.4.19, 📖 R4.4.8). Until G1/G2 are solved, k0s and Firebase
620	  deploys may need a stored credential in GitHub: a kubeconfig or token for k0s, a Firebase token or
621	  service-account key for Firebase Hosting. The owner accepts this as an exception to S2 = 0 until it
622	  is checked whether k0s and Firebase deploys can use OIDC (OD1, OD6). Conditions [design], in short: an environment secret of `production-k0s` (Expo: `production-mobile`), never a
623	  repository secret, which any writer can read (📖 R3.5.3b); GitHub-hosted runners, or a runner
624	  dedicated to that deploy; one copy; an owner, expiry and rotation in the exception register; for
625	  k0s, the namespaced, time-limited token of layer 1 and a Kubernetes API audit log. The exception
626	  covers CI deploy credentials only, not runtime credentials in the cluster. Detail and residual
627	  risk: [appendix L](07-framework-appendix.md#l-conditions-on-stored-deploy-credentials).
628	- **What runs in the deploy job (OD22, phase 1).** Approved code runs with a prod deploy role:
629	  the Pulumi program during preview and apply, Serverless plugins, and any install script.
630	  The risk stop sees resources, not SDK calls the program makes while it runs, so it cannot
631	  catch this (OD15). Three controls limit the damage instead [design]:
632	  - **one environment per kind of stack:** the IAM stack deploys from `production-iam`, database
633	    changes from `production-db`, every other stack from `production`; each has its own OIDC
634	    subject and roles, so a domain stack's job cannot obtain the IAM stack's role or the database
635	    change role (layer 1; examples E3, E4, E15). The `production-db` job installs no package and
636	    runs no Pulumi program, only the L3 scripts in `tools/db/` and the risk stop;
637	  - **domain roles are bounded:** they create or change only `svc-*` roles carrying the fixed
638	    permissions boundary (layer 1);
639	  - **no install scripts:** `npm_config_ignore_scripts` is set for the whole deploy and preview
640	    job ("npm does not run scripts specified in package.json files", 📖 R9.1.13; whether this
