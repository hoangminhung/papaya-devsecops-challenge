     1	# Engineer guide: working with Claude Code at Papaya
     2	
     3	> Status: a summary of the approved framework; it adds no rule · Updated: 2026-11-09 · Builds on

     5	
     6	This page answers one question: **what changes in my working day?** Each section says what you do,
     7	who approves, and how long it takes. The rules and their sources are in the framework layer linked
     8	from each section; if this page and the framework differ, the framework wins. Times are targets from
     9	the success criteria (S-n) or estimates marked ⚠️.
    10	
    11	## The short version
    12	
    13	- **Non-prod is yours.** Build, deploy and debug in non-prod with the agent, with no new approval (S4),
    14	  once a store has been scanned for real data (until then it follows the real-data rule, section 5).
    15	- **Prod reads are metrics and metadata.** No standing prod write for anyone, you included.
    16	- **Every prod change is a pull request.** One code owner who is not you approves; CI applies it.
    17	- **In an incident the path is the same, with faster people:** an on-call approver, 24/7.
    18	- **Real customer data, new tools and break-glass need a request.** Each has a named approver and a time limit.
    19	
    20	## 1. Daily development (non-prod)
    21	
    22	- **What you do:** use Claude Code as you do today, with non-prod roles. Manual permission mode is the
    23	  default; you may switch to auto mode (D1). Commands that run inside the sandbox run without a prompt
    24	  (phase 2, OD12).
    25	- **Approval:** none (risk level L1).
    26	- **What is different:** the organisation's managed settings apply to everyone; bypass mode is
    27	  removed; plugins and MCP servers come from the catalogue only (section 6). From phase 2 the sandbox
    28	  hides credentials and blocks Unix sockets, so `git push`, `gh`, Docker and private-registry `npm ci` fail inside it: run
    29	  them yourself at the `!` prompt. Using `--restricted` is recommended (D3).
    30	- **Workarounds (OD34):** ask the agent to write the PR text to a file, then run `git push` and
    31	  `gh pr create --body-file <file>` at the `!` prompt; run Docker-based tests in CI on the PR;
    32	  private packages install with the read-only registry token set up for you. For prod questions use
    33	  metrics and masked logs through `ProdReadMetadata` (section 4) before asking for real data (section 5).
    34	- **From phase 1** each `aws`, `pulumi` or `serverless` call asks you first, in auto mode too
    35	  (OD43): until standing prod write is removed, your sign-in can still change prod.
    36	- **From phase 2 you will also notice** (layer 2, examples E8): each WebFetch asks; your own and the project's permission
    37	  rules are ignored, so prompts may rise; sign-in is locked to Papaya's organisation (API-key sessions
    38	  are refused) and the minimum Claude Code version rises; on macOS, servers on localhost fail inside
    39	  the sandbox; native Windows is not supported (use WSL2).
    40	- **Layer:** [2](01-framework.md#layer-2--agent-runtime-controls).
    41	
    42	## 2. Reading prod
    43	
    44	- **What you do:** with `ProdReadMetadata` (1-hour session) you and your agent read metrics, metadata
    45	  and logs that are redacted at source and masked by a data protection policy (OD28): identifiers
    46	  such as national IDs, bank accounts and diagnoses show as masked values. Lambda configuration is readable per service once its secrets
    47	  are resolved at runtime; until then, read timeout and memory from the IaC code.
    48	- **Approval:** none (L0).
    49	- **Cost to know:** in the first months, raw logs of services not yet redacted are not readable
    50	  without a data-read request (section 5). This is the largest cost of the transition.
    51	- **Remember:** the agent uses **your** AWS SSO session, so it can do whatever you can (layer 1). Keep
    52	  the portal session short.
    53	- **Layer:** [1](01-framework.md#layer-1--identity-and-access).
    54	
    55	## 3. Shipping a prod change
    56	
    57	1. Write the change as code (Pulumi, `serverless.yml`, Kubernetes manifests) and preview it on non-prod.
    58	2. Push the branch and open a pull request. The PR runs secret scanning, dependency checks and SAST
    59	   (S10), and previews non-prod only.
    60	3. One code owner of the changed files approves. You cannot approve your own PR, and the approver may
    61	   not be the last person who pushed. An agent never approves a PR (OD5). Managed settings deny `gh pr review` for agents, but
    62	   that is hygiene only: another form of the same call gets past it, so the approval-gate check
    63	   flags approvals that look automated rather than blocking them (OD25).
    64	   - Domain code and stacks: your domain team. Members of the on-call group are co-owners, but
    65	     their approval counts for another team's files only on an incident PR while they are on shift;
    66	     the approval-gate check enforces it (OD27). A PR that touches several teams' files needs an
    67	     owner of each.
    68	   - Process files (`.github/`, `CLAUDE.md`, `.claude/`, the catalogue, the SCP and IAM stacks,
    69	     `tools/risk-stop/`, `tools/ci/`, `oncall/`): **two** members of the L3 owner team (OD26,
    70	     OD32). A night fix that needs an IAM change goes through JIT.
    71	   - Clicking "Update branch" after someone else's merge keeps your approvals as long as your own
    72	     changes are the same; a push that changes them needs a new approval (OD31).
    73	4. Merge (squash only). The deploy job previews prod and applies the change.
    74	5. **If the deploy stops at the risk stop** (stateful replace or delete, IAM, network, a policy
    75	   finding): open a second PR that adds only `deploy-approvals/<stack>/<stopped commit>.yaml` with the
    76	   hash from the job summary. By default the first approver approves it; if they are unavailable,
    77	   another owner of the stack does, which is recorded as a deviation (OD13, OD11). Merging it deploys
    78	   if the new prod preview has the same hash. While the stack is stopped, later merges to it stop too.
    79	
    80	- **Time:** same working day from PR to prod; approval wait ≤ 1 hour in working hours (S4 targets).
    81	- **What CI does differently (OD22):** npm install scripts do not run in preview and deploy jobs;
    82	  if a package needs its script, ask the L3 owner team to add it to `tools/ci/allowed-install-scripts.txt`.
    83	  A stack may create IAM roles for its own services only as `svc-*` roles with the standard
    84	  permissions boundary; roles that read claim data (`app-claims-*`) are created in the IAM stack
    85	  and referenced by ARN. PRs that touch infrastructure code also get an automated agent review,
    86	  which is advice, not an approval.
    87	- **Layer:** [3](01-framework.md#layer-3--change-workflow-by-risk-level); diagram
    88	  [`01-change-workflow`](../diagrams/01-change-workflow.svg).
    89	
    90	- **Other platforms (OD36, OD40):** mobile releases and over-the-air updates go through the same PR;
    91	  the CI publishes to the `production` EAS channel, and nobody runs `eas update` against it from a
    92	  laptop (your Expo role cannot). GCP prod access for a person is a Privileged Access Manager
    93	  request approved by the on-call approver, never a standing role; k0s access for people is
    94	  read-only through single sign-on once OIDC is in place.

    96	## 3a. Database changes and data fixes
    97	
    98	- **Schema and metadata:** write the migration (or GraphQL-engine metadata change) as a file under
    99	  `db/<service>/`, open a PR, get your domain owner's approval as for code. After merge the `sql`
   100	  deploy job applies it with its own database role; nobody, you included, holds database
   101	  credentials (OD29, ADR-0011).
   102	- **Data fix** (a stuck claim, a payout to retry): a file `db/<service>/data-fixes/<tenant>/<ticket>.sql`
   103	  for one tenant, with a `-- expected_rows: N` header. It needs a code owner **and** a different
   104	  person from that tenant's data owners (L3-data-write). The job rolls it back if the row count
   105	  differs, and its summary shows counts only. Name records by their internal IDs only: no account
   106	  numbers, national IDs, names or diagnoses in the file. If the fix needs such a value, the data
   107	  owner uploads it as a values file and your SQL uses `:'variable'`; the `data-fix-scan` check fails
   108	  the PR otherwise (OD48).
   109	- **Expect a stop** for `DROP`, `TRUNCATE`, column type changes, `DELETE`/`UPDATE` without a
   110	  `WHERE`, grants and row-level security, and every metadata change: open the
   111	  `deploy-approvals/` PR as in step 5 above. Prefer expand/contract migrations.
   112	- **In an incident:** the same path; the on-call approver may stand in for the data owner, who
   113	  reviews it the next working day.
   114	- **Layer:** [3](01-framework.md#layer-3--change-workflow-by-risk-level).
   115	
   116	## 4. An incident at 2 a.m.
   117	
   118	You are the **incident responder**. The **on-call approver** only approves; they never write the fix (OD7).
   119	
   120	1. Start an incident-analysis session with read-only roles, in an empty scratch directory outside
   121	   the repository: `claude --restricted --strict-mcp-config --tools "Bash,Read,Grep,Glob"` (no
   122	   WebFetch, no MCP servers; Bash can still reach the network). Read metrics and masked logs; the
   123	   `incident-triage` skill guides the session.
   124	2. Open (or find) the incident issue in Linear. Make the fix in a normal session, preview on
   125	   non-prod, and open a PR labelled `incident` that links the issue: the on-call approval counts
   126	   only while the issue is open and the approver is on shift (OD27).
   127	3. Call the on-call approver (phone in phase 1; routed alerts from phase 2). They review and approve.
   128	   If they find a problem, you push the fix and they approve again.
   129	4. Merge; the deploy job applies the change. If it stops at the risk stop, the approval PR it
   130	   needs (`deploy-approvals/<stack>/`) goes the same way: label it `incident` and link the same
   131	   open issue, or the approval-gate check does not count the on-call approval on it either.
   132	
   133	- **Time:** target ≤ 15 min waiting for approval (S7); 11–46 min from decision to apply is an
   134	  estimate (⚠️), measured first during rollout against a 30-minute target.
   135	- **Blockers to know:** a risky change already waiting on `main` blocks your fix for that stack until
   136	  it is approved or reverted; at night, process files (workflows, `CLAUDE.md`, catalogue) wait for the
   137	  L3 owner team, or the JIT fallback applies.
   138	- **Only if the PR path cannot be used** (GitHub Actions down, broken pipeline, an operation not in
   139	  IaC): end your AWS portal session and sign in fresh, then open a JIT request issue in Linear from
   140	  its template (outside GitHub), with the exact commands; it is the record of the request (OD30). The on-call approver approves before the grant by
   141	  moving the issue to "Approved"; the grant then arrives automatically, and is refused if you
   142	  approved it yourself, the approver is not on shift or the incident is closed (OD33).
   143	  You get `InfraOperator-<service>` (1-hour role session; the real window can approach 2 h) and type
   144	  the commands yourself, in a terminal **without an agent**. Afterwards your commands are compared
   145	  with CloudTrail (by hand in phase 1, by a job from phase 2), and you open a PR that codifies the change.
   146	- **Layers:** [3](01-framework.md#layer-3--change-workflow-by-risk-level),
   147	  [7](01-framework.md#layer-7--observability-audit-incident-response-and-break-glass); diagram
   148	  [`03-incident-lane`](../diagrams/03-incident-lane.svg).

   150	## 5. Reading real customer data
   151	
   152	- **What you do:** end your AWS portal session and sign in fresh, then open a data-read request issue
   153	  in Linear from its template, with one tenant, purpose, store, time window and the agreement that
   154	  covers it (OD30). You get a data-read role for 1 hour.
   155	  After reading one tenant's data, do not post to shared places without review.
   156	- **Approval:** an approver who is not you, plus the data owner. At night the on-call approver
   157	  approves alone, and the data owner reviews it the next working day.
   158	- **PHI (medical records):** you read it yourself, in a terminal **without an agent**; give the agent
   159	  only a redacted summary. A store that holds PHI counts as PHI unless the agent reads a view without
   160	  it. Partner-uploaded claim documents never go into an agent session raw: reproduce with synthetic
   161	  documents, or de-identify them first.
   162	- **Non-prod** should hold no real data; a store not yet scanned follows this section's rule.
   163	- **Layer:** [6](01-framework.md#layer-6--data-protection-and-prompt-injection-defence).
   164	
   165	## 6. Adding a plugin or MCP server
   166	
   167	- **What you do:** open a request with what the tool reads, where it sends data and which write
   168	  tools it needs. A local MCP server is admitted only as a container image pinned by digest or as
   169	  code inside a pinned plugin, not as `npx -y <package>` (OD26). Keep your GitHub CLI token in the
   170	  system credential store (`gh auth status` shows where it is). A catalogue entry is added by a PR with a review record (examples
   171	  [`reviews/`](../examples/claude/marketplace/reviews/)).
   172	- **Approval:** two members of the L3 owner team (the catalogue is a process path, OD26).
   173	- **Time:** decided within 5 working days (S6).
   174	- **Not allowed:** installing a plugin or MCP server outside the catalogue, or sideloading one with
   175	  command-line flags.
   176	- **Layer:** [4](01-framework.md#layer-4--supply-chain-for-mcp-servers-and-plugins).
   177	
   178	## 7. When you are the on-call approver
   179	
   180	- You are on a named 24/7 schedule: a primary and a backup. The primary approves; the backup steps in
   181	  only if the primary is unavailable (OD2).
   182	- While on call you **only approve**: you do not write fixes or request JIT grants (OD7). A night
   183	  incident therefore needs two people awake: the responder and you.
   184	- Target: approve within 15 minutes (S7). Approve JIT only when the PR path cannot be used, and record
   185	  why you refuse it otherwise.
   186	- Approve another domain's PR only if it is labelled `incident`, links an open incident, and you
   187	  are on shift (OD9, OD27); the approval-gate check does not count it otherwise.
   188	- **Layers:** [3](01-framework.md#layer-3--change-workflow-by-risk-level),
   189	  [7](01-framework.md#layer-7--observability-audit-incident-response-and-break-glass).
   190	
   191	## 8. Shared agent knowledge
   192	
   193	`CLAUDE.md` and other agent configuration files define how the whole team works, so changes to them
   194	are approved by two members of the L3 owner team; a domain-team approval does not count (OD3, OD26). Review your agent's auto memory
   195	and delete it after a suspicious session (D3). The shared `CLAUDE.md` starts from the template in
   196	`examples/claude/repo-templates/CLAUDE.md`; pull requests use the template in
   197	`examples/github/pull_request_template.md`, which asks which parts an agent wrote.
   198	
   199	## 9. Using the agent for DevSecOps tasks
   200	
   201	The internal plugin `devsecops-guardrails` carries the skills; invoke them by describing the task
   202	([framework §2](01-framework.md#2-agent-assisted-devsecops-workflows)):
   203	
   204	| Task | Skill | Where you run it | What you get |
   205	|---|---|---|---|
   206	| Ship an infrastructure change | `prod-change` | normal session | IaC change, non-prod preview, PR text |
   207	| Triage an alert | `incident-triage` | incident-analysis session (section 4) | likely cause, smallest fix, JIT command list if needed |
   208	| Understand a stopped deploy before approving | `risk-summary-explainer` | normal session, or the CI agent's comment | what each stopped operation does and whether it can be undone |
   209	| Fix a vulnerable dependency | `dependency-fix` | normal session, or a CI-agent PR | one small PR per advisory |
   210	
   211	The agent drafts; you approve nothing it wrote yourself, and nobody approves through an agent.

   379	  that order; broad read roles stay until 1.9 and 1.10 land. Until 1.20 lands,
   380	  `OrganizationAccountAccessRole` remains a standing admin path from the management account, so
   381	  S1 is reported as "0 except the management account's named group" in that window. Which variant (more people or more
   382	  days) is a decision for Papaya's management.
   383	- **If the approval-gate app is late (degraded mode).** The ruleset ships without the
   384	  `approval-gate` check; GitHub still enforces code-owner review, no self-approval and approval
