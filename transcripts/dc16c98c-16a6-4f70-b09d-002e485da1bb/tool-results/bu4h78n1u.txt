285	## I. Risk stop, mechanics
286	
287	- **Risk stop [design]:** applies to every deploy, whatever the level. The deploy job previews prod;
288	  on stateful replace/delete, an IAM change, a network or security-group change, or an advisory
289	  policy finding (from phase 2) it stops and posts the filtered preview. The original author opens a second PR that adds
290	  `deploy-approvals/<stack>/<sha>.yaml` (`<sha>` = the stopped commit) holding that SHA and the
291	  preview hash; the workflow does not open it, because the setting that lets Actions create and approve PRs stays
292	  off (📖 R3.3.3; ⚠️ R3.6 #3). CODEOWNERS on `deploy-approvals/<stack>/` names the owners of that stack and the
293	  on-call group (OD8, OD9). The approver is ≠ author and may be the first PR's approver, who now sees
294	  which prod resources and properties change; values stay out of the summary to keep secrets out
295	  of logs, and are reviewed in the code of the stopped PR. Merging it triggers the deploy on the new HEAD, which previews again and continues
296	  only if the hash matches the approved one; if another PR merged in between, the hash differs and
297	  the deploy stops again (Options §1; hash stability ⚠️ Options §8). The approval is bound to git
298	  history, not only to the hash (six conditions, 7-day expiry; examples E7, finding 2) [design].
299	  Known gap (OD18): an early approval can match a later change outside the stack (G19 closes it: the app checks that the stopped run's summary carries the same hash).
300	  The stop catches risky diffs nobody looked at, not approved malicious code (OD15); OD22 limits what such code can reach (layer 5). Cost: while a stack is
301	  stopped, later merges to that stack stop too until a matching approval lands; in an incident, a
302	  risky change already waiting on `main` blocks the fix for the same stack until it is approved or
303	  reverted. A
304	  `mandatory` policy violation always blocks `pulumi up` (📖 R4.2.2): the fix is a code change, or a
305	  change to the policy pack through its own L3 PR. Preview output is filtered for
306	  outputs and secrets before it is posted (Options §1; ⚠️ R4.6 #2).

310	## J. Database changes, mechanism
311	
312	- **Database changes (OD29, ADR-0011) [design].** Aurora schema migrations, GraphQL-engine
313	  (Hasura) metadata and data fixes are files under `db/<service>/`, merged like code and applied by
314	  a `sql` job of the deploy workflow (examples E3):
315	  - where it runs [design]: Aurora is reachable only inside the prod VPC, and layer 5 avoids
316	    self-hosted runners, so the GitHub-hosted job never connects to the database. Its OIDC role may
317	    only start one ECS task definition (`db-change-<service>`) on one cluster, pass that task's two
318	    roles, and use one S3 prefix, and it trusts only the `production-db` environment, so no other
319	    deploy job can obtain it (examples E15). The bundle hash proves integrity between the job and
320	    the task; approval comes from the job itself, which runs only reviewed L3 code from `main`. The one-off Fargate task runs in private subnets
321	    from an image pinned by digest; its role may only `rds-db:connect` as the migration user (IAM
322	    database authentication, 📖 R9.2.11). ECS lets the caller override the command and environment
323	    of a task (📖 [RunTask](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_RunTask.html)),
324	    so the task re-checks the SHA-256 of the file bundle the risk stop classified and refuses any
325	    other; `ecs:ExecuteCommand` is denied. That `iam:PassRole` is what lets a caller start a task
326	    with a role is ⚠️ recalled, not checked in this round;
327	  - GraphQL-engine metadata is not a database change: the task applies it with
328	    `hasura metadata apply`, which needs the engine's admin secret and replaces all metadata
329	    (📖 [Hasura CLI](https://hasura.io/docs/2.0/hasura-cli/commands/hasura_metadata_apply/),
330	    [manage metadata](https://hasura.io/docs/2.0/migrations-metadata-seeds/manage-metadata/)). The
331	    secret sits in Secrets Manager and reaches only the task, through its task definition. No
332	    person holds database credentials or the admin secret day to day; a break-glass role that
333	    can read Secrets Manager can read it, which the JIT record shows (layer 7);
334	  - it lists the pending files through `tools/db/` wrappers around Papaya's migration tool (an L3
335	    path; the tool is not known here), runs the risk stop on them with `--tool sql`, and applies
336	    exactly the classified files, each in its own transaction;
337	  - the SQL risk stop (a heuristic, not a parser; examples E7) stops on DROP, TRUNCATE, column type
338	    changes, DELETE or UPDATE without a top-level WHERE, grants, roles, row-level security, COPY,
339	    function bodies and `EXECUTE`; every metadata change stops too, because it holds row
340	    permissions per role, i.e. tenant isolation; and any INSERT, UPDATE or DELETE inside a
341	    migration stops, because data changes belong in `data-fixes/<tenant>/`, where the data owner
342	    approves;
343	  - data fixes (`db/<service>/data-fixes/<tenant>/<ticket>.sql`) touch one tenant, declare
344	    `-- expected_rows: N`, and are rolled back when the count differs; approval is L3-data-write
345	    (layer-3 table); the job summary shows statement kinds and row counts, never values;
346	  - a data fix names records only by opaque internal IDs, because the file stays in git and every
347	    engineer and agent session can read it (OD48). A sensitive value the fix needs (a corrected
348	    bank account) goes into a values file that the data owner puts in the `db-change` bucket,
349	    which only the in-VPC task reads; the SQL refers to it as a psql variable [design]. A required
350	    check, `data-fix-scan`, fails a PR whose data fix matches one of the masking identifiers of
351	    layer 6 or holds a run of 9 or more digits (examples E19);
352	  - IAM database authentication is not in CloudTrail (📖 R9.2.11), so database-side evidence comes
353	    from Database Activity Streams (layer 7). Expand/contract migrations are recommended, not
354	    enforced. Cost: a data fix takes a PR and two approvals instead of a `psql` session.

358	## K. Pinning what every laptop runs
359	
360	- **Pinning what every laptop runs (OD26).** A plugin, hook or local MCP server runs on every
361	  engineer's laptop, outside the sandbox, with that engineer's GitHub and AWS sessions. One
362	  compromised entry would hand an attacker many logins at once, enough to be both author and
363	  approver of a PR (threat T23). So nothing that reaches laptops follows a moving branch [design
364	  unless marked]:
365	  - managed settings pin the marketplace to one release tag: marketplace sources take a `ref`,
366	    with no `sha` field (📖 R9.4.4; a community schema describes `ref` as "branch, tag, or SHA",
367	    a SHA there is ⚠️ untested). In the marketplace repository, release tags can be created only by
368	    the L3 owner team and never moved or deleted, and every change needs two approvals (rulesets,
369	    examples E9b);
370	  - every plugin entry, internal ones included, carries a commit `sha` (📖 R9.4.5) and a review
371	    record; a relative `./plugins/…` source is not used, because it follows the marketplace's files;
372	  - auto-update stays off for the marketplace, locked through managed `extraKnownMarketplaces`
373	    (📖 R9.4.6); an update is a reviewed change of the pin;
374	  - engineers keep the GitHub CLI token in the system credential store; `gh` falls back to a
375	    plain-text file when there is none (📖 R9.1.11), so the guide asks them to check `gh auth status`.
376	  Cost: a plugin release takes three reviewed steps (change, tag, settings), and onboarding a local
377	  MCP server means packaging it (layer 4, "MCP").

381	## L. Conditions on stored deploy credentials
382	
383	  - stored only as an **environment secret** of a protected environment (`production-k0s`), never as a repository secret. Anyone
384	    with write access can read repository secrets (📖 R3.5.3b), which would turn the exception into
385	    standing prod write for every engineer and their agent. Environment secrets and a deployment
386	    branch rule limited to `main` are available on Team for private repos (📖 R3.1.2, R3.1.3), and
387	    only the reviewed deploy workflow references the environment (layer 3);
388	  - the deploy job runs on GitHub-hosted runners. On self-hosted runners, jobs "are not run in an
389	    isolated container, even if they use environments", so environment secrets there must be
390	    treated like repository secrets (📖 R3.1.5). Self-hosted runners "can be persistently
391	    compromised by untrusted code" from anyone who can open a PR, and runner groups limit only which
392	    repositories use them (📖 R3.5.2); in a monorepo any workflow can likely target the runner's label (⚠️ G15).
393	    How to restrict a runner to one workflow is not researched (⚠️ G15); just-in-time runners exist
394	    (📖 R3.5.2, not read in detail). If reaching k0s needs a self-hosted runner, that
395	    runner is dedicated to the `production-k0s` deploy, and the residual risk is recorded;
396	  - that environment secret is the single source of truth: no copy elsewhere (OD1);
397	  - an owner, an expiry and rotation in the exception register;
398	  - a separate environment `production-k0s` (required since OD24, was optional), limited to
399	    `main` and referenced only by the k0s/Firebase deploy workflow, so AWS deploy jobs cannot read
400	    these secrets [design];
401	  - for k0s, the credential is the namespaced, time-limited ServiceAccount token of layer 1
402	    (OD24), rotated before it expires, and the cluster writes a Kubernetes API audit log: k0s has
403	    none by default and enables it only through `spec.api.extraArgs`, "outside k0s support"
404	    (📖 R9.3.1, R9.3.2). Secrets and token requests are logged at `Metadata` level so their
405	    contents stay out of the log (📖 R9.3.3; examples E11). A leaked token is then limited to
406	    deploys in its namespaces and leaves a trace; shipping that log to the log archive is part
407	    of G1.
408	
409	  Residual risk: admins can change the environment, and a deleted environment comes back without
410	  protection (⚠️ R3.1.4); the alerts and settings comparison in layer 7 cover this. The exception
411	  covers **CI deploy credentials only**. Runtime credentials, such as a k0s autoscaler's AWS access to
412	  add or remove nodes, live in the cluster, not in GitHub; they follow layer 1 (no static keys, a
413	  role attached to the machine; ⚠️ not researched for k0s, G1).

418	
419	- **Mobile releases (OD40) [design unless marked].** EAS Update can push JavaScript to every

432	    Expo token alone cannot ship code. Whether the app rejects an unsigned update is not stated
433	    plainly (⚠️ R9.8.8): tested before relying on it. The certificate in the repository is an L3
434	    path (CODEOWNERS, examples E2);
435	  - EAS Workflows cannot publish to a protected channel (📖 R9.8.11), and Expo's GitHub app is not

438	  - evidence: Expo's audit log is Enterprise-only and does not list update publishes (📖 R9.8.9),
439	    so the nightly evidence export also compares the updates on the `production` channel with the

441	  - rollback is `eas update:republish` of the previous update or `eas update:rollback`, both
442	    protected actions (📖 R9.8.3): a revert PR in the normal lane, JIT on the robot in an incident.
