    44	## How to run
    45	
    46	```bash
    47	examples/validate.sh            # tools that are not installed are SKIPPED, and reported as such
    48	ACTIONLINT=/path/actionlint ZIZMOR=/path/zizmor examples/validate.sh
    49	```
    50	
    51	Needs Python 3 with `jsonschema`, `PyYAML` and `git`; optional `jq`, `yamllint`, `shellcheck`,
    52	`actionlint`, `zizmor`, `claude` (for `claude plugin validate`), and Node.js with
    53	`npm ci` run once in `pulumi-policy/` (downloads packages; `node_modules/` is not committed).
    54	Tests use the standard `unittest`.

   146	## Limits of the risk stop
   147	
   148	The risk stop answers one framework problem: on GitHub Team nobody sees the prod diff before
   149	apply (framework §1). It catches **risky prod diffs that nobody looked at**. It is not a boundary
   150	against **malicious or prompt-injected code that was approved**:
   151	
   152	- The stack's own code runs with the stack's prod deploy role: `npm` packages are installed before the
   153	  credentials, with install scripts off (OD22), but the Pulumi program runs during `preview` and
   154	  `up`, and Serverless plugins during `package`/`diff`/`deploy`. That code could call AWS
   155	  directly, or tamper with files the classifier reads, in the same job. The defence against it
   156	  is the PR review itself, and from phase 2 IAM Access Analyzer and policy packs (layer 5).
   157	- A stronger variant [design, not in the framework]: preview with a separate prod **preview**
   158	  role (read and state access, no write), run the classifier in its own job on a fresh
   159	  checkout without credentials, and assume the deploy role only in a later job after the stop.
   160	  It adds a role and a job split; it is an open question for the owner.
   161	- `pulumi up` previews again before applying. A change made outside the pipeline between the
   162	  two previews (JIT, drift) is not re-checked. `pulumi preview --save-plan` + `pulumi up --plan`
   163	  would bind the two, but update plans are experimental (📖 R4.1.3).
   164	- Concurrency: a running deploy is never cancelled, but GitHub cancels a run that is still
   165	  pending when a newer one arrives for the same group (📖 GitHub docs source,
   166	  `data/reusables/actions/actions-group-concurrency.md`). Some merged commits therefore have no
   167	  deploy run of their own; the newer run deploys them too, and the change record must link both
   168	  commits to that run. `queue: max` would give every commit its own run, but the same page says
   169	  the order "is not guaranteed": an older commit could then deploy after a newer one and undo it
   170	  in prod. So the default is kept on purpose [design].
   171	- The type lists are examples. For types that are missing, the rule on property names
   172	  (`policy`, `role`, `securityGroup`, `vpcConfig`, `public`, `authorization`, `logging`, …;
   173	  a narrower set on creates) catches some changes, not all.
   174	- **Code in the deploy job can act as either deploy role of its environment.** `id-token: write`
   175	  is job-wide, so the Pulumi program, Serverless plugins and any allowlisted install script can
   176	  request the job's OIDC token (⚠️ from memory of GitHub's OIDC docs) and assume either role that
   177	  trusts that environment. Since OD22 (phase 1) that is a domain stack's bounded roles, never the
   178	  IAM stack's role (`production-iam`, E4), and no other install script runs
   179	  (`npm_config_ignore_scripts`). Still on the phase-2 roadmap with OD15: a separate preview role
   180	  and a build job without `id-token`.
   181	- **Open gap:** nothing proves that a deploy really stopped at `stopped_commit` with the
   182	  approved hash. An approval merged early (naming a commit whose deploy did not stop, with a
   183	  hash computed in advance, which needs knowledge of prod inputs) is accepted if a later change
   184	  **outside** the stack's directory, such as a shared library, produces exactly that diff. Changes
   185	  inside the stack's directory are rejected. Watching the whole repository instead would cancel
   186	  every approval at each unrelated merge in a monorepo. The fix is for the approval-gate app to
   187	  check, on the approval PR, that the stopped run's summary carries the same hash (G19) [design].
   188	  `test_known_gap_early_approval_and_change_outside_the_stack` documents the current behaviour.
   189	- The approver of the approval PR sees **which** prod resources and properties change, not the
   190	  new values (the summary never prints values, to keep secrets out of logs). The values are
   191	  reviewed in the code of the stopped PR. Framework layer 3 and ADR-0004 say the approver "sees
   192	  the prod diff"; that wording is too strong and is corrected in the framework's final pass.
   193	- Any commit to the stack's directory between the stop and the approval merge cancels the
   194	  approval: the author names the newer stopped commit and the owner approves again. In an
   195	  incident that is one more review round.
   196	- `npm ci` runs before the credentials with lifecycle scripts off (OD22). The allowlisted
   197	  packages' scripts still run, and could write to `$GITHUB_ENV` / `$GITHUB_PATH` and so influence
   198	  later steps that hold credentials; that is why the allowlist is an L3 path.
   199	- If the newest merge to `main` carries `[skip ci]` (or similar) in its message, no push run
   200	  exists for the tip and the older runs refuse to deploy; prod stays behind until the next merge
   201	  (📖 GitHub docs source, `content/actions/how-tos/manage-workflow-runs/skip-workflow-runs.md`,
   202	  via review). Operator action: merge an empty change.
   203	- Within 7 days, an approved change that is reverted and then merged again with identical code
   204	  passes without a new approval. This is intended: it is the same code and the same prod diff
   205	  that an owner approved.
   206	- The binding relies on squash-only merges (`ruleset-main.json`); with merge commits, a PR's
   207	  inner commits would be invisible to the first-parent check.
