## Refinements since acceptance

Writing and testing the files in [`../../examples/`](../../examples/README.md) made some details more
precise. None changes a decision, so no ADR is superseded; the framework carries the current wording.

- **ADR-0003:** "merge approval = deploy approval" gains two conditions: squash-only merges (OD16)
  and deploying only the current tip of `main`, because a writer can re-run an old deploy run for
  30 days and roll prod back without approval (OD17; examples finding 4).
- **ADR-0004:** "the approver sees the prod diff" means the approver sees **which** prod resources and
  properties change, not the new values, which stay out of the job summary so that secrets stay out of
  logs; values are reviewed in the code of the stopped PR. The approval is also bound to git history
  (examples E7, finding 2), and an early approval can match a later change outside the stack, an
  accepted gap until G19 (OD18).
- **ADR-0007:** the "read-only allowlist" became two exact repo scripts, because Claude Code already runs
  read-only commands without a prompt and wildcard rules can write files (examples finding 19); phase 1
  adds a `Read(~/.aws/**)` deny rule and `autoMode.classifyAllShell` (OD21). `sandbox.excludedCommands`
  entries need a trailing ` *` and are paired with `ask` rules, so each excluded CLI call prompts, auto
  mode included (examples finding 22).

After the independent review (`work/07-review.md`; owner decisions from OD22, 2026-11-09). Two
changes are decisions and got their own ADR: ADR-0011 (database changes) and ADR-0012, which
supersedes parts of ADR-0003 and ADR-0010. The others narrow how a decision is carried out:

- **ADR-0002:** "nobody holds standing prod write" now also covers who administers Identity Center:
  permission sets and assignments are code owned by the L3 owner team only, other changes raise an
  alert, `OrganizationAccountAccessRole` is denied in the prod OU and member-account root
  credentials are removed (OD23). The management account stays outside SCPs: detected, not prevented.
- **ADR-0003 / ADR-0004:** what runs in the deploy job is limited from phase 1: one GitHub
  environment per kind of stack (`production-iam` for the IAM stack), bounded domain deploy roles,
  no install scripts except a reviewed allowlist, and an agent review on infrastructure PRs (OD22).
  This was OD20's phase-2 roadmap item. The risk stop's scope is unchanged (OD15).
- **ADR-0008:** the k0s exception gets conditions: a separate `production-k0s` environment (was
  optional), a namespaced, time-limited ServiceAccount token instead of a kubeconfig, and the
  Kubernetes API audit log; target is k0s trusting GitHub OIDC directly (OD24).
- **ADR-0006:** its example entry `serverCommand` = `["npx", "<package>@<exact-version>"]` is no longer allowed: it pins the package, not its dependencies. "Pinned catalogue" now covers what reaches every laptop: the marketplace is pinned
  to a protected release tag, every plugin (internal ones too) to a commit, auto-update is off, and
  local MCP servers are admitted only as immutable artifacts (OD26).
- **ADR-0003 / ADR-0007:** managed deny rules for `gh pr review` and the `gh` token file from phase 1,
  as hygiene behind OD5; a login register maps GitHub accounts to people (OD25). The parts of
  ADR-0003 that ADR-0012 supersedes are listed in ADR-0012.
- **ADR-0004:** the SQL risk stop of ADR-0011 adds stops for DML in migrations and for every
  GraphQL-engine metadata change; the IAM stack's risk-stop approvals need two L3 owner team
  members (OD32, OD42).
- **ADR-0007:** the `ask` rules for `aws`, `pulumi` and `serverless` ship in phase 1, while
  engineers' sessions can still write to prod (OD43); still hygiene, not the boundary.
- **ADR-0008:** one environment per kind of credential holder: `production-db` for the database
  job, `production-mobile` for the Expo token and update-signing key, the second exception (OD40,
  OD42).
- **ADR-0005:** a receiver grants the JIT role only after checking approver ≠ requester, on shift
  and an open incident, once per request, with a role scoped to tagged permission sets (OD33,
  OD41, OD42).
- **ADR-0009:** log groups the agent may read get a second layer outside application code: a
  CloudWatch Logs masking policy with custom identifiers, no `logs:Unmask` for agent-usable roles,
  and a SAST rule against logging whole events (OD28).
- **ADR-0005:** JIT requests and approvals are Linear issues from a template, mirrored to the
  evidence bucket with Object Lock; no longer "a channel" left open (OD30).
=== docs/adr/0001-prod-changes-only-through-ci.md
# ADR-0001: Every production change goes through a reviewed PR applied by CI

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (Options §9, "A + D2'")
- **Scope:** all writes to production AWS, GCP, k0s and Firebase; incidents included (k0s and Firebase
  have no risk stop and no break-glass yet, G1, G2; human GCP access is open, G3)

## 1. Context

Engineering wants Claude Code to talk to AWS directly; Compliance wants no production change without
a named human who reviewed and approved it. "Most engineers' profiles can reach production" (brief), and deploys from laptops are assumed
(GĐ-10, unconfirmed), so an agent on that laptop can deploy too. Incidents are where the pressure to bypass
review is highest.

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. PR → approval → CI deploy for everything ("IaC first") | One path, approval before apply, evidence by construction | Slower incidents (est. 11–46 min ⚠️ vs 2–20 min, Options §6) |
| B. SSM Automation runbooks with an approval step | Approval inside AWS | Not verified that it meets the approval rule (G6); only for operations someone scripted. Kept on the roadmap, verified in phase 2 (OD4) |
| C. JIT direct access for the engineer + agent | Fastest | Approves access, not the change; agent holds prod write |
| D. Hosted agent with its own identity | Clean separation | New platform; does not remove the need for approval |

## 3. Decision

"A + D2'": option A is the default path for every production change, incidents included. A narrow JIT
fallback exists only when the PR path cannot be used during an incident (ADR-0005). The owner accepts
that this fallback meets the approval rule only partly (Options §9 Q2). Incident target: ≤ 30 min from
decision to apply.

## 4. Consequences

- **Positive:** the PR, its approvals, the run log and CloudTrail form one evidence chain keyed by
  commit SHA. Agent-written and human-written changes pass the same checks (S10).
- **Negative / trade-offs:** slower incident fixes; operations that are not in IaC must first be
  written as code or a runbook. Two write paths remain (PR and JIT), while the framing asked for one.
- **Risks & how we watch them:** the fallback stays narrow only if most incidents are expressible in
  IaC (unknown, Options §8). Metrics: JIT grants per month, share of incidents needing non-IaC
  operations; above about 25 % (⚠️ starting threshold), make the PR lane faster or add a runbook, never widen JIT.
- **Example:** Lambda timeouts at 2 a.m. The responder's agent proposes `timeout` 30 → 90 s in
  `serverless.yml`; the PR is labelled `incident`; the on-call approver reviews and approves; CI
  packages, previews prod and deploys with the OIDC role. Estimate 11–46 min (⚠️ Options §6).
- **Next steps:** measure the incident PR lane on one service first (phase 1).

## 5. References

- Framework §1 and layer 3; `work/03-options.md` §1, §6, §9.
- Related: ADR-0002, ADR-0003, ADR-0005.
=== docs/adr/0002-no-standing-prod-write-read-only-agent-identity.md
# ADR-0002: Nobody holds standing prod write; in prod, the engineer's (and so the agent's) only standing role reads metadata

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (Options §9; D2)
- **Scope:** AWS IAM Identity Center permission sets and SCPs on the prod OU; k0s, GCP and Firebase by the same principle

## 1. Context

On a laptop the agent uses the engineer's AWS SSO cache, and one portal session reaches every role
assigned to that engineer (📖 R2.2.1, R2.2.2; token-reuse detail ⚠️ R2.2.2). A separate "agent"
permission set therefore does not separate the agent from the engineer (⚠️ R2.9 #1). Whatever the
engineer holds, the agent holds.

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. Separate agent permission set, engineer keeps write | Looks like least privilege | Same SSO cache: the agent can still assume the write role |
| B. No standing prod write for anyone; `ProdReadMetadata` as the only standing prod role | Agent cannot write prod with the engineer's identity | Engineers also lose direct writes and raw-log reads |
| C. Separate OS user or container for agent sessions | Real separation of credentials | More setup; planned for phase 3 only |

## 3. Decision

Option B. Prod is written only by the CI pipeline role, or by an approved, time-boxed JIT grant
(ADR-0005). The standing prod role is `ProdReadMetadata` [design name]: metrics, redacted log groups,
configuration of services whose secrets are resolved at runtime; no data-plane reads of claim stores;
1-hour role session, the minimum (📖 R2.1.4). From phase 2, SCPs on the prod OU deny data-plane reads and
direct Lambda updates except for named roles (pattern ⚠️ R2.9 #4, R4.6 #3). Option C follows in phase 3.

## 4. Consequences

- **Positive:** once standing write and broad read roles are removed (end of phase 1), an agent,
  even a manipulated one, cannot write prod AWS or read AWS claim stores with the engineer's standing
  identity (data-plane action list ⚠️ G13); k0s and GCP follow the same principle, mechanisms open
  (G1, G3). In non-prod the agent keeps broad rights (`NonProdDeveloper`, ADR-0010 L1). Compliance gets least privilege enforced by IAM (S1).
- **Negative / trade-offs:** during the transition, engineers lose raw logs and configuration of
  services not yet redacted. Configuration values then come from the IaC code; raw logs need a
  data-read grant in an incident. Process rules remain where
  IAM cannot separate engineer and agent: no agent in the JIT terminal (D2).
- **Risks & how we watch them:** SSO-token theft during a session could open later grants (⚠️);
  mitigations [design] are a short portal session and a fresh sign-in before a grant. The data-plane action
  list is incomplete (⚠️ G13). Identity Center assignment export is reviewed quarterly.
- **Next steps:** phase 1 removes broad read roles only after the minimal real-data read flow works,
  then removes standing prod write once its prerequisites are in place.

## 5. References

- Framework layer 1, layer 2 ("Trade-off on AWS credentials"), layer 8 rollout.
- Related: ADR-0001, ADR-0005, ADR-0009.
=== docs/adr/0003-merge-to-main-is-the-approval-gate.md
# ADR-0003: The merge to `main` is the approval gate: two people, code owners, on-call co-ownership

- **Status:** Accepted; superseded in part by [ADR-0012](0012-approval-integrity-checked-by-the-gate-app.md)
  (which approvals count, two approvers on process paths, on-call approvals only in an incident)
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (GĐ-5, GĐ-8, GĐ-11; OD2, OD5, OD7, OD9, OD10, OD13)
- **Scope:** GitHub monorepo rulesets, CODEOWNERS, `production` environment, on-call schedule

## 1. Context

Papaya is assumed to be on GitHub Team (GĐ-5), where environment required reviewers do not exist for
private repositories (📖 R3.1.2), so the approval must happen before the deploy job. Incidents need an
approver within 15 minutes, 24/7 (S7), and code-owner review requires an approval from an owner of the files (📖 R3.2.3, R3.2.7;
per-file behaviour ⚠️).

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. Upgrade to Enterprise for environment reviewers | Approval sits next to the deploy | Cost; not assumed (GĐ-5) |
| B. Merge to `main` as the gate; `production` limited to `main` | Works on Team; the approver sees the code that will be applied | Nobody sees the prod diff before apply (partly handled by ADR-0004) |
| C. More approvers for high-risk changes | More eyes | Slower; the owner wants two people per change |

## 3. Decision

Option B. Ruleset on `main`: PR required, 1 approval, code-owner review, dismiss stale approvals,
approval by someone other than the last pusher, required checks from a pinned source app, no force
push, empty bypass list (📖 R3.2.2, R3.2.3, R3.2.5); branch up to date, since there is no merge queue
(⚠️ R4.6 #1). `production` accepts only `main` (📖 R3.1.3).

- **Merge = deploy approval** only if the reusable deploy workflow alone references `production`,
  with no ref/SHA inputs, no `issue_comment`, `pull_request_target` or `workflow_run` triggers, one
  concurrency group per stack without `cancel-in-progress` (📖 R4.1.4; ⚠️ R3.6 #1, from 📖 R3.1.3, R3.4.5c).
- **Two people per change:** one makes it, one approves it; the approver is always an engineer,
  never an agent (OD2, OD5). L3 changes need one approver too, who must own the path.
- **Incidents:** on-call engineers only approve; an incident responder writes the fix (OD7).
- **Night coverage:** an on-call approver group co-owns every deployable path in CODEOWNERS; one
  primary, one backup (OD9). It does not co-own process-defining paths (`.github/**`, CODEOWNERS,
  agent config, catalogue) or the SCP stack, which only the L3 owner team approves (OD13); IAM-only
  stacks are deployable, so it co-owns them with the L3 owner team. *Superseded by OD32: the IAM
  stack is a process path, L3 owner team only.*
- **Agent review:** an independent agent may post an automated review; it never counts as an
  approval (GĐ-11).
- **Cross-team PRs:** one approval is enough (OD10). *Superseded by ADR-0012: each team's files need
  their own owner's approval; the on-call approval covers another team's files only in an incident (OD27).*

## 4. Consequences

- **Positive:** four-eyes enforced by GitHub, not by the agent; one rule for normal days and incidents.
- **Negative / trade-offs:** GitHub accepts an approval from any listed owner (📖 R3.2.7), so the
  on-call group can approve another domain's PR; domain review on normal days is a process rule.
- **Risks & how we watch them:** admins can edit the gate, logged, not prevented (⚠️ R3.2.2, R3.6 #1;
  logging 📖 R3.2.2); alerts on ruleset changes; monthly report of cross-domain approvals. An agent could approve through its engineer's login; no detection found (⚠️). The
  required-check app's hosting, key and triggers are open (⚠️ G19).
- **Next steps:** rulesets, CODEOWNERS and its validation check in phase 1; the required-check app
  before any agent workflow may open PRs; L3 owner team composition open (G17).

## 5. References

- Framework layer 3 ("Gate = merge to `main`", "Who approves at night"), layer 7 (audit alerts).
- Related: ADR-0001, ADR-0004.
=== docs/adr/0004-risk-stop-on-risky-prod-diffs.md
# ADR-0004: Risky prod diffs stop the deploy until a stack owner approves the prod preview

- **Status:** Accepted; refined after the independent review (see [ADR index](README.md), "refinements": deploy-job isolation OD22, SQL stops ADR-0011, IAM-stack approvals OD32)
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (OD8, OD11, OD13)
- **Scope:** deploy workflows for Pulumi and Serverless stacks; k0s and Firebase not covered yet

## 1. Context

With the gate at merge time (ADR-0003), the approver reviews the code change, not the prod diff. A
PR may not preview prod, because that would run PR code with state-write and secret access
(📖 R4.3.3, R4.3.4; ⚠️ R4.6 #2). So a stateful delete or an IAM change can reach prod without anyone
seeing its real effect. Most IAM, network and stateful changes sit inside domain files such as
`serverless.yml`, not in separate L3 paths (assumed ⚠️; we have no access to the repo).

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. Accept the gap | No extra step | Destructive diffs applied unseen |
| B. Risk stop, approved by the L3 owner team | Specialist review | Often a third person; L3 team must be on call 24/7 |
| C. Risk stop, approved by an owner of the stack | Stays at two people; works at night | Less specialist review; compensated by automated checks |

## 3. Decision

Option C [design]. The deploy job on `main` previews prod. On stateful replace/delete, an IAM
change, a network or security-group change, or (from phase 2) an advisory policy finding, it stops
and posts the filtered preview. The original author opens a PR (the workflow does not, as "Allow GitHub Actions to create and
approve pull requests" stays off, 📖 R3.3.3; ⚠️ R3.6 #3) adding
`deploy-approvals/<stack>/<sha>.yaml` with the SHA and preview hash (owned by the stack's owners and the
on-call group, OD8, OD9); the first approver approves it
(OD13). If that approver is unavailable, another stack owner approves; this makes three people and
is recorded as a deviation (OD11). After the merge the workflow previews again on the new HEAD and
continues only if the hash matches. Serverless uses `serverless diff --json` (sf-core ≥ 4.37.0), parsed by CI because
differences do not change the exit code (📖 R4.4.2). A `mandatory` Pulumi policy violation always
blocks `pulumi up` (📖 R4.2.2; policy packs from phase 2).

## 4. Consequences

- **Positive:** the person who approves now sees the prod diff for the changes that can do lasting
  damage. Still two people in the normal case.
- **Negative / trade-offs:** while a stack is stopped, later deploys to it stop too (the hash
  differs), including an incident fix, until the approval lands or the change is reverted. One more review round when the stop fires.
- **Risks & how we watch them:** preview output may not be stable enough to hash (⚠️ Options §8); if
  not, compare a structured summary. Until phase 2, the risk stop is the only compensation for OD8;
  Access Analyzer `check-no-new-access` (📖 R2.8.1) and policy packs follow. k0s and Firebase have no
  preview step in this design (⚠️ G1, G2).
- **Next steps:** risk stop in the deploy job in phase 1.

## 5. References

- Framework layer 3 ("Risk stop"), layer 5 (required checks); `work/03-options.md` §1.
- Related: ADR-0001, ADR-0003.
=== docs/adr/0005-break-glass-is-time-limited-jit.md
# ADR-0005: Break-glass is a time-limited, approved JIT grant, for incidents only

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (GĐ-8; Options §9 Q2; D2; OD7, OD13)
- **Scope:** AWS production accounts through IAM Identity Center; k0s and Firebase not covered (G1, G2)

## 1. Context

Some incidents cannot use the PR path: GitHub or Actions is down, the pipeline is broken, or the
operation is not in IaC and has no runbook. Without a defined fallback, people keep standing access
"just in case", which ADR-0002 removes.

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. No fallback | Single path | Outage of GitHub blocks every fix; pressure to keep standing access |
| B. Standing break-glass account, used first and approved later | Always available | Standing prod write; unapproved use, rejected by the owner (GĐ-8, Options §0.4) |
| C. Approved JIT grant, 1-hour role session, command list, reconciled after | Approval before use; time-boxed; traceable | Approves a command list, not an applied change (partial) |

## 3. Decision

Option C [design], used only during an incident when the PR path cannot be used.

- **Request:** command list, scope, reason, incident link, in a channel that does not depend on GitHub.
- **Approval:** the on-call approver ≠ requester, before the grant; the on-call approver counts as
  owner of the service (OD13).
- **Grant:** `InfraOperator-<service>` [design name], assigned via `CreateAccountAssignment` and removed
  via `DeleteAccountAssignment` (📖 R2.4.2); role session 1 h (📖 R2.1.4). *Refined by OD33:* a
  receiver of the Linear webhook makes the grant only after checking approver ≠ requester, on
  shift, open incident and the allowed set (examples E16), so the approval rule is enforced
  before the grant, not only reviewed after it.
- **Execution:** the incident responder types the commands in a terminal without an agent (D2, OD7).
- **Example request** (illustrative command ⚠️): "INC-123, ECS service `claims-api`, Actions outage.
  Run `aws ecs update-service --cluster <prod-cluster> --service <svc> --force-new-deployment`. Scope
  `InfraOperator-claims`, 1 h."
- **After:** CloudTrail writes in the window are compared with the list; a codify PR follows by a
  fixed deadline; drift detection runs until it merges.

## 4. Consequences

- **Positive:** no standing prod write even for emergencies; every use has an approval, a window and
  a reconciliation.
- **Negative / trade-offs:** meets the approval rule only partly (accepted by the author; Papaya's Compliance signs off, framework §1). "No agent in the
  JIT terminal" is a process rule: the grant is reachable from the same laptop.
- **Risks & how we watch them:** deleting the assignment likely stops only new sessions, so a grant
  can run up to about 2 h (⚠️ R2.4.2, R2.9 #3). An immediate stop needs the revocation SCP, which keeps
  the user blocked ≥ 12 h (📖 R2.4.4); no night-time path to apply it is designed yet (⚠️ G20).
  Metrics: JIT used where a PR was possible, writes outside the list, late codify PRs (review at 1).
- **Next steps:** minimal JIT with per-grant CloudTrail comparison and a manual drift check of the
  touched stacks in phase 1 (a temporary deviation from D2); revocation SCP and
  automated reconciliation in phase 2.

## 5. References

- Framework layer 7 ("Break-glass = JIT fallback"); `work/03-options.md` §4b, §9.
- Related: ADR-0001, ADR-0002.

# ADR-0006: MCP servers and plugins are allowed only from a reviewed, pinned catalogue

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (framework approval 2026-11-09; rollout priority framing Q8)
- **Scope:** Claude Code on all engineer laptops and in CI; Papaya's internal plugin marketplace

## 1. Context

Local MCP servers, plugins and hooks run with the engineer's access (📖 R1.6.2, R5.5.5); remote MCP
servers receive tokens and data. Papaya runs an internal plugin marketplace (brief, Appendix A), and
engineers install MCP servers without review (brief); use of Linear and Slack through MCP is assumed
(⚠️ G9). An unreviewed server or a plugin update can read the repo, the SSO cache or claim
data and send it out.

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. Free choice, guidance only | No friction | No inventory; any server can exfiltrate |
| B. Denylist known-bad servers | Low friction | Misses new and changed servers |
| C. Allowlist (catalogue) enforced by managed settings | Inventory and supplier records; blocks unknown servers | Up to 5 working days' wait for a new tool (S6) |

## 3. Decision

Option C. The catalogue is a file in git, changed by PR under the L3 owner team.

- **Plugins:** only Papaya's marketplace via managed `strictKnownMarketplaces`, plus
  `blockedMarketplaces` (📖 R1.4.2); sources pinned to `ref`/`sha` (📖 R1.4.1b, link only);
  `disableSideloadFlags` (📖 R1.4.2); version floor covering the plugin-pin fix of 2.1.179 (📖 R6.2.7).
- **MCP:** `allowedMcpServers` with `allowManagedMcpServersOnly: true` (📖 R1.3.1, R1.3.4); match by
  `serverUrl` or `serverCommand` (exact argv), never `serverName`, which "is not a security control"
  (📖 R1.3.3); `disableClaudeAiConnectors: true` (📖 R1.3.7).
- **Review checklist** [design]: publisher, local or remote, what it reads and where it sends data,
  supplier-register entry and BAA/DPA status, no token passthrough (📖 R6.4.2), pinned version.
  Example entry: `serverCommand` = `["npx", "<package>@<exact-version>"]` [design; placeholder].
- **CI:** server-managed settings do not reach a CI job (📖 R1.7.10); CI uses a managed-settings

# ADR-0010: Risk level decides who approves, not how many; non-prod needs no approval

- **Status:** Accepted; superseded in part by [ADR-0012](0012-approval-integrity-checked-by-the-gate-app.md)
  (two approvers on process paths) and extended by [ADR-0011](0011-database-changes-through-the-pipeline.md) (L3-data-write)
- **Date:** 2026-11-09
- **Decided by:** owner of this submission (GĐ-14; OD2, OD3, OD8, OD9, OD13)
- **Scope:** every change made by engineers and their agents, from non-prod to production

## 1. Context

Engineering says "Let Claude Code talk to AWS directly" (brief); the need is speed. Compliance's
sentence covers production writes only (framing §3.1). A single rule for all changes either slows non-prod for
no gain or leaves high-risk prod changes with too light a review. The owner also wants every prod
change to need two people, no more by default: one who makes it and one who approves it (OD2).

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. Same approval for everything | Simple | Non-prod loop slowed for no gain; high-risk changes get no extra scrutiny |
| B. More approvers as risk grows (e.g. two for L3) | More eyes on dangerous changes | Breaks the two-person rule; slower incidents |
| C. Risk level narrows who may approve, plus a risk stop; non-prod free | Fast where damage is small; specialist owners where it is large | One reviewer for high-risk changes can miss things |

## 3. Decision

Option C [design levels]:

| Level | What | Approval |
|---|---|---|
| L0 | Reads: non-prod anything, prod metadata | none |
| L1 | Changes in non-prod (synthetic or masked data only, GĐ-14) | none, author only |
| L2 | Routine prod change, e.g. Lambda memory 1024 → 2048 MB | 1 code owner ≠ author, ≠ last pusher |
| L3 | IAM/SCP, stateful replace/delete, network, workflow and agent-config files, catalogue, advisory policy finding (full list: framework layer 5) | 1 owner of that path; *two members of the L3 owner team on process paths (ADR-0012)* |
| L3-JIT | Break-glass in an incident | on-call approver ≠ requester (ADR-0005) |
| L3-data-write | Data fix on one tenant's rows (added by ADR-0011) | code owner + a different person from that tenant's data-owner team (ADR-0012, rule R4) |
| L3-data | Real customer data read | approver ≠ requester + agreement; data-owner co-approval [design] (ADR-0009) |

`CLAUDE.md` and the other agent-configuration files are L3, because they define the workflow for the
whole team (OD3). Process-defining paths and the SCP stack are owned by the L3 owner team; IAM or
stateful changes inside a domain file are approved by that stack's owners (OD8, OD13). At every level,
the risk stop applies to any deploy whose prod diff is risky (ADR-0004).

## 4. Consequences

- **Positive:** a free non-prod loop for engineers and agents (S4); the same two-person rule for every
  prod change, incidents included (three people only by recorded deviation, OD11). Compliance gets a written rule for who may approve what.
- **Negative / trade-offs:** one approver for high-risk changes (owner's trade-off for speed);
  `CLAUDE.md` edits wait for the L3 owner team, not the domain team that edits them most.
- **Risks & how we watch them:** the free loop holds only if non-prod has no real data; a non-prod
  store not yet scanned follows the L3-data rule until scanned (S11). A risky diff hidden in an L2 PR is
  caught by the risk stop, not by the level (Pulumi and Serverless stacks only;
  k0s and Firebase have none yet, G1, G2).
- **Next steps:** non-prod data scan and CODEOWNERS with the L3 path list in phase 1; composition of
  the L3 owner team is open (G17).

## 5. References

- Framework layer 3 (levels table), layer 5 (canonical L3 path list), layer 6 (non-prod).
- Related: ADR-0003, ADR-0004, ADR-0005, ADR-0009.

# ADR-0011: Database schema changes and data fixes go through the pipeline like any prod change

- **Status:** Accepted
- **Date:** 2026-11-09
- **Decided by:** owner of this submission, after the independent review (`work/07-review.md`; OD29)
- **Scope:** Aurora PostgreSQL schema migrations, GraphQL-engine (Hasura) metadata, and data fixes on prod

## 1. Context

"Every prod change is a pull request" (ADR-0001) had no designed path for the two most frequent
prod changes of a claims platform on Aurora with a GraphQL engine: schema migrations and data fixes
(a stuck claim, a payout to retry). Once standing prod write is removed (rollout 1.16), nobody has a
legitimate way to run them, which invites a shared database account or an admin endpoint: the
shortcut the framework exists to remove. Data fixes also touch one tenant's customer data, which
layer 6 treats as L3-data. IAM database authentication is not logged by CloudTrail (📖 R9.2.11).

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. JIT grant with `psql` for data fixes; migrations at app start | Fast; no new tooling | An approved command list, not an approved change (ADR-0005's weakness) for routine work; migrations run with the app's role |
| B'. As B, but a self-hosted runner inside the VPC connects directly | One less hop | A long-lived runner with prod network access (framework layer 5 avoids self-hosted runners) |
| B. Migration and data-fix files in the monorepo, applied by the deploy workflow with a database role of its own, behind the risk stop | Same gate, same evidence as every other change | A migration job and two wrapper scripts per migration tool; data fixes need two approvers |
| C. A separate database change tool with its own approvals | Purpose-built | A second approval system outside GitHub; a side path (T20) |

## 3. Decision

Option B [design]:

- **Files:** migrations, GraphQL-engine metadata and data fixes live under `db/<service>/`; data
  fixes under `db/<service>/data-fixes/<tenant>/<ticket>.sql`, one tenant per file, with an
  `-- expected_rows: N` header.
- **Approval:** migrations and metadata as any deployable path (domain owner, on-call in an
  incident). Data fixes are **L3-data-write**: a code owner plus a different person from that
  tenant's data-owner team, checked by the approval-gate app (E12, rule R4), which reads the
  tenant from the path; data owners are not code owners, so they need read access only, and a
  tenant without a data-owner team fails the check. In an incident the on-call approver stands
  in and the data owner reviews the next working day (layer 6).
- **Apply:** a `sql` job of the deploy workflow lists the pending files, runs the risk stop on them
  (`--tool sql`: DROP, TRUNCATE, column type changes, unscoped DELETE/UPDATE, grants, roles,
  row-level security, COPY, function bodies, every metadata change, and any INSERT, UPDATE or
  DELETE in a migration, which belongs in a data fix, stop for a stack owner's approval), then applies exactly the classified files, each in its own transaction; a data fix
  whose affected-row count differs from its header is rolled back.
- **Where it runs and credentials:** Aurora is private to the prod VPC, so the GitHub-hosted job
  does not connect to it. The job runs in its own environment, `production-db`, which no other
  deploy job can use, and installs no package. Its OIDC role may only start the `db-change-<service>` ECS task on one
  cluster, pass that task's roles and use one S3 prefix; the one-off Fargate task runs in private
  subnets, checks the SHA-256 of the classified bundle, and connects with `rds-db:connect` as the
  migration user (📖 R9.2.11). Metadata is applied by the same task with `hasura metadata apply`
  and the engine's admin secret, injected from Secrets Manager (📖 Hasura CLI docs, framework
  layer 3). No person holds database credentials or the admin secret day to day (examples E15).
- **Evidence:** the PR, the job log and summary (statement kinds and row counts, never values),
  the risk-stop record; database-side activity through Database Activity Streams (layer 7),
  because IAM database authentication is not in CloudTrail.

## 4. Consequences

- **Positive:** the most common prod changes get the same gate and evidence chain as code; data
  fixes are scoped to one tenant and approved by its data owner; no standing database access.
- **Negative / trade-offs:** a data fix takes a PR, two approvals and a deploy run instead of a
  `psql` session; the two `tools/db/` scripts, the task image and its task definition must be
  built for Papaya's migration tool (unknown here); a Fargate task start adds about a minute per
  run (⚠️ not measured); the SQL classifier is a heuristic, not a parser (examples E7).
- **Risks & how we watch them:** a destructive statement hidden in a form the heuristic does not
  know (function bodies and `EXECUTE` already stop); a wrong `expected_rows` is caught only if the
  count differs; long migrations hold locks (expand/contract recommended, not enforced).
- **Next steps:** `tools/db/` wrappers and the migration role in phase 1, before standing prod write
  is removed (rollout 1.23).

## 5. References

- Framework layer 3 ("Database changes"), layer 6 (L3-data), layer 7 (Database Activity Streams).
- Examples E3 (`sql` job), E7 (SQL rules), E12 (rule R4), E15 (the CI and task roles).

# ADR-0012: Approval integrity is checked by the approval-gate app: two approvals on process paths, on-call approvals only for open incidents

- **Status:** Accepted; supersedes in part ADR-0003 (domain review on normal days as a process rule; one approval for cross-team PRs, OD10) and ADR-0010 (one approver for L3 process paths)
- **Date:** 2026-11-09
- **Decided by:** owner of this submission, after the independent review (`work/07-review.md`; OD26, OD27)
- **Scope:** pull requests to `main` of the monorepo; the `approval-gate` required check

## 1. Context

ADR-0003 made the merge to `main` the approval gate, with an on-call group that co-owns every
deployable path, so that one primary can approve any fix at night. GitHub accepts an approval from
any listed owner (📖 R3.2.7), so on normal days that group could approve any domain's PR, and the
`incident` label that was meant to limit this can be applied by anyone with Triage (📖 R9.1.9).
ADR-0010 kept one approver for every level. The review also found that a compromised plugin or
local MCP server runs on every laptop and could give an attacker many GitHub logins at once
(threat T23), so a single approval on the files that define the process is one stolen login away.
A path-scoped reviewer rule was not found for GitHub Team (📖 R9.1.15), and the ruleset's approval
count is repository-wide.

## 2. Options considered

| Option | Pros | Cons |
|---|---|---|
| A. Keep process rules and the monthly report | No new logic | The label is free to apply; the report misses labelled PRs; one login changes the process |
| B. Raise the ruleset to two approvals for every PR | Built into GitHub | Doubles review for every change, against S4 and the owner's two-person rule |
| C. The approval-gate app, already required, checks the rules per file | Exact rules per path; works on Team | More logic in a custom app that every merge depends on (G19) |

## 3. Decision

Option C [design]. The app's decision logic is examples E12 (`examples/approval-gate/gate.py`):

- an approval counts only if it is on the head commit, or on an earlier commit with the same diff
  against its merge base (OD31), by a human who is not the author, the last pusher of a change to
  that diff or the person who triggered an app-opened PR (📖 R9.1.10 for the review fields);
- every changed file needs a counted approval from one of its owner teams;
- an on-call group member's approval counts for another team's file only if the PR carries the
  `incident` label, links an incident that is open when the check runs, and the approver is on
  shift (OD27);
- a file owned only by the L3 owner team (a process path, including the IAM stack since OD32) needs
  two different members of that team (OD26);
- approvals within two minutes of the last push, or at night without an incident, are flagged for
  the monthly report, not blocked.

## 4. Consequences

- **Positive:** domain review on normal days and the two-person rule on process paths are enforced,
  not trained; the incident lane cannot be opened by a label alone; flagged approvals give a
  detection signal for rubber-stamping and stolen logins.
- **Negative / trade-offs:** process-path PRs need two L3 owner team members; a cross-team PR on a
  normal day needs an owner of each team (OD10's single approval now holds only in incidents);
  a stale schedule or incident record blocks a night approval until the backup or a domain owner
  approves; every merge depends more on the app.
- **Risks & how we watch them:** if the app is down, every merge is blocked, incident PRs included,
  and the JIT fallback applies (layer 7); its hosting, key and triggers stay open (G19); the schedule
  file is an L3 path; the monthly report lists every `incident` PR and every flagged approval.
- **Next steps:** the app becomes a hard prerequisite in phase 1, before the ruleset requires its
  check (rollout).

## 5. References

- Framework layer 3 ("L3 approvals", "Who approves at night"), layer 4 ("Pinning what every
  laptop runs"), layer 7 (on-call); threat model T7, T23.
- Related: ADR-0003, ADR-0006, ADR-0010.
