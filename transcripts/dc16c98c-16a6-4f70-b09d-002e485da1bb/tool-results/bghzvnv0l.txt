    33	## 1. The decision in one page
    34	
    35	Engineering and Compliance disagree only about **writes to production**; reads of metadata and all
    36	of non-prod are outside Compliance's sentence (framing §3.1). Real customer data is layer 6.
    37	
    38	**Chosen approach "A + D2'"** (Options §9, owner decision 2026-11-09):
    39	
    40	1. **Default path:** every prod change is a pull request, approved by a named human who is not the
    41	   author, applied by CI. Incidents included ("IaC first").
    42	2. **Fallback (break-glass):** only when the PR path cannot be used, a human gets an approved grant
    43	   with a 1-hour role session (effective window up to about 2 h, ⚠️ R2.9 #3) and runs an approved command list in a terminal without an agent (layer 7) [design].
    44	3. **Nothing standing:** no human or agent holds standing prod write; no long-lived credentials.
    45	
    46	| Engineering gets | Compliance gets |
    47	|---|---|
    48	| A free loop in non-prod: read, change, deploy without approval (non-prod is synthetic or masked, GĐ-14; stores not yet scanned are excluded, layer 6). | Every prod change approved **before** apply by a named human ≠ author (GĐ-8, GĐ-11), enforced in GitHub and AWS IAM, outside the agent (limits below). |
    49	| Read-only prod metadata for the agent. | No standing prod write (S1), no long-lived CI keys (S2, with an owner-approved exception for k0s/Firebase deploy credentials, OD1, OD6; storage conditions [design], layer 5). |
    50	| Self-service PRs, one approval, same-day ship (S4). | One evidence chain per change; approval and change records ≥ 6 years (📖 R5.2.9; applied to change records ⚠️ R5.7 #2). |
    51	| Incident lane: approval wait ≤ 15 min, 24/7 (S7). Decision-to-apply target ≤ 30 min (Options §9); current estimate 11–46 min ⚠️, measured first in rollout. | Agent-side controls as a second layer, not the control of record. |
    52	
    53	**Where the design falls short, stated openly:**
    54	
    55	- **The fallback meets the approval rule only partly** (approves a command list, not an applied
    56	  change); accepted by the owner (Options §9 Q2). It is a second, process-controlled path, while the
    57	  framing asked for one technically enforced path (framing §3.3, Options §7). It stays narrow only
    58	  if most incidents are expressible in IaC (unknown, Options §8); layer 7 measures this.
    59	- **On GitHub Team nobody sees the prod diff before apply** (⚠️ R4.6 #1; Team assumed, GĐ-5).
    60	  Risky prod diffs stop the deploy until an owner of the stack approves the prod preview [design].
    61	- **Admins can edit the gate**; logged, not prevented (logging 📖 R3.2.2; ability to edit ⚠️ R3.2.2,
    62	  R3.6 #1). An admin's agent has
    63	  the same power, because the agent uses its engineer's GitHub login (⚠️ R6.5 #10).
    64	- **Some rules are process, not technology:** see "Process rules" in layer 1. The owner's rule
    65	  "the PR approver is always an engineer, never an agent" (OD5) is absolute as policy, but on
    66	  laptops it is enforced by policy and training, not by a technical control: an agent could approve
    67	  through its engineer's login, and no detection was found.
    68	- **Incident approvers vs domain review:** code-owner review means an approver must own the file,
    69	  at L2 as at L3. So that one on-call primary can approve any deployable path at 2 a.m., the on-call approver
    70	  group co-owns every deployable path (owner decision OD9, layer 3). The cost: GitHub accepts an
    71	  approval from any listed owner (📖 R3.2.7), so on normal days that group could approve another
    72	  domain's PR. Domain review on normal days becomes a process rule with a monthly check, not a
    73	  technical control. Because on-call approvers only
    74	  approve (OD7), a night incident needs two people awake: the incident responder and the on-call
    75	  approver (the backup only replaces an unavailable primary).
    76	- **One approver for high-risk changes.** L3 changes (IAM, stateful deletes, workflow files) get one
    77	  approver, like L2, but the path is owned by the L3 owner team (or by the stack's owners for L3
    78	  content in domain files, OD8), and risky prod diffs stop for a look at
    79	  the prod preview (OD2, OD8, layer 3). A single reviewer can miss things; this is the owner's trade-off
    80	  for speed.
    81	- **k0s and Firebase are weaker:** no prod preview or risk stop, no break-glass when Actions is
    82	  down (G1, G2), and their deploy credentials are stored in GitHub (OD1). For k0s, the interim
    83	  controls of OD24 (a namespaced, time-limited deploy token and the Kubernetes API audit log) rely
    84	  on `extraArgs`, which is "outside k0s support" (📖 R9.3.1).
    85	- **New dependencies on two GitHub Apps** (required check, CI agent): if the required-check app is
    86	  down, every merge to `main` is blocked, incident PRs included; that counts as "pipeline
    87	  unavailable" for JIT. Their keys and hosting are open (G19).
    88	- **HIPAA applicability is a legal question** (⚠️ R1.11.1.11); the design treats Papaya as a
    89	  business associate, as the brief implies.
    90	
    91	**Cross-cutting rules** (owner's balance principle, research 6.8):
    92	
    93	1. **The boundary is IAM and the CI gate.** Server-managed settings are "a client-side control, not
    94	   a security boundary" (📖 R1.1.7); local admins can edit endpoint files (📖 R1.1.8).
    95	2. **Assume prompt injection succeeds:** neither OWASP nor NIST knows a full prevention (📖 R6.1.1, R6.1.2).
    96	3. **Friction where damage is large, none where it is small**, measured, with a time-boxed escape.
    97	4. **Evidence by construction:** the path produces the records.

    99	### Roles
   100	
   101	| Role | Rule |
   102	|---|---|
   103	| Author (engineer + their agent) | Never approves own change; GitHub blocks PR authors from approving (📖 R3.3.1). |
   104	| Approver | Always an engineer, never an agent (owner rule, OD5). Named in CODEOWNERS; ≠ author, ≠ last pusher (📖 R3.2.3); for an app-opened PR, ≠ the person who triggered it (⚠️ R3.3.4, layer 5). |
   105	| Incident responder | Engineer who diagnoses and writes the fix or the JIT request. Never the on-call approver of the same shift (OD7). |
   106	| On-call approver | Engineer on the on-call schedule, primary + backup, 24/7; wait ≤ 15 min (S7). While on call they only approve: they write no fix and file no JIT request, so the approver is always distinct from the author (OD7). The primary approves; the backup replaces an unavailable primary (OD2). No platform-team membership is required; all engineers follow one agreed approval procedure (OD2). |
   107	| Data owner [design] | Named per tenant; co-approves real-data reads, or reviews a night-time read the next working day (layer 6). |
   108	| Control owner | DevSecOps (1–2 people, GĐ-1); owns policies and metrics; not the only approver. |
   109	| L3 owner team | Owns the process-defining L3 paths and the SCP stack (layer 3); composition open (G17). |

   113	## Layer 1 — Identity and access
   114	
   115	**Principle.** Every action traces to one named human. Nobody holds standing prod write: prod is
   116	written by the pipeline role, or in the fallback by an approved, time-boxed grant. Prod reads default
   117	to metadata. No long-lived credentials. Prod and non-prod are separate boundaries.
   118	
   119	**On Papaya's stack**
   120	
   121	- **The engineer's access is the agent's access.** The agent uses the engineer's AWS SSO cache, and
   122	  one portal session reaches every role assigned to that engineer (📖 R2.2.1, R2.2.2; token-reuse
   123	  detail ⚠️ R2.2.2). A separate
   124	  "agent" permission set does not separate them (⚠️ R2.9 #1). The control is what the **engineer**
   125	  holds.
   126	- **Process rules** that follow from this:
   127	  - the JIT terminal runs no agent, though the grant is reachable from the same laptop (owner
   128	    accepted as a process control, D2);
   129	  - the incident-analysis session is meant to use only read-only roles (D2; `--restricted` per D3,
   130	    research 6.9.4 Q2);
   131	  - the real-data terminal runs no agent when the store holds PHI [design], same weakness as D2;
   132	  - an agent never approves PRs: an owner rule (OD5), enforced on laptops by policy and training.
   133	    GitHub blocks self-approval only. The auto-mode default block list
   134	    excerpt read names "approving Claude's own pull request" (📖 R6.3.3); whether approving
   135	    someone else's PR is blocked is unverified (⚠️), and the list
   136	    applies only in auto mode. No detection was found (⚠️; `actor_is_agent` in the audit log has no
   137	    documented meaning, R3.5.6).
   138	- **IAM Identity Center permission sets** (📖 R2.1.1) [design names]:
   139	  - `ProdReadMetadata`: metrics, redacted log groups, configuration; no data-plane read on claim
   140	    stores; 1 h session, the minimum (📖 R2.1.4). Some "metadata" reads (mostly ⚠️) return configuration or
   141	    secrets, so `Resource: "*"` only for a reviewed action list (examples E6, findings 11, 12). Until a service's logs are redacted at source
   142	    (layer 6), it gets that service's metrics only. Lambda configuration can hold secrets resolved by
   143	    Serverless in plain text (⚠️ R4.4.7), so configuration reads are allowed per service only after
   144	    its secrets move to runtime resolution (⚠️ R4.6 #7). Cost: until then the agent reads
   145	    timeout/memory from the IaC code;
   146	  - `NonProdDeveloper`: broad, non-prod accounts only;
   147	  - `InfraOperator-<service>`: assigned only by the JIT flow (layer 7), via a partner product, the
   148	    TEAM sample (📖 R2.4.1, R2.4.1b) or a small home-built flow (⚠️ R2.4.2) on the documented APIs
   149	    `CreateAccountAssignment` / `DeleteAccountAssignment` (📖 R2.4.2);
   150	  - no standing prod-write permission set.
   151	- **SCPs on the prod OU** [design] (SCPs cap member-account principals, 📖 R2.3.1, R2.3.2):
   152	  - deny data-plane reads on claim stores except application roles and the approved data-read role,
   153	    by `aws:PrincipalArn` (📖 R2.3.8; pattern ⚠️ R2.9 #4). Actions, e.g. `s3:GetObject`,
   154	    `sqs:ReceiveMessage`, `states:GetExecutionHistory`, are incomplete and unchecked (⚠️ G13);
   155	  - deny `lambda:UpdateFunctionCode` / `lambda:UpdateFunctionConfiguration` (⚠️ R4.6 #3) except
   156	    CloudFormation `deploymentRole`s, the Pulumi prod deploy role (if Pulumi manages Lambdas) and the
   157	    JIT roles. The Serverless prod deploy role is a separate role and is not exempt: it only passes
   158	    the `deploymentRole` (examples finding 13). This closes `serverless deploy function`, which changes config outside CloudFormation
   159	    (📖 R4.4.4), and needs `deploymentRole` set on every Serverless stack (key 📖 R4.4.5; need ⚠️ R4.6 #3);
   160	  - a pre-deployed revocation Deny on `identitystore:UserId` (📖 R2.4.4); deny changes to any trail
   161	    in prod accounts, since member accounts cannot touch the organization trail anyway (📖 R2.6.2;
   162	    examples findings 10, 15);
   163	  - exempt role names are protected: only the IAM stack's deploy role may create or change such
   164	    roles (OD19), and from phase 1 that is a role of its own (OD22): the IAM stack deploys from a
   165	    separate GitHub environment, `production-iam`, whose OIDC subject only that role trusts. So
   166	    code running in a domain stack's deploy job cannot obtain it. Domain deploy roles (and the
   167	    CloudFormation `deploymentRole` of each Serverless stack) may create or change only `svc-*`
   168	    roles, and only with a fixed permissions boundary attached that they cannot remove or edit
   169	    (pattern 📖 R9.2.1; role action list ⚠️; examples E4b). The boundary denies `iam:*` and
   170	    root sessions. Cost: Lambda and ECS roles that read claim data (`app-claims-*`) live in the
   171	    IAM stack and are referenced by ARN (examples finding 16);
   172	  - deny every action of `OrganizationAccountAccessRole` in the prod OU (OD23). Organizations
   173	    creates this role with "full administrative permissions" in each account it creates, trusted
   174	    by the management account (📖 R9.2.4); SCPs cover it as any other member-account role
   175	    (📖 R9.2.6, inference). Using it in an emergency needs an SCP change, an L3 path.
   176	  - Limits: 10 SCPs per target, 10,240 characters; no SCP applies to the management account
   177	    (📖 R2.3.2, R2.3.4), so whatever deploys SCPs there is the most sensitive role (L3 path, held by the L3 owner team only, not co-owned by the on-call group; OD13).
   178	- **Who administers the administrators (OD23).** Whoever administers IAM Identity Center can
   179	  assign themselves any permission set, so "no standing prod write" holds only if that power is
   180	  itself controlled [design unless marked]:
   181	  - permission sets and account assignments are code in an identity stack (an L3 path, L3 owner
   182	    team only, not the on-call group), applied from CI; the only other writer is the JIT flow's
   183	    automation, which creates and deletes `InfraOperator-*` and `DataRead-*` assignments;
   184	  - an alert fires on Identity Center changes (`CreateAccountAssignment`, `CreatePermissionSet`,
   185	    `PutInlinePolicyToPermissionSet`, `AttachManagedPolicyToPermissionSet` and the other events
   186	    with source `sso.amazonaws.com`, 📖 R9.2.2) made by any principal other than those two;
   187	    which account's trail records changes made from a delegated administrator is not documented
   188	    (📖 R9.2.2 "not found"), so the organization trail covers both accounts;
   189	  - day-to-day administration from a delegated administrator account (📖 R9.2.3). It cannot touch
   190	    permission sets provisioned in the management account, which stays a smaller circle;
   191	  - the management account: no workloads, a named group of at least two L3 owners with hardware
   192	    MFA, reviewed quarterly (C-03). SCPs never apply there (📖 R9.2.6), so this group is a
   193	    detective control only;
   194	  - member-account root users: credentials removed through centralized root access; privileged
   195	    root tasks run from the management account with `sts:AssumeRoot` (📖 R9.2.5).
   196	- **Sessions/MFA:** portal session length set on purpose; an IdP session can extend it silently
   197	  (📖 R2.1.5, R2.1.6). MFA lives in the external IdP if one is used (📖 R2.1.7).
   198	- **CI → AWS:** GitHub OIDC, no stored keys (📖 R3.4.1). The prod role trusts only the `production`
   199	  environment of the monorepo, in its `sub` format (📖 R3.4.3, R3.4.4; immutable format assumed,
   200	  ⚠️ R3.7 A2), ideally customised with the deploy workflow's `job_workflow_ref` (📖 R3.4.5; on Team ⚠️ G10).
   201	- **CI → GCP:** Workload Identity Federation restricted to Papaya's GitHub organization, which Google
   202	  requires (📖 R3.4.5b).
   203	- **k0s, GCP and Firebase for humans:** same principles; mechanisms not researched (G1–G3). Today
   204	  k0s is reached with kubeconfigs, no SSO (GĐ-4, unconfirmed). Interim: no admin kubeconfig and no GCP
   205	  owner role on laptops; prod deploys only from CI. Firebase is not on the GCP BAA list (📖 R5.5.3), so
   206	  Firebase Hosting must hold no PHI (⚠️ R5.7 #7).
   207	- **k0s deploy identity (OD24).** Interim, phase 1: the CI credential is a time-limited
   208	  ServiceAccount token, not an admin kubeconfig, bound to a namespaced Role that cannot read
   209	  Secrets, exec into pods, read pod logs, issue tokens, change RBAC, impersonate or delete
   210	  (📖 R9.3.6, R9.3.7; examples E11). Creating a workload grants it the API access of any
   211	  ServiceAccount in its namespace (📖 R9.3.7), so deploy namespaces hold no privileged
   212	  ServiceAccount. Target: kube-apiserver trusts GitHub's OIDC tokens directly through structured
   213	  authentication, stable from Kubernetes 1.34 (📖 R9.3.4), so nothing is stored in GitHub; k0s
   214	  does not document it (📖 R9.3.5), the API server must be reachable from the runner (📖 R9.3.8),
   215	  and the claim rule must use the repository's real `sub` format (📖 R9.3.9).
   216	
   217	**Audit evidence.** Identity Center assignment export (S1), CloudTrail grant events per JIT request, SCP and trust-policy code, Access Analyzer results from phase 2, and a quarterly access review; full register: [04-compliance-mapping.md](04-compliance-mapping.md#register).
   218	
   219	**Cost / value.** Engineers lose standing prod write and keep a free non-prod loop. Prod reads stay
   220	fast for metrics and metadata, but shrink during the transition: because the engineer's access is the
   221	agent's access, from phase 1 the engineer too loses raw logs and configuration of services not yet
   222	redacted or moved to runtime secrets. Configuration values come from the IaC code instead (layer 1
   223	above); raw logs that may hold customer data need an L3-data grant. The data owner is not on the
   224	on-call schedule, so at night the grant is approved by the on-call approver alone and the data owner
   225	reviews it the next working day [design]; the wait still counts against S7. This is
   226	the largest cost of the first months. Compliance gets least privilege that is enforced.

   230	## Layer 2 — Agent runtime controls
   231	
   232	**Principle.** Agent-side controls are hygiene, not the boundary. They are central, versioned in git
   233	and the same for everyone. Defaults are safe; overrides are measured. The session that reads
   234	untrusted content holds as little power as possible (📖 R6.1.2).
   235	
   236	**On Papaya's stack**
   237	
   238	- **Delivery:** server-managed settings (available on Team, 📖 R1.1.5) for all laptops. With MDM, also
   239	  an endpoint file; by default one managed source supplies most keys, so the two must carry the same
   240	  keys or use `managedSourcesBehavior: "merge"` (📖 R1.1.3, R1.1.4). MDM is unknown; both are prepared.
   241	- **Baseline** (template: Anthropic's `settings-hipaa.json`, 📖 R5.5.4). All keys 📖 at the row cited. Only the phase-1 subset ([rollout plan](03-rollout-plan.md) item 1.18) ships first; the other keys (sandbox, `allowManagedHooksOnly`, most credential denies, `allowManagedPermissionRulesOnly`, `allowedProviders`, `forceLoginOrgUUID`, the `ask` rule for WebFetch, and the other deny rules) arrive in phase 2 (OD4):

   259	- **Trade-off on AWS credentials [design].** With `~/.aws` hidden from the sandbox, phase 2 lists
   260	  `aws *`, `pulumi *` and `serverless *` in `sandbox.excludedCommands`. Excluded commands run "with
   261	  full access" (📖 R1.6.4), network included ("no filesystem restrictions and no network proxy", 📖 [sandboxing](https://code.claude.com/docs/en/sandboxing.md#run-commands-outside-the-sandbox-with-excludedcommands)). Matching follows `Bash(...)` rule
   262	  syntax on the command text (same page; details in examples finding 22); each excluded
   263	  call prompts through the `ask` rules above. This is worse than an
   264	  egress channel: `pulumi preview` runs the Pulumi program and `serverless` loads its config and
   265	  plugins, all code in the repo that the agent can edit, so excluding them lets repo code run
   266	  outside the sandbox with network access and with `~/.aws` readable (⚠️ inference). For these
   267	  commands the sandbox gives no protection. And an injected `aws` command could send out the SSO
   268	  token cache itself. That token likely opens every role assigned to the engineer for the rest of the
   269	  portal session (📖 R2.1.5; token reuse ⚠️ R2.2.2), probably including JIT or data-read grants added
   270	  later in that session (⚠️ inference). Mitigations [design]: a short portal session (📖 R2.1.5); end
   271	  the existing portal session and sign in fresh **before** a JIT or data-read grant is created
   272	  (whether ending a session invalidates a token already stolen is unverified ⚠️; ending it does not
   273	  end role sessions, 📖 R2.4.3); an SCP that denies writes to resources outside Papaya's organization using
   274	  `aws:ResourceOrgID` (key 📖 R2.3.8), on every OU, since the token can be stolen from a non-prod
   275	  session; legitimate writes to outside resources need exceptions (⚠️ not inventoried). That SCP only stops Papaya's own credentials writing to a
   276	  foreign bucket; it does not stop a command that sends the token to a non-AWS endpoint or uses the
   277	  attacker's credentials (⚠️ inference). Prefer running `pulumi` and `serverless` against real
   278	  accounts only in CI; on laptops keep them to non-prod roles, and move them into the phase-3
   279	  container. Residual risk: token theft during a session. It is accepted
   280	  because the engineer holds no **standing** prod write and no **standing** PHI read; during a JIT
   281	  or data-read window the protection is the process rule in layer 1 (D2). Stronger option, phase 3:
   282	  a separate OS user or container for prod-reading sessions
   283	  (⚠️ R6.5 #2).
