   152	## Limits of the risk stop
   153	
   154	The risk stop answers one framework problem: on GitHub Team nobody sees the prod diff before
   155	apply (framework §1). It catches **risky prod diffs that nobody looked at**. It is not a boundary
   156	against **malicious or prompt-injected code that was approved**:
   157	
   158	- The stack's own code runs with the stack's prod deploy role: `npm` packages are installed before the
   159	  credentials, with install scripts off (OD22), but the Pulumi program runs during `preview` and
   160	  `up`, and Serverless plugins during `package`/`diff`/`deploy`. That code could call AWS
   161	  directly, or tamper with files the classifier reads, in the same job. The defence against it
   162	  is the PR review itself, and from phase 2 IAM Access Analyzer and policy packs (layer 5).
   163	- A stronger variant [design, not in the framework]: preview with a separate prod **preview**
   164	  role (read and state access, no write), run the classifier in its own job on a fresh
   165	  checkout without credentials, and assume the deploy role only in a later job after the stop.
   166	  It adds a role and a job split; it is an open question for the owner.
   167	- `pulumi up` previews again before applying. A change made outside the pipeline between the
   168	  two previews (JIT, drift) is not re-checked. `pulumi preview --save-plan` + `pulumi up --plan`
   169	  would bind the two, but update plans are experimental (📖 R4.1.3).
   170	- Concurrency: a running deploy is never cancelled, but GitHub cancels a run that is still
   171	  pending when a newer one arrives for the same group (📖 GitHub docs source,
   172	  `data/reusables/actions/actions-group-concurrency.md`). Some merged commits therefore have no
   173	  deploy run of their own; the newer run deploys them too, and the change record must link both
   174	  commits to that run. `queue: max` would give every commit its own run, but the same page says
   175	  the order "is not guaranteed": an older commit could then deploy after a newer one and undo it
   176	  in prod. So the default is kept on purpose [design].
   177	- The type lists are examples. For types that are missing, the rule on property names
   178	  (`policy`, `role`, `securityGroup`, `vpcConfig`, `public`, `authorization`, `logging`, …;
   179	  a narrower set on creates) catches some changes, not all.
   180	- **Code in the deploy job can act as either deploy role of its environment.** `id-token: write`
   181	  is job-wide, so the Pulumi program, Serverless plugins and any allowlisted install script can
   182	  request the job's OIDC token (⚠️ from memory of GitHub's OIDC docs) and assume either role that
   183	  trusts that environment. Since OD22 (phase 1) that is a domain stack's bounded roles, never the
   184	  IAM stack's role (`production-iam`, E4), and no other install script runs
   185	  (`npm_config_ignore_scripts`). Still on the phase-2 roadmap with OD15: a separate preview role
   186	  and a build job without `id-token`.
   187	- **Open gap:** nothing proves that a deploy really stopped at `stopped_commit` with the
   188	  approved hash. An approval merged early (naming a commit whose deploy did not stop, with a
   189	  hash computed in advance, which needs knowledge of prod inputs) is accepted if a later change
   190	  **outside** the stack's directory, such as a shared library, produces exactly that diff. Changes
   191	  inside the stack's directory are rejected. Watching the whole repository instead would cancel
   192	  every approval at each unrelated merge in a monorepo. The fix is for the approval-gate app to
   193	  check, on the approval PR, that the stopped run's summary carries the same hash (G19) [design].
   194	  `test_known_gap_early_approval_and_change_outside_the_stack` documents the current behaviour.
   195	- The approver of the approval PR sees **which** prod resources and properties change, not the
   196	  new values (the summary never prints values, to keep secrets out of logs). The values are
   197	  reviewed in the code of the stopped PR. Framework layer 3 and ADR-0004 say the approver "sees
   198	  the prod diff"; that wording is too strong and is corrected in the framework's final pass.
   199	- Any commit to the stack's directory between the stop and the approval merge cancels the
   200	  approval: the author names the newer stopped commit and the owner approves again. In an
   201	  incident that is one more review round.
   202	- `npm ci` runs before the credentials with lifecycle scripts off (OD22). The allowlisted
   203	  packages' scripts still run, and could write to `$GITHUB_ENV` / `$GITHUB_PATH` and so influence
   204	  later steps that hold credentials; that is why the allowlist is an L3 path.
   205	- If the newest merge to `main` carries `[skip ci]` (or similar) in its message, no push run
   206	  exists for the tip and the older runs refuse to deploy; prod stays behind until the next merge
   207	  (📖 GitHub docs source, `content/actions/how-tos/manage-workflow-runs/skip-workflow-runs.md`,
   208	  via review). Operator action: merge an empty change.
   209	- Within 7 days, an approved change that is reverted and then merged again with identical code
   210	  passes without a new approval. This is intended: it is the same code and the same prod diff
   211	  that an owner approved.
   212	- The binding relies on squash-only merges (`ruleset-main.json`); with merge commits, a PR's
   213	  inner commits would be invisible to the first-parent check.

   215	## Findings from writing these files
   216	
   217	Points the framework text does not yet say; carried into the framework in the final pass.
   218	Owner decisions 2026-11-09 (framework OD14–OD18): findings 1, 3 and 4 accepted; the risk stop keeps
   219	its current scope (OD15); the early-approval gap is an accepted limit for G19 to close (OD18).
   220	Step 2: finding 16 accepted (OD19); the job-wide OIDC token limit goes to the phase-2 roadmap
   221	with OD15 (OD20). After the independent review (2026-11-09), OD22 moves the per-environment roles
   222	into phase 1.
   223	
   224	1. **The risk-stop classifier must be an L3 path** [design]. The deploy runs it from the merged
   225	   commit, so a PR that edits it together with an IAM change, approved by the domain team, could
   226	   switch the stop off. `CODEOWNERS` adds `/tools/risk-stop/` to the L3 owner team. Confirmed by
   227	   the owner (OD14): it extends the canonical L3 list of framework layer 5.
   228	2. **An approval must be bound to git history, not only to a hash** [design]. Two review rounds
   229	   found ways for one PR to carry its own risky change and approval, or for an approval to be
   230	   reused. Rules now: read from git objects only; file named `<stopped_commit>.yaml`, never
   231	   edited; stopped commit and approval commit both on `main`'s first-parent history, in that
   232	   order; the approval commit touches only `deploy-approvals/<stack>/`; the stack's directory
   233	   and the classifier unchanged since the stopped commit; at most 7 days old.
   234	3. **Squash-only merges** [design]: `ruleset-main.json` allows only squash, so each PR is one
   235	   commit on `main`. Cost: PR-internal history is not kept on `main`.
   236	4. **Deploy only the tip of `main`** [design]: people with write access can re-run a workflow run
   237	   for up to 30 days, with the same `GITHUB_SHA` (📖 GitHub docs source,
   238	   `content/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs.md`, via review). An
   239	   old deploy run re-run would roll prod back without any approval. `deploy-prod.yml` stops unless
   240	   the run's commit is the current tip of `main`, read with `GET /repos/{owner}/{repo}/git/ref/heads/main`
   241	   (✅ branch-only form; `commits/main` could resolve to a tag named `main`). This is a new
   242	   condition for framework layer 3's "merge approval = deploy approval" list.
   243	5. **Classification beyond the framework's categories** [design]: the property-name rule, the
   244	   audit/detection category and "an unknown operation stops" go beyond layer 3's list
   245	   (stateful replace/delete, IAM, network, policy finding).
   246	6. **The approval hash must cover changed values**, not only resource names, or an approval for
   247	   one IAM policy would let a different change to the same policy through; and it must leave out
   248	   values that change on every build, or an approval never matches. ⚠️ From memory, not checked:
   249	   Serverless puts a timestamped path in the Lambda `Code.S3Key` and a code hash in
   250	   `AWS::Lambda::Version` logical IDs; both are left out of the hash.
   251	7. **Fail-safe CODEOWNERS default** [design]: without it, root `package.json`, a new stack or a new
   252	   `deploy-approvals/<stack>/` folder would be unowned, and GitHub then accepts an approval from
   253	   any writer (📖 about code owners).
   254	8. **Same-repository reusable workflows can use `uses: $/.github/workflows/<file>`**, which GitHub
   255	   now recommends: it resolves to the running commit, not to the runner's workspace (📖 GitHub docs
   256	   source, `data/reusables/actions/reusable-workflow-calling-syntax.md`; flagged by zizmor's
   257	   `self-repository` audit). `actionlint` 1.7.12 (✅ latest release on 2026-11-09, published
   258	   2026-03-30) does not know the syntax; `validate.sh` ignores only that message.
   259	9. **`runner.temp` is not available in job-level `env`** (✅ caught by `actionlint`); paths use
   260	   `$RUNNER_TEMP` inside steps.

   262	### Step 2 (identity and access)
   263	
   264	10. **SCP "protect the org trail" is mostly redundant** for member accounts: they cannot delete
   265	    an organization trail or turn its logging off anyway (📖 R2.6.2). E5 instead denies changes
   266	    to any trail inside prod accounts. The framework's layer-1 bullet is reworded in the final pass.
   267	11. **"Metadata" reads can leak configuration, data or secrets** (⚠️ response contents from
   268	    memory of the API references): `lambda:ListFunctions` and `ecs:DescribeTaskDefinition` return
   269	    environment variables and cannot be limited to one resource (✅ catalogue: not resource-scoped);
   270	    `lambda:GetFunction` also returns a code download URL; `ecs:DescribeTasks` returns container
   271	    environment overrides; `cloudformation:DescribeStacks` returns stack outputs (it could be scoped
   272	    per stack); `cloudformation:DescribeStackEvents` returns `ResourceProperties`, "the properties
   273	    used to create the resource" (📖 [StackEvent](https://docs.aws.amazon.com/AWSCloudFormation/latest/APIReference/API_StackEvent.html)),
   274	    which for a function includes its environment variables (⚠️ inferred); `logs:DescribeQueries`
   275	    returns other users' query strings. E6 leaves all of them out [design];
   276	    `lambda:GetFunctionConfiguration` is granted per function instead.
   277	12. **AWS's annotations are signals, not a classification of customer data**: `IsDataPlane` marks
   278	    `cloudwatch:GetMetricData` too; `sqs:ListQueues` is not marked `IsList`; and many `IsList`
   279	    actions return data or configuration (`s3:ListBucket` object keys, `ec2:Describe*` launch
   280	    templates, `ssm:ListCommandInvocations` output; ✅ annotations in the catalogue, ⚠️ response
   281	    contents from memory). The tests use an explicit allowlist for `Resource: "*"`. One entry has a
   282	    condition: `states:ListExecutions` returns execution names, so names must not be built from
   283	    claim data [design].
   284	13. **Two prod deploy roles** (framework layer 1 already implies it): the SCP exempts the Pulumi
   285	    role from the Lambda-update deny, but not the Serverless role, so `serverless deploy function`
   286	    cannot change a function outside CloudFormation (drift). It does not stop malicious code in
   287	    the job (Limits). `deploy-prod.yml` has one credentials step per tool, so an unset role
   288	    variable fails instead of falling back to the other role.
   289	14. **The claim-data deny assumes a naming convention** [design]: every legitimate reader must
   290	    match `app-claims-*` or a `DataRead-*` permission set. Lambda execution roles behind SQS event
   291	    sources, Step Functions execution roles and an AWS Backup role that reads the bucket would be
   292	    denied otherwise (only service-linked roles are outside SCPs, 📖 R2.3.2). Phase-2 prerequisite:
   293	    inventory the real callers of these actions (CloudTrail, IAM last-accessed data) and add them
   294	    before the SCP is attached.
   295	15. **The trail deny blocks every principal in prod accounts**, including deploy roles and
   296	    `OrganizationAccountAccessRole`: a member-account trail can only be changed after a temporary
   297	    change to the SCP (an L3 path), or an exempt audit role would have to be added [design].
   298	16. **Exempt role names must be protected** (OD19): the exemptions are name patterns, so anyone in
   299	    a prod account who could create or re-trust a role named `app-claims-*` or `cfn-deployment-*`
   300	    would bypass both denies. E5 lets only `github-prod-deploy-pulumi` change those roles.
   301	    - **Today that role deploys every Pulumi stack**, not only the IAM stack, and any job in the
   302	      deploy workflow can obtain it (OD20). So "only the IAM stack" holds only after OD20 (since
   303	      OD22: phase 1, E4, E4b) gives the
   304	      IAM stack its own role and OIDC subject; until then the protection is "only an approved prod
   305	      Pulumi deploy" (agent's reading of OD19, confirmed by the owner 2026-11-09).
   306	    - **Residual risks:** a principal that may pass an `app-claims-*` role could create a new
   307	      function with it (`lambda:CreateFunction` is not denied), and one that may pass
   308	      `cfn-deployment-*` to CloudFormation could change any function through a template;
   309	      `iam:PassRole` is left out on purpose because the Serverless role must pass
   310	      `cfn-deployment-*`. An `InfraOperator-*` grant may change an `app-claims` function's code
   311	      and so read claim data indirectly (accepted with break-glass, ADR-0005; JIT reconciliation
   312	      in layer 7 is the control).
   313	    - **Constraints and prerequisites (phase 2):** Serverless services cannot create their own
   314	      `app-claims-*` execution roles (CloudFormation runs as `cfn-deployment-*`, not exempt); those
   315	      roles live in the Pulumi IAM stack and are referenced by ARN. The protected roles must exist
   316	      before the SCP is attached, and if `github-prod-deploy-pulumi`'s own trust breaks (e.g. the
   317	      subject-format opt-in of E4), only an SCP change from the management account (an L3 path)
   318	      can repair it.
   319	17. **Gaps in the claim-data deny, under G13** (⚠️ not verified): S3 requests through access
   320	    points may be authorised on the access-point ARN, not the bucket ARN; KMS `Decrypt` on the
   321	    claim keys would be a second layer.
   322	    The deny also covers `sqs:StartMessageMoveTask` (a write, ✅ catalogue), which could move claim
   323	    messages to another queue; cost: a JIT grant cannot redrive a claims dead-letter queue.

   325	### Step 3 (agent runtime, supply chain, policy pack)
   326	
   327	18. **The settings schema on schemastore.org is community-maintained and lags behind**: it accepts
   328	    unknown keys and lacks `allowedProviders` and `managedSourcesBehavior` (✅ checked). The tests
   329	    therefore check keys by path and require a documentation source for every key it lacks.
   330	19. **The phase-1 allowlist gives no protection for `~/.aws`, and a "read-only" wildcard rule
   331	    can write files** (review step 3): Claude Code runs a built-in set of read-only commands
   332	    (`cat`, `grep`, `head`, read-only `git` …) without a prompt in every mode, and the set is not
   333	    configurable (📖 [permissions](https://code.claude.com/docs/en/permissions.md#read-only-commands)).
   334	    Leaving `cat` out of the allowlist protected nothing. Worse, `Bash(git log *)`, `Bash(git show *)`
   335	    and `Bash(git diff *)` also match `--output=<path>`, which writes chosen content to any path
   336	    (✅ git 2.34.1; the docs use `git log --output=<file>` as an example match). The allowlist is now
   337	    two exact repo scripts, and those run whatever `package.json` says [limit]. Owner decision OD21
   338	    adds two keys to phase 1: a `Read(~/.aws/**)` deny rule, which also applies to recognized
   339	    `cat`/`head`/`tail` (📖 permissions), and `autoMode.classifyAllShell` (📖, ≥ 2.1.193), so the two
   340	    allow rules do not skip the auto-mode classifier. Left open until the phase-2 sandbox: a command
   341	    that reads files without naming them (`grep -r` from `~`) or a script that opens `~/.aws` itself
   342	    is not covered by a deny rule (📖 permissions). Not chosen: `blockReadsOutsideWorkingDirectories`
   343	    (📖, ≥ 2.1.257), which would also block every read outside the repository.
   344	20. **Credential paths beyond the HIPAA template** [design]: `~/.aws` as a whole (the SSO token
   345	    cache opens every role of the engineer, layer 2), `~/.kube`, `~/.pulumi`, `~/.config/gcloud`,
   346	    the Firebase CLI token, `~/.docker/config.json`. `~/.config/gh` must be hidden from the sandbox
   347	    too, not only from Claude's Read tool: sandboxed commands run without a prompt (OD12) and
   348	    `api.github.com` is allowed, so a readable token lets the agent approve PRs as the engineer (OD5).
   349	    This closes only the sandboxed route: an excluded CLI (`pulumi`, `serverless`) runs repository
   350	    code outside the sandbox with full access (finding 22), so hiding credentials from the sandbox
   351	    is hygiene, not a boundary (ADR-0007).
   352	21. **TypeScript 7 is not yet supported by `@pulumi/pulumi`** (✅ npm peer-dependency error:
   353	    `typescript >= 3.8.3 < 7`); the pack pins TypeScript 6.0.3.
   354	22. **`sandbox.excludedCommands` entries match like `Bash(...)` rules** (📖
   355	    [sandboxing](https://code.claude.com/docs/en/sandboxing.md#run-commands-outside-the-sandbox-with-excludedcommands)):
   356	    `aws` alone matches only `aws` with no arguments, so the first draft kept every `aws` call in the
   357	    sandbox, where it fails (no `~/.aws`, no AWS endpoints). Entries are now `aws *`, `pulumi *`,
   358	    `serverless *`. The docs also answer the framework's ⚠️ on matching: every command in the call
   359	    must match; a call with `cd`, a redirect, `$(...)` or a subshell stays sandboxed; the match is on
   360	    the text, so `/usr/local/bin/aws`, a script that calls `aws`, and `npx serverless` do not match.
   361	    Excluded commands go through the permission flow: they prompt in Manual mode, but in auto mode
   362	    the classifier decides (📖 sandboxing), so phase 2 also lists them as `ask` rules, which prompt
   363	    in every mode (📖 auto-mode-config). The prompt shows the command (`pulumi preview`), not the
   364	    repository code it runs, which a sandboxed command may have changed without a prompt.
   365	23. **A mandatory Pulumi policy is only advisory while a value is unknown** (✅ `@pulumi/policy`
   366	    1.21.0 `server.js` catches `UnknownValueError` and reports `advisory`). A PR-time or prod
   367	    preview of a policy built from a resource of the same update passes; the stop comes during the
   368	    update. Access Analyzer is the preview-time check (layer 5).
   369	24. **The first policy pack missed the usual ways to grant admin** (review step 3): user and
   370	    group policies, `AdministratorAccess` attached by ARN, `Role.managedPolicyArns`, and wildcards
   371	    such as `iam:Pass*`. All are now covered and tested. Round 2: IAM also accepts `?`, so `s3:?*` and
   372	    `*?` are full wildcards (📖 IAM Action element); covered too. Round 3: a wildcard in the service
   373	    prefix (`*:*`, `s?:Get*`) is refused as a full wildcard (⚠️ whether IAM accepts it is unverified).
   374	25. **The template's auto-mode `"$defaults"` pins keep the built-in rules in place** (📖
   375	    auto-mode-config: a list without `"$defaults"` replaces the built-in rules; entries from managed
   376	    settings cannot be removed). The first phase-2 draft dropped them, which would let a developer's
   377	    own `hard_deny: []` discard the built-in data-exfiltration rule. Restored and tested. They are not
   378	    a policy boundary: a developer's own `autoMode.allow` or `environment` entries still widen what the
   379	    classifier approves ("the combination is additive, not a hard policy boundary", same page), and
   380	    `allowManagedPermissionRulesOnly` does not cover `autoMode` [limit]. For prod CLIs the boundary is
   381	    the managed `ask` rules plus layers 1 and 3.
