L213+249	## Layer 3 — Change workflow by risk level
L214+249	
L215+249	**Principle.** The level is set by the damage a change can do. One default path above non-prod: a
L216+249	reviewed PR applied by the pipeline, with the JIT fallback (layer 7) as the only other write path.
L217+249	The approver reviews the code change that will be applied. By default a prod change needs two
L218+249	people: one who makes it and one who approves it; the on-call backup only replaces an unavailable
L219+249	primary (OD2). Higher risk narrows **who** may approve (the owners of that path), not how many, with
L220+249	two exceptions: a process path needs two L3 owner team members (OD26), and a PR that touches files of
L221+249	several teams needs an owner of each, except in an incident (OD27). Separately, any prod diff that looks risky stops the deploy, whatever its level; that adds a
L222+249	second approval by an owner of the same stack, which keeps it to two people (OD8). Confirmed by the owner
L223+249	(OD13): the original author opens the approval PR and the first approver
L224+249	approves it. If the first approver is unavailable, another owner of the stack approves; that makes
L225+249	three people and is recorded as a deviation, counted monthly (OD11). A cross-team PR needs an
L226+249	approval from an owner of each team's files: OD10 allowed one on-call group member to cover them
L227+249	all, but since OD27 that counts only for an incident (layer 3, "Who approves at night"). A real-data read is not a change and has its own rule, L3-data. Incidents use the same
L228+249	path with faster people, not fewer security checks.

L240+249	`CLAUDE.md` and the other agent configuration files are L3, because they define the workflow for
L241+249	the whole team (OD3). With code-owner review on, every PR, L2 included, needs an approval from an
L242+249	owner of the files it touches (📖 R3.2.3, R3.2.7; per-file behaviour ⚠️ not a separate research row).
L243+249	What differs at L3 is **which team** owns the path: L3 paths are owned in CODEOWNERS by a designated
L244+249	L3 owner team, L2 paths by their domain team; and IaC changes at L3 meet the
L245+249	risk stop. Most IAM, network and stateful changes sit inside domain files, so they are approved by
L246+249	the stack's owners, not the L3 team (OD8); automated checks make up for this: IAM Access Analyzer
L247+249	`check-no-new-access` (📖 R2.8.1) and the Pulumi policy pack (📖 R4.2.2), both from phase 2 (layer 5). Cost: changes to `CLAUDE.md` (where D3 puts shared knowledge) need the L3 owner team, not
L248+249	the domain team that edits it most.

L256+249	  no merge queue (⚠️ R4.6 #1). GitHub dismisses an approval as stale only when the PR's diff
L257+249	  changes, e.g. after "Update branch" if the merge base brings new changes (📖
L258+249	  [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches));

L260+249	  own changes alone costs no new approval. Cost: when another merge does change the diff, the PR
L261+249	  is approved again; how often that happens in the monorepo is measured in rollout (S4). What
L262+249	  "most recent reviewable push" means for "Update branch" is not documented (⚠️); it is tested
