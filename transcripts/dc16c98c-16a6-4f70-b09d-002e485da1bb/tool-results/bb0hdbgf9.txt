388	## Layer 3 — Change workflow by risk level
389	
390	**Principle.** The level is set by the damage a change can do. One default path above non-prod: a
391	reviewed PR applied by the pipeline, with the JIT fallback (layer 7) as the only other write path.
392	The approver reviews the code change that will be applied. By default a prod change needs two
393	people: one who makes it and one who approves it; the on-call backup only replaces an unavailable
394	primary (OD2). Higher risk narrows **who** may approve (the owners of that path), not how many, with
395	two exceptions: a process path needs two L3 owner team members (OD26), and a PR that touches files of
396	several teams needs an owner of each, except in an incident (OD27). Separately, any prod diff that looks risky stops the deploy, whatever its level; that adds a
397	second approval by an owner of the same stack, which keeps it to two people (OD8). Confirmed by the owner
398	(OD13): the original author opens the approval PR and the first approver
399	approves it. If the first approver is unavailable, another owner of the stack approves; that makes
400	three people and is recorded as a deviation, counted monthly (OD11). A cross-team PR needs an
401	approval from an owner of each team's files: OD10 allowed one on-call group member to cover them
402	all, but since OD27 that counts only for an incident (layer 3, "Who approves at night"). A real-data read is not a change and has its own rule, L3-data. Incidents use the same
403	path with faster people, not fewer security checks.
404	
405	| Level | What | Examples | Approval | Path |
406	|---|---|---|---|---|
407	| **L0** | Read: non-prod anything; prod metadata | metrics, redacted logs | none | read-only identity |
408	| **L1** | Change in non-prod | deploy a branch to dev; `pulumi preview` on non-prod (needs state-write permission on a DIY S3 backend, 📖 R4.3.3) | author only | non-prod roles or PR pipeline |
409	| **L2** | Routine prod change in code | Lambda timeout/memory, ECS desired count, release | 1 code owner ≠ author, ≠ last pusher | PR → `main` → deploy workflow |

497	- **Risk stop [design]:** applies to every deploy, whatever the level. The deploy job previews prod;
498	  on stateful replace/delete, an IAM change, a network or security-group change, or an advisory
499	  policy finding (from phase 2) it stops and posts the filtered preview. The original author opens a second PR that adds
500	  `deploy-approvals/<stack>/<sha>.yaml` (`<sha>` = the stopped commit) holding that SHA and the
501	  preview hash; the workflow does not open it, because the setting that lets Actions create and approve PRs stays
502	  off (📖 R3.3.3; ⚠️ R3.6 #3). CODEOWNERS on `deploy-approvals/<stack>/` names the owners of that stack and the
503	  on-call group (OD8, OD9). The approver is ≠ author and may be the first PR's approver, who now sees
504	  which prod resources and properties change; values stay out of the summary to keep secrets out
505	  of logs, and are reviewed in the code of the stopped PR. Merging it triggers the deploy on the new HEAD, which previews again and continues
506	  only if the hash matches the approved one; if another PR merged in between, the hash differs and
507	  the deploy stops again (Options §1; hash stability ⚠️ Options §8). The approval is bound to git
508	  history, not only to the hash (six conditions, 7-day expiry; examples E7, finding 2) [design].
509	  Known gap (OD18): an early approval can match a later change outside the stack (G19 closes it: the app checks that the stopped run's summary carries the same hash).
510	  The stop catches risky diffs nobody looked at, not approved malicious code (OD15); OD22 limits what such code can reach (layer 5). Cost: while a stack is
511	  stopped, later merges to that stack stop too until a matching approval lands; in an incident, a
512	  risky change already waiting on `main` blocks the fix for the same stack until it is approved or
513	  reverted. A

516	  outputs and secrets before it is posted (Options §1; ⚠️ R4.6 #2).
517	- **Database changes (OD29, ADR-0011) [design].** Aurora schema migrations, GraphQL-engine
518	  (Hasura) metadata and data fixes are files under `db/<service>/`, merged like code and applied by
519	  a `sql` job of the deploy workflow (examples E3):
520	  - where it runs [design]: Aurora is reachable only inside the prod VPC, and layer 5 avoids
521	    self-hosted runners, so the GitHub-hosted job never connects to the database. Its OIDC role may
522	    only start one ECS task definition (`db-change-<service>`) on one cluster, pass that task's two
523	    roles, and use one S3 prefix (examples E15). The one-off Fargate task runs in private subnets
524	    from an image pinned by digest; its role may only `rds-db:connect` as the migration user (IAM
525	    database authentication, 📖 R9.2.11). ECS lets the caller override the command and environment
526	    of a task (📖 [RunTask](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_RunTask.html)),
527	    so the task re-checks the SHA-256 of the file bundle the risk stop classified and refuses any
528	    other; `ecs:ExecuteCommand` is denied. That `iam:PassRole` is what lets a caller start a task
529	    with a role is ⚠️ recalled, not checked in this round;
530	  - GraphQL-engine metadata is not a database change: the task applies it with
531	    `hasura metadata apply`, which needs the engine's admin secret and replaces all metadata
532	    (📖 [Hasura CLI](https://hasura.io/docs/2.0/hasura-cli/commands/hasura_metadata_apply/),
533	    [manage metadata](https://hasura.io/docs/2.0/migrations-metadata-seeds/manage-metadata/)). The
534	    secret sits in Secrets Manager and reaches only the task, through its task definition. No
535	    person holds database credentials or the admin secret day to day; a break-glass role that
536	    can read Secrets Manager can read it, which the JIT record shows (layer 7);
537	  - it lists the pending files through `tools/db/` wrappers around Papaya's migration tool (an L3
538	    path; the tool is not known here), runs the risk stop on them with `--tool sql`, and applies
539	    exactly the classified files, each in its own transaction;
540	  - the SQL risk stop (a heuristic, not a parser; examples E7) stops on DROP, TRUNCATE, column type
541	    changes, DELETE or UPDATE without a top-level WHERE, grants, roles, row-level security, COPY,
542	    function bodies and `EXECUTE`; every metadata change stops too, because it holds row
543	    permissions per role, i.e. tenant isolation;
544	  - data fixes (`db/<service>/data-fixes/<tenant>/<ticket>.sql`) touch one tenant, declare
545	    `-- expected_rows: N`, and are rolled back when the count differs; approval is L3-data-write
546	    (table above); the job summary shows statement kinds and row counts, never values;
547	  - IAM database authentication is not in CloudTrail (📖 R9.2.11), so database-side evidence comes
548	    from Database Activity Streams (layer 7). Expand/contract migrations are recommended, not
549	    enforced. Cost: a data fix takes a PR and two approvals instead of a `psql` session.
550	- **Merge approval = deploy approval** only if (⚠️ R3.6 #1, from 📖 R3.1.3, R3.4.5c): `production`
551	  allows only `main`; only the reusable deploy workflow (under CODEOWNERS) references it; no ref/SHA
552	  inputs; no `issue_comment`, `pull_request_target` or `workflow_run` triggers; one concurrency group
553	  per stack without `cancel-in-progress` (📖 R4.1.4); squash-only merges, so each PR is one commit on
554	  `main` (OD16); and the job deploys only the current tip of `main`, because a writer can re-run an
555	  old run for 30 days and roll prod back without approval (OD17; 📖 GitHub docs, linked in examples finding 4).

596	**Example: Lambda timeouts at 2 a.m.** (Options §6)
597	
598	The incident responder is engineer E; the on-call approver is R (a backup replaces R only if R is
599	unavailable).
600	
601	1. E's incident-analysis session reads metrics and redacted logs and proposes `timeout` 30 → 90 s,
602	   memory 1024 → 2048 MB, and a larger visibility timeout on the source queue (ratio ⚠️ Options §8).
603	2. A second session (edit tools; not meant to use prod roles) edits `serverless.yml`, runs
604	   `serverless diff` on non-prod, and opens a PR labelled `incident` as E.
605	3. R, a co-owner of `serverless.yml` through the on-call group (OD9), reviews the diff. If R
606	   catches a missing queue change, R does not fix it (OD7): E pushes the fix, the stale approval is
607	   dismissed, and R approves again, one more review round (Options §6). E merges.
608	4. The deploy workflow packages, previews prod, finds no risky change, deploys with the OIDC role.
609	5. Estimate 11–46 min (⚠️ Options §6) against ≤ 30 min: measured first in rollout.
610	
611	**Audit evidence.** The PR (diff, approvers, checks), the deploy run log and risk-stop summary (exported, retention ⚠️ G7), the `deploy-approvals/` PR, and CloudTrail events linked by commit SHA and run ID; walk-through: [04-compliance-mapping.md](04-compliance-mapping.md#evidence-for-one-prod-change-s8).
612

614	team members on process paths, OD26); two approvals,
615	usually by the same approver, when the risk stop fires (OD13; OD11). Cross-team PRs: an owner of each team on normal days, one on-call approver in an incident (OD10 as narrowed by OD27). None in non-prod.
