    38	## 1. The decision in one page
    39	
    40	**Who decided.** This is a proposal by the author of this submission. Where the documents say
    41	"owner" or cite an owner decision (OD-n), that is the author's design decision taken while writing
    42	it, not a sign-off by Papaya. The choices that are Papaya's to make are in the last table below.
    43	
    44	**The disagreement is narrower than it looks.** Engineering wants Claude Code to talk to AWS
    45	directly; Compliance wants nothing to change in production without a named person who reviewed and
    46	approved it. Reading metadata and working in non-prod are outside Compliance's sentence. The
    47	conflict is only about **writes to production**, and about real customer data, which has its own
    48	rules (layer 6).
    49	
    50	**The answer:**
    51	
    52	1. Every production change is a pull request: approved by a person who owns the changed files and
    53	   did not write the change, then applied by the pipeline. Incidents use the same path, with a
    54	   24/7 on-call approver.
    55	2. Only when that path cannot be used during an incident, a person gets a one-hour approved grant
    56	   and types an approved list of commands in a terminal without an agent.
    57	3. Nobody, person or agent, keeps standing write access to production, and the pipeline uses no
    58	   stored cloud keys (a few exceptions, each with an owner and an expiry).
    59	
    60	| Engineering gets | Compliance gets |
    61	|---|---|
    62	| An agent that works freely in non-prod and reads production metadata | Approval before every production change, by a named person who is not the author, enforced by GitHub and AWS, not by the agent |
    63	| One approval for most changes, same-day shipping, an approver within 15 minutes at night | One evidence record per change, kept six years in locked storage |
    64	| Agent help with incidents, risky-deploy reviews, dependency fixes and audits (§2) | Agent controls as a second layer, never the control of record |
    65	| **Costs:** a slower incident lane; a confirmation for each cloud command; from phase 2, pushing and opening pull requests yourself; raw logs only after masking; night duty | **Not delivered:** a technical stop on an agent approving through its engineer's login; prevention (not just logging) of administrators editing the gate; full approval of the break-glass path, which approves a command list rather than the applied change |
    66	
    67	**Decisions Papaya must take** (the design works either way; the recommendation is the author's):
    68	
    69	| Decision | Recommendation | Where |
    70	|---|---|---|
    71	| Accept break-glass as partly meeting "approved before applied" | Accept, with its metrics reviewed monthly; Compliance signs | layer 7 |
    72	| One approver for high-risk changes in service code, or two | One, plus the risk stop; two on the files that define the process | layer 3 |
    73	| GitHub Team or Enterprise Cloud | Enterprise Cloud in phase 2 if up to about 100 users: identity-linked approvals, prod diff before apply | layer 3 |
    74	| GitHub secret-scanning and code-scanning licences | At least secret scanning with push protection | layer 5 |
    75	| Stored deploy credentials for k0s, Firebase, Expo | Accept with an expiry until keyless login works | layer 5 |
    76	| Staffing of phase 1 | Two DevSecOps people and one platform engineer for about 45 days | rollout plan |
    77	| A 24/7 rota of approvers and responders | Yes; two people awake for a night incident | layer 7 |
    78	| Auto mode on laptops | Allowed, measured, with a switch to turn it off | layer 2 |
    79	| Whether HIPAA applies; Papaya's role per insurer (controller or processor) | Legal counsel | compliance register |

    84	### 1a. Limits and trade-offs, in detail
    85	
    86	The chosen approach is called "A + D2'" in the working notes (Options §9): option A, the PR path
    87	for every prod change, plus D2', a narrow JIT fallback. The codes used from here on are explained
    88	in "How to read this". Its limits, each argued with its sources in [appendix A](07-framework-appendix.md#a-limits-and-trade-offs-in-detail):
    89	
    90	- the fallback meets "approved before applied" only partly (a command list, not the applied
    91	  change), and stays narrow only if most incidents can be written as IaC; layer 7 measures it;
    92	- on GitHub Team nobody sees the prod diff before apply; risky prod diffs stop for an owner's look
    93	  at the prod preview instead (layer 3);
    94	- admins can edit the gate, and so can an admin's agent: logged, not prevented;
    95	- "an agent never approves" rests on policy, training and deny rules that are hygiene; "named" means
    96	  a GitHub login that a register maps to a person (layer 1);
    97	- an on-call approver counts for another team's file only in an open incident, checked by the
    98	  approval-gate app; a night incident needs two people awake (layer 3);
    99	- one approver for most high-risk changes; two on the process paths (layer 3);
   100	- k0s and Firebase have weaker controls (G1, G2);
   101	- the approval-gate app blocks every merge when it is down, and is the longest phase-1 item;
   102	- whether HIPAA applies is a legal question.
   103	**Cross-cutting rules** (owner's balance principle, research 6.8):
   104	
   105	1. **The boundary is IAM and the CI gate.** Server-managed settings are "a client-side control, not
   106	   a security boundary" (📖 R1.1.7); local admins can edit endpoint files (📖 R1.1.8).
   107	2. **Assume prompt injection succeeds:** neither OWASP nor NIST knows a full prevention (📖 R6.1.1, R6.1.2).
   108	3. **Friction where damage is large, none where it is small**, measured, with a time-boxed escape.
   109	4. **Evidence by construction:** the path produces the records.
   110	
   111	### Roles
   112	
   113	| Role | Rule |
   114	|---|---|
   115	| Author (engineer + their agent) | Never approves own change; GitHub blocks PR authors from approving (📖 R3.3.1). |
   116	| Approver | Always an engineer, never an agent (owner rule, OD5). Named in CODEOWNERS; ≠ author, ≠ last pusher (📖 R3.2.3); for an app-opened PR, ≠ the person who triggered it (⚠️ R3.3.4, layer 5). Their GitHub account is in the login register (OD25). Process paths need two (OD26). |
   117	| Incident responder | Engineer who diagnoses and writes the fix or the JIT request. Never the on-call approver of the same shift (OD7). |
   118	| On-call approver | Engineer on the on-call schedule, primary + backup, 24/7; wait ≤ 15 min (S7). Approves another team's file only for a PR linked to an open incident while on shift, checked by the approval-gate app (OD27). While on call they only approve: they write no fix and file no JIT request, so the approver is always distinct from the author (OD7). The primary approves; the backup replaces an unavailable primary (OD2). No platform-team membership is required; all engineers follow one agreed approval procedure (OD2). |
   119	| Data owner [design] | Named per tenant; co-approves real-data reads, or reviews a night-time read the next working day (layer 6). |
   120	| Control owner | DevSecOps (1–2 people, GĐ-1); owns policies and metrics; not the only approver. |
   121	| L3 owner team | Owns the process-defining L3 paths and the SCP stack (layer 3); composition open (G17). |

   125	## 2. Agent-assisted DevSecOps workflows
   126	
   127	The layers below say what agents may not do. This section says what Papaya's engineers use them
   128	for in DevSecOps work, inside those limits [design]. Each workflow names the session it runs in
   129	(layer 2), the identity it uses (layer 1), the skill that encodes it (internal plugin
   130	`devsecops-guardrails`, examples E9), its output, the person accountable, and the metric that shows
   131	whether it helps.
   132	
   133	| Workflow | Session and identity | Skill / tool | Output | Accountable | Value metric |
   134	|---|---|---|---|---|---|
   135	| **Ship an infrastructure change** | Daily development; non-prod roles + `ProdReadMetadata` | `prod-change` | IaC change, non-prod preview, PR text; the engineer opens the PR | Author; approver | PR to prod same day (S4) |
   136	| **Triage an alert or incident** | Incident analysis: `--restricted`, read-only tools, scratch directory; `ProdReadMetadata` | `incident-triage` | Likely cause, smallest fix as a PR or a JIT command list, timeline draft | Incident responder | Time from page to fix PR (S7) |
   137	| **Explain a stopped deploy** | Daily development, or the CI agent on the approval PR | `risk-summary-explainer` | Plain-language comment on `deploy-approvals/<stack>/`: what each stopped operation does, what is irreversible, what the summary cannot show | The approver decides | Approval wait on risk-stop PRs |
   138	| **Review a PR for security** | CI agent, its own GitHub App token, never `production` (layer 5) | `claude-code-action` with the review prompt, read-only tools, no MCP (examples E18) | Review comments on every PR touching infrastructure; never an approval (OD5, OD22) | The human approver | Findings accepted per month |
   139	| **Fix a vulnerable dependency or image** | CI agent from a Dependabot alert or an ECR scan finding (layer 5) | `dependency-fix` | One small PR per advisory, tests run, `pr-size` check passed | Owners of the changed files | Time to fix high and critical findings |
   140	| **Codify after break-glass or drift** | Daily development, after the JIT window or a drift finding (layer 7) | `prod-change` | The codify PR that brings IaC in line with what was changed by hand | Incident responder | Late codify PRs (JIT metric) |
   141	| **Prepare a catalogue review** | Daily development on the marketplace repository | — | Draft review record for a new MCP server or plugin (reviews/, examples E9) | Two L3 owner team members | Requests decided in ≤ 5 days (S6) |
   142	| **Answer an auditor's question** | Daily development with read access to the evidence bucket (no write) | — | The change record of a sampled change from PR, run log, risk summary and CloudTrail | Compliance | Evidence shown in ≤ 30 min (S8) |
   143	
   144	Shared context that makes these work, all in the monorepo and reviewed as L3 paths:
   145	
   146	- **A shared `CLAUDE.md`** at the repository root: how production changes, the Pulumi and
   147	  Serverless conventions, logging rules, the data rule (template: examples
   148	  `claude/repo-templates/CLAUDE.md`).
   149	- **A pull request template** that records which parts an agent wrote, the expected prod impact,
   150	  the data touched and the rollback (examples `github/pull_request_template.md`). It makes the
   151	  reviewer read agent-written code as a stranger's code.
   152	- **The skills above** in the internal plugin, pinned and reviewed like any catalogue entry (OD26).
   153	
   154	What stays manual on purpose: approving, running anything in a JIT window, deciding a data-read
   155	request, and changing the gate itself.
   156	
   157	**Measuring the value.** Papaya's current numbers are unknown, so each metric gets a baseline in
   158	the first 30 days (from GitHub, the paging tool and the scanners, before the workflow is switched
   159	on) and a target agreed at the final review (rollout 3.5) [design]. A workflow whose metric does
   160	not improve over its baseline by then is dropped or changed, so that the agent's place in the
   161	process is earned, not assumed:
   162	
   163	| Metric | Source | Baseline | Target |
   164	|---|---|---|---|
   165	| PR to prod, median (ship a change) | GitHub, deploy runs | first 30 days | same working day (S4) |
   166	| Page to fix PR, median (incident triage) | paging tool, PR timestamps | first 30 days | lower than baseline |
   167	| Approval wait on risk-stop PRs (explainer) | `deploy-approvals/` PRs | first 30 days | ≤ 1 h in working hours |
   168	| Security review comments accepted per month (review) | PR review threads | — (new) | reviewed at the final review; turned off if noise |
   169	| Days to fix high and critical findings (dependency fix) | Dependabot, ECR scans | first 30 days | lower than baseline |
   170	| Late codify PRs (codify) | JIT records | — (new) | 0 |

   174	## Layer 1 — Identity and access
   175	
   176	**Principle.** Every action traces to one named human. Nobody holds standing prod write: prod is
   177	written by the pipeline role, or in the fallback by an approved, time-boxed grant. Prod reads default
   178	to metadata. No long-lived credentials. Prod and non-prod are separate boundaries.
   179	
   180	**On Papaya's stack**
   181	
   182	- **The engineer's access is the agent's access.** The agent uses the engineer's AWS SSO cache, and
   183	  one portal session reaches every role assigned to that engineer (📖 R2.2.1, R2.2.2; token-reuse
   184	  detail ⚠️ R2.2.2). A separate
   185	  "agent" permission set does not separate them (⚠️ R2.9 #1). The control is what the **engineer**
   186	  holds.
   187	- **Process rules** that follow from this:
   188	  - the JIT terminal runs no agent, though the grant is reachable from the same laptop (owner
   189	    accepted as a process control, D2);
   190	  - the incident-analysis session is meant to use only read-only roles (D2; `--restricted` per D3,
   191	    research 6.9.4 Q2);
   192	  - the real-data terminal runs no agent when the store holds PHI [design], same weakness as D2;
   193	  - an agent never approves PRs: an owner rule (OD5), enforced on laptops by policy, training and
   194	    managed deny rules for `Bash(gh pr review *)` and `Bash(gh api *reviews*)` plus
   195	    `Read(~/.config/gh/**)` from phase 1 (OD25; valid patterns, not a boundary, 📖 R9.4.1).
   196	    GitHub blocks self-approval only. The auto-mode default block list
   197	    excerpt read names "approving Claude's own pull request" (📖 R6.3.3); whether approving
   198	    someone else's PR is blocked is unverified (⚠️), and the list
   199	    applies only in auto mode. No detection was found (⚠️; `actor_is_agent` in the audit log has no
   200	    documented meaning, R3.5.6).
   201	- **IAM Identity Center permission sets** (📖 R2.1.1) [design names]:
   202	  - `ProdReadMetadata`: metrics, redacted log groups, configuration; no data-plane read on claim
   203	    stores; 1 h session, the minimum (📖 R2.1.4). Some "metadata" reads (mostly ⚠️) return configuration or
   204	    secrets, so `Resource: "*"` only for a reviewed action list (examples E6, findings 11, 12). Until a service's logs are redacted at source
   205	    and masked (layer 6, OD28), it gets that service's metrics only. Lambda configuration can hold secrets resolved by
   206	    Serverless in plain text (⚠️ R4.4.7), so configuration reads are allowed per service only after
   207	    its secrets move to runtime resolution (⚠️ R4.6 #7). Cost: until then the agent reads
   208	    timeout/memory from the IaC code;
   209	  - `NonProdDeveloper`: broad, non-prod accounts only;
   210	  - `InfraOperator-<service>`: assigned only by the JIT flow's receiver (layer 7, OD33) after its
   211	    pre-grant check (examples E16), on the documented APIs `CreateAccountAssignment` /
   212	    `DeleteAccountAssignment` (📖 R2.4.2). A partner product or the TEAM sample (📖 R2.4.1,
   213	    R2.4.1b) can replace the receiver only if it enforces the same checks before the grant;
   214	  - no standing prod-write permission set.
   215	- **SCPs on the prod OU** [design] (SCPs cap member-account principals, 📖 R2.3.1, R2.3.2):
   216	  deny data-plane reads on claim stores except application roles and the approved data-read role
   217	  (action list incomplete, ⚠️ G13); deny direct Lambda code and configuration updates except
   218	  CloudFormation deployment roles, the Pulumi deploy role and JIT roles, which closes `serverless
   219	  deploy function` (📖 R4.4.4); a pre-deployed revocation Deny (📖 R2.4.4) and a deny on trail
   220	  changes; only the IAM stack's own role (environment `production-iam`) may create or change the
   221	  SCP-exempt roles, while domain deploy roles create only `svc-*` roles under a fixed permissions
   222	  boundary (OD19, OD22; examples E4b); every action of `OrganizationAccountAccessRole` denied in
   223	  the prod OU (OD23). No SCP applies to the management account (📖 R2.3.4), so whatever deploys
   224	  SCPs there is the most sensitive role (L3 path, L3 owner team only, OD13). Statement by
   225	  statement: [appendix B](07-framework-appendix.md#b-scps-on-the-prod-ou).
   226	- **GitHub identity (OD25).** An approval proves a GitHub account; Compliance needs a named person
   227	  [design unless marked]:
   228	  - the organization requires two-factor authentication (📖 R9.1.1; the page names no plan, so
   229	    ⚠️ check the setting in Papaya's Team organization);
   230	  - a login register maps every member's GitHub login to an employee, fed by HR joiners and
   231	    leavers; a leaver is removed from the organization on the last day; reviewed quarterly (C-03);
   232	  - outside collaborators get no write access to the monorepo; classic personal access tokens are
   233	    restricted and fine-grained tokens need approval and a maximum lifetime (📖 R9.1.12; plan not
   234	    stated ⚠️);
   235	  - SAML SSO, which would tie the login to the identity provider, needs Enterprise Cloud
   236	    (📖 R9.1.2); see "GitHub plan" in layer 3.
   237	- **Who administers the administrators (OD23) [design unless marked].** Whoever administers IAM
   238	  Identity Center can assign themselves any permission set. So permission sets and assignments are
   239	  code in an identity stack (L3 path) applied from CI; the JIT receiver is the only other writer;
   240	  any other Identity Center change alerts (📖 R9.2.2); daily administration runs from a delegated
   241	  administrator account (📖 R9.2.3); the management account has no workloads and a named group of
   242	  at least two L3 owners with hardware MFA; member-account root credentials are removed
   243	  (📖 R9.2.5). Detail: [appendix C](07-framework-appendix.md#c-who-administers-the-administrators).
   244	- **Sessions/MFA:** portal session length set on purpose; an IdP session can extend it silently
   245	  (📖 R2.1.5, R2.1.6). MFA lives in the external IdP if one is used (📖 R2.1.7).
   246	- **CI → AWS:** GitHub OIDC, no stored keys (📖 R3.4.1). The prod role trusts only the `production`
   247	  environment of the monorepo, in its `sub` format (📖 R3.4.3, R3.4.4; immutable format assumed,
   248	  ⚠️ R3.7 A2), ideally customised with the deploy workflow's `job_workflow_ref` (📖 R3.4.5; on Team ⚠️ G10).
   249	- **GCP, Firebase and k0s (OD36, OD24) [design unless marked]:** the same principles with each
   250	  platform's own mechanism ([appendix D](07-framework-appendix.md#d-gcp-firebase-and-k0s-identity)):
   251	  - CI → GCP through Workload Identity Federation, limited to the monorepo and the `production`
   252	    subject; people get a read-metadata role and time-bound Privileged Access Manager grants approved
   253	    by on-call (📖 R9.6.1); Data Access logs on for Vertex AI and partner-document buckets; Papaya
   254	    confirms with Google that its Vertex use is BAA-covered before PHI goes there (📖 R9.6.4);
   255	  - Firebase Hosting holds no PHI; its deploy key is an environment secret until a WIF spike
   256	    removes it; previews come from non-prod only;
   257	  - k0s: people move from kubeconfigs to OIDC (outside k0s support, 📖 R9.6.9) with one sealed
   258	    break-glass certificate; CI deploys with a namespaced, time-limited ServiceAccount token that
   259	    cannot read Secrets, exec, read logs or change RBAC (examples E11); target: the API server
   260	    trusts GitHub OIDC directly.
   261	**Audit evidence.** Identity Center assignment export (S1), CloudTrail grant events per JIT request, SCP and trust-policy code, Access Analyzer results from phase 2, and a quarterly access review; full register: [04-compliance-mapping.md](04-compliance-mapping.md#register).
   262	
   263	**Cost / value.** Engineers lose standing prod write and keep a free non-prod loop. Prod reads stay
   264	fast for metrics and metadata, but shrink during the transition: because the engineer's access is the
   265	agent's access, from phase 1 the engineer too loses raw logs and configuration of services not yet
   266	redacted or moved to runtime secrets. Configuration values come from the IaC code instead (layer 1
   267	above); raw logs that may hold customer data need an L3-data grant. The data owner is not on the
   268	on-call schedule, so at night the grant is approved by the on-call approver alone and the data owner
   269	reviews it the next working day [design]; the wait still counts against S7. This is
   270	the largest cost of the first months. Compliance gets least privilege that is enforced.

   274	## Layer 2 — Agent runtime controls
   275	
   276	**Principle.** Agent-side controls are hygiene, not the boundary. They are central, versioned in git
   277	and the same for everyone. Defaults are safe; overrides are measured. The session that reads
   278	untrusted content holds as little power as possible (📖 R6.1.2).
   279	
   280	**On Papaya's stack**
   281	
   282	- **Delivery:** server-managed settings (available on Team, 📖 R1.1.5) for all laptops. With MDM, also
   283	  an endpoint file; by default one managed source supplies most keys, so the two must carry the same
   284	  keys or use `managedSourcesBehavior: "merge"` (📖 R1.1.3, R1.1.4). MDM is unknown; both are prepared.
   285	- **Baseline** (template: Anthropic's `settings-hipaa.json`, 📖 R5.5.4). All keys 📖 at the row cited. Only the phase-1 subset ([rollout plan](03-rollout-plan.md) item 1.18) ships first; the other keys (sandbox, `allowManagedHooksOnly`, most credential denies, `allowManagedPermissionRulesOnly`, `allowedProviders`, `forceLoginOrgUUID`, the `ask` rule for WebFetch, and the other deny rules) arrive in phase 2 (OD4). The `ask` rules for `aws`, `pulumi` and `serverless` ship in phase 1 (OD43):
   286	
   287	  | Key | Value and reason |
   288	  |---|---|
   289	  | `permissions.defaultMode` | `default` (Manual). A default, not a lock: users can switch to auto; VS Code remembers the last pick (D1, R6.9.3). |
   290	  | `permissions.allow` | Two exact repo scripts (`npm test`, `npm run lint`) [design]. Read-only commands need no rule: a built-in set runs without a prompt in every mode (R6.9.3); wildcard rules such as `Bash(git log *)` can write files (examples finding 19). Phase 1 also denies `Read(~/.aws/**)` and sets `autoMode.classifyAllShell` (OD21). |

   303	- **Trade-off on AWS credentials [design].** With `~/.aws` hidden from the phase-2 sandbox,
   304	  `aws`, `pulumi` and `serverless` run outside it (`sandbox.excludedCommands`) with full access and
   305	  network (📖 R1.6.4). Repo code they load (the Pulumi program, Serverless plugins) then runs
   306	  unsandboxed, and an injected command could send out the SSO token cache (⚠️ inference). Each call
   307	  prompts through the `ask` rules; real-account runs belong in CI. Residual risk, accepted: token
   308	  theft during a session, bounded because nobody holds standing prod write or PHI read. Mitigations
   309	  and their limits: [appendix E](07-framework-appendix.md#e-aws-credentials-on-laptops).
