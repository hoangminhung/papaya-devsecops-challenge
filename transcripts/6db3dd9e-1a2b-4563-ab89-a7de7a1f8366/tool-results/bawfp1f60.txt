   120	## Limits of the risk stop
   121	
   122	The risk stop answers one framework problem: on GitHub Team nobody sees the prod diff before
   123	apply (framework §1). It catches **risky prod diffs that nobody looked at**. It is not a boundary
   124	against **malicious or prompt-injected code that was approved**:
   125	
   126	- The stack's own code runs with the prod deploy role: `npm` packages are installed before the
   127	  credentials (so install scripts get none), but the Pulumi program runs during `preview` and
   128	  `up`, and Serverless plugins during `package`/`diff`/`deploy`. That code could call AWS
   129	  directly, or tamper with files the classifier reads, in the same job. The defence against it
   130	  is the PR review itself, and from phase 2 IAM Access Analyzer and policy packs (layer 5).
   131	- A stronger variant [design, not in the framework]: preview with a separate prod **preview**
   132	  role (read and state access, no write), run the classifier in its own job on a fresh
   133	  checkout without credentials, and assume the deploy role only in a later job after the stop.
   134	  It adds a role and a job split; it is an open question for the owner.
   135	- `pulumi up` previews again before applying. A change made outside the pipeline between the
   136	  two previews (JIT, drift) is not re-checked. `pulumi preview --save-plan` + `pulumi up --plan`
   137	  would bind the two, but update plans are experimental (📖 R4.1.3).
   138	- Concurrency: a running deploy is never cancelled, but GitHub cancels a run that is still
   139	  pending when a newer one arrives for the same group (📖 GitHub docs source,
   140	  `data/reusables/actions/actions-group-concurrency.md`). Some merged commits therefore have no
   141	  deploy run of their own; the newer run deploys them too, and the change record must link both
   142	  commits to that run. `queue: max` would give every commit its own run, but the same page says
   143	  the order "is not guaranteed": an older commit could then deploy after a newer one and undo it
   144	  in prod. So the default is kept on purpose [design].
   145	- The type lists are examples. For types that are missing, the rule on property names
   146	  (`policy`, `role`, `securityGroup`, `vpcConfig`, `public`, `authorization`, `logging`, …;
   147	  a narrower set on creates) catches some changes, not all.
   148	- **Code in the deploy job can act as any prod deploy role.** `id-token: write` is job-wide, so
   149	  install scripts, the Pulumi program and Serverless plugins can request the job's OIDC token
   150	  (⚠️ from memory of GitHub's OIDC docs) and assume either deploy role, since both trust the same
   151	  subject. The two-role split and the install-before-credentials order stop drift and honest
   152	  mistakes, not malicious approved code. Phase-2 roadmap with OD15: a build job without
   153	  `id-token`, and per-role environments (different subjects) or `job_workflow_ref` (G10).
   154	- **Open gap:** nothing proves that a deploy really stopped at `stopped_commit` with the
   155	  approved hash. An approval merged early (naming a commit whose deploy did not stop, with a
   156	  hash computed in advance, which needs knowledge of prod inputs) is accepted if a later change
   157	  **outside** the stack's directory, such as a shared library, produces exactly that diff. Changes
   158	  inside the stack's directory are rejected. Watching the whole repository instead would cancel
   159	  every approval at each unrelated merge in a monorepo. The fix is for the approval-gate app to
   160	  check, on the approval PR, that the stopped run's summary carries the same hash (G19) [design].
   161	  `test_known_gap_early_approval_and_change_outside_the_stack` documents the current behaviour.
   162	- The approver of the approval PR sees **which** prod resources and properties change, not the
   163	  new values (the summary never prints values, to keep secrets out of logs). The values are
   164	  reviewed in the code of the stopped PR. Framework layer 3 and ADR-0004 say the approver "sees
   165	  the prod diff"; that wording is too strong and is corrected in the framework's final pass.
   166	- Any commit to the stack's directory between the stop and the approval merge cancels the
   167	  approval: the author names the newer stopped commit and the owner approves again. In an
   168	  incident that is one more review round.
   169	- `npm ci` runs before the credentials, but its lifecycle scripts can still write to
   170	  `$GITHUB_ENV` / `$GITHUB_PATH` and so influence later steps that hold them.
   171	  `npm ci --ignore-scripts` reduces this where the stack's packages allow it.
   172	- If the newest merge to `main` carries `[skip ci]` (or similar) in its message, no push run
   173	  exists for the tip and the older runs refuse to deploy; prod stays behind until the next merge
   174	  (📖 GitHub docs source, `content/actions/how-tos/manage-workflow-runs/skip-workflow-runs.md`,
   175	  via review). Operator action: merge an empty change.
   176	- Within 7 days, an approved change that is reverted and then merged again with identical code
   177	  passes without a new approval. This is intended: it is the same code and the same prod diff
   178	  that an owner approved.
   179	- The binding relies on squash-only merges (`ruleset-main.json`); with merge commits, a PR's
   180	  inner commits would be invisible to the first-parent check.

   189	
   190	1. **The risk-stop classifier must be an L3 path** [design]. The deploy runs it from the merged
   191	   commit, so a PR that edits it together with an IAM change, approved by the domain team, could
   192	   switch the stop off. `CODEOWNERS` adds `/tools/risk-stop/` to the L3 owner team. Needs owner
   193	   confirmation: it extends the canonical L3 list of framework layer 5.
   194	2. **An approval must be bound to git history, not only to a hash** [design]. Two review rounds
   195	   found ways for one PR to carry its own risky change and approval, or for an approval to be
   196	   reused. Rules now: read from git objects only; file named `<stopped_commit>.yaml`, never
   197	   edited; stopped commit and approval commit both on `main`'s first-parent history, in that
   198	   order; the approval commit touches only `deploy-approvals/<stack>/`; the stack's directory
   199	   and the classifier unchanged since the stopped commit; at most 7 days old.
   200	3. **Squash-only merges** [design]: `ruleset-main.json` allows only squash, so each PR is one
   201	   commit on `main`. Cost: PR-internal history is not kept on `main`.
   202	4. **Deploy only the tip of `main`** [design]: people with write access can re-run a workflow run
   203	   for up to 30 days, with the same `GITHUB_SHA` (📖 GitHub docs source,
   204	   `content/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs.md`, via review). An
   205	   old deploy run re-run would roll prod back without any approval. `deploy-prod.yml` stops unless
   206	   the run's commit is the current tip of `main`, read with `GET /repos/{owner}/{repo}/git/ref/heads/main`
   207	   (✅ branch-only form; `commits/main` could resolve to a tag named `main`). This is a new
   208	   condition for framework layer 3's "merge approval = deploy approval" list.
   209	5. **Classification beyond the framework's categories** [design]: the property-name rule, the
   210	   audit/detection category and "an unknown operation stops" go beyond layer 3's list
   211	   (stateful replace/delete, IAM, network, policy finding).
   212	6. **The approval hash must cover changed values**, not only resource names, or an approval for
   213	   one IAM policy would let a different change to the same policy through; and it must leave out
   214	   values that change on every build, or an approval never matches. ⚠️ From memory, not checked:
   215	   Serverless puts a timestamped path in the Lambda `Code.S3Key` and a code hash in
   216	   `AWS::Lambda::Version` logical IDs; both are left out of the hash.
   217	7. **Fail-safe CODEOWNERS default** [design]: without it, root `package.json`, a new stack or a new
   218	   `deploy-approvals/<stack>/` folder would be unowned, and GitHub then accepts an approval from
   219	   any writer (📖 about code owners).
   220	8. **Same-repository reusable workflows can use `uses: $/.github/workflows/<file>`**, which GitHub
   221	   now recommends: it resolves to the running commit, not to the runner's workspace (📖 GitHub docs
   222	   source, `data/reusables/actions/reusable-workflow-calling-syntax.md`; flagged by zizmor's
   223	   `self-repository` audit). `actionlint` 1.7.12 (✅ latest release on 2026-11-09, published
   224	   2026-03-30) does not know the syntax; `validate.sh` ignores only that message.
   225	9. **`runner.temp` is not available in job-level `env`** (✅ caught by `actionlint`); paths use
   226	   `$RUNNER_TEMP` inside steps.

   228	### Step 2 (identity and access)
   229	
   230	10. **SCP "protect the org trail" is mostly redundant** for member accounts: they cannot delete
   231	    an organization trail or turn its logging off anyway (📖 R2.6.2). E5 instead denies changes
   232	    to any trail inside prod accounts. The framework's layer-1 bullet is reworded in the final pass.
   233	11. **"Metadata" reads can leak configuration, data or secrets** (⚠️ response contents from
   234	    memory of the API references): `lambda:ListFunctions` and `ecs:DescribeTaskDefinition` return
   235	    environment variables and cannot be limited to one resource (✅ catalogue: not resource-scoped);
   236	    `lambda:GetFunction` also returns a code download URL; `ecs:DescribeTasks` returns container
   237	    environment overrides; `cloudformation:DescribeStacks` returns stack outputs (it could be scoped
   238	    per stack); `cloudformation:DescribeStackEvents` returns `ResourceProperties`, "the properties
   239	    used to create the resource" (📖 [StackEvent](https://docs.aws.amazon.com/AWSCloudFormation/latest/APIReference/API_StackEvent.html)),
   240	    which for a function includes its environment variables (⚠️ inferred); `logs:DescribeQueries`
   241	    returns other users' query strings. E6 leaves all of them out [design];
   242	    `lambda:GetFunctionConfiguration` is granted per function instead.
   243	12. **AWS's annotations are signals, not a classification of customer data**: `IsDataPlane` marks
   244	    `cloudwatch:GetMetricData` too; `sqs:ListQueues` is not marked `IsList`; and many `IsList`
   245	    actions return data or configuration (`s3:ListBucket` object keys, `ec2:Describe*` launch
   246	    templates, `ssm:ListCommandInvocations` output; ✅ annotations in the catalogue, ⚠️ response
   247	    contents from memory). The tests use an explicit allowlist for `Resource: "*"`. One entry has a
   248	    condition: `states:ListExecutions` returns execution names, so names must not be built from
   249	    claim data [design].
   250	13. **Two prod deploy roles** (framework layer 1 already implies it): the SCP exempts the Pulumi
   251	    role from the Lambda-update deny, but not the Serverless role, so `serverless deploy function`
   252	    cannot change a function outside CloudFormation (drift). It does not stop malicious code in
   253	    the job (Limits). `deploy-prod.yml` has one credentials step per tool, so an unset role
   254	    variable fails instead of falling back to the other role.
   255	14. **The claim-data deny assumes a naming convention** [design]: every legitimate reader must
   256	    match `app-claims-*` or a `DataRead-*` permission set. Lambda execution roles behind SQS event
   257	    sources, Step Functions execution roles and an AWS Backup role that reads the bucket would be
   258	    denied otherwise (only service-linked roles are outside SCPs, 📖 R2.3.2). Phase-2 prerequisite:
   259	    inventory the real callers of these actions (CloudTrail, IAM last-accessed data) and add them
   260	    before the SCP is attached.
   261	15. **The trail deny blocks every principal in prod accounts**, including deploy roles and
   262	    `OrganizationAccountAccessRole`: a member-account trail can only be changed after a temporary
   263	    change to the SCP (an L3 path), or an exempt audit role would have to be added [design].
   264	16. **Exempt role names must be protected** (OD19): the exemptions are name patterns, so anyone in
   265	    a prod account who could create or re-trust a role named `app-claims-*` or `cfn-deployment-*`
   266	    would bypass both denies. E5 lets only `github-prod-deploy-pulumi` change those roles.
   267	    - **Today that role deploys every Pulumi stack**, not only the IAM stack, and any job in the
   268	      deploy workflow can obtain it (OD20). So "only the IAM stack" holds only after OD20 gives the
   269	      IAM stack its own role and OIDC subject; until then the protection is "only an approved prod
   270	      Pulumi deploy" (agent's reading of OD19, confirmed by the owner 2026-11-09).
   271	    - **Residual risks:** a principal that may pass an `app-claims-*` role could create a new
   272	      function with it (`lambda:CreateFunction` is not denied), and one that may pass
   273	      `cfn-deployment-*` to CloudFormation could change any function through a template;
   274	      `iam:PassRole` is left out on purpose because the Serverless role must pass
   275	      `cfn-deployment-*`. An `InfraOperator-*` grant may change an `app-claims` function's code
   276	      and so read claim data indirectly (accepted with break-glass, ADR-0005; JIT reconciliation
   277	      in layer 7 is the control).
   278	    - **Constraints and prerequisites (phase 2):** Serverless services cannot create their own
   279	      `app-claims-*` execution roles (CloudFormation runs as `cfn-deployment-*`, not exempt); those
   280	      roles live in the Pulumi IAM stack and are referenced by ARN. The protected roles must exist
   281	      before the SCP is attached, and if `github-prod-deploy-pulumi`'s own trust breaks (e.g. the
   282	      subject-format opt-in of E4), only an SCP change from the management account (an L3 path)
   283	      can repair it.
   284	17. **Gaps in the claim-data deny, under G13** (⚠️ not verified): S3 requests through access
   285	    points may be authorised on the access-point ARN, not the bucket ARN; KMS `Decrypt` on the
   286	    claim keys would be a second layer.
   287	    The deny also covers `sqs:StartMessageMoveTask` (a write, ✅ catalogue), which could move claim
   288	    messages to another queue; cost: a JIT grant cannot redrive a claims dead-letter queue.

   290	### Step 3 (agent runtime, supply chain, policy pack)
   291	
   292	18. **The settings schema on schemastore.org is community-maintained and lags behind**: it accepts
   293	    unknown keys and lacks `allowedProviders` and `managedSourcesBehavior` (✅ checked). The tests
   294	    therefore check keys by path and require a documentation source for every key it lacks.
   295	19. **The phase-1 allowlist gives no protection for `~/.aws`, and a "read-only" wildcard rule
   296	    can write files** (review step 3): Claude Code runs a built-in set of read-only commands
   297	    (`cat`, `grep`, `head`, read-only `git` …) without a prompt in every mode, and the set is not
   298	    configurable (📖 [permissions](https://code.claude.com/docs/en/permissions.md#read-only-commands)).
   299	    Leaving `cat` out of the allowlist protected nothing. Worse, `Bash(git log *)`, `Bash(git show *)`
   300	    and `Bash(git diff *)` also match `--output=<path>`, which writes chosen content to any path
   301	    (✅ git 2.34.1; the docs use `git log --output=<file>` as an example match). The allowlist is now
   302	    two exact repo scripts, and those run whatever `package.json` says [limit]. Until phase 2,
   303	    an agent can read `~/.aws` with a built-in command without a prompt. Options that close it in
   304	    phase 1 would change OD4 and are an owner decision: `permissions.blockReadsOutsideWorkingDirectories`
   305	    (📖, Claude Code ≥ 2.1.257) or `Read(~/.aws/**)` deny rules, which also apply to recognized
   306	    `cat`/`head`/`tail` (📖 permissions); and `autoMode.classifyAllShell` (📖, ≥ 2.1.193), so allow
   307	    rules do not skip the auto-mode classifier.
   308	20. **Credential paths beyond the HIPAA template** [design]: `~/.aws` as a whole (the SSO token
   309	    cache opens every role of the engineer, layer 2), `~/.kube`, `~/.pulumi`, `~/.config/gcloud`,
   310	    the Firebase CLI token, `~/.docker/config.json`. `~/.config/gh` must be hidden from the sandbox
   311	    too, not only from Claude's Read tool: sandboxed commands run without a prompt (OD12) and
   312	    `api.github.com` is allowed, so a readable token lets the agent approve PRs as the engineer (OD5).
   313	21. **TypeScript 7 is not yet supported by `@pulumi/pulumi`** (✅ npm peer-dependency error:
   314	    `typescript >= 3.8.3 < 7`); the pack pins TypeScript 6.0.3.
   315	22. **`sandbox.excludedCommands` entries match like `Bash(...)` rules** (📖
   316	    [sandboxing](https://code.claude.com/docs/en/sandboxing.md#run-commands-outside-the-sandbox-with-excludedcommands)):
   317	    `aws` alone matches only `aws` with no arguments, so the first draft kept every `aws` call in the
   318	    sandbox, where it fails (no `~/.aws`, no AWS endpoints). Entries are now `aws *`, `pulumi *`,
   319	    `serverless *`. The docs also answer the framework's ⚠️ on matching: every command in the call
   320	    must match; a call with `cd`, a redirect, `$(...)` or a subshell stays sandboxed; the match is on
   321	    the text, so `/usr/local/bin/aws`, a script that calls `aws`, and `npx serverless` do not match.
   322	    Excluded commands still go through the permission flow, so each one prompts.
   323	23. **A mandatory Pulumi policy is only advisory while a value is unknown** (✅ `@pulumi/policy`
   324	    1.21.0 `server.js` catches `UnknownValueError` and reports `advisory`). A PR-time or prod
   325	    preview of a policy built from a resource of the same update passes; the stop comes during the
   326	    update. Access Analyzer is the preview-time check (layer 5).
   327	24. **The first policy pack missed the usual ways to grant admin** (review step 3): user and
   328	    group policies, `AdministratorAccess` attached by ARN, `Role.managedPolicyArns`, and wildcards
   329	    such as `iam:Pass*`. All are now covered and tested.
