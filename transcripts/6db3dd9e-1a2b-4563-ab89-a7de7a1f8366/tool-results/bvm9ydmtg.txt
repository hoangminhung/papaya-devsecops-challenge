    80	## Limits of the risk stop
    81	
    82	The risk stop answers one framework problem: on GitHub Team nobody sees the prod diff before
    83	apply (framework §1). It catches **risky prod diffs that nobody looked at**. It is not a boundary
    84	against **malicious or prompt-injected code that was approved**:
    85	
    86	- The stack's own code runs with the prod deploy role: `npm` packages are installed before the
    87	  credentials (so install scripts get none), but the Pulumi program runs during `preview` and
    88	  `up`, and Serverless plugins during `package`/`diff`/`deploy`. That code could call AWS
    89	  directly, or tamper with files the classifier reads, in the same job. The defence against it
    90	  is the PR review itself, and from phase 2 IAM Access Analyzer and policy packs (layer 5).
    91	- A stronger variant [design, not in the framework]: preview with a separate prod **preview**
    92	  role (read and state access, no write), run the classifier in its own job on a fresh
    93	  checkout without credentials, and assume the deploy role only in a later job after the stop.
    94	  It adds a role and a job split; it is an open question for the owner.
    95	- `pulumi up` previews again before applying. A change made outside the pipeline between the
    96	  two previews (JIT, drift) is not re-checked. `pulumi preview --save-plan` + `pulumi up --plan`
    97	  would bind the two, but update plans are experimental (📖 R4.1.3).
    98	- Concurrency: a running deploy is never cancelled, but GitHub cancels a run that is still
    99	  pending when a newer one arrives for the same group (📖 GitHub docs source,
   100	  `data/reusables/actions/actions-group-concurrency.md`). Some merged commits therefore have no
   101	  deploy run of their own; the newer run deploys them too, and the change record must link both
   102	  commits to that run. `queue: max` would give every commit its own run, but the same page says
   103	  the order "is not guaranteed": an older commit could then deploy after a newer one and undo it
   104	  in prod. So the default is kept on purpose [design].
   105	- The type lists are examples. For types that are missing, the rule on property names
   106	  (`policy`, `role`, `securityGroup`, `vpcConfig`, `public`, `authorization`, `logging`, …;
   107	  a narrower set on creates) catches some changes, not all.
   108	- **Open gap:** nothing proves that a deploy really stopped at `stopped_commit` with the
   109	  approved hash. An approval merged early (naming a commit whose deploy did not stop, with a
   110	  hash computed in advance, which needs knowledge of prod inputs) is accepted if a later change
   111	  **outside** the stack's directory, such as a shared library, produces exactly that diff. Changes
   112	  inside the stack's directory are rejected. Watching the whole repository instead would cancel
   113	  every approval at each unrelated merge in a monorepo. The fix is for the approval-gate app to
   114	  check, on the approval PR, that the stopped run's summary carries the same hash (G19) [design].
   115	  `test_known_gap_early_approval_and_change_outside_the_stack` documents the current behaviour.
   116	- The approver of the approval PR sees **which** prod resources and properties change, not the
   117	  new values (the summary never prints values, to keep secrets out of logs). The values are
   118	  reviewed in the code of the stopped PR. Framework layer 3 and ADR-0004 say the approver "sees
   119	  the prod diff"; that wording is too strong and is corrected in the framework's final pass.
   120	- Any commit to the stack's directory between the stop and the approval merge cancels the
   121	  approval: the author names the newer stopped commit and the owner approves again. In an
   122	  incident that is one more review round.
   123	- `npm ci` runs before the credentials, but its lifecycle scripts can still write to
   124	  `$GITHUB_ENV` / `$GITHUB_PATH` and so influence later steps that hold them.
   125	  `npm ci --ignore-scripts` reduces this where the stack's packages allow it.
   126	- If the newest merge to `main` carries `[skip ci]` (or similar) in its message, no push run
   127	  exists for the tip and the older runs refuse to deploy; prod stays behind until the next merge
   128	  (📖 GitHub docs source, `content/actions/how-tos/manage-workflow-runs/skip-workflow-runs.md`,
   129	  via review). Operator action: merge an empty change.
   130	- Within 7 days, an approved change that is reverted and then merged again with identical code
   131	  passes without a new approval. This is intended: it is the same code and the same prod diff
   132	  that an owner approved.
   133	- The binding relies on squash-only merges (`ruleset-main.json`); with merge commits, a PR's
   134	  inner commits would be invisible to the first-parent check.

   136	## Findings from writing these files
   137	
   138	Points the framework text does not yet say; carried into the framework in the final pass.
   139	Owner decisions 2026-11-09 (framework OD14–OD18): findings 1, 3 and 4 accepted; the risk stop keeps
   140	its current scope (OD15); the early-approval gap is an accepted limit for G19 to close (OD18).
   141	
   142	1. **The risk-stop classifier must be an L3 path** [design]. The deploy runs it from the merged
   143	   commit, so a PR that edits it together with an IAM change, approved by the domain team, could
   144	   switch the stop off. `CODEOWNERS` adds `/tools/risk-stop/` to the L3 owner team. Needs owner
   145	   confirmation: it extends the canonical L3 list of framework layer 5.
   146	2. **An approval must be bound to git history, not only to a hash** [design]. Two review rounds
   147	   found ways for one PR to carry its own risky change and approval, or for an approval to be
   148	   reused. Rules now: read from git objects only; file named `<stopped_commit>.yaml`, never
   149	   edited; stopped commit and approval commit both on `main`'s first-parent history, in that
   150	   order; the approval commit touches only `deploy-approvals/<stack>/`; the stack's directory
   151	   and the classifier unchanged since the stopped commit; at most 7 days old.
   152	3. **Squash-only merges** [design]: `ruleset-main.json` allows only squash, so each PR is one
   153	   commit on `main`. Cost: PR-internal history is not kept on `main`.
   154	4. **Deploy only the tip of `main`** [design]: people with write access can re-run a workflow run
   155	   for up to 30 days, with the same `GITHUB_SHA` (📖 GitHub docs source,
   156	   `content/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs.md`, via review). An
   157	   old deploy run re-run would roll prod back without any approval. `deploy-prod.yml` stops unless
   158	   the run's commit is the current tip of `main`, read with `GET /repos/{owner}/{repo}/git/ref/heads/main`
   159	   (✅ branch-only form; `commits/main` could resolve to a tag named `main`). This is a new
   160	   condition for framework layer 3's "merge approval = deploy approval" list.
   161	5. **Classification beyond the framework's categories** [design]: the property-name rule, the
   162	   audit/detection category and "an unknown operation stops" go beyond layer 3's list
   163	   (stateful replace/delete, IAM, network, policy finding).
   164	6. **The approval hash must cover changed values**, not only resource names, or an approval for
   165	   one IAM policy would let a different change to the same policy through; and it must leave out
   166	   values that change on every build, or an approval never matches. ⚠️ From memory, not checked:
   167	   Serverless puts a timestamped path in the Lambda `Code.S3Key` and a code hash in
   168	   `AWS::Lambda::Version` logical IDs; both are left out of the hash.
   169	7. **Fail-safe CODEOWNERS default** [design]: without it, root `package.json`, a new stack or a new
   170	   `deploy-approvals/<stack>/` folder would be unowned, and GitHub then accepts an approval from
   171	   any writer (📖 about code owners).
   172	8. **Same-repository reusable workflows can use `uses: $/.github/workflows/<file>`**, which GitHub
   173	   now recommends: it resolves to the running commit, not to the runner's workspace (📖 GitHub docs
   174	   source, `data/reusables/actions/reusable-workflow-calling-syntax.md`; flagged by zizmor's
   175	   `self-repository` audit). `actionlint` 1.7.12 (✅ latest release on 2026-11-09, published
   176	   2026-03-30) does not know the syntax; `validate.sh` ignores only that message.
   177	9. **`runner.temp` is not available in job-level `env`** (✅ caught by `actionlint`); paths use
   178	   `$RUNNER_TEMP` inside steps.
   179	
   180	### Step 2 (identity and access)
   181	
   182	10. **SCP "protect the org trail" is mostly redundant** for member accounts: they cannot delete
   183	    an organization trail or turn its logging off anyway (📖 R2.6.2). E5 instead denies changes
   184	    to any trail inside prod accounts. The framework's layer-1 bullet is reworded in the final pass.
   185	11. **"Metadata" reads can leak configuration or data**: `lambda:ListFunctions` and
   186	    `lambda:GetFunction` return function configuration, `ecs:DescribeTaskDefinition` container
   187	    environment variables, `cloudformation:DescribeStacks` stack outputs (⚠️ from memory of the
   188	    API responses). None can be limited to one service, so E6 leaves them out [design].
   189	12. **AWS's own `IsDataPlane` annotation does not mean "customer data"**: it marks
   190	    `cloudwatch:GetMetricData` too (✅ catalogue). The tests use an explicit list instead.
