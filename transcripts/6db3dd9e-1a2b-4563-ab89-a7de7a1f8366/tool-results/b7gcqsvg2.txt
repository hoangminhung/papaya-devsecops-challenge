   276	## Layer 3 — Change workflow by risk level
   277	
   278	**Principle.** The level is set by the damage a change can do. One default path above non-prod: a
   279	reviewed PR applied by the pipeline, with the JIT fallback (layer 7) as the only other write path.
   280	The approver reviews the code change that will be applied. Every prod change needs two people, and
   281	no more by default: one who makes it and one who approves it; the on-call backup only replaces an
   282	unavailable primary (OD2). Higher risk narrows **who** may approve (the owners of that path), not how
   283	many. Separately, any prod diff that looks risky stops the deploy, whatever its level; that adds a
   284	second approval by an owner of the same stack, which keeps it to two people (OD8). Confirmed by the owner
   285	(OD13): the original author opens the approval PR and the first approver
   286	approves it. If the first approver is unavailable, another owner of the stack approves; that makes
   287	three people and is recorded as a deviation, counted monthly (OD11). A cross-team PR needs one
   288	approval, as GitHub accepts one on-call group member for files of several owner teams (OD10,
   289	OD9, 📖 R3.2.7); domain review there is a recommendation, counted in the monthly report. A real-data read is not a change and has its own rule, L3-data. Incidents use the same
   290	path with faster people, not fewer security checks.
   291	
   292	| Level | What | Examples | Approval | Path |
   293	|---|---|---|---|---|
   294	| **L0** | Read: non-prod anything; prod metadata | metrics, redacted logs | none | read-only identity |
   295	| **L1** | Change in non-prod | deploy a branch to dev; `pulumi preview` on non-prod (needs state-write permission on a DIY S3 backend, 📖 R4.3.3) | author only | non-prod roles or PR pipeline |
   296	| **L2** | Routine prod change in code | Lambda timeout/memory, ECS desired count, release | 1 code owner ≠ author, ≠ last pusher | PR → `main` → deploy workflow |
   297	| **L3** | High-risk prod change | IAM/SCP; replace/delete of stateful resources; network; `.github/**`, CODEOWNERS, `CLAUDE.md`, `CLAUDE.local.md`, `.claude/**`, `.claude.json`, `.mcp.json`, `.husky/`, `.gitmodules`, `.ripgreprc`, plugin/MCP catalogue and the rest of the canonical list in layer 5; advisory policy finding | 1 code owner ≠ author, ≠ last pusher.    313	- **Gate = merge to `main`.** On Team, environment reviewers do not exist for private repos
   314	  (📖 R3.1.2). Ruleset on `main`: PR required, 1 approval, code-owner review, dismiss stale approvals,
   315	  approval by someone other than the last pusher, required checks from a pinned source app, no force
   316	  push, empty bypass list (📖 R3.2.2, R3.2.3, R3.2.5). Branch up to date before merge, since there is
   317	  no merge queue (⚠️ R4.6 #1; whether updating drops approvals is open, Options §8).
   318	- **L3 approvals [design]:** CODEOWNERS plus code-owner review only, no path-based required
   319	  reviewers rule. That rule (📖 R3.2.4) asks for approvals from specific teams, which the on-call
   320	  group would not satisfy at night, and how it combines several teams is not researched (⚠️), so it
   321	  would break OD9 or add a third person. GitHub stops the author from approving (📖 R3.3.1). A required check with a pinned source app (📖 R3.2.5), set by a dedicated GitHub App that reacts to review events and is the pinned source [design; hosting, key storage and whether its key counts against S2 are not researched, ⚠️ G19], adds what
   322	  the rules cannot: for app-opened PRs it excludes the person who triggered the agent, and it counts
   323	  only human approvals, since an app's approval might count (⚠️ R3.3.4, R3.7 A3). A workflow
   324	  instead of an app is weaker: pinning the source to GitHub Actions likely lets any workflow set a
   325	  check of the same name, and the trigger that runs on review events from trusted code is not
   326	  researched (⚠️ G19).

   328	  are silently not assigned, 📖 R3.2.7; the CODEOWNERS validation check covers this), the on-call approvers, is listed as
   329	  co-owner on every deployable path in CODEOWNERS (infrastructure and service code), next to the
   330	  domain team. Confirmed by the owner (OD13): the group does **not** co-own the paths that
   331	  define the process (`.github/**`, CODEOWNERS, `CLAUDE.md` and agent config, catalogue); those stay
   332	  with the L3 owner team only. If a broken workflow blocks a night fix, the pipeline counts as
   333	  unavailable and the JIT fallback applies (layer 7). One primary and one backup from that team are on call. Technically any member can approve any
   334	  path; by rule the primary approves and the backup only if the primary is unavailable (OD2).
   335	  Membership is fixed, not changed per shift [design]. GitHub team membership is set in organization
   336	  settings, not by a PR; managing it as code (e.g. with Pulumi's GitHub provider) and the audit
   337	  event for a membership change are not researched (⚠️ G16). Meanwhile the layer-7 settings
   338	  comparison includes the group's member list. Cost: an approval from any
   339	  listed owner satisfies code-owner review (📖 R3.2.7), so on normal days a member could approve
   340	  another domain's PR, on or off shift. Mitigation [design]: process rule "approve another
   341	  domain's PR only if it carries the `incident` label and you are on shift", and a monthly report of
   342	  every cross-domain approval by group members on PRs without that label (layer 7). Whether Papaya's team size allows full coverage is unknown
   343	  (§1, S7).
   344	- **Risk stop [design]:** applies to every deploy, whatever the level. The deploy job previews prod;
   345	  on stateful replace/delete, an IAM change, a network or security-group change, or an advisory
   346	  policy finding (from phase 2) it stops and posts the filtered preview. The original author opens a second PR that adds
   347	  `deploy-approvals/<stack>/<sha>.yaml` (`<sha>` = the stopped commit) holding that SHA and the
   348	  preview hash; the workflow does not open it, because the setting that lets Actions create and approve PRs stays
   349	  off (📖 R3.3.3; ⚠️ R3.6 #3). CODEOWNERS on `deploy-approvals/<stack>/` names the owners of that stack and the
   350	  on-call group (OD8, OD9). The approver is ≠ author and may be the first PR's approver, who now sees
   351	  which prod resources and properties change; values stay out of the summary to keep secrets out
   352	  of logs, and are reviewed in the code of the stopped PR. Merging it triggers the deploy on the new HEAD, which previews again and continues
   353	  only if the hash matches the approved one; if another PR merged in between, the hash differs and
   354	  the deploy stops again (Options §1; hash stability ⚠️ Options §8). The approval is bound to git
   355	  history, not only to the hash (six conditions, 7-day expiry; examples E7, finding 2) [design].
   356	  Known gap (OD18): an early approval can match a later change outside the stack (G19 closes it).
   357	  The stop catches risky diffs nobody looked at, not approved malicious code (OD15, OD20). Cost: while a stack is
   358	  stopped, later merges to that stack stop too until a matching approval lands; in an incident, a
   359	  risky change already waiting on `main` blocks the fix for the same stack until it is approved or
   360	  reverted. A

   390	**Example: Lambda timeouts at 2 a.m.** (Options §6)
   391	
   392	The incident responder is engineer E; the on-call approver is R (a backup replaces R only if R is
   393	unavailable).
   394	
   395	1. E's incident-analysis session reads metrics and redacted logs and proposes `timeout` 30 → 90 s,
   396	   memory 1024 → 2048 MB, and a larger visibility timeout on the source queue (ratio ⚠️ Options §8).
   397	2. A second session (edit tools; not meant to use prod roles) edits `serverless.yml`, runs
   398	   `serverless diff` on non-prod, and opens a PR labelled `incident` as E.
   399	3. R, a co-owner of `serverless.yml` through the on-call group (OD9), reviews the diff. If R
   400	   catches a missing queue change, R does not fix it (OD7): E pushes the fix, the stale approval is
   401	   dismissed, and R approves again, one more review round (Options §6). E merges.
   402	4. The deploy workflow packages, previews prod, finds no risky change, deploys with the OIDC role.
   403	5. Estimate 11–46 min (⚠️ Options §6) against ≤ 30 min: measured first in rollout.
