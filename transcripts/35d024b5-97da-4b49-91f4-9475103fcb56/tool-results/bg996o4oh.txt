# DevSecOps Challenge 1 — DevSecOps with Coding Agents at Papaya

## Note

- You are required to use a coding agent (e.g. Claude Code, Codex, Cursor) to complete this challenge.
- If you have any issues or questions, don't hesitate to contact us.

## Context

Papaya builds a GenAI-powered enterprise platform for the insurance industry — Claim, Underwriting, Policy Servicing, and FWA (Fraud/Waste/Abuse) — serving insurer partners across SEA and Asia. Our platform processes sensitive data every day: medical documents, diagnoses, claim histories, national IDs, and bank accounts of insured members.

Every engineer at Papaya works agent-first: Claude Code (Team Premium) is the primary tool for writing code, running git, opening PRs, and increasingly for infrastructure work.

This is where we are today (see [Appendix A](#appendix-a--papaya-platform-context) for the full picture):

- Engineers run Claude Code on their laptops, signed in to AWS through their SSO profiles. Most engineers' profiles can reach production.
- Some engineers run Claude Code with permission prompts turned off because "it is faster".
- Engineers install MCP servers and plugins they find useful; there is no review process.
- CI/CD runs on GitHub Actions. Some workflows use a long-lived GitHub token and AWS access keys stored as repository secrets.
- Monitoring and alerting exist but are fragmented across CloudWatch, GCP, and Slack channels. On-call is informal.
- We are working towards ISO 27001 and must satisfy HIPAA and regional data-protection regulations for our partners.

We've heard two strong opinions from inside the company:

> **Engineering:** "Let Claude Code talk to AWS directly. I want to debug and ship my own infra changes without waiting for someone else."
>
> **Compliance:** "Nothing changes in production — by a human or an agent — without a named person who reviewed and approved it."

## Problem

You are joining as our DevSecOps Engineer. Your first mission: **design the framework and workflow for how Papaya uses coding agents for DevSecOps.**

You don't have access to our systems or code, and we don't expect you to.

## Requirements

- The format of the deliverable is up to you.

## Submission

Submit everything in **one GitHub repository** and send us the link. Other channels (cloud storage, email attachments) are not accepted.

The repository must contain:

- Your deliverable(s).
- The **complete, raw, unedited conversation(s)** with your coding agent — every session you used for this challenge. Native session files are preferred (e.g. Claude Code: `~/.claude/projects/**/*.jsonl`; Codex CLI: `~/.codex/sessions/`); for chat apps, commit an export of the conversation.

**Submissions without the agent conversation will be automatically marked as failed.**

## Appendix A — Papaya Platform Context

### Cloud

- **AWS (primary):** Lambda (Serverless Framework), ECS, EC2, Aurora PostgreSQL, SNS, SQS, Step Functions, S3 (claim documents), CloudWatch.
- **GCP:** Vertex AI and Gemini API workloads for document AI and ML models.
- **Kubernetes ([k0s](https://k0sproject.io/)):** workloads for AI agents and internal services.
- **Hosting:** Firebase Hosting for web frontends.

### Application

- **Backend:** Node.js, TypeScript, GraphQL (Apollo Server, Hasura), PostgreSQL.
- **Frontend / Mobile:** Next.js, React, React Native (Expo).
- **AI/ML:** Python, PyTorch, OpenAI, Vertex AI, Gemini, Claude.
- **AI agents in production:** claim assessment, document extraction and classification, FWA detection — they read documents uploaded by partners and members.

### Engineering

- **Source control & CI/CD:** a single monorepo on GitHub for the whole system — apps, web, backend, mobile, AI/ML, and Infrastructure as Code ([Pulumi](https://www.pulumi.com/), plus [Serverless Framework](https://www.serverless.com/) for Lambda functions); GitHub Actions for CI/CD.
- **Coding agent:** Claude Code (Team Premium) for every engineer; internal Claude Code plugins are distributed via a plugin marketplace.
- **Work tracking & communication:** Linear, Slack.
- **Tenancy:** multiple insurer partners across countries (e.g. Vietnam, Thailand, Hong Kong), each with their own data and contractual requirements.

### Compliance

- ISO 27001 (in progress), HIPAA, and regional data-protection regulations in the countries we operate in.

   106	## 3. Mâu thuẫn trung tâm
   107	
   108	**Engineering:** "Let Claude Code talk to AWS directly. I want to debug and ship my own infra changes without waiting for someone else."
   109	
   110	**Compliance:** "Nothing changes in production — by a human or an agent — without a named person who reviewed and approved it."
   111	
   112	### 3.1 Hai câu thực ra đang nói về những thứ khác nhau
   113	
   114	Tách từng câu thành các phần:
   115	
   116	| | Engineering | Compliance |
   117	|---|---|---|
   118	| Phạm vi môi trường | AWS nói chung (không nói prod hay non-prod) | **Chỉ production** |
   119	| Loại hành động | debug (chủ yếu đọc) **và** ship (ghi) | **thay đổi** (ghi) |
   120	| Chủ thể | Claude Code, nhân danh engineer | "a human or an agent", trung lập về công cụ |
   121	| Điều kiện | "without waiting for someone else" | "named person who reviewed and approved" |
   122	
   123	Từ bảng này:
   124	- **Không mâu thuẫn:** debug (đọc) và mọi việc ở non-prod nằm ngoài phạm vi câu của Compliance.
   125	- **Mâu thuẫn thật** nằm ở đúng một ô: **ghi vào production**. Engineering không muốn *chờ*, Compliance muốn *có người duyệt*.
   126	- **Vùng xám:** "debug" trên prod có thể là đọc dữ liệu nhạy cảm (P2b, A7b). Compliance không nói về đọc,
   127	  nhưng HIPAA và luật dữ liệu thì có. Vậy câu "không mâu thuẫn" ở trên chỉ đúng với đọc **metadata**, không đúng với đọc **dữ liệu**.
   128	
   129	### 3.2 Những chỗ hai câu chưa định nghĩa (framework phải định nghĩa)
   130	
   131	- "Change in production" gồm những gì? Deploy code, đổi config, đổi IAM, chạy migration, sửa một bản ghi DB, restart service, scale?
   132	- "Reviewed" là review cái gì? Diff code, bản preview hạ tầng (plan), hay đoạn chat với agent?
   133	- "Named person" có bắt buộc **khác** người đề xuất không (four-eyes / segregation of duties)? Câu của Compliance không nói.
   134	- "Waiting for someone else" là chờ bao lâu thì chấp nhận được?
   135	- Khi có sự cố và không kịp chờ duyệt thì sao?
   136	
   137	### 3.3 Câu hỏi thiết kế
   138	
   139	> **Làm thế nào để engineer, làm việc qua Claude Code, có vòng lặp debug-và-ship tự phục vụ và nhanh,
   140	> trong khi mọi thay đổi vào production (kể cả trong sự cố) đều đi qua một con đường duy nhất, ép bằng kỹ thuật,
   141	> gắn với một người có tên đã review đúng thứ sẽ được áp dụng, và để chi phí của con đường đó đủ thấp
   142	> để không ai có lý do đi đường tắt?**
   143	
   144	Các vế của câu hỏi và vấn đề tương ứng:
   145	- "tự phục vụ và nhanh": nhu cầu của Engineering; bài học từ P3b.
   146	- "mọi thay đổi … một con đường duy nhất": A1, A8, P5c (đường vòng).
   147	- "ép bằng kỹ thuật": P3c, P4 (đang dựa vào thiện chí).
   148	- "người có tên … review đúng thứ sẽ được áp dụng": Compliance; A9 (drift giữa preview và apply).
   149	- "kể cả trong sự cố": P7b.
   150	- "chi phí đủ thấp": P3b, rủi ro chính của framework.
   151	
   152	Câu hỏi phụ đi kèm (về **đọc**, không phải ghi):
   153	
   154	> **Agent được nhìn thấy gì trong production, đặc biệt dữ liệu MED/NID/BANK của từng tenant, và ai quyết định điều đó?**
